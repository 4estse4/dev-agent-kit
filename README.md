# ai-native-kit

AI 코딩 에이전트와 함께 개발할 때 쓰는 **절차·검증 체계 킷**.
새 프로젝트에 clone 해서 `install.sh` 를 한 번 실행하면 게이트·훅·템플릿·스킬이 설치된다.

## 설계 원칙 세 개

1. **강제는 에이전트 밖에 둔다.**
   git hooks · CI · 브랜치 보호는 어떤 에이전트를 쓰든, 사람이 손으로 해도 작동한다.
   에이전트 훅에만 강제를 두면 도구를 바꾸는 순간 강제가 사라진다.
   → 에이전트 훅은 *편의*(자동 포맷·조기 피드백)와,
     놓쳐도 다음 단계가 고칠 수 있는 것을 대조하는 데에만 쓴다.

2. **아래 단계가 찾아낼 수 있으면 위 단계에서 뺀다.**
   린터가 결정론적으로 찾아내는 것을 AI 리뷰에 맡기지 않는다.
   리뷰 체크리스트에서 그만큼 삭제하면 **품질이 오르면서 리뷰가 짧아진다.**

3. **못 찾은 것은 쓰지 않는다.**
   AI 산출물은 길어서 믿을 만해 보인다. 검증 산출물은 발견만 기록하고,
   무엇을 봤는지는 범위 한 줄로 적는다.

자세한 근거: [`common/docs/artifact-rules.md`](common/docs/artifact-rules.md) ·
[`common/docs/verification-stages.md`](common/docs/verification-stages.md)

## 구조

```
common/                에이전트 없이도 작동하는 것 — 킷의 본체
  docs/                산출물 규칙(R1~R7) · 검증 단계 (설계 근거)
  templates/           CLAUDE.md · SPEC · 추적 매트릭스 · ADR · dev-log · plan · PR
  git-hooks/           pre-commit · pre-push  ← 실제로 강제하는 곳
  gate/                게이트 본체 · 언어별 어댑터 · 도구 설치기
    tool-versions      게이트 도구의 고정 버전 — **단일 출처**(CI·로컬·안내가 함께 읽음)
    install-tools.sh   그 버전대로 설치
  lint/                언어별 린터 설정 (하드룰을 린트 규칙으로 코드화)
                       go · ts · py · jvm(Kotlin). **Java 는 다루지 않는다**
  ci/                  게이트 · 시크릿 스캔 · 취약점 스캔 워크플로

claude-code/           Claude Code 가 있어야 의미 있는 것
  settings.json · hooks/ · skills/ · agents/ · statusline-command.sh

```

**`common/` 은 에이전트 없이도 작동한다** — git·CI·린터·사람이 그대로 실행한다.
에이전트가 있어야 의미 있는 것만 도구 이름 디렉터리에 둔다. 트리를 보면 도구 이름 디렉터리는
`claude-code/` 하나이고 나머지가 전부 `common/` 이라는 것이 드러나는데, 그것이 **설계 원칙 1의 시각적 증거**다.

**테마·터미널 표시 모드·모델·effort 같은 개인 취향은 킷이 다루지 않는다.**
`/config` 나 `~/.claude/settings.json` 에서 각자 정한다 — 킷이 정해 두면 개발자의
`/model` 선택을 무력화한다.

### 규칙의 단일 출처는 `CLAUDE.md`

**프로젝트 규칙은 `CLAUDE.md` 한 파일에만 쓴다.** 두 벌이 되면 반드시 어긋나고,
어느 쪽이 진짜인지 아무도 모르게 된다.

이 킷은 Claude Code 용이다 — 훅·스킬·서브에이전트가 모두 Claude Code 기능이다.

## 검증 상태

| 부분 | 상태 |
|---|---|
| `common/` 전부 | **검증됨** — 실제 프로젝트에 적용해 결함을 찾아냄 |
| `claude-code/` 의 statusline | **검증됨** — 상시 사용 중 |

무엇이 실제로 깨졌고 누가 찾아냈는지는 [`docs/dev-log.md`](docs/dev-log.md) 에,
그래서 무엇을 정했는지는 [`docs/adr/`](docs/adr/) 에 있다.

## 누가 썼나

이 레포의 코드·문서는 **전부 Claude 가 작성했다.** 사람은 방향 설정 · 범위 결정 ·
리뷰 · 수용 여부를 맡았고 일부를 직접 수정했다.

어느 모델이 어떤 effort 로 썼는지는 **커밋마다** 적혀 있다:

```
Co-Authored-By: Claude Opus 5 (xhigh) <noreply@anthropic.com>
```

문서에 한 줄로 적지 않고 커밋에 적는 이유는 비대칭이다. 기록 비용은 커밋당 ~20자인데
**기록하지 않으면 나중에 되찾을 수 없다** — 모델이나 effort 를 바꿔 결과를 비교하려는 시점이
오면 이전 커밋을 어느 모델이 어떤 effort 로 썼는지는 이미 알 수 없고, 머지된 히스토리에는
소급할 수 없다.
지금까지의 분포는 이렇게 센다:

```bash
git log --format='%(trailers:key=Co-Authored-By,valueonly)' \
  | sed -n 's/.*(\([^)]*\)).*/\1/p' | sort | uniq -c
```

> 이 킷의 전제는 "AI 가 썼으니 못 믿는다"도 "AI 가 썼으니 빠르다"도 아니다.
> **누가 썼든 기계로 확인되지 않은 것은 확인되지 않은 것**이라는 쪽이다.
> 그래서 강제를 에이전트 밖에 두고(원칙 1), 검증 상태를 위 표처럼 적는다.

## 쓰는 법

```bash
git clone <this-repo> ~/git/ai-native-kit        # 킷은 아무 데나 한 번만
~/git/ai-native-kit/install.sh ~/work/myproj     # 대상 프로젝트에 설치
```

**대상 경로는 필수다.** 현재 레포에 설치하려면 `.` 를 준다. 이 명령은 파일 수십 개를
쓰고 git config 를 바꾸므로, 어디에 쓰는지 추측하지 않는다 — `cd` 를 빠뜨려 엉뚱한 레포에
설치하는 사고가 실제로 있었다.

### 도구가 없으면 검사는 **실패한다** — 로컬도 CI 와 같은 기준이다

도구가 없다는 것은 "통과" 가 아니라 **"검사되지 않았다"** 다. 예전에는 로컬에서만 도구가 없는 검사를 건너뛰어서,
로컬에서 통과한 것이 CI 에서 실패했다. 그 왕복(푸시 → 몇 분 대기 → 실패 확인 → 로컬
수정 → 다시 푸시)은 로컬에서 30초면 끝날 일을 공용 CI 자원과 사람 시간으로 치르는 것이다.

```bash
bash .kit/gate/install-tools.sh              # 이 레포에 필요한 것만
bash .kit/gate/install-tools.sh --dry-run    # 무엇을 설치할지만
```

버전은 **`.kit/gate/tool-versions` 가 단일 출처**다. 로컬 설치 안내·설치 도우미·CI 가
모두 그 파일을 읽는다 — 어딘가에 숫자를 적어 두면 로컬과 CI 의 버전이 달라진다.

불가피하게 도구를 못 쓰는 상황에서만 도구가 없는 검사를 건너뛰게 한다. 그러면
**무엇이 검사되지 않는지 출력한다:**

```bash
AI_KIT_ALLOW_MISSING_TOOLS=1 git push
```

### 어느 검사가 언제 실행되나

| 시점 | 무엇 | 막나 |
|---|---|---|
| 파일 편집 직후 | 포맷(gofmt·prettier·ruff·ktlint) | **못 막는다** — `PostToolUse` 는 도구 실행 뒤에 호출되어서 구조적으로 불가. 포매터가 없으면 에이전트에게 알린다 |
| `git commit` | 보호 브랜치 · 신원 · 충돌 마커 · 시크릿 · **포맷 · 린트 · 타입**(`gate.sh --lint`. JVM 은 ktlint 만) | 막는다 |
| `git push` | 시크릿 · 포맷 · 린트 · 타입 · 테스트 · 빌드(`gate.sh`) · 요구 추적 | 막는다 |
| CI | 같은 게이트 + 커버리지 · 취약점 스캔 | 막는다(우회 불가) |

CI 가 같은 검사를 다시 실행하는 이유는 **로컬 검사가 실행되지 않을 수 있기 때문**이다 — `--no-verify`,
훅을 활성화하지 않은 clone, 실행권한 없는 훅. 셋 다 이 킷에서 실증했다.

설치되는 강제 단계:

| 단계 | 막는 것 |
|---|---|
| `pre-commit` (git) | 보호 브랜치 직접 커밋 · 커밋 신원 불일치 · 충돌 마커 · 시크릿 · 스테이지한 파일이 있는 모듈의 포맷·린트·타입(테스트·빌드는 뺀다. JVM 은 ktlint 만) |
| `pre-push` (git) | 변경 영역의 포맷·린트·타입·테스트·빌드 실패 · 시크릿 · 요구 추적 |
| CI | 게이트 전체(`gate.sh --all`) · 시크릿 스캔 · 요구 추적 + 커버리지 + 취약점 스캔 |
| 브랜치 보호 | 위를 통과 못 한 머지 |

## 킷이 바뀌면 — 갱신

```bash
<kit>/install.sh <경로> --dry-run   # 무엇이 달라질지만 본다
<kit>/install.sh <경로>             # 다시 설치한다
```

`--dry-run` 은 킷이 놓을 파일을 임시 트리에 만들어 이 레포와 대조한다. 아무것도
바꾸지 않고 이렇게 말한다:

```
지금 설치하면 — 설치 0 · 교체 1 · 보존 1 · 동일 39 · 삭제 1

교체 — .kit, .claude 의 스킬·에이전트·훅, docs/process 는 킷 소유다
  ~ .kit/gate/secrets.sh

보존 — 이 레포 것을 두고 킷의 것은 <파일>.kit-new 로 옆에 놓는다
  ~ CLAUDE.md

삭제 — 재설치가 지운다
  - .kit/gate/adapters/extra.sh

diff (- 지금 이 레포 / + 킷이 놓을 것)
  ...

병합용 트리: /tmp/kit-dryrun.XXXXXX
```

**병합은 하지 않는다.** 트리가 남으므로 사람이나 에이전트가 그것을 보고 정한다.
diff 가 길면 `AI_KIT_DIFF_MAX_LINES`·`AI_KIT_DIFF_MAX_TOTAL` 로 조절한다.

| 대상 | 갱신 방식 |
|---|---|
| `.kit/gate/` · `git-hooks/` | 킷 소유 — 통째로 교체 |
| `CLAUDE.md` · `.claude/settings.json` · CI · 린터 · 템플릿으로 놓는 `docs/` 문서와 PR 템플릿 | 프로젝트 소유 — 건드리지 않고 킷의 것을 `<파일>.kit-new` 로 옆에 둔다 |
| `.claude/skills|agents|hooks` · `docs/process` | **킷 소유 — 재설치가 덮어쓴다** |

### 자동 병합을 하지 않는 이유

3-way 병합은 **프로젝트가 커스터마이즈한 곳과 킷이 바꾼 곳이 겹치는** 상황을 위한
장치다. 그런데 이 킷을 실제 프로젝트 하나에 끝까지 적용한 뒤 세어 보니, 그 상황이 거의
일어나지 않았다 — 프로젝트가 킷 파일에 손댄 24군데 중 **그 프로젝트만의 사정은 둘**이고
나머지는 전부 킷 자신의 버그였다. 게다가 그중 셋은 킷 쪽에서도 같은 기간에 따로
고쳐서 **같은 코드가 두 곳에서 두 번 나왔고, 그때 셋 다 킷 `main` 에 없었다**
(미머지 브랜치에만 있었다).

즉 실제로 치른 비용은 병합으로 줄일 수 있는 것이 아니었고, 수정을 **업스트림에 빨리 올려야** 줄어드는 것이었다.
그래서 병합 장치를 걷어내고, 무엇이 달라지는지를 보여주는 데 집중한다. 근거는 이슈 #38.

낡았는지는 `SessionStart` 훅이 한 줄로 알린다. CI 가 아니라 로컬인 이유: CI 에서 하려면
러너가 킷 레포를 읽어야 하는데, **킷과 프로젝트가 같은 사람의 private 레포여도** Actions 의
`GITHUB_TOKEN` 은 그 워크플로가 실행되는 레포에만 권한이 있다. 다른 레포를 읽으려면 PAT 이나
deploy key 를 프로젝트 secrets 에 넣어야 하고, 그러면 킷을 읽을 자격증명이 프로젝트마다
복제된다. **낡음 감지는 정확성 게이트가 아니라 편의다** — 놓쳐도 깨지지 않고 옛 킷 코드를
쓸 뿐이다. 킷을 public 으로 바꾸면 토큰 없이 읽히므로 그때 CI 단계를 더하면 된다.

## 킷 템플릿이 낡는 것은 자동으로 찾아낸다

`install.sh` 는 킷에 있는 파일을 **그대로** 복사한다 — 설치 시점에 최신을 받아오지
않는다. 그래서 킷의 워크플로 템플릿에 적힌 액션 버전이 낡으면 **새 프로젝트가 낡은 채로
시작**한다(설치 직후 Dependabot PR 몇 개를 받게 된다).

Dependabot 이 이걸 못 막는다. `github-actions` 생태계는 `.github/workflows/` 와 루트
`action.yml` **만** 훑고, 킷의 원본은 `common/ci/gates.yml` 이라 그 범위 밖이다.

그래서 킷이 자기 템플릿을 스스로 본다:

```bash
bash common/ci/check-action-pins.sh     # 뒤처진 핀이 있으면 종료코드 1
```

주간 워크플로가 이것을 실행해 뒤처지면 이슈를 연다. 조회에 실패하면 "이상 없음" 으로
처리하지 않고 잡을 실패시킨다. **설치된 프로젝트 쪽은 그 프로젝트의 Dependabot 이 맡는다.**

게이트 도구 핀(`common/gate/tool-versions`)은 Dependabot 이 지원하는 생태계의 파일이 아니어서 보지 않는다. 같은 주간 워크플로가
따로 최신과 견주고, 뒤처지면 이슈를 연다:

```bash
bash common/ci/check-tool-pins.sh       # 뒤처진 도구가 있으면 종료코드 1, 최신을 읽지 못하면 2
```

Go 도구는 `go list -m <모듈>@latest`, ruff 는 PyPI, ktlint 는 GitHub releases 에서 최신을 읽는다.

## 무엇이 공유되고 무엇이 프로젝트 소유인가

| | 소유 | 이유 |
|---|---|---|
| `.kit/gate/*` | **킷** (vendor·버전 기록) | 게이트 정의는 한 곳이어야 로컬·CI 가 어긋나지 않는다 |
| `.github/workflows/gates.yml` | **프로젝트** (시작 템플릿) | 서비스 컨테이너·시크릿 등 CI 요구는 본질적으로 프로젝트마다 다르다 |
| `.golangci.yml` · `eslint.config.js` | **프로젝트** (시작 템플릿) | 하드룰이 프로젝트마다 다르다 |

워크플로가 프로젝트 소유여도 **게이트 명령을 워크플로에 다시 적지 않는다** — `gate.sh` 를 부른다.
프로젝트가 플래그를 더 줘야 하면 확장점(`AI_KIT_GO_TEST_FLAGS` 등)을 쓴다.
