# CLAUDE.md — <프로젝트명>

> **이 프로젝트 규칙의 단일 출처.** 규칙을 다른 파일에 중복해 적지 않는다 —
> 두 벌이 되면 반드시 어긋나고, 어느 쪽이 진짜인지 아무도 모르게 된다.

## 이 문서를 쓰는 규칙

1. **규칙마다 누가 막나를 적는다.** 쓸 수 있는 말은 여덟이다:

   `git 훅` · `에이전트 훅` · `권한 프롬프트` · `린터` · `테스트` · `CI` · `리뷰` · `막는 것 없음`

   **각각이 무엇을 막고 어떻게 우회되는지는 `docs/process/verification-stages.md` 3.3 에
   있다.** 여기 옮겨 적지 마라.

2. **`리뷰`·`막는 것 없음` 만 적힌 규칙은 안 지켜진다고 가정하고 계획을 정하라.**
   어겨도 기계가 찾지 못하므로 언젠가 어겨지고, 어겨져도 아무도 모른다.
3. **적용 대상이 없는 규칙은 지운다.** 없는 코드에 대한 규칙이 남아 있으면
   나머지 규칙까지 덜 믿게 된다.
4. **일반론이 프로젝트 내용보다 길면 잘라라.** 근거 설명은 `docs/process/` 에 있다.

## 작업 루프

feature 브랜치 → 구현 → 테스트 → `commit` → `open-pr` → 리뷰 한 라운드 → 수정 → `dev-log` → 머지.

- 파일 3개 이상 또는 구조에 영향 주는 변경은 **먼저 계획을 제시하고 승인받는다.**
- **세션을 시작해 할 일을 고를 때와 일 하나가 끝나 다음 일을 물을 때는 `merge-pr` 의 「다음 일」 문단(`checks.md`)대로
  한다.** 그때마다 열린 이슈 전체를 다시 받아(`bash .claude/hooks/backlog.sh`) 고르고, 앞서 정한 순서는 다시 따질
  후보의 하나로 둔다 — 하던 일의 다음 차례만 보기로 올리면 먼저 할 것이 보기에 오르지 않는다. 고르면 계획을 쓰기
  전에 브랜치를 만들고 `Refs #N` 을 단 첫 커밋을 둔다 — PR 전에 다른 세션이 그 일을 맡은 일로 아는 것은 이 커밋뿐이다.
  `막는 것 없음`
- **feature 브랜치는 `origin` 의 기본 브랜치에서 만든다.** 그 전에 auto-merge 가 켜진 열린 PR 과 머지된 PR 을 본다 — Approve 를
  받고도 열려 있는 PR 은 사람에게 알리고, 머지된 PR 의 로컬 브랜치는 `merge-pr <번호>` 로 정리한다(`merge-pr` 3절).
  `막는 것 없음`
- **`dev-log` 는 머지 전에 실행한다.** 겪은 일은 겪은 세션만 쓸 수 있다. 머지 뒤로 미루면 다음
  세션이 결론만 보고 쓰게 된다. `막는 것 없음`
- **리뷰는 한 라운드를 진행하고 멈춘다.** 두 리뷰의 결과를 코멘트 하나로 합쳐 올리고,
  **다음 라운드를 진행할지·머지할지는 사람이 정한다.** 라운드 수에 상한은 없다 —
  진짜로 고칠 것이 나오면 여러 번 진행해도 된다. 사람이 정하기만 하면 된다. `막는 것 없음`
- **머지는 사람이 지시했을 때만 한다.** 두 리뷰가 `Approve` 를 냈다는 것은 그 리뷰들의
  의견이지 허락이 아니다. `권한 프롬프트`
- **세션이 이슈를 열고 닫는 것은 초안을 보이고 승인받은 뒤다.** 열린 이슈 목록이 레포의
  상태를 말한다. 보인다는 것은 승인을 묻기 바로 전에 세션의 응답에 초안의 최종본 전문을 출력하는 것이다 —
  파일 경로나 요약으로 대신하지 않는다. 승인을 받는 모든 글이 그렇다. `권한 프롬프트`
- GitHub 에 올리는 글(이슈 · PR 본문 · 코멘트)은 **문단과 목록 항목을 한 줄로 쓴다.** GitHub 은
  그 안의 줄바꿈 하나도 줄을 바꿔 보여 줘서, 레포 문서처럼 줄을 바꿔 쓰면 문장 한가운데서 끊긴다.
  목록 항목 아래 `→` 줄처럼 일부러 바꾸는 줄은 그대로 둔다. `막는 것 없음`
- 외부 API·SDK 는 **기억에 기대어 코드를 쓰지 않는다.** 공식 문서나 실제 호출로 확인한다. `리뷰`
  → 확인한 근거(문서 URL·실행 결과)를 코드 주석이나 ADR 에 남긴다.
- 읽지 않은 파일의 내용을 단정하지 않는다. 먼저 읽는다.
- 머지 전 검토에서 나온 수정은 **diff 제시 → 확인 → 커밋** 순서. 푸시 먼저 하지 않는다.
- 고친 것의 파급은 고친 세션이 직접 찾는다. 같은 부류가 다른 자리에 있는지 찾는다. 절차는 `open-pr` 0단계

## 산출물 언어

| 산출물                                                | 언어                                                   |
| ----------------------------------------------------- | ------------------------------------------------------ |
| 코드 주석 · 식별자 · 커밋 메시지 · PR 제목 · 브랜치명 | **영어**                                               |
| **CI 워크플로(잡·스텝 이름)**                         | **영어(ASCII)** — 잡 이름이 required check 이름이 된다 |
| PR 본문 · 리뷰 코멘트 · 설계 문서 · README · RUNBOOK  | 팀 언어                                                |
| 이 파일 · 스킬 · 에이전트 정의 · 훅의 사람용 메시지   | 팀 언어 + 영어 기술용어                                |

**기술용어는 번역하지 않는다.** `errors.Is` · `idempotency` 는 원어로 둔다.

**글은 세 기준을 지킨다.** 레포에 쓰는 글과 GitHub 에 올리는 글 모두다. `리뷰`

1. **한 뜻으로만 읽힌다.** 두 가지로 읽히는 말, 무엇을 하는지나 왜 하는지가 빠진 말은 그 자리의
   뜻을 적은 말로 바꾼다. 「실수가 실제로 나는 곳」은 「실수가 실제로 생기는 곳」이다.
2. **그 글의 언어로 자연스럽다.** 글의 언어는 위 표가 정한다. 다른 언어 문장을 그대로 옮긴 말과,
   소리 내어 읽으면 어색한 말은 풀어 쓴다.
3. **바로 말한다.** 할 말 앞에 말을 덧붙여 판단을 흐리지 않는다. 「~하는 편이 좋겠다」 ·
   「~할 수 있을 것 같다」, 이미 확인한 것에 쓰는 「~로 보인다」가 그런 말이다. 할 말만 쓴다.
   덧붙이면 뜻이 흐려지고 글이 길어진다.

### 커밋 트레일러

커밋 메시지에 붙이는 트레일러는 이 한 줄뿐이다. `리뷰`

```
Co-Authored-By: Claude Opus 5 (xhigh) <noreply@anthropic.com>
```

**커밋 시점의 실제 모델·effort 를 쓴다** — 세션 중간에 바뀌므로 기억으로 쓰지 마라.
상태줄에 표시돼 있다. 세션 URL(`Claude-Session:`)은 붙이지 않는다.

## 명령

|                  |                                                                      |
| ---------------- | -------------------------------------------------------------------- |
| 실행             |                                                                      |
| 테스트           |                                                                      |
| 게이트 전체      | `bash .kit/gate/gate.sh`                                             |
| 린트만(빠름)     | `bash .kit/gate/gate.sh --lint` — 커밋 훅이 이것을 부른다            |
| 요구 추적 검사   | `bash .kit/gate/trace.sh`                                            |
| 게이트 도구 설치 | `bash .kit/gate/install-tools.sh` (버전은 `.kit/gate/tool-versions`) |

> **도구가 없으면 검사는 실패한다** — 로컬도 CI 와 같은 기준이다. 도구 부재는 통과가
> 아니라 "검사되지 않았다" 이다. 로컬만 도구 없이 통과시키면 로컬에서 통과한 커밋이 CI 에서
> 실패하고, 고쳐서 다시 푸시하는 데 CI 와 사람의 시간이 든다. 불가피할 때만
> `KIT_ALLOW_MISSING_TOOLS=1` 로 도구가 없는 검사를 건너뛰게 하고, 그때 무엇이 검사되지 않는지 출력된다.
> **Claude Code 세션 안에서는 게이트가 이 변수를, 커밋 훅이 보호 브랜치 예외(`KIT_ALLOW_PROTECTED`)를 받지 않는다.**
> 세션은 도구를 설치하고, 불가피한 예외는 사람에게 세션 밖 터미널에서 실행해 달라고 한다
> (`docs/process/verification-stages.md` 6.4).
