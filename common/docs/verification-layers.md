# 검증 계층

같은 결함을 세 계층이 중복해서 보지 않는다. **아래 계층이 잡을 수 있으면 위 계층에서 뺀다.**
이것이 품질을 올리면서 동시에 리뷰 시간을 줄이는 유일한 수다.

| 계층 | 잡는 것 | 성질 | 비용 |
|---|---|---|---|
| **L1 기계** — 타입·린터·테스트·스캐너 | 결정론적으로 판정 가능한 것 | 100% 재현. 놓치지 않음. | 1회 설정, 이후 0 |
| **L2 AI 리뷰** | 의도·설계 정합·누락된 케이스 | 확률적. **자기 코드에 특히 약함.** | 매 PR |
| **L3 사람** | 제품 판단·시각·실사용 흐름·트레이드오프 | 대체 불가 | 비쌈. 아껴 쓴다. |

---

## L1로 내려야 하는데 L2에 남아있기 쉬운 것들

리뷰 체크리스트에 아래가 **문장으로** 적혀 있으면, 그건 린터 설정이 빠졌다는 뜻이다.

| 리뷰 체크리스트에 흔히 적히는 문장 | 실제로 막는 것 |
|---|---|
| "에러를 `%w`로 래핑했나" | `errorlint` |
| "response body·rows·파일을 닫았나" | `bodyclose` · `sqlclosecheck` · `rowserrcheck` |
| "context를 전파·취소하나" | `contextcheck` · `noctx` |
| "시크릿이 코드·로그에 없나" | `gosec` · `gitleaks` |
| "루프 변수 캡처 문제 없나" | `copyloopvar` |
| "에러를 삼키지 않나" | `errcheck` · `nilerr` |
| "접근성 속성이 있나" | `jsx-a11y` |
| "`any`를 쓰지 않았나" | `@typescript-eslint/no-explicit-any` |
| "프론트가 절대 URL을 쓰지 않나" | `no-restricted-syntax` (프로젝트 하드룰 코드화) |
| "금지한 라이브러리를 안 썼나" | `no-restricted-imports` · `depguard` |

> **프로젝트 하드룰은 산문이 아니라 린트 규칙으로 쓴다.** 산문 규칙은 AI가 읽고
> 지키려 "노력"하지만, 린트 규칙은 지켜지지 않으면 빌드가 깨진다.

## L2가 실제로 필요한 것 (기계가 못 잡음)

- 이 diff가 **한 가지 일**을 하는가
- 테스트가 *의미 있는* 케이스를 덮는가 — 커버리지 %는 L1, **케이스 선택**은 L2
- **PR 본문이 말한 목적에서 diff 가 벗어났는가** (산출물 규칙 R3) — 본문은 열 때 쓰고
  얼리므로 **diff 가 본문보다 큰 것은 정상이다.** 보는 것은 최신인지가 아니라
  본문이 세운 목적·결론을 이후 커밋이 뒤집었는지다. 아래 「PR 본문은 열 때 쓰고 끝이다」
- **SPEC의 요구가 구현에 실제로 도달했는가** (추적표 대조)
- 에러 분류가 맞는가 (재시도 가능 / 불가)
- 이 추상화가 지금 필요한가, 아니면 투기적 seam인가

## L2를 두 번 돌리는 조건 — 콜드 리뷰어

자기 코드를 자기 컨텍스트로 보는 리뷰는 자기 가정을 재확인하기 쉽다.
그래서 **콜드 컨텍스트 리뷰어**(diff + 규칙 + SPEC만 보고 시작하는 별도 에이전트)를
2차로 돌린다.

**기본은 "돈다" 다.** 건너뛰는 경우는 하나뿐이다:

- [ ] **글만 바뀐 PR** — README·ADR·dev-log 같은 산문. 사람이 읽을 글만 바뀌었을 때.

> **설정·CI 워크플로·훅·게이트 스크립트·템플릿은 "글"이 아니다 — 돈다.**
> 확장자로 판단하지 마라. `.json`·`.yml`·`.md` 여도 그것이 *동작을 규정*하면 코드다.
> 되돌릴 수 없는 실수는 바로 거기에 산다.

판단이 애매하면 아래 축에 걸리는지 본다. 하나라도 걸리면 **반드시** 돈다:

돈이 나가는 경로 · 동시성/트랜잭션/락 · 인증/시크릿/권한 ·
DB 스키마/마이그레이션 · 배포 절차 · **게이트·훅·CI 자체**

### 두 층을 다 돌린다 — 서로 다른 것을 잡는다

| 층 | 잡는 것 | 그쪽만 가능한 이유 |
| --- | --- | --- |
| 셀프(맥락 보유) | 결정과 어긋난 구현 · **뒤집힌 전제**(본문이 말한 목적을 이후 커밋이 벗어남) | 무엇이 언제 정해지고 바뀌었는지 아는 쪽만 안다 |
| 콜드(맥락 없음) | 작성자가 "맞다고 아는" 가정 · diff 밖 파급 | 작성자의 설명으로 안심할 수 없다 |

> 실측: 첫 두 번의 실전에서 셀프 3건 vs 콜드 11건, 셀프 3건 vs 콜드 7건.
> 콜드가 크게 앞섰지만 **셀프만 잡은 것도 있었다** — "이 커밋이 본문이 말한 목적 밖으로
> 나갔다"는 맥락을 가진 쪽만 알 수 있다. 한 층으로 줄이지 마라.
>
> 처음에는 다섯 개 위험 축에만 걸었는데, 그 문구가 하필 **설정·CI·훅 변경을 좁게**
> 읽히게 만들었다 — 되돌릴 수 없는 실수가 실제로 사는 곳이다. 기본값을 "돈다"로 뒤집었다.

### 라운드는 사람이 센다

두 층이 한 번 돌면 그것이 **한 라운드**다. 라운드가 끝나면 결과를 **하나의 코멘트로
올리고 멈춘다.** 다음 라운드를 돌지, 그만하고 머지할지는 사람이 정한다.

**게시는 메인 에이전트가 한다.** 두 층 다 결과를 돌려주기만 한다. 이유는 **읽는 사람**
이다 — 두 층이 따로 올리면 코멘트 둘을 각각 읽어야 하고, 그 사이에 다음 라운드가
시작될 수 있다. 그리고 요약을 코멘트의 본체로 두려면 두 결과가 한 자리에 있어야 한다.

권한 때문이 아니다. 공식 문서는 서브에이전트의 도구 호출도 권한 규칙을 지난다고 적는다.

**라운드 수에 상한을 두지 않는다.** 진짜로 고칠 것이 계속 나오면 여러 번 돌아야 한다.
정하는 것이 사람이면 된다.

> 이 절이 없어서 한 프로젝트에서 라운드가 **사람 승인 없이 20회** 돌았다. 설정 파일
> 한 개를 옮기는 작업이었고, 실제 변경은 여섯 번째 커밋에서 끝났으며 나머지 18커밋은
> 그 변경을 *설명하는 문장*을 고치는 것이었다. 코멘트 40건 중 20건은 서브에이전트가
> 직접 올렸다. 그 프로젝트의 `open-pr` 에 적혀 있던 것은 "3단계로 돌아와 다시 돌린다"
> 한 줄이었고, 멈추라는 말이 없었다.
>
> **라운드마다 head 가 움직이므로 "같은 head 를 두 번 리뷰하지 마라" 로는 못 막는다** —
> 수정 커밋을 밀고 다음 라운드를 도는 것이 정상 절차다. 실제로 그 20라운드는 서로 다른
> head 20개였다. 세는 것은 기계가 아니라 사람이다.

### 규칙마다 누가 막나 — 어휘

프로젝트의 `CLAUDE.md` 는 규칙마다 **무엇이 막는지**를 이 말들로 적는다. 라벨은 이름만
붙이지만 평문은 **무엇이 막고 어떻게 뚫리는지**를 말한다.

| 적는 말 | 무엇이 막나 | 우회 |
| --- | --- | --- |
| `git 훅` | 커밋·푸시 직전에 도는 스크립트 | `--no-verify` · 훅을 안 켠 clone |
| `에이전트 훅` | 에이전트의 도구 호출을 보는 `.claude/hooks/` 스크립트 | 사람이 직접 치거나 웹에서 누르면 · 훅이 탈출구를 두었으면 |
| `권한 프롬프트` | `permissions.deny`·`ask` 에 걸린 것을 Claude Code 가 사람에게 묻는다 | 사람이 안 보고 승인하면 · 규칙이 지목한 도구 밖으로 우회하면 |
| `린터` | 린트 설정 | 규칙을 끄면 |
| `테스트` | 테스트 | 테스트를 지우면 |
| `CI` | GitHub Actions | 검사 자체는 못 피한다. 다만 **머지를 막는 것은 브랜치 보호**다 |
| `리뷰` | PR 리뷰에서 사람이 본다 | 못 보고 넘어가면 |
| `사람` | 막는 것이 없다. 사람이 기억해야 한다 | 항상 |

**`리뷰`·`사람` 만 적힌 규칙은 안 지켜진다고 치고 계획을 세워라.** 어겨도 아무 검사에
안 걸리므로 언젠가 어겨지고, 어겨져도 아무도 모른다.

### 라운드 사이에 무엇이 넘어가나

두 리뷰 층(`self-review`·`cold-reviewer`)이 여러 라운드를 도는 동안 **지적이 조용히
사라지는 경로가 넷** 있었다. 두 층의 정의(`self-review`·`cold-reviewer`)와 게시하는
쪽(`open-pr`)이 이 절을 가리키기만 한다.

**1. 한 층의 지적을 아무도 추적하지 않는다.** 콜드에만 재리뷰 절이 있고 셀프에는 없으면,
셀프 지적은 닫혔는지 아닌지 어느 라운드에도 안 적힌다. 그래서 **두 층 다** 직전 라운드
코멘트를 읽고 항목마다 판정한다.

**2. 직전 라운드만 본다.** `일부 해결`·`미해결` 로 남은 것이 다음 라운드 목록에 안 오르면
그 다음 라운드는 그것의 존재를 모른다. 그래서 **닫힐 때까지 매 라운드 다시 오른다.**

**3. 판정을 수로만 적는다.** `2건 일부 해결` 이라고만 적으면 무엇을 다시 올릴지 그 기록에서
읽을 수 없다. 그래서 **항목을 이름으로 적고**, 직전 기록이 수만 남겼으면 **그 라운드의
발견 목록으로 돌아가 재검증한다.**

**4. 아직 아무도 안 정한 항목이 판정어에 없다.** 넷 중 고르면 `미해결`(= 안 고쳐졌다)
뿐인데 그러면 정하기 전인 것이 매 라운드 「꼭 고쳐야 함」 으로 올라오고, 안 고르면
다음 라운드가 존재를 모른다. 그래서 `결정 필요` 를 둔다.

판정은 다섯 가지다. 앞의 셋은 **고쳐졌나**를 정도로 나눈다. 뒤의 둘은 **결정이 났나**로 나눈다.

| | |
| --- | --- |
| `해결` | 고쳐졌다 |
| `일부 해결` | 일부만 고쳐졌다 |
| `미해결` | 안 고쳐졌다 |
| `기각` | **지적이 틀렸다는 뜻이 아니다.** 맞는 지적인데 **안 하기로 정했다.** 그 결정에 시한이 있으면(예: `CLAUDE.md` 의 v1.0 조항) 시한이 왔을 때 이 표시로 되찾는다 |
| `결정 필요` | 아직 아무도 안 정했고, **층이 정할 것이 아니다.** 이월은 되지만 「꼭 고쳐야 함」 에는 안 오른다 |

### 이월에는 끝이 있다

**이월된 항목은 두 라운드 안에 결정된다.** 고치거나(`해결`), 안 하기로 정하거나(`기각`),
사람이 정할 일로 올리거나(`결정 필요`) 셋 중 하나다.

**세 번째 라운드에 같은 항목이 `미해결`·`일부 해결` 로 다시 오르면 그것은 발견이 아니라
결정이 밀린 것이다.** 그 라운드의 요약 맨 앞에 그렇게 적고 사람에게 올린다 — 리뷰가 또
한 바퀴 돈다고 없어질 문제가 아니기 때문이다.

끝을 안 두면 `[낮음]` 은 영원히 밀린다. 목록이 길어지면 이월이 배경 소음이 되고, 그것은
이 절이 없애려는 "안 읽히는 리뷰" 로 돌아가는 길이다.

**읽는 범위는 PR 전체 diff 다.** 직전 라운드 이후의 증분만 보면 *"지적한 자리를 아예 안
건드린 것"* 이 안 보인다 — 안 건드렸으니 증분에 없다. 증분은 **어디를 먼저 볼지** 정하는
커밋 목록으로만 쓴다.

**독립을 지키는 자리는 이번 라운드뿐이다.** 두 층이 같은 코드를 동시에 독립으로 보는
것이 이 구조의 값이므로 **게시 전에 상대의 결과를 보는 것은 금지**다. 그러나 지난
라운드의 코멘트는 이미 게시된 기록이고, 그것은 PR 본문과 같은 성격이다 — **배경이 아니라
검증 대상**으로 읽는다. 콜드가 셀프 블록까지 읽는 이유는 하나다: 셀프가 지적하고 저자가
고치면 **그 수정이 맞았는지 보는 층이 그것 말고 없다.**

## PR 본문은 열 때 쓰고 끝이다

**본문은 `open-pr` 이 한 번 쓰고, 그 뒤로는 아무도 고치지 않는다.** 라운드가 만든 것은
코멘트에 쌓이고, 최종 정리는 `merge-pr` 이 머지 직전에 코멘트 하나로 올린다.

**왜 이렇게 바뀌었나.** 예전에는 라운드마다 본문을 갱신했고, 그럴 수밖에 없었다 —
**그때 두 층이 받는 것에 직전 코멘트가 없었다.** 받는 것은 diff·파일 목록·본문·메타데이터
넷뿐이었으므로 **라운드 사이에 상태를 나르는 통로가 본문 하나였다.** 지금은 두 층 다
직전 코멘트를 통째로 받는다(위 「라운드 사이에 무엇이 넘어가나」). 통로가 생겼는데 옛
통로도 계속 쓰면 두 벌이 된다.

**두 벌의 값은 실측됐다.** 한 PR 의 본문이 열한 라운드 동안 갱신되면서 **거듭 거짓이
됐다** — `bash -n a b` 가 첫 파일만 검사한 것을 "전부 통과" 로, 출력이 없는 명령 밑에 손으로
쓴 요약을, 돌린 적 없는 명령줄을, 그리고 코드가 바뀐 뒤에도 그대로 남은 설정 출력을.
**전부 `$` 가 붙어 있어 읽는 사람은 실행 결과로 믿는다.** 몇 번이었는지는 여기 적지
않는다 — 수를 두 곳에 적으면 반드시 갈린다.

원인은 게으름이 아니라 구조다. **본문의 증거는 코드에서 파생된 값인데 손으로 관리된다.**
코드가 바뀌어도 본문을 고쳐주는 것이 없다 — 훅도 게이트도 CI 도 본문은 안 본다.

**그래서 규칙은 둘이다:**

1. **라운드가 바꿀 값을 본문에 적지 마라.** 파일 내용을 떠서 붙이는 것 같은 파생 출력이
   그것이다. 붙일 것은 **연 시점에 실행한 게이트 출력**이고, 그건 낡는 것이 아니라
   그때의 기록이다.
2. **두 층은 본문이 낡은 것을 발견으로 올리지 않는다.** 본문은 **연 시점의 기록**이므로
   그 안의 명령을 지금 다시 돌려 다르게 나오는 것은 정상이다. 발견인 것은 둘뿐이다 —
   **쓸 당시에도 거짓이었던 것**, 그리고 **본문이 세운 목적을 이후 diff 가 벗어난 것.**

   낡은 증거는 **처음 확인된 라운드의 코멘트에 「본문 정정」 절로 한 번 적고 거기서
   닫는다.** 그 절이 없으면 그 지적은 매 라운드 다시 올라오는데 `open-pr` 이 본문을 못
   고치게 하므로 **닫을 방법이 없는 이월 항목**이 된다. 규칙이 스스로 만든 구멍이라
   규칙이 막는다.

3. **코멘트는 append-only 다.** 본문을 얼리면 코멘트가 유일한 기록이 되므로, 이미 올라간
   코멘트를 고치는 것은 기록을 고치는 것이다. `gh pr edit` 으로 본문을, `gh api -X PATCH`
   로 코멘트를 고치지 마라. 틀린 것이 있으면 **새 코멘트로 정정한다.**
   (실제로 7라운드에 이미 게시된 코멘트를 `gh api -X PATCH` 로 고친 적이 있고, 그때
   아무 프롬프트도 뜨지 않았다. 그래서 `permissions.ask` 에 `Bash(gh api*)` 가 있다.)

## L3(사람)에게 남기는 것 — 명시적으로

- 시각 · 레이아웃 · 모션 · 색의 실제 지각
- 여러 화면을 오가는 실사용 흐름
- 제품 판단 (이 기능이 맞나, 이 문구가 맞나)

> 측정값 통과와 실제 지각은 **다른 평가축**이다. 대비비 기준을 통과하고도
> 다크 배경에서 안 보일 수 있고, 단위 테스트가 개별 동작을 다 덮고도
> 화면을 오가는 흐름에서 깨질 수 있다.

산출물 규칙 R6에 따라, **자동화가 닿지 않는 이 범위를 문서에 적는다.**
적지 않으면 검증이 조용히 사라지고 아무도 사라진 줄 모른다.

## 강제는 에이전트 밖에 둔다 (핵심)

에이전트 훅(`.claude/settings.json`)은 **그 에이전트가
그 도구를 통해 행동할 때만** 작동한다. 사람이 터미널에서 직접 하거나,
다른 에이전트로 갈아타면 강제가 통째로 사라진다.

**표를 읽을 때 먼저 볼 것은 그 줄이 모델 안에 있느냐 밖에 있느냐다.** 맨 윗줄만 안에 있고
나머지는 밖에 있다. 안에 있는 것은 모델이 따라줄 때만 존재한다.

| 두는 곳 | 누구에게 걸리나 | 우회 |
|---|---|---|
| **CLAUDE.md 규칙 · 스킬 절차 · 스킬 description** ← 모델 안 | 모델이 따라줄 때만 | 안 따라주면 끝. **흔적도 안 남는다** |
| 에이전트 훅 | 그 에이전트, 그 도구를 쓸 때만 | 도구를 바꾸면 사라짐 · 훅이 탈출구를 두었으면 모델이 그것을 씀 |
| **permissions (`deny`·`ask`)** | 그 에이전트의 도구 호출. **모델이 끌 수 없다**(문서) | 규칙이 지목한 도구 밖으로 나가면(`Bash(gh …)` 를 막아도 `curl` 은 남는다) · **이 파일 자체를 고치면** — `deny` 에 그것을 막는 규칙이 없다 |
| **git hooks** | 그 레포에서 커밋·푸시하는 **모두** (사람 포함) | `--no-verify` · 활성화 안 한 clone |
| **CI** | 원격에 올라온 **모든** 변경 | 없음(머지는 가능) |
| **브랜치 보호** | 우회 불가 | 없음 |

첫 줄과 나머지의 차이는 문서가 못 박아둔다:

> *"Permission rules are enforced by Claude Code, **not by the model**. Instructions in
> your prompt or `CLAUDE.md` shape what Claude **tries** to do, but they don't change
> what Claude Code **allows**."* — `/docs/en/permissions`

**첫 줄만으로 선 규칙은 이 레포에서 실제로 무너졌다** — 킷 PR 넷이 스킬을 안 거치고
`gh pr create --fill` 로 나갔고, "사람 허락 없이 머지하지 않는다" 를 어기고 머지된 적이
있고, 리뷰가 사람 없이 스무 바퀴 돌았다. 전부 첫 줄에만 있던 규칙이다.

그리고 **아래 세 줄만이 의도를 막는다.** 위 세 줄은 실수를 막는다. 되돌릴 수 없는 것은
아래에 둔다.

### 권한 규칙이 실제로 무엇을 잡나

`permissions` 줄에 무엇을 적을지 정할 때 필요한 사실을 한자리에 둔다. **다른 파일에
옮겨 적지 마라 — `settings.json` 은 여기를 가리키기만 한다.**

**규칙은 셸이 해석하지 않는다.** `Bash(gh pr create *)` 라는 문자열은 셸에 도달하지
않는다. Claude Code 가 에이전트가 치려는 명령 **문자열**을 자기 매처로 이 패턴에 맞춰볼
뿐이다. 그래서 동작을 아는 길은 문서를 읽거나 돌려보는 것 둘뿐이고, 셸 글로브의 직관을
그대로 들이대면 틀린다.

**문서로 아는 것** — 규칙은 명령을 조각내 각 조각을 본다:

| | |
| --- | --- |
| 구분자 | *"The recognized command separators are `&&`, `\|\|`, `;`, `\|`, `\|&`, `&`, and newlines."* |
| 중첩 | *"Deny and ask rules apply when any subcommand matches them, including a command nested inside a subshell, a command substitution…"* |
| 앞 대입 | *"A deny or ask rule matches past any leading assignment"* |
| allow 와의 관계 | *"a matching ask rule prompts even when a more specific allow rule also matches"* |
| auto mode | *"Content-scoped ask rules … always force a permission prompt, even in auto mode"* · *"The classifier cannot auto-approve a matching action."* |

**실측으로 아는 것** — 규칙이 없으면 그냥 도는 읽기전용 명령으로 대조군을 만들어 쟀다.
막히면 그것은 규칙이 막은 것이다:

```
명령: cat AI_KIT_PROBE_FILE.txt

규칙 없음                              → 실행됨
ask: Bash(cat AI_KIT_PROBE*)           → 차단          개행·주석 형태도 같이 차단됨
ask: Bash(cat AI_KIT_PROBE_FILE*)      → 차단          뒤에 무엇이 붙어도 잡는다
ask: Bash(cat AI_KIT_PROBE_FILE *)     → 실행됨        토큰이 정확히 그것일 때만 잡는다
```

세 번째와 네 번째의 차이가 **뒤 `*` 앞의 공백**이다. 공백이 있으면 그 토큰으로 **시작하는
다른 명령**을 안 잡는다(문서의 `ls` / `lsof` 예시). **맨몸 명령은 두 형태 다 잡는다** —
공백 없는 쪽은 `*` 가 빈 문자열에 붙어서, 공백 있는 쪽은 문서가 그 경우를 따로 열어둬서.

**그래서 `deny`·`ask` 에는 공백 없는 형태를 쓴다.** 넓게 잡으면 안 쓰는 명령에 프롬프트가
한 번 더 뜰 뿐이지만, 좁게 잡으면 그것이 구멍이다. `allow` 는 반대다 — 거기서 과매칭은
`Bash(ls*)` 가 `lsof` 까지 자동 승인하는 사고이므로 공백 형태를 쓴다.

**대화형에서 프롬프트가 실제로 뜬다 — 그리고 `allow` 를 이긴다.** 문서로만 알던 것을
쟀다. `git status` 는 킷의 `allow` 에 있다. 그것을 `ask` 에도 넣고 에이전트가 실행하니
**승인 프롬프트가 떴고, 사람이 누른 뒤에야 돌았다.** 인용(*"a matching ask rule prompts
even when a more specific allow rule also matches"*)이 실행으로 닫혔다.

> 헤드리스(`-p`)로는 이것을 못 잰다 — 답할 사람이 없어 `ask` 가 "차단" 으로 나타나고,
> 그러면 "프롬프트가 떴다" 와 "다른 이유로 막혔다" 가 구분되지 않는다. 대화형 세션에서
> 사람이 화면을 보는 것 말고 다른 방법이 없다.

**한 번 관찰된 것 — 보증으로 읽지 마라.** 위 측정을 하려고 에이전트가 `settings.json` 의
`ask` 배열을 편집하려 하자 auto mode 분류기가 막았다(`Blocked by classifier`). 사람이
허락한 뒤에야 편집됐다. **이것은 한 번의 관찰이고 층이 아니다** — 분류기는 auto mode
에서만 돌고 판정이 확률적이며, 공식 문서가 권한 장치로 규정한 것이 아니다.
**`deny` 에 `Edit`·`Write` 로 이 파일을 막는 규칙은 없다.** 여기 적힌 층 전체가 그
파일 하나에 얹혀 있으므로, 그것을 막고 싶으면 규칙으로 막아야 한다.

**스킬은 예외가 될 수 없다.** 스킬 정의의 `allowed-tools` 로도, 명령 앞의 환경변수
대입으로도 `ask` 를 비켜갈 수 없다. 같은 명령으로 2x2:

```
ask 없음 · allowed-tools 없음   → 차단
ask 없음 · allowed-tools 있음   → 실행됨      allowed-tools 는 작동한다
ask 있음 · allowed-tools 없음   → 차단
ask 있음 · allowed-tools 있음   → 차단        ask 가 이긴다
```

그러므로 `ask` 가 세우는 것은 **"스킬을 거쳤나" 가 아니라 "사람이 봤나" 다.** 전자를
세우려면 규칙이 아니라 훅이 필요한데, 훅은 표의 둘째 줄이라 모델이 탈출구를 쓰면 사라진다.

**남는 한계.** 규칙은 **지목한 도구**만 본다. `Bash(gh pr create*)` 를 세워도 `curl` 로
같은 API 를 치면 안 걸린다. 게으른 지름길은 막고 작정한 우회는 못 막는다 — 그 자리는
아래 두 줄(CI·브랜치 보호)이다.

### git hooks 의 정직한 한계

훅 파일은 `.ai-kit/git-hooks/` 에 커밋되므로 clone 을 따라온다. 그러나 이를 활성화하는
`core.hooksPath` 는 **로컬 설정이라 clone 되지 않는다** — git 이 보안상 의도한 동작이고
우회 방법이 없다. 새로 clone 한 사람은 한 줄이 필요하다:

```bash
git config core.hooksPath .ai-kit/git-hooks
```

그리고 `git commit --no-verify` 로도 넘어간다.

세 번째 한계는 더 조용하다. **훅 파일이 실행권한 없이 커밋돼 있으면 git 은 그것을
건너뛴다** — `hint:` 한 줄이 stderr 로 나갈 뿐 커밋은 성공한다.

```
$ git commit -m ...
hint: The '.ai-kit/git-hooks/pre-commit' hook was ignored because it's not set as executable.
[main abc1234] ...        ← 훅이 exit 1 인데도 커밋됨
```

설치가 잘못될 걱정은 아니다(`cp -R` 이 킷의 100755 를 그대로 옮긴다). **설치 이후**에
모드가 떨어지는 경로가 실재한다 — 둘 다 재현했다:

| 방아쇠 | 결과 |
|---|---|
| `core.fileMode=false` 인 레포 | 작업트리는 755 인데 **커밋된 모드는 100644** |
| 훅을 편집기가 지우고 다시 쓸 때 | 인덱스 모드가 **100644** 로 바뀜 |

훅은 `.ai-kit/` 에 vendor 돼 레포 안에 있으니 누군가 손대는 것을 전제한 파일이다.
그런데 손대는 순간 강제가 조용히 꺼질 수 있고, 로컬에서는 아무도 눈치채지 못한다.

파일이 *있는지*만 보는 검사는 이것을 통과시킨다. 그래서 CI 가 커밋된 모드까지 본다
(`[ -x ]`). 게이트 스크립트는 훅이 `bash <경로>` 로 부르므로 권한이 필요 없다 —
거기까지 요구하면 멀쩡한 레포에서 오탐이 난다.

> **그래서 로컬 훅은 강제가 아니라 조기 피드백이다.** 되돌릴 수 없는 결과를 막는
> 진짜 강제는 CI + 브랜치 보호뿐이다. 훅을 믿고 CI 를 생략하면 강제가 0 이 된다.

> 규칙: **되돌릴 수 없는 결과를 막는 강제는 git hooks·CI·브랜치 보호에 둔다.**
> 에이전트 훅은 *편의*(자동 포맷·조기 피드백)에만 쓴다.

### 어느 검사를 어디에 둘 것인가 — 실측으로 정한다

실 모노레포(Go 백엔드 + React 프론트)에서 잰 값이다. 반복 측정해 워밍업 후 안정된 수치다.

| 검사 | 소요 | 어디서 |
|---|---|---|
| `gofmt` · `goimports` | 0.1s 미만 | 편집 직후(훅) · 게이트 |
| `prettier` | 1.7s | 편집 직후(훅, 파일 1개) · 게이트 |
| `golangci-lint` | 0.9s | 게이트 |
| `eslint` | 6.5s | 게이트 |
| `tsc` | 2.5s | 게이트 |
| `go test` | 0.3s (캐시 없으면 3.6s) | 게이트 |
| `vitest` | 7.8s | 게이트 |
| `build` | 3.1s | 게이트 |
| **`gate.sh --lint`**(테스트·빌드 제외) | **22s** | 수동 |
| **`gate.sh` 전체** | **37~42s** | pre-push · CI |

**처음에는 이 측정으로 린트를 pre-commit 에서 뺐다가, 되돌렸다.** 22초는
`gate.sh --all --lint`(CI 모드, 전체 검사)였고 커밋은 **변경 영역만** 본다 — Go 파일
하나를 고친 커밋은 2.8초다. 그리고 커밋은 의미 단위라 수 분~수 시간 작업의 끝에 오므로,
`pre-push` 가 이미 물리는 40초와 견주면 반대할 근거가 못 됐다.
지금은 `pre-commit` 이 `gate.sh --lint --staged` 를 부른다. 아래 문단은 남겨둔다 — 직관적으로는 "커밋 전에 린트가
맞다" 지만, 테스트와 빌드를 빼도 **22초**다. `npm run` 을 거칠 때마다 붙는 Node 기동
비용이 개별 도구 시간보다 크다. 커밋마다 22초를 물리면 사람은 `--no-verify` 를 습관으로
쓰게 되고, **끄는 게이트는 없는 게이트다.**

"변경된 파일만 린트하면 싸다" 도 틀렸다 — `eslint` 은 파일 하나에도 4.4초다(전체 6.5초).
시작 비용이 지배적이라 대상을 줄여도 거의 안 줄어든다.

> 지금 배치는 이렇다: **포맷은 편집마다**(0.1초 수준이라 공짜에 가깝다),
> **나머지 전부는 푸시**(되돌리기 어려운 경계에서 한 번), **CI 는 같은 것을 다시**
> (로컬은 `--no-verify`·미설치 훅·실행권한 누락으로 안 돌 수 있다 — 셋 다 이 킷에서
> 실증했다). `gate.sh --lint --staged` 를 `pre-commit` 이 부른다.

### 충돌 마커는 훅이 막는다

3-way 병합이 실패하면 파일에 충돌 마커가 남는다 — `git merge`·`rebase`·`cherry-pick`·
`stash pop` 이 전부 그렇다. 손으로 해소하다 한 덩어리를 빠뜨리면 마커가 든 채로
커밋되고, 설정·훅·워크플로가 조용히 망가진다(JSON·YAML 은 파싱부터 실패한다).
그래서 `pre-commit` 이 스테이지된 내용을 검사한다.

마커 셋 중 **`=======` 는 보지 않는다** — 마크다운 setext 제목의 밑줄과 구분되지 않아
정상 문서를 막는다. 진짜 충돌에는 항상 셋이 다 있으므로, 뒤에 라벨이 붙어 모호하지 않은
`<<<<<<< ` 와 `>>>>>>> ` 만으로 충분하다.

> 이건 R7 의 적용례다. 재현에 환경 조작이 필요 없다 — 이 킷을 만들면서 실제로 밟았고,
> 그때는 확인용 `grep '<<<<<<<\|>>>>>>>'` 이 BSD grep 에서 `\|` 를 못 읽어
> **"마커 없음" 이라는 거짓 통과**까지 났다.

### 왜 에이전트 `pre_push` 훅을 두지 않는가

킷은 이 훅을 처음부터 두지 않았고, 프로젝트에서도 킷 도입 때 지웠다. 근거를 남긴다 —
**제거한 구성요소의 이유를 안 적는 것이 R4·R5 위반**이고, 안 적으면 다음 사람이
"빠졌네" 하고 되살린다.

이유는 셋이고 전부 확인했다:

1. **중복이다.** git `pre-push` 훅이 이미 **모든** push 에서 게이트를 돌린다
   (`common/git-hooks/pre-push` 가 `gate.sh --base` 를 호출한다). 에이전트 훅을 더하면
   같은 검사가 두 번 돈다.
2. **비싸다.** 게이트는 실 모노레포에서 한 번에 수십 초다. 두 번이면 그만큼 두 배다.
3. **얻는 게 없다.** 에이전트 훅을 두는 유일한 이유는 "에이전트가 결과를 보게" 인데,
   **git 훅의 stderr 는 그대로 에이전트에게 전달된다.** 실측:

   ```
   $ git commit -m x
   훅이 남긴 메시지 (stderr)      ← 에이전트가 받는 출력에 그대로 들어온다
   ```

> 게다가 에이전트 훅은 그 에이전트가 그 도구를 쓸 때만 걸린다(원칙 1). 사람이 손으로
> push 하면 사라진다. **없어도 되는 층이면서 신뢰할 수도 없는 층**이라 두지 않는다.
