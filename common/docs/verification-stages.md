# 검증 단계

같은 결함을 세 단계가 중복해서 보지 않는다. **번호가 작은 단계가 찾아낼 수 있으면 번호가 큰 단계에서 뺀다.**
이것이 품질을 올리면서 동시에 리뷰 시간을 줄이는 유일한 방법이다.

| 단계 | 찾아내는 것 | 성질 | 비용 |
|---|---|---|---|
| **L1 기계** — 타입·린터·테스트·스캐너 | 결정론적으로 판정 가능한 것 | 100% 재현. 놓치지 않음. | 1회 설정, 이후 0 |
| **L2 AI 리뷰** | 의도·설계와 맞는지·누락된 케이스 | 확률적. **자기 코드에 특히 약함.** | 매 PR |
| **L3 사람** | 제품 판단·시각·실사용 흐름·트레이드오프 | 대체 불가 | 비쌈. 아껴 쓴다. |

번호는 바꾸지 않는다. 새 절은 끝에 붙이거나 이어지는 번호를 쓴다.

---

## 1 L1 으로 옮길 것

L1 으로 옮겨야 하는데 L2 에 남아 있기 쉬운 것들이다.
리뷰 체크리스트에 아래가 **문장으로** 적혀 있으면, 그건 린터 설정이 빠졌다는 뜻이다.

| 리뷰 체크리스트에 흔히 적히는 문장 | 실제로 막는 것 |
|---|---|
| "에러를 `%w`로 래핑했나" | `errorlint` |
| "response body·rows·파일을 닫았나" | `bodyclose` · `sqlclosecheck` · `rowserrcheck` |
| "context를 전파·취소하나" | `contextcheck` · `noctx` |
| "시크릿이 코드·로그에 없나" | `gosec` · `gitleaks` |
| "루프 변수 캡처 문제 없나" | `copyloopvar` |
| "에러를 무시하지 않나" | `errcheck` · `nilerr` |
| "접근성 속성이 있나" | `jsx-a11y` |
| "`any`를 쓰지 않았나" | `@typescript-eslint/no-explicit-any` |
| "프론트가 절대 URL을 쓰지 않나" | `no-restricted-syntax` (프로젝트가 켠다 — 시작 설정에 주석 예시) |
| "금지한 라이브러리를 안 썼나" | `no-restricted-imports` · `depguard` (프로젝트가 켠다 — 시작 설정에 주석 예시) |

> **프로젝트 하드룰은 산문이 아니라 린트 규칙으로 쓴다.** 산문 규칙은 AI가 읽고
> 지키려 "노력"하지만, 린트 규칙은 지켜지지 않으면 게이트가 실패한다.

## 2 L2 가 볼 것

기계가 찾아내지 못하는 것만 L2 가 본다.

- 이 diff가 **한 가지 일**을 하는가
- 테스트가 *의미 있는* 케이스를 다루는가 — 커버리지 %는 L1, **케이스 선택**은 L2
- **PR 본문이 말한 목적에서 diff 가 벗어났는가** (산출물 규칙 R3) — 본문은 열 때 쓰고
  그 뒤로 고치지 않으므로 **diff 가 본문보다 큰 것은 정상이다.** 보는 것은 최신인지가 아니라
  본문이 밝힌 목적과 내린 결론을 이후 커밋이 뒤집었는지다. 이유는 아래 4 에 있다.
- **SPEC의 요구가 실제로 구현됐는가** (추적표 대조)
- 에러 분류가 맞는가 (재시도 가능 / 불가)
- 이 추상화가 지금 필요한가, 아니면 아직 쓰는 곳이 없는 seam 인가

## 3 콜드 리뷰어

콜드 리뷰어는 L2 를 한 번 더 실행하는 것이다. 이 절은 언제 실행하는지를 정한다.
자기 코드를 자기 컨텍스트로 보는 리뷰는 자기 가정을 재확인하기 쉽다.
그래서 **콜드 컨텍스트 리뷰어**(diff + 규칙 + SPEC만 보고 시작하는 별도 에이전트)를
2차로 실행한다.

**기본은 "실행한다" 다.** 건너뛰는 경우는 하나뿐이다:

- [ ] **글만 바뀐 PR** — README·ADR·dev-log 같은 산문. 사람이 읽을 글만 바뀌었을 때.

> **설정·CI 워크플로·훅·게이트 스크립트·템플릿은 "글"이 아니다 — 실행한다.**
> 확장자로 판단하지 마라. `.json`·`.yml`·`.md` 여도 그것이 *동작을 규정*하면 코드다.
> 되돌릴 수 없는 실수는 바로 이런 파일에서 생긴다.

판단이 애매하면 아래 항목에 해당하는지 본다. 하나라도 해당하면 **반드시** 실행한다:

돈이 나가는 경로 · 동시성/트랜잭션/락 · 인증/시크릿/권한 ·
DB 스키마/마이그레이션 · 배포 절차 · **게이트·훅·CI 자체**

### 3.1 두 리뷰

두 리뷰를 다 실행한다. 서로 다른 것을 찾아낸다.

| 리뷰 | 찾아내는 것 | 그쪽만 가능한 이유 |
| --- | --- | --- |
| 셀프(맥락 보유) | 결정과 어긋난 구현 · **뒤집힌 전제**(본문이 말한 목적을 이후 커밋이 벗어남) | 무엇이 언제 정해지고 바뀌었는지 아는 쪽만 안다 |
| 콜드(맥락 없음) | 이 PR 을 만든 쪽이 "맞다고 아는" 가정 · diff 밖 파급 | 만든 쪽의 설명으로 안심할 수 없다 |

> 센 결과: 처음 실제로 쓴 두 번에서 셀프 3건 vs 콜드 11건, 셀프 3건 vs 콜드 7건.
> 콜드가 크게 앞섰지만 **셀프만 찾아낸 것도 있었다** — "이 커밋이 본문이 말한 목적 밖으로
> 나갔다"는 맥락을 가진 쪽만 알 수 있다. 한 리뷰로 줄이지 마라.
>
> 처음에는 위험한 변경 다섯 가지에만 적용했는데, 그 문구 때문에 **설정·CI·훅 변경은 적용 대상이
> 아닌 것처럼** 읽혔다. 되돌릴 수 없는 실수가 실제로 생기는 곳이 바로 그 변경이다. 기본값을 "실행한다"로 뒤집었다.

### 3.2 라운드

두 리뷰가 한 번 실행되면 그것이 **한 라운드**다. 라운드가 끝나면 결과를 **코멘트 하나로 합쳐
올리고 멈춘다.** 다음 라운드를 진행할지, 그만하고 머지할지는 사람이 정한다. 그 코멘트를 사람의
승인 없이 올리는 이유와 대신 무엇이 보는지는 아래 6.3 에 있다.

**게시는 메인 에이전트가 한다.** 두 리뷰 다 결과를 돌려주기만 한다. 이유는 사람에게 가는
**보고가 한 번**이어야 해서다 — 두 리뷰가 따로 올리면 게시도 보고도 둘로 나뉘고, 그 사이에
다음 라운드가 시작될 수 있다. 그리고 요약을 코멘트의 본체로 두려면 두 결과가 한 자리에 있어야 한다.

권한 때문이 아니다. 공식 문서는 서브에이전트의 도구 호출도 권한 규칙을 거친다고 적는다.

**라운드 수에 상한을 두지 않는다.** 진짜로 고칠 것이 계속 나오면 여러 번 진행해야 한다.
사람이 정하기만 하면 된다.

> 이 절이 없어서 한 프로젝트에서 라운드가 **사람 승인 없이 20회** 진행됐다. 설정 파일
> 한 개를 옮기는 작업이었고, 실제 변경은 여섯 번째 커밋에서 끝났으며 나머지 18커밋은
> 그 변경을 *설명하는 문장*을 고치는 것이었다. 코멘트 40건 중 20건은 서브에이전트가
> 직접 올렸다. 그 프로젝트의 `open-pr` 에 적혀 있던 것은 "3단계로 돌아와 다시 돌린다"
> 한 줄이었고, 멈추라는 말이 없었다.
>
> **라운드마다 head 가 움직이므로 "같은 head 를 두 번 리뷰하지 마라" 로는 못 막는다** —
> 수정 커밋을 푸시하고 다음 라운드를 진행하는 것이 정상 절차다. 실제로 그 20라운드는 서로 다른
> head 20개였다. 멈출 때를 정하는 것은 기계가 아니라 사람이다.

### 3.3 「누가 막나」의 어휘

프로젝트의 `CLAUDE.md` 는 규칙마다 **무엇이 막는지**를 이 말들로 적는다. 말마다
**무엇이 막고 어떻게 우회되는지**는 아래 표에 있다.

| 적는 말 | 무엇이 막나 | 우회 |
| --- | --- | --- |
| `git 훅` | 커밋·푸시 직전에 실행되는 스크립트 | `--no-verify` · 훅을 안 켠 clone · 우회 변수(Claude Code 세션 밖에서만, 6.4) |
| `에이전트 훅` | 에이전트의 도구 호출을 보는 `.claude/hooks/` 스크립트 | 사람이 직접 입력하거나 웹에서 누르면 · 훅이 검사를 건너뛰는 조건을 두었으면 |
| `권한 프롬프트` | `ask` 규칙에 맞는 명령은 Claude Code 가 사람에게 묻고, `deny` 규칙에 맞는 명령은 거절한다. 막는 것은 그 명령의 실행이다. 글을 보이고 승인받는 일(6.3)을 대신하지 않는다 | 사람이 안 보고 승인하면 · 규칙이 지목한 도구 밖으로 우회하면 · 본문을 파일로 전달하면(보이는 것은 경로뿐) |
| `린터` | 린트 설정 | 규칙을 끄면 |
| `테스트` | 테스트 | 테스트를 지우면 |
| `CI` | GitHub Actions 가 PR 과 기본 브랜치 푸시마다 검사를 실행해 결과를 낸다. 그것만으로는 푸시도 머지도 막지 않는다 — 막는 것은 `브랜치 보호` 다 | 검사 자체는 못 피한다 |
| `브랜치 보호` | GitHub 이 보호 브랜치에 정한 조건(PR · 검사 통과 · Approve)을 채우지 않은 푸시와 머지를 막는다. 설치된 레포에서는 `install.sh --protect` 가 켠다 | `--protect` 를 켜지 않으면 · 관리자(`--protect` 가 켜는 보호는 `enforce_admins` 를 끈다) · 레포 설정을 바꾸면 |
| `리뷰` | PR 리뷰에서 사람이 본다 | 못 보고 지나치면 |
| `막는 것 없음` | 기계도 리뷰도 막지 않는다. 사람이 기억해야 한다 | 항상 |

**`리뷰`·`막는 것 없음` 만 적힌 규칙은 안 지켜진다고 가정하고 계획을 정하라.** 어겨도 기계가
찾지 못하므로 언젠가 어겨지고, 어겨져도 아무도 모른다.

### 3.4 라운드 사이에 이어지는 것

두 리뷰(`self-review`·`cold-reviewer`)가 여러 라운드를 진행하는 동안 **발견이 알림 없이
사라지는 경로가 넷** 있었다. 두 리뷰의 정의(`self-review`·`cold-reviewer`)와 게시하는
쪽(`open-pr`)이 이 절을 가리키기만 한다.

**1. 한 리뷰의 발견을 아무도 추적하지 않는다.** 콜드에만 재리뷰 절이 있고 셀프에는 없으면,
셀프의 발견은 닫혔는지 아닌지 어느 라운드에도 안 적힌다. 그래서 **두 리뷰 다** 직전 라운드
코멘트를 읽고 항목마다 판정한다.

**2. 직전 라운드만 본다.** `일부 해결`·`미해결` 로 남은 것이 다음 라운드 목록에 안 오르면
그 다음 라운드는 그것의 존재를 모른다. 그래서 **닫힐 때까지 매 라운드 다시 오른다.**

**3. 판정을 수로만 적는다.** `2건 일부 해결` 이라고만 적으면 무엇을 다시 올릴지 그 기록에서
읽을 수 없다. 그래서 **항목을 이름으로 적고**, 직전 기록이 수만 남겼으면 **그 라운드의
발견 목록으로 돌아가 재검증한다.**

**4. 아직 아무도 안 정한 항목이 판정어에 없다.** 판정어 넷 가운데서 고르면 맞는 것이
`미해결`(= 안 고쳐졌다)뿐인데 그러면 정하기 전인 것이 매 라운드 「필수」 로 올라오고, 안 고르면
다음 라운드가 존재를 모른다. 그래서 `결정 필요` 를 둔다.

판정은 다섯 가지다. 앞의 셋은 **고쳐졌나**를 정도로 나눈다. 뒤의 둘은 **결정됐나**로 나눈다.

| | |
| --- | --- |
| `해결` | 고쳐졌다 |
| `일부 해결` | 일부만 고쳐졌다 |
| `미해결` | 안 고쳐졌다 |
| `기각` | **발견이 틀렸다는 뜻이 아니다.** 맞는 발견인데 **안 하기로 정했다.** 정하는 것은 **사람**이고 리뷰는 그 사실을 관찰해 보고할 뿐이다. 그 결정에 시한이 있으면(예: `CLAUDE.md` 의 v1.0 조항) 시한이 왔을 때 이 표시로 그 항목을 다시 찾는다 |
| `결정 필요` | 아직 아무도 안 정했고, **리뷰가 정할 것이 아니다.** 이월은 되지만 「필수」 에는 안 오른다 |

### 3.5 판정어와 바구니

두 축을 섞지 마라.
위 다섯은 **축 하나**일 뿐이다. 라운드 코멘트에는 축이 둘 있고 **쓰는 주체가 다르다.**

| 축 | 누가 쓰나 | 무엇 |
| --- | --- | --- |
| **판정어 다섯** | 리뷰(셀프·콜드)가 `### 이전 라운드` 절에 | 직전 라운드 그 항목이 **어떻게 됐나**를 관찰해 보고 |
| **바구니 셋** | 메인이 라운드 코멘트에 | **이번 발견을 사람에게 어떻게 올리나** |

바구니 셋은 이렇다:

| | |
| --- | --- |
| `필수` | 고쳐야 머지된다 |
| `비추천` | **안 하는 쪽을 제안한다.** 이유는 바구니 이름에 담지 않고 한 줄로 적는다. 「고치면 나빠진다」 말고도 「지어낸 형태라 값이 없다」·「비용이 값보다 크다」·「다른 이슈가 다룬다」가 있다 |
| `결정 필요` | **리뷰가 정할 것이 아니다.** 사람이 정한다. 「이래도 그만 저래도 그만」인 것은 문장 맨 앞에 `*nit*` 를 붙여 여기 둔다 |

**한때 `선택` 이 넷째로 있었다.** 뺐다 — `결정 필요` 와 둘 다 「사람이 정한다」로 끝나서
구분되지 않았다. 사소하다는 것은 **바구니가 아니라 그 항목의 성질**이라 `*nit*` 로 적는다.

**바구니에 `기각` 을 두지 마라.** 위 판정어 표대로 그것은 **사람이 정한 사실을 리뷰가
보고하는 말**이라서다. 그래서 두 축이 만나는 자리는 하나다 — 사람이 `비추천` 을 받아들이고,
**그 결정이 그 라운드 코멘트 뒤에 코멘트로 적힌 뒤**(`open-pr` 3.5), 그것을 입력으로 받은
다음 라운드의 두 리뷰가 그 항목을 `기각` 으로 보고한다.

**리뷰는 코멘트에 적힌 것만 본다.** 사람이 정한 것은 창과 대화에 있고 리뷰는 그것을 못 본다 — 그래서
적히기 전까지 두 리뷰가 그 항목을 `미해결` 로 판정하는 것은 **리뷰의 잘못이 아니라 아직 안 적힌
것**이다. 정한 것을 그 라운드 코멘트 뒤에 사람 계정 코멘트로 올리는 것이 메인의 일이고(`open-pr` 3.5),
그 한 걸음이 빠지면 같은 항목에 두 리뷰가 다른 판정을 단다(실제로 확인함).

`결정 필요` 는 두 축에 같은 이름으로 있다. 구분하려 들지 마라 — 어느 축이든
"확실하지 않아 사람 판단이 필요하다" 로 뜻이 같다.

### 3.6 발견

발견은 목록이 아니라 판단 대상이다.
**콜드는 설계상 깨는 방법을 만들어낸다.** 그것이 같은 부류의 결함을 찾는 방식이고 그래서 값이 있다.
그러나 **일어날 법한 순서로 정렬해주지는 않는다** — 지어낸 형태와 실제로 생길 형태가 같은
목록에 같은 무게로 온다. 그 정렬은 받는 쪽의 일이다.

**받은 발견을 차례로 다 반영하지 마라.** **콜드가 낸 항목마다** 묻는다 — 형태를 지어내는 것이
콜드뿐이라 중요도 판단이 달라지는 자리도 거기다:

| 물음 | 아니라면 |
| --- | --- |
| 이 결함이 **누구의 실수로** 생기나 — 평범한 편집에서 생기나, 입력을 지어내야 생기나 | 지어내야 생기면 값이 낮다 |
| 막으려는 **비용**이 얼마인가 — 코드가 늘고 오탐이 늘지 않나 | 늘면 그 자체가 다음 결함이다 |
| **적대자가 있나** | 없으면 우회 경로를 다 막을 이유가 없다 |

**실제로 확인한 것.** 한 라운드에서 아홉 건을 이 물음 없이 다 반영했다. 그중 둘은 리뷰어가 지어낸
형태였고(메시지를 셸 변수에 숨기기 · `awk NR<=N` 으로 자르기), 그것을 막으려 넓힌 정규식이
**오탐 셋을 새로 만들었다.** 그 검사들이 그때까지 막으려던 실제 결함은 한 건인데, 검사는
그 한 건에 견줘 과하게 길어졌다. **줄 수를 여기 적지 않는다** — 검사는 계속 바뀌고,
문서에 적어 둔 수는 그 편집을 안 따라온다.

**안 하는 쪽을 제안하는 것은 그 라운드 코멘트의 `비추천` 바구니에 이유와 함께 올린다.**
안 적으면 다음 라운드가 같은 것을 다시 올리고, 그것이 아래 3.7 이 없애려는 그 소음이다.
그 자리에서 `기각` 을 쓰지 않는 이유는 위 3.5 에 있다.

### 3.7 이월

이월에는 끝이 있다.
**이월된 항목은 두 라운드 안에 결정된다.** 고치거나(`해결`), 안 하기로 정하거나(`기각`),
사람이 정할 일로 올리거나(`결정 필요`) 셋 중 하나다.

**세 번째 라운드에 같은 항목이 `미해결`·`일부 해결` 로 다시 오르면 그것은 발견이 아니라
결정이 미뤄진 것이다.** 그 라운드 코멘트의 「밀린 결정」 칸(`open-pr` 의 `comment-format.md` 템플릿)에 적고
`결정 필요` 로 사람에게 올린다 — 리뷰가 또 한 라운드 더 진행한다고 없어질 문제가 아니기 때문이다.

**`비추천` 은 사람이 정하면 거기서 닫힌다**(고치기로 하거나 `기각`). **사람이 정하지 않으면 그 항목이
처음 나온 라운드부터 두 라운드가 시한이다.** 사람이 정하지 않은 `비추천` 항목은 다음 라운드
코멘트의 「비추천」 바구니에 `(출처, N라운드부터)` 로 남아, **몇 번째인지가 그 표기로
세어진다.**

끝을 안 두면 `[낮음]` 은 영원히 미뤄진다. 목록이 길어지면 이월이 배경 소음이 되고, 그것은
이 절이 없애려는 "안 읽히는 리뷰" 로 돌아가는 길이다.

**읽는 범위는 PR 전체 diff 다.** 직전 라운드 이후의 증분만 보면 *"발견이 가리킨 자리를 아예 안
건드린 것"* 이 안 보인다 — 안 건드렸으니 증분에 없다. 증분은 **어디를 먼저 볼지** 정하는
커밋 목록으로만 쓴다.

**독립을 지키는 자리는 이번 라운드뿐이다.** 두 리뷰가 같은 코드를 동시에 독립으로 보는
것이 이 구조의 값이므로 **게시 전에 상대의 결과를 보는 것은 금지**다. 그러나 지난
라운드의 코멘트는 이미 게시된 기록이고, 그것은 PR 본문과 같은 성격이다 — **배경이 아니라
검증 대상**으로 읽는다. 콜드가 셀프 블록까지 읽는 이유는 하나다: 셀프가 발견으로 내고 저자가
고치면 **그 수정이 맞았는지 보는 리뷰가 그것 말고 없다.**

## 4 PR 본문

**본문은 `open-pr` 이 한 번 쓰고, 그 뒤로는 아무도 고치지 않는다.** 라운드가 만든 것은
코멘트에 쌓이고, 최종 정리는 `merge-pr` 이 머지 직전에 코멘트 하나로 올린다.

**왜 이렇게 바뀌었나.** 예전에는 라운드마다 본문을 갱신했고, 그럴 수밖에 없었다 —
**그때 두 리뷰가 받는 것에 직전 코멘트가 없었다.** 받는 것은 diff·파일 목록·본문·메타데이터
넷뿐이었으므로 **라운드 사이에 상태를 나르는 통로가 본문 하나였다.** 지금은 두 리뷰 다
직전 코멘트를 통째로 받는다(위 3.4). 통로가 생겼는데 옛
통로도 계속 쓰면 두 벌이 된다.

**두 벌의 대가는 실제로 확인됐다.** 한 PR 의 본문이 열한 라운드 동안 갱신되면서 **거듭 거짓이
됐다** — `bash -n a b` 가 첫 파일만 검사한 것을 "전부 통과" 로, 출력이 없는 명령 밑에 손으로
쓴 요약을, 실행한 적 없는 명령줄을, 그리고 코드가 바뀐 뒤에도 그대로 남은 설정 출력을.
**전부 `$` 가 붙어 있어 읽는 사람은 실행 결과로 믿는다.** 몇 번이었는지는 여기 적지
않는다 — 수를 두 곳에 적으면 반드시 어긋난다.

원인은 게으름이 아니라 구조다. **본문의 증거는 코드에서 파생된 값인데 손으로 관리된다.**
코드가 바뀌어도 본문을 고쳐주는 것이 없다 — 훅도 게이트도 CI 도 본문은 안 본다.

**그래서 규칙을 둔다:**

1. **라운드가 바꿀 값을 본문에 적지 마라.** 파일 내용을 복사해 붙이는 것 같은 파생 출력이
   그것이다. 붙일 것은 **연 시점에 실행한 게이트 출력**이고, 그건 낡는 것이 아니라
   그때의 기록이다.
2. **두 리뷰는 본문이 낡은 것을 발견으로 올리지 않는다.** 본문은 **연 시점의 기록**이므로
   그 안의 명령을 지금 다시 실행해 다르게 나오는 것은 정상이다. 발견인 것은 둘뿐이다 —
   **쓸 당시에도 거짓이었던 것**, 그리고 **본문이 밝힌 목적을 이후 diff 가 벗어난 것.**

   낡은 증거는 **처음 확인된 라운드의 코멘트에 「본문이 틀린 곳」 절로 한 번 적고 거기서
   닫는다.** 그 절이 없으면 그 발견은 매 라운드 다시 나오는데 `open-pr` 이 본문을 못
   고치게 하므로 **닫을 방법이 없는 이월 항목**이 된다. 본문을 고치지 않는 규칙 때문에 생긴
   문제라 「본문이 틀린 곳」 절로 해결한다.

3. **코멘트는 append-only 다.** 본문을 고치지 않으면 코멘트가 유일한 기록이 되므로, 이미 올라간
   코멘트를 고치는 것은 기록을 고치는 것이다. `gh pr edit` 으로 본문을, `gh api -X PATCH`
   로 코멘트를 고치지 마라. 틀린 것이 있으면 **새 코멘트로 정정한다.**
   (실제로 7라운드에 이미 게시된 코멘트를 `gh api -X PATCH` 로 고친 적이 있고, 그때
   아무 프롬프트도 표시되지 않았다. 그래서 `permissions.ask` 에 `Bash(gh api*)` 가 있다.)

## 5 L3 에 남기는 것

L3 에 남기는 것을 적는다.

- 시각 · 레이아웃 · 모션 · 색의 실제 지각
- 여러 화면을 오가는 실사용 흐름
- 제품 판단 (이 기능이 맞나, 이 문구가 맞나)

> 측정값 통과와 실제 지각은 **다른 평가축**이다. 대비비 기준을 통과하고도
> 다크 배경에서 안 보일 수 있고, 단위 테스트가 개별 동작을 다 확인하고도
> 화면을 오가는 흐름에서 깨질 수 있다.

산출물 규칙 R6에 따라, **자동 검증이 확인하지 않는 이 범위를 문서에 적는다.**
적지 않으면 검증이 사라지고 아무도 사라진 줄 모른다.

## 6 에이전트 밖에 두는 강제

강제는 에이전트 밖에 둔다. 이 문서의 핵심이다.
에이전트 훅(`.claude/settings.json`)은 **그 에이전트가
그 도구를 통해 행동할 때만** 작동한다. 사람이 터미널에서 직접 하거나,
다른 에이전트로 바꾸면 강제가 통째로 사라진다.

**표를 읽을 때 먼저 볼 것은 그 줄이 모델 안에 있느냐 밖에 있느냐다.** 맨 윗줄만 안에 있고
나머지는 밖에 있다. 안에 있는 것은 모델이 따라줄 때만 존재한다.

| 두는 곳 | 누구에게 적용되나 | 우회 |
|---|---|---|
| **CLAUDE.md 규칙 · 스킬 절차 · 스킬 description** ← 모델 안 | 모델이 따라줄 때만 | 따르지 않으면 아무것도 막지 못한다. **흔적도 안 남는다** |
| 에이전트 훅 | 그 에이전트, 그 도구를 쓸 때만 | 도구를 바꾸면 사라짐 · 훅이 검사를 건너뛰는 조건을 두었으면 모델이 그 조건을 맞춰 검사를 건너뜀 |
| **permissions (`deny`·`ask`)** | 그 에이전트의 도구 호출. **모델이 끌 수 없다**(문서) | 규칙이 지목한 도구 밖으로 나가면(`Bash(gh …)` 를 막아도 `curl` 은 남는다) · **이 파일 자체를 고치면** — `deny` 에 그것을 막는 규칙이 없다 |
| **git hooks** | 그 레포에서 커밋·푸시하는 **모두** (사람 포함) | `--no-verify` · 활성화 안 한 clone · 우회 변수(Claude Code 세션 밖에서만, 6.4) |
| **CI** | 원격에 올라온 **모든** 변경 | 없음(머지는 가능) |
| **브랜치 보호** | 보호한 브랜치로 들어가는 **모든** 머지와 푸시 | 없음 |

첫 줄과 나머지의 차이는 공식 문서가 분명히 적어 두었다:

> *"Permission rules are enforced by Claude Code, **not by the model**. Instructions in
> your prompt or `CLAUDE.md` shape what Claude **tries** to do, but they don't change
> what Claude Code **allows**."* — `/docs/en/permissions`

**첫 줄에만 적어 둔 규칙은 이 레포에서 실제로 지켜지지 않았다** — 킷 PR 넷이 스킬을 안 거치고
`gh pr create --fill` 로 나갔고, "사람 허락 없이 머지하지 않는다" 를 어기고 머지된 적이
있고, 리뷰가 사람 없이 스무 번 진행됐다. 전부 첫 줄에만 있던 규칙이다.

그리고 **CI 와 브랜치 보호만 일부러 하는 우회까지 막는다.** 나머지는 실수만 막는다. 되돌릴 수
없는 것은 git hooks · CI · 브랜치 보호에 둔다.

### 6.1 밖으로 옮긴 검사

검사를 밖에 옮겼다고 그 검사가 무언가를 막는 것은 아니다.
**막으려고 만든 것은 불변식을 깨서 발동을 봐야 한다.** 통과만 본 것은 "작동한다" 가 아니다.
그런데 **한 번 깨보는 것으로도 부족하다** — 불변식을 한 가지 방식으로 깨서 검사가 실패하는 것을 본 것은
그 검사가 *그 방식*을 찾아낸다는 뜻이지 그 결함을 찾아낸다는 뜻이 아니다.

**실제로 확인한 것.** 검사 둘을 세션 밖(CI)으로 옮기면서 각각 한 번씩 불변식을 깨서 그 검사가 실패하는 것을
확인하고 올렸다. 다음 라운드에 다른 방식으로 깨보니 **두 검사 다 통과했다.**

| 검사 | 처음 깬 방식 → 검사가 실패 | 다음 라운드에 깬 방식 → **검사가 통과** |
| --- | --- | --- |
| 설치기가 지웠다고 말한 것이 진짜인가 | 고친 코드를 옛 구현으로 되돌림 | **같은 되돌림을 다른 로케일에서** — 그 결함은 대소문자를 1차 비교에서 무시하는 collation 에서만 드러나고, CI 러너는 그쪽이 아니다 |
| | | **예고 쪽만 거짓으로** — 예고와 실제를 지운 파일이 0개인 경우에만 비교하고 있었다. `0 = 0` 은 그 칸이 틀려도 맞는다 |
| 주입이 내는 메시지를 설명서가 다 설명하나 | 설명 없는 새 메시지 추가 | **이 검사를 만든 계기였던 그 결함** — 한 줄이 넷을 내는데 표에 셋만 적힌 것. `!!` 로 시작하는 메시지를 통째로 면제하는 예외를 넣어뒀다 |

**그래서 규칙은 셋이다.**

1. **가드가 이름 붙인 결함의 *원본 형태*로 깨봐라.** 새로 지어낸 형태로 깨는 것은 쉽고,
   그것만 찾아내는 가드가 만들어진다. 위 표의 셋째 줄이 그 경우다.
2. **가드에 예외를 넣었으면 그 예외를 거치는 경로로 깨봐라.** 예외는 검사를 끄는 스위치다.
3. **증상이 아니라 원인을 검사하라.** 위 첫째 줄을 "그 결함이 드러나는 환경을 테스트가 고르게"
   고치려 했다가 되돌렸다 — 그러면 그 환경이 없는 머신에서 검사와 무관한 이유로 실패한다.
   고칠 때 **없앤 것**이 정렬 비교였으므로, 가드는 정렬 비교가 코드에 다시 들어왔는지만 검사한다.

### 6.2 권한 규칙

`permissions` 줄에 무엇을 적을지 정할 때 필요한 사실을 한자리에 둔다. **다른 파일에
옮겨 적지 마라 — `settings.json` 은 여기를 가리키기만 한다.**

**규칙은 셸이 해석하지 않는다.** `Bash(gh pr create *)` 라는 문자열은 셸에 도달하지
않는다. Claude Code 가 에이전트가 실행하려는 명령 **문자열**을 자기 매처로 이 패턴에 맞춰볼
뿐이다. 그래서 동작을 아는 길은 문서를 읽거나 실행해 보는 것 둘뿐이고, 셸 글로브처럼
읽으면 틀린다.

**문서로 아는 것** — 규칙은 명령을 조각내 각 조각을 본다:

| | |
| --- | --- |
| 구분자 | *"The recognized command separators are `&&`, `\|\|`, `;`, `\|`, `\|&`, `&`, and newlines."* |
| 중첩 | *"Deny and ask rules apply when any subcommand matches them, including a command nested inside a subshell, a command substitution…"* |
| 앞 대입 | *"A deny or ask rule matches past any leading assignment"* |
| allow 와의 관계 | *"a matching ask rule prompts even when a more specific allow rule also matches"* |
| auto mode | *"Content-scoped ask rules … always force a permission prompt, even in auto mode"* · *"The classifier cannot auto-approve a matching action."* |

**파일 경로 규칙은 `Read(…)` · `Edit(…)` 로만 쓴다.**

> *"Claude Code checks file permissions against `Edit(path)` and `Read(path)` rules only. If you write a path
> rule for `Write`, `NotebookEdit`, `Glob`, or the legacy `MultiEdit` tool instead, Claude Code accepts the rule
> but never consults it"* — `/docs/en/permissions`

`Write(…)` 로 쓴 규칙은 아무것도 막지 않고 세션을 열 때 경고만 낸다. 헤드리스 세션에서 `Edit(<경로>)` deny 하나로
Write 도구가 그 경로에 파일을 만들지 못하는 것과, 규칙이 없으면 만드는 것을 확인했다.

**실제로 확인해서 아는 것** — 규칙이 없으면 그대로 실행되는 읽기전용 명령으로 대조군을 만들어 확인했다.
막히면 그것은 규칙이 막은 것이다:

```
명령: cat AI_KIT_PROBE_FILE.txt

규칙 없음                              → 실행됨
ask: Bash(cat AI_KIT_PROBE*)           → 차단          개행·주석 형태도 같이 차단됨
ask: Bash(cat AI_KIT_PROBE_FILE*)      → 차단          뒤에 무엇이 붙어도 적용된다
ask: Bash(cat AI_KIT_PROBE_FILE *)     → 실행됨        토큰이 정확히 그것일 때만 적용된다
```

세 번째와 네 번째의 차이가 **뒤 `*` 앞의 공백**이다. 공백이 있으면 그 토큰으로 **시작하는
다른 명령**에는 적용되지 않는다(문서의 `ls` / `lsof` 예시). **토큰 뒤에 아무것도 붙지 않은 명령은 두 형태 모두에 적용된다** —
공백 없는 쪽은 `*` 가 빈 문자열에 붙어서, 공백 있는 쪽은 문서가 그 경우를 따로 허용해서.

**그래서 `deny`·`ask` 에는 공백 없는 형태를 쓴다.** 넓게 적으면 안 쓰는 명령에 프롬프트가
한 번 더 표시될 뿐이지만, 좁게 적으면 막아야 할 명령이 빠진다. `allow` 는 반대다 — 거기서 과매칭은
`Bash(ls*)` 가 `lsof` 까지 자동 승인하는 사고이므로 공백 형태를 쓴다.

**대화형에서 프롬프트가 실제로 표시된다 — 그리고 `allow` 보다 우선한다.** 문서로만 알던 것을
실행해 확인했다. `git status` 는 킷의 `allow` 에 있다. 그것을 `ask` 에도 넣고 에이전트가 실행하니
**승인 프롬프트가 표시됐고, 사람이 누른 뒤에야 실행됐다.** 인용(*"a matching ask rule prompts
even when a more specific allow rule also matches"*)이 실행으로 확인됐다.

> 헤드리스(`-p`)로는 이것을 확인할 수 없다 — 답할 사람이 없어 `ask` 가 "차단" 으로 나타나고,
> 그러면 "프롬프트가 표시됐다" 와 "다른 이유로 막혔다" 가 구분되지 않는다. 대화형 세션에서
> 사람이 화면을 보는 것 말고 다른 방법이 없다.

**한 번 관찰된 것 — 보증으로 읽지 마라.** 위 측정을 하려고 에이전트가 `settings.json` 의
`ask` 배열을 편집하려 하자 auto mode 분류기가 막았다(`Blocked by classifier`). 사람이
허락한 뒤에야 편집됐다. **이것은 한 번 관찰한 결과이지 막는 장치가 아니다** — 분류기는 auto mode
에서만 실행되고 판정이 확률적이며, 공식 문서가 권한 장치로 규정한 것이 아니다.
**`deny` 에 `Edit`·`Write` 로 이 파일을 막는 규칙은 없다.** 여기 적힌 `deny` · `ask` 규칙 전체가 그
파일 하나에 달려 있으므로, 그것을 막고 싶으면 규칙으로 막아야 한다.

**스킬은 예외가 될 수 없다.** 스킬 정의의 `allowed-tools` 로도, 명령 앞의 환경변수
대입으로도 `ask` 를 비켜갈 수 없다. 같은 명령으로 2x2:

```
ask 없음 · allowed-tools 없음   → 차단
ask 없음 · allowed-tools 있음   → 실행됨      allowed-tools 는 작동한다
ask 있음 · allowed-tools 없음   → 차단
ask 있음 · allowed-tools 있음   → 차단        ask 가 우선한다
```

그러므로 `ask` 가 확인하는 것은 **"스킬을 거쳤나" 가 아니라 "사람이 봤나" 다.** 전자를
확인하려면 규칙이 아니라 훅이 필요한데, 훅은 모델이 검사를 건너뛰는 조건을 맞추면 사라진다(6 의 표).
**다만 사람이 보는 것은 명령 문자열까지다** — 아래 「본문을 파일로 전달하면 안 보인다」.

**`ask` 에 무엇을 두나.** 아래 성질 가운데 하나다.

- **레포 밖으로 나가는 글.** PR·이슈·코멘트는 지우거나 고쳐도 알림으로 이미 나갔고,
  남이 읽은 뒤다. `ask` 의 대부분이 이것이다
- **레포 밖의 것을 지우는 명령.** 원격 브랜치 삭제(`git push … --delete`)가 이것이다. 글은
  아니지만 원격에서 일어나고, 되돌리려면 그 브랜치를 가진 클론에서 다시 푸시해야 한다
- **로컬에서 되돌리기 어려운 명령.** 강제 삭제(`git branch -D`)가 이것이다. 레포 밖으로는
  안 나가지만, 커밋만 하고 푸시하지 않은 것을 지우면 reflog 말고는 남는 자리가 없다

모두 되돌릴 수 없는 것을 되돌릴 수 있는 것과 같은 단계에 두지 않는다는 한 규칙이다.
**여기 수를 적지 마라.** 한때 「왜 이 아홉을 묻나. 전부 레포 밖으로 나가는 글이다」였는데,
`ask` 에 하나가 늘면서 수도 성질도 같이 거짓이 됐다.

이슈가 그중에서도 특별한 이유는 **남은 일 목록이 레포의 상태를 말하기 때문**이다.
에이전트가 이슈를 열면 그 목록이 자란다 — 사람이 안 정한 일이 정해진 일처럼 보이고,
그 이슈를 닫는 일은 사람에게 남는다. 그래서 **내용은 에이전트가 쓰고, 여는 것은 사람이 승인한다.**
사람이 제목과 본문을 읽는 자리는 `ask` 프롬프트가 아니라 **초안을 보이는 단계**다 — 본문을
파일로 전달하면 프롬프트에는 경로만 표시된다(바로 아래).

**남는 한계 — 본문을 파일로 전달하면 안 보인다.** 프롬프트는 명령 문자열을 보인다. PR 본문 ·
코멘트 · 이슈 본문은 백틱과 따옴표를 셸이 깨뜨리므로 `--body-file <파일>` 로 전달하는데, 그러면
**사람이 프롬프트에서 보는 것은 파일 경로뿐이다.** 무엇이 나가는지 안 보인다. 실제로 그렇게
됐다 — 코멘트를 `ask` 에 넣은 커밋이 같은 커밋에서 라운드 코멘트를 `--body-file` 로 올리게
했다. **게이트를 둔 커밋이 그 게이트가 내용을 보지 못하게 만들었다.** `--body-file` 은 셸이 백틱과 따옴표를 깨뜨리지 않게 그대로 두고, 글이 나가기 전에 사람이 읽는 자리는
스킬이 초안을 보이는 단계로 옮겼다(다음 절).

**남는 한계 — 스크립트 안은 안 보인다.** 규칙은 에이전트가 입력한 명령 **문자열**만 본다.
`bash <스크립트>` 는 Claude Code 가 벗겨 내고 안의 명령을 보는 래퍼가 아니므로 **그 안의 `gh` 는 어느 규칙에도 맞지 않는다.**
`curl` 로 같은 API 를 호출하는 것도 마찬가지다.

이건 가정이 아니라 실제로 확인한 것이다 — **킷 자신이 그런 경로를 하나 배포하고 있었다.**
`install.sh --protect` 가 킷의 브랜치 보호 스크립트를 부르고 그 안의
`gh api -X PUT .../branches/main/protection` 이 프롬프트 없이 원격 설정을 바꿨다.
`Bash(gh api*)` 를 `ask` 에 넣어둔 채로다. **그래서 그 스크립트를 부르는 자리가 직접
묻게 했다** — 규칙이 못 보는 자리는 그 자리가 스스로 물어야 한다.

읽기용 호출(`check-action-pins.sh` 의 태그 조회)도 스크립트 안이라 규칙이 보지 못해 프롬프트
없이 실행된다. **면제가 아니라 사각지대다** — 쓰는 쪽이 그것을 알고 써야 한다.

**`deny` 의 `pkill` · `killall` — 이름이나 명령줄 글자로 프로세스를 끝내지 않는다.** `pkill -f` 는 명령줄에
그 글자가 든 프로세스를, `killall` 은 이름이 같은 프로세스를 모두 끝낸다. 같은 머신에서 병렬로 일하는 다른
세션의 프로세스도 거기 든다. 실제로 리뷰
에이전트가 스크래치를 정리하며 `pkill -f 'sleep 30'` 을 실행했다. 그 글자는 다른 세션의 테스트가 띄우는
`sleep 300` 에도 맞는다. 그때 다른 세션의 프로세스가 끝났는지는 확인하지 못했다. settings 의 deny 규칙은
하위 에이전트에도 적용된다 — *"The rule applies to the main conversation and to subagents."* —
`/docs/en/sub-agents`. 헤드리스 세션에서 규칙이 없으면 메인 세션과 백그라운드 하위 에이전트의 `pkill -f` 가
실행되고, 규칙이 있으면 둘 다 막히는 것을 확인했다. 띄운 프로세스는 띄울 때 적어 둔 PID 로 끝낸다 —
`kill <PID>` 는 막지 않는다. `kill $(pgrep -f …)` · `/usr/bin/pkill` 같은 다른 형태는 규칙이 못 막으므로, 두
리뷰 정의(`cold-reviewer` · `self-review`)가 띄울 때 적어 둔 PID 로만 끝내라고 적는다.

권한 규칙은 규칙에 적힌 꼴의 명령만 막는다. 다른 꼴로 바꿔 일부러 하는 우회는 CI 와 브랜치 보호가 막는다(6 의
표).

### 6.3 승인이 필요한 행동

**사람의 승인은 정정 경로가 없거나 비싼 행동에만 받는다.** 사람이 모든 글을 읽게 하면 사람이
병목이 된다. 사람 없이 라운드가 스무 번 진행된 사고의 반대 방향이다. 사람이 판단할 것은
「무엇을 고칠까 · 머지할까」이지 「이 코멘트가 형식을 지켰나」가 아니다.

**정정 비용에는 잘못을 알아채는 비용이 들어간다.** 이슈를 다시 여는 것은 싸지만, 닫힌 이슈는
열린 목록에서 사라지고 세션은 시작할 때 그 목록만 본다. 잘못 닫혀도 알아챌 계기가 없다.

| 행동 | 정정 경로 | 사람의 승인 |
| --- | --- | --- |
| 머지 | 되돌리는 커밋. 히스토리에 영구히 남는다 | **받는다.** `merge-pr` 은 사람이 지시할 때만 실행한다. 봇 설정이 있으면 지금 head 에 대한 사람 계정의 Approve 가 그 승인이다 — 세션이 auto-merge 를 켜 두고, Approve 가 달리면 GitHub 이 머지한다(`merge-pr` 3절 「봇 설정이 있을 때」) |
| PR 열기 | 닫을 수는 있지만 본문은 연 뒤로 고치지 않는다 | **받는다.** 본문 전문을 보이고 승인받은 뒤 연다(`open-pr` 2절) |
| 이슈 열기 | 닫을 수는 있지만 열린 목록이 레포의 상태를 말한다 | **받는다.** 초안을 보이고 승인받은 뒤 연다 |
| 이슈 닫기 | 다시 열 수는 있지만 잘못 닫혀도 알아챌 계기가 없다 | **받는다.** 머지가 닫을 수 있는 것은 Approve 가 승인하고(Approve 하는 PR 웹에 본문의 `Closes #N` 이 보인다), 본문 밖에서 끝내기로 정한 이슈는 auto-merge 를 켜기 전에 따로 창으로 보이고 머지 명령의 `--body` 에 `Closes #N` 으로 넣는다 — Approve 는 코드에 대한 승인이라 본문 밖에서 정한 이슈는 보여 주지 않고, 머지 뒤에는 세션이 닫는 명령을 실행할 자리가 없다 |
| 머지 결정 코멘트 | 머지와 한 몸이다. 머지 전에 쓰는 마지막 기록이다 | **받는다.** 사람의 Approve 가 그 승인이다 — 세션은 응답에 전문을 출력하고 올린 뒤 Approve 를 요청하므로, 사람은 올라간 결정 코멘트를 읽고 Approve 한다(`merge-pr` 3절) |
| 스쿼시 커밋의 제목과 본문 | 히스토리 재작성 없이는 못 고친다 | **받는다.** 결정 코멘트와 같다 — 머지 명령 전문을 응답에 출력하고 Approve 를 요청한다(`merge-pr` 3절) |
| 라운드 코멘트 | 다음 라운드의 「지난 코멘트 정정」 | 받지 않는다. `(사람)` 인용은 에이전트 훅이 그 PR 의 사람 계정 코멘트와 대조해 없으면 막는다(`open-pr` 3.4, 아래) |
| 사람 계정 코멘트 | 세션은 고치지 않는다. 사람이 PR 웹에서 고치거나 창으로 다시 정해 새 코멘트로 올린다(`open-pr` 3.5) | **받는다.** 질문에 「이 결정은 사람 계정으로 PR #N 에 그대로 올라간다」를 적은 창에서 사람이 고른 것이 그 승인이다 — 세션은 글을 쓰지 않고, 창 기록 훅이 고른 보기를 기록해 `human_comment.sh` 가 그것만 올린다. 사람이 PR 웹에서 직접 쓸 수도 있다(아래) |
| 머지 뒤 후속 코멘트 | 뒤에 코멘트를 하나 더 붙인다 | **지금은 받는다**(`merge-pr` 4절). auto-merge 로 머지됐으면 사람이 「PR #N 최종 검토」 창에서 「Approve 했다」를 고른 뒤의 로컬 정리(`merge-pr` 4절)에서 묻는다 |
| 이슈 본문 수정 | 다시 고친다. 편집 이력이 남는다 | 받지 않는다 |
| 그 밖의 코멘트 | 편집하거나 뒤에 하나 더 붙인다 | 받지 않는다 |

**승인은 세션의 응답에 출력한 최종본 전문을 읽고 한다.** 위 표에서 「보이고 승인받는다」는, 세션이 승인을
묻기(질문 창 · 권한 프롬프트) 바로 전에 자기 응답에 그 글과 명령의 최종본 전문을 출력한다는 뜻이다. 파일
경로나 요약, 「초안을 대조했다」는 말로 대신하지 않는다. 사람은 그 글을 읽고 정한다. 초안을 누가 미리
대조했든 같다 — 승인을 묻는 자리에 글이 없으면 사람은 무엇을 허락하는지 모른다.

**사람에게 무엇을 해 달라고 하는 응답은 그 요청으로 끝낸다.** 질문 창 · 권한 프롬프트 허락 · Approve ·
GitHub 설정처럼 사람이 해야 다음으로 가는 자리다. 응답의 맨 끝에 짧게 적는다 — 할 일, 어디서(링크, 또는 이
세션의 질문 창 · 권한 프롬프트), 누르는 순서, 그 뒤 세션이 할 일이다. 길이 둘 이상이면(PR 웹 · 터미널) 나란히
적고 사람이 고르게 한다. 알림에도 할 일과 링크를 넣는다. 사람은 작업 중인 세션의 응답만 보고 할 수 있어야
한다 — 응답에 없는 곳(다른 세션 · 파일)을 근거나 안내로 대신하지 않는다. 링크도 순서도 없이 요청이 응답의
위아래에 흩어진 Approve 요청을 사람이 짚었다. Approve 요청은 `merge-pr` 2절의 요청 블록 모양으로 쓰고, 바로 뒤에
창을 띄운다. **사람이 글자를 입력해 알리는 단계를 두지 않는다** — 확인은 창으로 받는다. 응답 가운데 「올려」를
입력해 달라고 쓰고 사람이 그대로 입력하는 절차가 어색하다고 사람이 짚었다.

**사람의 행동을 기다리며 확인을 되풀이하지 않는다.** 요청으로 응답을 끝낸 뒤, 정해진 시간 동안 몇 초마다
결과(Approve · 코멘트 · 설정)를 조회하며 기다리지 않는다. 협업에서는 그 행동이 몇 시간 뒤에 올 수 있어 시간이
끝나면 결국 사람이 세션에 알려야 하고, 그동안 세션은 다른 일을 못 한다. 결과는 GitHub 이 처리하게
두고(auto-merge, `merge-pr` 3절), 사람이 창에서 고른 뒤에 한 번 본다. Approve 요청 뒤 40분 동안 15초마다
Approve 를 조회한 세션을 사람이 짚었고, 알리는 한 줄도 원하지 않아 머지를 auto-merge 로 바꿨다. 그 뒤 머지를
자동으로 알아채는 대기를 만들었다가 접었다 — 머지된 뒤에는 어차피 사람이 「다음 일」 창에서 다음 일을 골라야
해서, 자동으로 알아채도 줄어드는 것은 사람의 한 마디뿐이었다. 그래서 요청 블록 뒤의 창에서 「Approve 했다」를
고르게 한다.

**권한 프롬프트는 이 승인이 아니다.** 명령은 보이지만 본문은 안 보인다
(위 「본문을 파일로 전달하면 안 보인다」). 훅이 프롬프트의 사유에 본문 전문을 넣어도 그 사유는 덧붙이는
것이다 — 사람이 폰(Remote Control)에서 본 프롬프트에는 글이 없었다. 결정 코멘트 하나가 사유에만 기대 사람
계정으로 올라간 뒤 사람이 그것을 짚었다.
스쿼시 커밋의 제목과 본문은 파일이 아니라 명령 안에 있지만 그 행도 같다. 프롬프트가 표시되지 않는
레포가 있고, 프롬프트에서 거절하면 결정 코멘트가 두 벌이 되고, 여러 줄 본문이 프롬프트에
다 보이는지는 확인하지 않았다.

**「지금은 받는다」는 임시다.** 스킬이 쓰는 글이고, 스킬이 아직 안정되지 않아 틀린 내용이
섞이기 때문에 승인을 받는다. 아래 조건을 모두 갖추면 승인 단계를 없앤다:

- **코멘트가 형식을 지켰는지 기계가 본다.** 이미 기계가 보는 것은 같은 head 의 라운드 코멘트가
  있나와 불릿 줄의 줄표, 콜드 리뷰 전문이 그 head 의 콜드 리뷰 기록과 같은가다(`open-pr` 3.4). 기계가 아직 안 보는 것은 집계 두 줄의 합이 항목
  수와 같나(산술이라 오탐이 생길 수 없다) · 필수와 결정 필요가 한 줄인가 · 바구니 이름이 셋뿐인가 ·
  `리뷰한 head:` 가 `open-pr` 3.1 에서 읽은 값과 같은가다. 라운드 코멘트에서는 이 넷을 사람도 안
  본다(아래)
- **코멘트가 봇 계정으로 나간다.** 봇은 품질을 안 바꾸고 **귀속**을 바꾼다. 지금은 틀린 글이
  나가면 사람 계정 이름으로 남아서 승인이 필요하다. 봇으로 나가면 사람이 안 읽은 글에 사람
  이름이 붙지 않는다
- **`(사람)` 인용이 사람 계정이 쓴 코멘트에 그대로 있는지 기계가 확인한다.** `(사람)` 항목은
  다음 라운드의 두 리뷰가 다시 판정하지 않는 출처라서(`open-pr` 의 `comment-format.md` 「출처 다섯」),
  이 조건 없이 승인 단계를 없애면 그 인용을 사람도 리뷰도 안 본다. 이 인용은 봇의 라운드 코멘트에 실리고,
  머지 뒤 후속 코멘트에는 실리지 않는다. 그래서 후속 코멘트의 승인 단계는 이 조건을 기다리지
  않는다. 라운드 코멘트는 아래처럼 이 조건을 갖추고 먼저 승인 단계를 없앴다

**사람이 정한 것은 사람 계정 코멘트로 남는다.** 둘째 조건(봇)과 셋째 조건(사람 계정의 글)이 갖춰진다.
**세션은 그 글을 쓰지 않는다.** 질문에 「이 결정은 사람 계정으로 PR #N 에 그대로 올라간다」를 적은 창을
띄우면, 창 기록 훅(`window_record.sh`, `PostToolUse`)이 사람이 고른 보기로 `- <머리말>: <보기>` 줄을 만들어
봇 디렉터리에 적는다. 세션은 `human_comment.sh <PR 번호>` 로 그 기록만 사람 계정으로 올린다(`open-pr` 3.5).
창에서 고른 것이 게시 동의라서 초안 · sha256 이 없고, 설치되는 `settings.json` 이 레포 루트에서 입력한 그 명령을
허용해 권한 프롬프트도 없다. 세션 도중 들어간 worktree 에서 올릴 때만 다르다 — 그 worktree 루트에서 프로젝트의
스크립트까지의 경로로 부르므로 allow 의 모양과 달라 권한 검사를 거친다 — default 모드에서는 권한 프롬프트가 한 번
표시되고 auto 모드에서는 분류기가 정한다(`open-pr` 3.5). 세션이 봇 디렉터리를 읽거나 쓰는 명령은 막는다(`settings.json` 의 `deny` · 막기 훅
`bot_guard.sh`). 문서 규칙만으로는 지켜지지 않아서 이렇게 바꿨다 — 응답에 전문을 출력한 뒤 권한 프롬프트로
허락받게 했던 동안, 한 PR 의 1라운드에서 세션은 전문을 출력하지 않고 게시 명령을 실행했고 사람은 프롬프트만
보고 허락했다. 사람이 보기 대신 직접 쓴 말 · 보기에 단 메모 · 창에 쓴 글이 있는 질문과 답을 비운 질문은 그대로
올리지 않는다 — 같은 머리말의 창으로 다시 묻고, 직접 쓴 것이 있던 질문은 결정이 담긴 구간이나 요지를 보기로
만든다. 봇 설정이 있는 레포 안에서 세션이 창 기록 훅을 직접 실행해 기록을 만드는 명령도 막기 훅이 막는다(사람이
정했다). 사람이 자리를 비워 저절로 닫힌 창은 사람이 고른 것이
아니라서 기록하지 않는다. 사람이 PR 웹에서 직접 쓸 수도 있다 — 창에서 「PR 웹에 쓴다」를 고르고, 쓴 뒤 「PR
웹에 썼다」를 고른다(`open-pr` 3.5). 머지
승인은 사람의 Approve 다 — PR 작성자가 봇이라 사람이 승인할 수 있다. 어떻게 켜는지는 `kit-guide.md` 6절에
있다

**라운드 코멘트는 승인 단계를 없앴다.** 사람이 정했다. 정정 경로가 가장 싸고(다음 라운드가 받는다) 사람이
가장 자주 누르던 자리다. 셋째 조건은 이렇게 확인한다 — 라운드 코멘트의 `(사람)` 인용이 그 PR 의 사람 계정
코멘트에 글자 그대로 있는지를 에이전트 훅(`round_comment_quotes.sh`)이 보고, 없으면 그 `gh pr comment` 를
막는다. 원본의 단위는 `>` 인용 줄을 뺀 불릿 하나나 줄 하나다 — Quote reply 로 넣은 줄은 남의 글이고, 서로
다른 줄의 조각을 이은 인용은 사람이 쓴 적 없는 문장이다. 따옴표 없이 `(사람)` 라벨만 단 항목도 막는다. 명령
글자 어디에든 `gh pr comment` 가 보이면 따옴표 · heredoc 안이라도 한 줄 정규형(`--body-file <절대 경로>`)만
받고, 나머지는 게시인지 가리지 않고 막는다. 게시인지, 명령 자리인지 해석해 가리던 동안 라운드마다 새 우회가
나왔다. 명령 이름을 꾸미거나, 스크립트 파일이나 인라인 인터프리터의 인자 목록으로 올리는 우회는 일부러 하는 것이라 막으려
하지 않는다. 봇 설정이 없는 레포에서는 사람의 글과 세션의 글이 같은 계정이라 원본이 없다 — 훅은 `(사람)`
인용이 든 라운드 코멘트를 막는다. 킷은 봇과 함께 쓴다(사람이 정했다, 2026-09-29). 그 레포의 한계는
`kit-guide.md` 6절 머리에 있다. 남는 것은 하나다.

- 첫째 조건(형식) 중 위에서 기계가 아직 안 본다고 적은 넷을 이제 게시 전에 아무도 안 본다.
  틀리면 다음 라운드의 두 리뷰가 「지난 코멘트 정정」으로 받는다

이 훅은 실제로 있었던 일 때문에 생겼다. 한 PR 의 7라운드 코멘트가, 세션이 사람의 결정을 옮긴 코멘트에 적어 둔
`→` 줄, 곧 세션의 판단을 `(사람)` 인용으로 옮겼다. 지금 사람 계정 코멘트에는 사람이 고른 보기 줄만 있어 세션의
판단이 원본에 섞이지 않는다.

**설치된 레포에서는 `gh pr comment` 의 `ask` 를 그대로 둔다.** 그래서 라운드 코멘트에도 권한
프롬프트가 한 번 표시된다. 훅으로는 이것을 못 없앤다 — *"Deny and ask rules … are still
evaluated regardless of what the hook returns"* 라 훅이 통과시켜도 `ask` 프롬프트는 그대로 표시된다. 없애려면
`ask` 에서 빼야 하는데, 훅은 오류로 끝나거나 시간을 초과하면 막지 못한다 — *"A timed-out …
hook doesn't block the tool call"*, 스크립트가 없을 때도 *"the action proceeds"*
(`/docs/en/hooks`). 그러면 결정 코멘트까지 모든 코멘트가 프롬프트 없이 나가고, 라운드 코멘트는 대조도
없이 나간다. 라운드 코멘트와 결정 코멘트는 같은 명령(`gh pr comment`)으로 올라가서 규칙으로는 둘을
구분하지 못하므로 프롬프트 한 번을 남겼다.

**같은 까닭으로, 훅이 실행되지 못하면 라운드 코멘트의 대조가 빠진다.** `python3` 가 없거나 시간을
초과하면 훅은 오류로 끝나고 호출은 그대로 실행된다. `ask` 가 남아 있으면 프롬프트가 표시되지만,
`ask` 에서 `gh pr comment` 를 뺀 레포에서는 그 코멘트가 대조 없이 나간다. 훅이 실행됐지만
판정을 못 한 경우(`gh` 실패 · 본문을 못 읽음)는 이와 달리 막는다.

**사람이 초안을 눈으로 봐도 따옴표 안이 자기 말인지 가려내지 못한다.** 실제로 그랬다. 사람이
세션에 건넨 전달문 안에 고친 답글 전문이 있었고, 세션은 그 전문대로 올렸다. 그 안의 `(사람)`
불릿 둘은 전달문을 쓴 다른 세션이 자기 발견 둘을 `open-pr` 3.5 에서 사람이 준 지시라고 적어 넣은
것이었고, 사람은 건네면서 알아보지 못했다. 요약한 인용이 아니라 사람이 한 적 없는 말이었다.
인용을 사람의 눈에 맡기지 않고 기계가 확인하는 조건을 두는 이유가 이것이다.

**내용이 옳은지는 기계가 못 본다. 그건 다음 라운드의 두 리뷰가 본다** — 그것이 이 구조의
설계다.

### 6.4 git hooks 의 한계

훅 파일은 `.kit/git-hooks/` 에 커밋되므로 clone 을 따라온다. 그러나 이를 활성화하는
`core.hooksPath` 는 **로컬 설정이라 clone 되지 않는다** — git 이 보안상 의도한 동작이고
우회 방법이 없다. 새로 clone 한 사람은 한 줄이 필요하다:

```bash
git config core.hooksPath .kit/git-hooks
```

Claude Code 세션에서는 이것을 알 수 있게 했다. git 훅이 꺼진 레포에서 세션을 열면 세션 시작 훅이 그렇다고 알리고,
꺼진 동안은 에이전트 훅이 그 레포에 입력한 `git commit` · `git push` 를 막고 켜는 명령을 적는다. 켤지는 세션이 사람에게
묻고, 켜지 않기로 하면 사람이 세션 밖 터미널에서 커밋한다. 알림만 두면 세션이 읽고 따라야 지켜지지만, 막으면 켜기
전에는 세션이 커밋도 푸시도 하지 못한다. 킷의 `.claude/` 를 설치하지 않은 레포와 세션 없이 터미널에서 커밋하는 사람에게
닿는 것은 `.kit/README.md` 의 안내뿐이다.

그리고 `git commit --no-verify` 로도 우회된다.

세 번째 한계는 알아채기가 더 어렵다. **훅 파일이 실행 권한 없이 커밋돼 있으면 git 은 그것을
건너뛴다** — `hint:` 한 줄이 stderr 로 나갈 뿐 커밋은 성공한다.

```
$ git commit -m ...
hint: The '.kit/git-hooks/pre-commit' hook was ignored because it's not set as executable.
[main abc1234] ...        ← 훅이 exit 1 인데도 커밋됨
```

설치할 때는 문제가 없다(`cp -R` 이 킷의 100755 를 그대로 옮긴다). **설치 이후**에
실행 권한이 빠지는 경로가 있다 — 둘 다 재현했다:

| 원인 | 결과 |
|---|---|
| `core.fileMode=false` 인 레포 | 작업트리는 755 인데 **커밋된 모드는 100644** |
| 훅을 편집기가 지우고 다시 쓸 때 | 인덱스 모드가 **100644** 로 바뀜 |

훅은 `.kit/` 에 복사돼 레포 안에 있으니 누군가 손대는 것을 전제한 파일이다.
그런데 손대는 순간 강제가 꺼질 수 있고, 로컬에서는 아무도 눈치채지 못한다.

파일이 *있는지*만 보는 검사는 이것을 통과시킨다. 그래서 CI 가 커밋된 모드까지 본다
(`[ -x ]`). 게이트 스크립트는 훅이 `bash <경로>` 로 부르므로 권한이 필요 없다 —
거기까지 요구하면 멀쩡한 레포에서 오탐이 생긴다.

우회 변수도 있다 — 사람이 의도적 예외를 둘 때 쓴다. `KIT_ALLOW_PROTECTED=1` 은 보호 브랜치 커밋을 허용하고,
`KIT_PROTECTED_BRANCHES` 는 보호할 브랜치 목록을 바꾸고, 게이트의 `KIT_ALLOW_MISSING_TOOLS=1` · `GATE_STRICT=0` 은
도구가 없는 검사를 건너뛴다. **Claude Code 세션 안에서는 이 변수들로 보호를 풀거나 검사를 건너뛰지 못한다.**
Claude Code 는 자기가 띄운 프로세스(Bash 도구 · 훅)에 `CLAUDE_CODE_CHILD_SESSION=1` 을 두고, git 훅과 게이트는
세션이 실행한 `git` · `bash` 의 자식이라 그 값을 물려받는다. 그 값이 있으면 훅은 `KIT_ALLOW_PROTECTED` 를 받지 않고,
`KIT_PROTECTED_BRANCHES` 에서는 더한 브랜치만 받아 기본값(`main` · `master`)을 늘 보호하며, 게이트는 도구가 없는
검사를 실패로 둔다. 거부할 때는 사람이 세션 밖 터미널에서 하라고 적고, 그 변수 이름도 적는다 — 세션이 띄운
`screen` 같은 데서 그 값을 물려받은 터미널이면 사람도 거부되기 때문이다.

권한 규칙으로는 막지 못한다. 규칙은 세션이 쓴 명령 글자에만 맞춰 보고, 규칙이 이름 붙인 명령을 다른 꼴로 실행하는
것까지 막지는 않는다 — *"A Bash rule matches the command text Claude writes"* · *"isn't a security boundary around
the program"*(`/docs/en/permissions`). 세션이 스크립트 파일 안에서 우회 변수를 두면 명령 글자에 그것이 없어 규칙이
보지 못한다. 세션이 `CLAUDE_CODE_CHILD_SESSION` 을 지우고 실행하면 훅과 게이트도 받는다. 그것은 일부러 하는 우회라 CI 와 브랜치
보호가 막는다.

게이트 설정은 환경 변수로 받지 않는다. 실행할 테스트 · 태스크(`KIT_GO_TEST_FLAGS` · `KIT_PYTEST_FLAGS` ·
`KIT_GRADLE_TASKS`)와 모듈을 찾을 때 건너뛸 디렉터리(`KIT_PRUNE_DIRS`)는 커밋된 `.kit/gate.conf` 에서만 읽는다.
명령 앞에 붙인 값은 커밋에도 리뷰에도 남지 않는데 검사를 줄인다 — 건너뛸 디렉터리 이름 한 낱말로 모듈 하나가 검사에서
빠졌다. 그 파일을 고친 값은 diff 에 남아 리뷰가 보고, 그 파일에 커밋에 안 들어간 변경이 있으면 커밋 훅과 푸시 훅이
실패한다. 훅이 부를 킷 디렉터리(시크릿 검사 · 게이트 · 요구 추적)도 환경 변수로 받지 않고 훅이 있는 자리에서 찾는다.

> **그래서 로컬 훅은 실수만 막는 강제다.** 일부러 하는 우회까지 막는 것은 CI + 브랜치 보호뿐이지만,
> 시크릿처럼 푸시되면 되돌릴 수 없는 것을 킷이 푸시 전에 막는 자리는 훅뿐이다. 훅을 믿고 CI 를 생략하면,
> 훅이 꺼졌거나 `--no-verify` 로 건너뛴 변경은 아무 검사도 받지 않는다.

> 규칙: **되돌릴 수 없는 결과를 막는 강제는 git hooks·CI·브랜치 보호에 둔다.**
> 에이전트 훅은 *편의*(자동 포맷·조기 피드백)와, **다음 단계가 고칠 수 있는 것의 대조**에만
> 쓴다. 라운드 코멘트의 `(사람)` 인용을 확인하는 훅이 그 예다 — 틀린 코멘트는 다음 라운드가 고치고, 훅은 이
> 에이전트가 올릴 때만 작동한다(위 6.3).

### 6.5 검사를 둘 자리

어느 검사를 어디에 둘지는 측정한 시간으로 정한다.
아래 표는 실제 모노레포(Go 백엔드 + React 프론트)에서 반복 측정해 워밍업 뒤 안정된 값이다.

| 검사 | 소요 | 어디서 |
|---|---|---|
| `gofmt` · `goimports` | 0.1s 미만 | 편집 직후(훅) · 게이트 |
| `prettier` | 1.7s | 편집 직후(훅, 파일 1개) · 게이트 |
| `golangci-lint` | 0.9s | 게이트 |
| `eslint` | 6.5s | 게이트 |
| `tsc` | 2.5s | 게이트 |
| `go test` | 0.3s (캐시 없으면 3.6s) | 게이트 |
| `vitest` | 7.8s | 게이트 |
| `build` | 3.1s | 게이트 |
| **`gate.sh --lint`**(테스트·빌드 제외) | **22s** | 수동 |
| **`gate.sh` 전체** | **37~42s** | pre-push · CI |

**처음에는 이 측정으로 린트를 pre-commit 에서 뺐다가, 되돌렸다.** 22초는
`gate.sh --all --lint`(CI 모드, 전체 검사)였고 커밋은 **변경 영역만** 본다 — Go 파일
하나를 고친 커밋은 2.8초다. 그리고 커밋은 의미 단위라 수 분~수 시간 작업의 끝에 오므로,
`pre-push` 가 이미 기다리게 하는 40초와 견주면 반대할 근거가 못 됐다.
지금은 `pre-commit` 이 `gate.sh --lint --staged` 를 부른다. 처음에 `pre-commit` 에서 린트를 뺀 근거는 이랬다 — 직관적으로는 "커밋 전에 린트가
맞다" 지만, 테스트와 빌드를 빼도 **22초**다. `npm run` 을 거칠 때마다 붙는 Node 기동
비용이 개별 도구 시간보다 크다. 커밋마다 22초를 기다리게 하면 사람은 `--no-verify` 를 습관으로
쓰게 되고, **끄는 게이트는 없는 게이트다.**

"변경된 파일만 린트하면 싸다" 도 틀렸다 — `eslint` 은 파일 하나에도 4.4초다(전체 6.5초).
시작 비용이 지배적이라 대상을 줄여도 거의 안 줄어든다.

> 지금 검사를 두는 자리는 이렇다: **포맷은 편집마다**(0.1초 수준이라 공짜에 가깝다),
> **린트는 커밋마다 바뀐 영역만**(`pre-commit` 이 `gate.sh --lint --staged` 를 부른다),
> **나머지 전부는 푸시**(되돌리기 어려운 경계에서 한 번), **CI 는 같은 것을 다시**
> (로컬은 `--no-verify`·미설치 훅·실행 권한 누락으로 실행되지 않을 수 있다 — 셋 다 이 킷에서
> 실증했다).

### 6.6 충돌 마커

충돌 마커는 훅이 막는다.
3-way 병합이 실패하면 파일에 충돌 마커가 남는다 — `git merge`·`rebase`·`cherry-pick`·
`stash pop` 이 전부 그렇다. 손으로 해소하다 한 덩어리를 빠뜨리면 마커가 든 채로
커밋되고, 설정·훅·워크플로가 알림 없이 망가진다(JSON·YAML 은 파싱부터 실패한다).
그래서 `pre-commit` 이 스테이지된 내용을 검사한다.

마커 셋 중 **`=======` 는 보지 않는다** — 마크다운 setext 제목의 밑줄과 구분되지 않아
정상 문서를 막는다. 진짜 충돌에는 항상 셋이 다 있으므로, 뒤에 라벨이 붙어 모호하지 않은
`<<<<<<< ` 와 `>>>>>>> ` 만으로 충분하다.

> 이건 R7 의 적용례다. 재현에 환경 조작이 필요 없다 — 이 킷을 만들면서 실제로 겪었고,
> 그때는 확인용 `grep '<<<<<<<\|>>>>>>>'` 이 BSD grep 에서 `\|` 를 못 읽어
> **"마커 없음" 이라는 거짓 통과**까지 생겼다.

### 6.7 에이전트 `pre_push` 훅을 두지 않는 이유

킷은 이 훅을 처음부터 두지 않았고, 프로젝트에서도 킷 도입 때 지웠다. 근거를 남긴다 —
**제거한 구성요소의 이유를 안 적으면** 다음 사람이 "빠졌네" 하고 되살린다.

이유는 셋이고 전부 확인했다:

1. **중복이다.** git `pre-push` 훅이 이미 **모든** push 에서 게이트를 실행한다
   (`.kit/git-hooks/pre-push` 가 `gate.sh --base` 를 호출한다). 에이전트 훅을 더하면
   같은 검사가 두 번 실행된다.
2. **비싸다.** 게이트는 실제 모노레포에서 한 번에 수십 초다. 두 번이면 그만큼 두 배다.
3. **얻는 게 없다.** 에이전트 훅을 두는 유일한 이유는 "에이전트가 결과를 보게" 인데,
   **git 훅의 stderr 는 그대로 에이전트에게 전달된다.** 실제로 확인한 결과:

   ```
   $ git commit -m x
   훅이 남긴 메시지 (stderr)      ← 에이전트가 받는 출력에 그대로 들어온다
   ```

> 게다가 에이전트 훅은 그 에이전트가 그 도구를 쓸 때만 작동한다(위 6). 사람이 손으로
> push 하면 사라진다. **없어도 되는 단계이면서 신뢰할 수도 없는 단계**라 두지 않는다.
