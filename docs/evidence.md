# 이 킷을 실제로 돌려서 드러난 것

킷의 규칙은 대부분 여기 적힌 사고에서 나왔다. **규칙만 읽고 근거를 잃으면 규칙이
취향처럼 보이고, 취향은 다음 사람이 지운다.** 그래서 근거를 따로 둔다.

새 항목은 **겪은 그 자리에서** 적는다. 미결 항목은 여기 적지 말고 이슈로 만든다
(`CLAUDE.md` 참조).

## 실전에서 드러난 것 (읽어서는 안 나오는 것들)

**스킬 6개 중 5개가 첫 사용에서 버그였다.** 전부 *써야만* 드러났다:

| | 버그 |
| --- | --- |
| `open-pr` | 게이트 경로가 vendor 레이아웃과 불일치 |
| `devlog` | "최신이 위" 가정 — 프로젝트는 반대 순서 |
| `devlog` | 코멘트 없는 PR 에서 PR 맥락이 통째로 사라짐(jq 빈 배열 함정) |
| `trace` | `git diff main...HEAD` 만 봐서 **미커밋·untracked 변경이 안 보임** — 추적표의 테스트 칸을 채우는 게 이 스킬의 일인데 새 테스트 파일은 거의 항상 untracked 다 |
| 권한 deny | 넓힌 패턴이 커밋 메시지 내용까지 매칭 → 정상 커밋 차단 |

`open-pr`·`devlog`·`trace` 는 같은 형태다: **스킬이 돌아가는 실제 상태를 잘못 가정했다**
(vendor 레이아웃 · 로그 순서 · git 작업트리). 새 스킬을 쓸 때
"이 명령이 내가 있는 상태에서 실제로 뭘 보는가" 를 먼저 확인하라.

**리뷰 두 층은 서로 다른 것을 잡는다** (실측 2회):

| | 1차 PR | 2차 PR |
| --- | --- | --- |
| 셀프(맥락 보유) | 3건 | 3건 |
| 콜드(맥락 없음) | **11건** | **7건** |

콜드가 크게 앞섰지만 **셀프만 잡은 것도 있다** — "PR 본문이 5개 커밋만큼 낡았다"는
맥락을 가진 쪽만 안다. 한 층으로 줄이지 마라.

**같은 결함 부류를 세 번 놓쳤다.** "검사가 고장 나면 조용히 통과" 를 `secrets.sh` 에서
막아놓고 `gate_run_empty`·`gate_skip`·coverage 잡에 그대로 남겨뒀다. 인스턴스를 고치고
부류를 안 닫는 패턴이 반복된다 — 결함을 고칠 때 **같은 형태가 어디 또 있는지 먼저 찾아라.**
(카운트에는 **발현 가능했던 것만** 넣는다. 도달 불가능한 경로를 섞으면 이 숫자가
검증 체계의 근거로 못 쓰게 된다.)

**"부류를 닫아라"에는 정지 조건이 필요하다 — R7 이 그것이다.** 위 문장만 읽고 설치
스크립트의 `cp`·`chmod` 실패까지 방어하다가, 그 경로가 **도달 불가능**함을 뒤늦게
확인하고 되돌렸다(`cp -R` 이 모드를 보존하므로 `chmod` 실패는 가짜 바이너리를 PATH 에
심어야만 재현된다). 재현에 환경 조작이 필요하면 방어가 아니라 죽은 코드다.

**훅은 실행권한 없이 커밋돼 있으면 조용히 안 돈다.** 설치 문제가 아니라 **설치 이후**
문제다 — `core.fileMode=false` 인 레포, 그리고 편집기가 훅을 지우고 다시 쓸 때 인덱스
모드가 100644 로 떨어진다(둘 다 재현). CI 는 파일 *존재*만 봤기에 통과시켰다.
CI 에 `[ -x ]` 를 넣었다. 게이트 스크립트는 훅이 `bash <경로>` 로 부르므로 권한이
필요 없다 — 거기까지 요구했다가 정상 레포에서 오탐이 나 좁혔다.

**리뷰 없이 8커밋을 밀었더니 기능이 죽어 있었다.** 2026-08-24 세션에서 킷 `main` 에
PR 없이·콜드 리뷰 없이 8커밋을 넣었고, 뒤늦게 콜드 리뷰를 돌리자 **9건**이 나왔다.
가장 나쁜 것은 `gate_go_tool` 함수가 통째로 사라진 것이었다 — 다른 함수를 슬라이스로
교체하면서 같은 구간의 무관한 함수를 같이 지웠고 호출부만 남았다. `GATE_STRICT` 기본값을
1 로 바꾼 직후라 **모든 Go 프로젝트가 커밋·푸시·CI 에서 실패**하는 상태로 올라가 있었고,
메시지는 이미 설치된 도구를 설치하라고 했다.

| | 찾은 것 |
| --- | --- |
| 작성자 자신(우연히 다시 보다) | 4건 — 전부 "덜 좋은 것" |
| 콜드 리뷰 | **9건** — 상당수가 "기능이 죽어 있음" |

같은 세션에서 커밋 린트가 **엉뚱한 파일을 검사**하고 있었던 것(범위가 `main...HEAD` 라
브랜치 두 번째 커밋부터 스테이지한 파일이 범위 밖), 충돌 마커 검사가 **한글 파일명에서
조용히 통과**하던 것(`core.quotePath` 기본값)도 콜드 리뷰가 잡았다.

> **킷이 자기 문서에 "설정·CI·훅·게이트 스크립트는 글이 아니라 코드다 — 콜드 리뷰는
> 기본으로 돈다" 고 써놓고, 그 파일들만 골라 고치면서 한 번도 안 돌렸다.**
> 그래서 이 레포도 **브랜치 → PR → 콜드 리뷰 → 머지**로 간다(PR #1 부터).
> 게이트·훅 설치 여부(열린 결정 1)와는 별개로 채택한 작업 흐름이다.

**측정하지 않은 수치로 설계를 결정하지 마라.** 같은 세션에서 "커밋에 린트를 넣으면
22초"라는 이유로 그 안을 두 번 폐기했는데, 22초는 `--all`(CI 모드)이었고 실제 커밋은
**2.8초**였다. "변경 파일만 린트하면 싸다" 도 틀렸다(eslint 은 파일 1개도 4.4초).
"npm 기동 비용이 크다" 도 틀렸다(node 기동 0.07초, eslint 자체가 4.7초).
**세 번 다 추정이었고 세 번 다 틀렸다.**

**권한 deny 는 원리적으로 신뢰할 수 없다.** Bash 권한 glob 은 플래그와 인자 내용을
구분하지 못한다. 단축 플래그(`-n`·`-f`)·결합 형태(`-an`)·장문 조합을 열거로 닫을 수 없고,
넓히면 오탐만 는다. 그래서 speed bump 로 강등하고 한계를 명시했다.
**이건 원칙 1을 강화하는 증거다** — 에이전트 안의 층은 못 믿고, 밖의 층은 믿을 수 있다.

**YAML 파싱 통과는 워크플로가 유효하다는 뜻이 아니다.** `--lang py,ts` 로 거른
`gates.yml` 이 `yaml.safe_load` 를 통과했고 잡·스텝·체크섬까지 다 맞았는데, GitHub 은
`This run likely failed because of a workflow file issue` 로 거부했다. 원인은 언어 전용
변수를 다 뺀 뒤 남은 값 없는 `env:` 였다 — YAML 로는 `env: None` 으로 멀쩡히 파싱된다.

**그 `env: None` 은 내 검증 출력에 이미 찍혀 있었다.** 잡 목록과 줄 수만 보고 지나쳤다.
출력을 냈다고 읽은 것이 아니다.

고친 뒤로는 `actionlint` 로 닫는다(스크래치패드에 받아서 쓴다). 파서가 아니라
**그 파일을 실제로 소비하는 도구**로 검증해야 이 부류가 닫힌다.

## 체크섬을 걷어낸 근거 (2026-09)

`.ai-kit/VERSION` 에 vendor 내용의 체크섬을 적고 CI 가 재계산해 대조했다. 그 층이
**킷의 다른 설계와 정면으로 부딪힌다.** `.ai-kit/README.md` 는 게이트에 문제가 있으면
그 레포에서 고치라고 말하는데, 체크섬은 그것을 CI 실패로 만든다.

설치된 데모 레포에서 실제 결함(`secrets.sh` 가 AWS secret access key 를 못 잡는 것)을
고치는 시나리오로 한 바퀴 돌렸다:

```
1) .ai-kit/gate/secrets.sh 에 패턴 추가   → 차단됨 (결함이 고쳐졌다)
2) CI 의 vendored 잡                      → ::error:: 기록 3995903652f8ff97 ≠ 실제 f595946954f16a85
3) 안내대로 install.sh 재실행             → 수정 잔존 0건. 출력에 경고 한 줄 없음
```

2번은 **실제 러너가 아니라 로컬에서 그 잡의 스크립트를 그대로 돌린 것**이다
(`recorded` 를 읽고 `gate_checksum` 을 재계산해 대조하는 세 줄). 이 킷의 CI 는 아직
러너에서 돌려보지 않았고, 그 사실은 PR 본문의 "자동화가 닿지 않은 것" 에도 적혀 있다.

3번이 결정적이다. 빨간 것을 푸는 유일한 안내가 **그 수정을 말없이 지운다.**

조사해 보니 "체크섬 불일치 = CI 실패" 는 개발 도구의 관행도 아니었다. 같은 목적에
쓰는 것은 **재생성 후 diff** 다(k8s 의 `hack/verify-codegen.sh` 는 실패 메시지에
`Please run hack/update-codegen.sh` 를 담는다). 체크섬은 "달라졌다" 만 말하고 **어떻게
되돌리는지를 말하지 못한다.** 체크섬 기반 3-way 병합은 재생성이 불가능한 환경, 즉 OS
패키지 매니저(dpkg conffiles 의 md5sum, ucf 의 `diff3`)에 있다.

킷의 vendor 내용은 프로젝트 안에서 생성되는 것이 아니라 **다른 레포에서 복사돼 온 것**
이라, "재생성" 에 해당하는 동작이 곧 덮어쓰기다. 그래서 둘 중 어느 쪽도 아닌 자리에
있었다. 걷어내고, 대신 무엇이 달라졌는지를 `--dry-run` 이 보여주게 했다.

킷을 실제 프로젝트 하나(`sera`)에 설치해 24개 PR 을 굴린 뒤, 포크 시점 킷(`a93ee25`)을
**같은 언어 선택으로 빈 레포에 재설치해** 순수 델타를 냈다. 이 단계를 건너뛰면 언어

결과: 프로젝트가 킷 파일에 손댄 자리는 **24군데**다 — 내용을 고친 19개, 지운 3개

그중 **그 프로젝트만의 사정은 둘뿐이다** — 프로젝트 전용 CI 워크플로 하나와,

어느 쪽도 업스트림에 못 올린 것**이었다. 병합으로는 풀리지 않는다.

## `--diff-merges=cc` 가 하는 일과 안 하는 일 (2026-09)

시크릿 범위 스캔을 `git diff A..B` 에서 `git log --diff-merges=cc` 로 옮기며 실측했다.

| 시나리오 | `git diff` | `git log` 기본 | `--diff-merges=cc` |
| --- | --- | --- | --- |
| 넣었다 다음 커밋에서 지움 | **못 잡음** | 잡음 | 잡음 |
| 충돌 해소 중에 손으로 써넣음 | 잡음 | **못 잡음** | 잡음 |
| 시크릿이 든 main 을 머지 | 잡음 | 잡음 | 잡음 |

**읽는 법.** `git diff` 가 지는 것은 1행 하나다. 2행은 해소한 줄이 최종 트리에 남으므로
끝점 비교가 본다 — 처음에 이 칸을 `—` 로 적었는데 실측하니 잡았다.

그래서 `git log` 로 옮기는 것만으로는 **1행을 얻고 2행을 잃는다.** `git log` 는 기본적으로
머지 커밋의 diff 를 내지 않아 해소 자리가 통째로 안 보인다. `--diff-merges` 가 그것을
되돌려놓는다 — `cc` 는 안 잃기 위해 필요한 것이지 덤이 아니다.

**3행은 어느 방식도 오탐으로 걸러내지 않는다.** 머지로 딸려 들어온 커밋이 범위 안에
있으면 그 내용도 검사 대상이다. `cc` 가 그 오탐을 없앤다고 적어둔 사본이 있었는데
(설치된 프로젝트 쪽) 재현해 보니 사실이 아니었다.

`cc` 를 `--first-parent` 대신 고른 이유는 **머지 커밋이 내놓는 양**이다. 재현:

```bash
d=$(mktemp -d); cd "$d"; git init -q -b main
git config user.email a@b.c; git config user.name t
: > seed; git add -A; git commit -qm seed
git checkout -q -b feat; printf 'mine\n' > mine.txt; git add -A; git commit -qm mine
git checkout -q main
for i in $(seq 1 20); do seq 1 30 | sed "s/^/main-$i /" > "big$i.txt"; done
git add -A; git commit -qm "main: 20 files"
printf 'X\n' > shared.txt; git add -A; git commit -qm "main: shared=X"
git checkout -q feat; printf 'Y\n' > shared.txt; git add -A; git commit -qm "mine: shared=Y"
git merge -q --no-ff main >/dev/null 2>&1 || true
printf 'Z\n' > shared.txt; git add -A; git commit -qm "merge: resolved"
echo "cc           $(git show --diff-merges=cc --format= HEAD | wc -l)"
echo "first-parent $(git show --first-parent    --format= HEAD | wc -l)"
```

```
cc           8
first-parent 727
```

`cc` 는 모든 부모와 같은 hunk 를 생략하므로 머지 커밋에 남는 것이 해소 자리뿐이다.
`--first-parent` 는 머지가 들여온 것 전부를 그 커밋 하나에 몰아 보고한다 — 같은 내용을
원본 커밋에서 한 번, 머지에서 또 한 번 짚는다.

**결합 diff 는 열이 여럿이다.** 부모가 둘이면 `++` 는 어느 부모에도 없는 줄, ` +` 는
부모1 에만 있던 줄이다. `^\+` 로만 거르면 뒤엣것을 놓친다 — 머지가 부모1 쪽 시크릿을
남긴 경우가 그 모양이고, 실측으로 확인해 `^[ +]*\+` 로 고쳤다.

## 리뷰 라운드가 사람 없이 스무 바퀴 돌았다 (2026-09)

킷을 설치한 프로젝트 하나에서 PR 한 건에 리뷰 라운드가 **20회** 돌았다. 사람의 승인은
그 사이 한 번도 없었고, 개입은 20라운드가 끝난 뒤였다.

```
$ gh pr view 7 -R 4estse4/SERA --json comments -q '.comments | length'
40
$ gh pr view 7 -R 4estse4/SERA --json comments -q '.comments[].body' | grep -c '^## Cold review'
20
$ ... | grep -oE '리뷰한 head: `?[0-9a-f]{7,40}' | sort -u | wc -l
20
```

**일이 끝난 시점**: 커밋 24개 중 `[tool.ruff]` 블록을 마지막으로 바꾼 것은 **6번째**
(`6f25ed7`)이고, 이후 18커밋이 전부 `docs:` 였다. 종류별로 `docs 20 · fix 2 ·
refactor 1 · chore 1`. 설정 파일 하나를 옮기는 작업이었다.

**세 겹이 다 열려 있었다.**

1. 그 프로젝트의 `open-pr` 이 "3단계로 돌아와 두 층을 다시 돌린다" 로 끝났다.
   멈추는 조건도, 보고하라는 단계도 없었다. **킷의 스킬에도 멈춤은 없었다** — 루프가
   없었을 뿐이다. 스킬이 자라는 순간 같은 일이 난다(그 프로젝트의 것은 킷 원본에서 자랐다).
2. 규칙 문서의 승인 목록에 리뷰 라운드가 없었다.
3. `settings.json` 의 `allow` 에 `Bash(gh pr comment*)` 가 있었다. 40번 게시하는 동안
   권한 프롬프트가 한 번도 안 떴다.
   (당시 "서브에이전트 스폰이 `allow`·`ask`·`deny` 어디에도 없었다" 도 원인으로 셌는데
   **그것은 원인이 아니다** — 문서상 스폰 자체가 프롬프트를 띄우지 않는다. 아래 절.)

**코멘트 40건 중 20건은 서브에이전트가 직접 올렸다.** 그 프로젝트의 `cold-reviewer.md` 가
`gh pr comment` 를 시켰다. 킷의 것에는 그 지시가 없었지만, 이슈 #41 이 "게시 지시가 없어
기록이 안 남는다" 며 넣으라고 하고 있었다.

**막을 수 없는 것을 먼저 지웠다.** "같은 head 에서 2라운드째를 훅으로 거부한다" 는 제안이
있었는데, 라운드마다 head 가 움직이므로(위 실측: 서로 다른 head 20개) 이 사고를 한 번도
못 막는다. 게다가 그 프로젝트의 스킬 자체가 매 라운드 push 를 **요구**한다 — 안 하면 다음
라운드가 옛 head 를 읽어 수정이 머지에 안 들어간다고 적혀 있다.

**그래서 고친 곳은 셋이다.** 스킬이 라운드 끝에서 멈추고 보고한다 · 게시를 메인 한 자리로
모은다(사람이 한 자리에서 읽게 하려는 것이다 — 권한 때문이 아니다) · gh 쓰기 명령 넷을
`ask` 에 둔다. 마지막 것은 횟수를 제한하지 않는다 — 매번 사람 눈에 띄게 할 뿐이고,
세는 것은 사람이다.


## 검증 안 한 것을 설계 근거로 썼다 (2026-09)

리뷰 라운드 사고를 고치면서 "**콜드 리뷰어가 게시하지 않고 돌려준다**" 를 넣었다.
그 근거로 이렇게 적었다 — *"서브에이전트가 부모 세션의 권한 규칙을 물려받는지는
확인되지 않았다. 확인되지 않은 것에 강제를 기대지 않는다."*

**확인해 보니 반대였다.** 공식 문서:

```
tools-reference:  Launching the subagent doesn't itself prompt for permission.
                  Claude Code checks the subagent's own tool calls against your
                  permission rules as it runs.
permissions:      Use `Agent(AgentName)` rules to control which subagents Claude
                  can use … Add these rules to the `deny` array
```

두 가지가 한꺼번에 드러났다. **서브에이전트도 권한 규칙을 지난다**(내 근거가 틀렸다).
그리고 **`Agent(...)` 는 `deny` 로 쓰는 규칙이고 스폰 자체는 프롬프트를 안 띄운다**
— `ask` 에 넣었던 줄은 애초에 아무 일도 안 했을 것이다.

**설계 자체는 안 바뀌었다.** 게시를 메인으로 모으는 데는 다른 이유가 있었고
(사람이 한 자리에서 읽는다 · 요약이 코멘트의 본체가 되려면 한 자리여야 한다)
그것만으로 선다. 바꾼 것은 **근거를 적어둔 자리들**이다.

### 어떻게 새어 들어왔나

근거의 출처는 이 세션이 띄운 조사용 서브에이전트가 GitHub 이슈를 인용해 보고한
"서브에이전트가 권한을 우회한다" 였다. **나는 그것을 검증하지 않았고, 검증하지 않았다는
것을 알고 있었다** — 사용자에게 "이 플랫폼 동작을 직접 검증하지 못했습니다" 라고 적어
보내기까지 했다. 그러고도 그것을 설계 근거로 썼다.

검증 비용은 `WebFetch` 한 번이었다. 도구는 있었고, 안 썼다.

**"미검증" 이라고 적는 것이 검증을 대신했다.** R1 은 "못 찾은 것은 쓰지 않는다" 이지
"못 찾았다고 적으면 써도 된다" 가 아니다. 라벨이 안전하다는 느낌을 만들었고,
그 느낌이 확인을 미루게 했다.

**그래서 규칙을 하나 세운다: 결론을 떠받치는 것은 "미검증" 상태로 둘 수 없다.**
사실이 그냥 기록될 뿐이면 미검증 표시로 충분하다. 그러나 그것이 *왜 이렇게 설계했나* 의
근거라면, 확인하거나 다른 근거를 찾아야 한다. 확인 못 하면 **그 근거는 못 쓴다.**
`cold-reviewer` 가 그것을 찾도록 목록에 넣었다.

### 그 규칙을 세운 작업에서 그 규칙을 어겼다

같은 수정을 하면서 `gh issue create` 를 `ask` 에서 뺐다. 근거로 *"PreToolUse 의 deny 가
권한 평가보다 먼저 끝나는 것을 실측했다"* 를 적었다. **실측은 있었고 일반화가 틀렸다** —
그때 그 설정에는 그 명령에 대한 `ask` 규칙이 애초에 없었으므로 프롬프트가 안 뜬 것은 두
설명 중 어느 쪽으로도 읽힌다. 문서는 반대다: *"Hook decisions don't bypass permission
rules"*, 그리고 "먼저 끝난다" 는 `exit 2` 로 죽는 훅에만 해당한다.

**인용이 원문인 것과 인용이 주장을 떠받치는 것은 다른 검사다.** 앞 절의 규칙은 지켰는데
— 인용은 원문 그대로였다 — 그것이 결론을 실제로 떠받치는지를 안 봤다.

### 훅을 걷어내고 권한 규칙으로 갔다

`use_skill.sh` 는 셸 명령 문자열을 정규식으로 파싱해 `gh` 쓰기 명령을 막던 훅이다.
**못 잡는 형태 넷을 스스로 적어두고 "안 고치기로 정했다" 고 못 박았고**, 스킬만
통과시키려는 탈출구 `AI_KIT_SKILL=1` 이 스킬 파일에 평문으로 적혀 있어 에이전트가 읽고
붙일 수 있었다. 그 자리의 공식 답은 `auto-mode-config` 의 「Add a human checkpoint」이고,
예시로 든 규칙이 `Bash(gh pr create *)` 다.

**이것을 다시 넣지 마라.** 훅으로 세울 수 있는 것은 "스킬을 거쳤나" 이고, 세워야 하는
것은 "사람이 봤나" 다. 후자는 `permissions.ask` 가 하고, 전자는 탈출구 때문에 못 한다.
규칙이 무엇을 잡는지의 실측은 `docs/process/verification-layers.md` 에 있다.

> `use_skill.sh` 는 `main` 에 도달한 적이 없다 — 이 브랜치가 만들고 같은 브랜치가 지웠다.
> **릴리스된 킷이 그 훅을 설치한 프로젝트는 없다.**

### 검증 출력이 실제 출력이 아니었던 것들

이 레포에서 가장 자주 반복된 결함이고, **어느 층도 못 막았다.** 매번 사람이나 콜드
리뷰가 잡았다. **횟수는 이 표가 유일한 출처다** — 다른 문서에 수를 옮겨 적지 마라.
한 번 그렇게 갈렸다(한쪽은 "여섯 번" 이라 쓰고 다섯을 나열했고, 이 표는 다섯이었다).

마지막 둘이 이 PR 이 **본문을 얼리기로** 한 이유다. 둘 다 붙일 때는 참이었고 나중에
거짓이 됐다 — 손으로 관리되는 파생 값이라 아무도 안 고쳐준다.

| | 무엇을 붙였나 |
| --- | --- |
| 1 | `bash -n a b` 가 첫 파일만 검사하는데 "전부 통과" 로 적음 |
| 2 | 출력이 없는 `json.load` 아래에 손으로 쓴 요약을 붙임 |
| 3 | `ask` 항목을 실제보다 하나 더 적음 |
| 4 | 실행한 명령 대신 **보기 좋게 다듬은 가짜 명령줄**을 붙임 |
| 5 | 붙일 때는 맞았으나 **줄 번호가 밀려** 재현이 안 됨 |
| 6 | 붙일 때는 맞았으나 **코드가 바뀌어** 본문의 `ask` 목록이 실제와 갈림 |

5번이 그중 유일하게 형식의 문제였다 — **증거 블록에 줄 번호를 박으면 다음 편집에
틀린다.** 그래서 줄 번호를 출력하는 명령(`grep -n` 등)은 증거로 쓰지 않는다.

앞의 넷은 형식이 아니라 습관이었다. `docs/process/artifact-rules.md` 가 *"주장 대신 명령
출력"* 이라고 적어둔 그 자리에서 네 번 어겼다. **기록이 예방하지 못한다는 것 자체가
이 표의 내용이다.**
