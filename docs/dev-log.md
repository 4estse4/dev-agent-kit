**왜 남기나**: 나중에 "AI 를 어떻게 썼는가"를 쓸 때, 결론만 있으면 재구성이 안 된다.

## 2026-08-22 — 스킬 첫 사용에서 드러난 것과 같은 부류를 세 번 놓친 것 (PR 없음, 커밋 855955b · 9063270)

- **작업**: 킷을 실제 프로젝트에 처음 설치해 스킬 · 권한 deny · 설치 스크립트를 써봤다.
- **사람이 잡은 것**: 스킬 6개 중 5개가 첫 사용에서 버그였다. 전부 *써야만* 드러났다.

  | | 버그 |
  | --- | --- |
  | `open-pr` | 게이트 경로가 vendor 레이아웃과 불일치 |
  | `devlog` | "최신이 위" 가정 — 프로젝트는 반대 순서 |
  | `devlog` | 코멘트 없는 PR 에서 PR 맥락이 통째로 사라짐(jq 빈 배열 함정) |
  | `trace` | `git diff main...HEAD` 만 봐서 **미커밋·untracked 변경이 안 보임** — 추적표의 테스트 칸을 채우는 게 이 스킬의 일인데 새 테스트 파일은 거의 항상 untracked 다 |
  | 권한 deny | 넓힌 패턴이 커밋 메시지 내용까지 매칭 → 정상 커밋 차단 |

  `open-pr`·`devlog`·`trace` 는 같은 형태다: **스킬이 돌아가는 실제 상태를 잘못 가정했다**
  (vendor 레이아웃 · 로그 순서 · git 작업트리). 새 스킬을 쓸 때 "이 명령이 내가 있는
  상태에서 실제로 뭘 보는가" 를 먼저 확인하라.
- **부류를 닫아라 (원문)**: **같은 결함 부류를 세 번 놓쳤다.** "검사가 고장 나면 조용히 통과"
  를 `secrets.sh` 에서 막아놓고 `gate_run_empty`·`gate_skip`·coverage 잡에 그대로 남겨뒀다.
  인스턴스를 고치고 부류를 안 닫는 패턴이 반복된다 — 결함을 고칠 때 **같은 형태가 어디 또
  있는지 먼저 찾아라.** (카운트에는 **발현 가능했던 것만** 넣는다. 도달 불가능한 경로를
  섞으면 이 숫자가 검증 체계의 근거로 못 쓰게 된다.)
- **폐기**: `[AI]` 위 문장만 읽고 설치 스크립트의 `cp`·`chmod` 실패까지 방어 → 폐기. 그
  경로가 **도달 불가능**함을 뒤늦게 확인했다(`cp -R` 이 모드를 보존하므로 `chmod` 실패는
  가짜 바이너리를 PATH 에 심어야만 재현된다). 재현에 환경 조작이 필요하면 방어가 아니라
  죽은 코드다. 「부류를 닫아라」에는 정지 조건이 필요하고, 그것이 산출물 규칙 R7 이다.
- **채택**: 권한 deny 를 speed bump 로 강등하고 한계를 명시한다. **권한 deny 는 원리적으로
  신뢰할 수 없다.** Bash 권한 glob 은 플래그와 인자 내용을 구분하지 못한다. 단축
  플래그(`-n`·`-f`)·결합 형태(`-an`)·장문 조합을 열거로 닫을 수 없고, 넓히면 오탐만 는다.
  **이건 원칙 1을 강화하는 증거다** — 에이전트 안의 강제는 못 믿고, 밖의 강제는 믿을 수 있다.

## 2026-09-08 — 리뷰 라운드가 사람 없이 스무 바퀴 돌았다 (PR #48)

- **작업**: 리뷰 라운드가 사람에게서 끝나게 `open-pr` 을 고치고, gh 쓰기 명령을
  `permissions.ask` 에 두고, `use_skill.sh` 훅을 걷어냈다(ADR-0006). PR 본문을 열 때 쓰고
  얼리기로 했다.
- **사람이 잡은 것 · 리뷰가 잡은 것**: 스무 바퀴는 사람이 잡았고, 아래 검증 출력 표는 사람이나
  콜드 리뷰가 잡았다. 킷을 설치한 프로젝트 하나에서 PR 한 건에 리뷰 라운드가 20회 돌았다.
  사람의 승인은 그 사이 한 번도 없었고, 개입은 20라운드가 끝난 뒤였다.

  ```
  $ gh pr view 7 -R 4estse4/SERA --json comments -q '.comments | length'
  40
  $ gh pr view 7 -R 4estse4/SERA --json comments -q '.comments[].body' | grep -c '^## Cold review'
  20
  $ ... | grep -oE '리뷰한 head: `?[0-9a-f]{7,40}' | sort -u | wc -l
  20
  ```

  일이 끝난 시점: 커밋 24개 중 `[tool.ruff]` 블록을 마지막으로 바꾼 것은 6번째(`6f25ed7`)
  이고, 이후 18커밋이 전부 `docs:` 였다. 종류별로 `docs 20 · fix 2 · refactor 1 · chore 1`.
  설정 파일 하나를 옮기는 작업이었다.

  세 겹이 다 열려 있었다. 그 프로젝트의 `open-pr` 이 "3단계로 돌아와 두 층을 다시 돌린다"
  로 끝났고 멈추는 조건도 보고하라는 단계도 없었다(킷의 스킬에도 멈춤은 없었다 — 루프가
  없었을 뿐이다). 규칙 문서의 승인 목록에 리뷰 라운드가 없었다. `settings.json` 의 `allow`
  에 `Bash(gh pr comment*)` 가 있어 40번 게시하는 동안 권한 프롬프트가 한 번도 안 떴다.
  코멘트 40건 중 20건은 서브에이전트가 직접 올렸다 — 그 프로젝트의 `cold-reviewer.md` 가
  `gh pr comment` 를 시켰다. 킷의 것에는 그 지시가 없었지만, 이슈 #41 이 "게시 지시가 없어
  기록이 안 남는다" 며 넣으라고 하고 있었다.

  **검증 출력이 실제 출력이 아니었던 것들.** 이 레포에서 가장 자주 반복된 결함이고, 어느
  단계도 못 막았다. 매번 사람이나 콜드 리뷰가 잡았다. 표의 항목마다 누가 잡았는지는 원문에
  없다. **횟수는 이 표가 유일한 출처다** — 다른 문서에 수를 옮겨 적지 마라. 한 번 그렇게
  갈렸다(한쪽은 "여섯 번" 이라 쓰고 다섯을 나열했고, 이 표는 다섯이었다).

  | | 무엇을 붙였나 |
  | --- | --- |
  | 1 | `bash -n a b` 가 첫 파일만 검사하는데 "전부 통과" 로 적음 |
  | 2 | 출력이 없는 `json.load` 아래에 손으로 쓴 요약을 붙임 |
  | 3 | `ask` 항목을 실제보다 하나 더 적음 |
  | 4 | 실행한 명령 대신 **보기 좋게 다듬은 가짜 명령줄**을 붙임 |
  | 5 | 붙일 때는 맞았으나 **줄 번호가 밀려** 재현이 안 됨 |
  | 6 | 붙일 때는 맞았으나 **코드가 바뀌어** 본문의 `ask` 목록이 실제와 갈림 |

  마지막 둘이 이 PR 이 본문을 얼리기로 한 이유다. 둘 다 붙일 때는 참이었고 나중에 거짓이
  됐다 — 손으로 관리되는 파생 값이라 아무도 안 고쳐준다. 5번이 그중 유일하게 형식의
  문제였다 — **증거 블록에 줄 번호를 박으면 다음 편집에 틀린다.** 그래서 줄 번호를 출력하는
  명령(`grep -n` 등)은 증거로 쓰지 않는다. 앞의 넷은 형식이 아니라 습관이었다.
  `common/docs/artifact-rules.md` 가 *"주장 대신 명령 출력"* 이라고 적어둔 그 자리에서 네
  번 어겼다. **기록이 예방하지 못한다는 것 자체가 이 표의 내용이다.** 옛 파일은 이 경로를
  설치된 레포의 `docs/process/artifact-rules.md` 로 적었다. 되살리며 경로만 킷 것으로 바꿨다.
- **폐기**: "같은 head 에서 2라운드째를 훅으로 거부한다" 는 제안 → 폐기. 라운드마다 head 가
  움직이므로(위 실측: 서로 다른 head 20개) 이 사고를 한 번도 못 막는다. 게다가 그
  프로젝트의 스킬 자체가 매 라운드 push 를 **요구**한다.
  `[AI]` "서브에이전트 스폰이 `allow`·`ask`·`deny` 어디에도 없었다" 를 원인으로 셈 → 폐기.
  문서상 스폰 자체가 프롬프트를 띄우지 않는다.
- **채택**: 고친 곳 셋. 스킬이 라운드 끝에서 멈추고 보고한다 · 게시를 메인 한 자리로
  모은다(사람이 한 자리에서 읽게 하려는 것이다 — 권한 때문이 아니다) · gh 쓰기 명령을 `ask`
  에 둔다. 마지막 것은 횟수를 제한하지 않는다 — 매번 사람 눈에 띄게 할 뿐이고, 세는 것은
  사람이다.
- **검증 안 한 것을 설계 근거로 썼다**: "콜드 리뷰어가 게시하지 않고 돌려준다" 의 근거로
  *"서브에이전트가 부모 세션의 권한 규칙을 물려받는지는 확인되지 않았다. 확인되지 않은 것에
  강제를 기대지 않는다."* 를 적었다. **확인해 보니 반대였다** — 서브에이전트도 권한 규칙을
  지나고, `Agent(...)` 는 `deny` 로 쓰는 규칙이며 스폰 자체는 프롬프트를 안 띄운다(문서
  인용은 ADR-0006). 근거의 출처는 이 세션이 띄운 조사용 서브에이전트가 GitHub 이슈를
  인용해 보고한 것이었고, **검증하지 않았고 검증하지 않았다는 것을 알고 있었다** —
  사용자에게 "이 플랫폼 동작을 직접 검증하지 못했습니다" 라고 적어 보내기까지 했다. 검증
  비용은 `WebFetch` 한 번이었다. **"미검증" 이라고 적는 것이 검증을 대신했다.** R1 은 "못
  찾은 것은 쓰지 않는다" 이지 "못 찾았다고 적으면 써도 된다" 가 아니다. 라벨이 안전하다는
  느낌을 만들었고, 그 느낌이 확인을 미루게 했다. 그래서 규칙 하나 — **결론을 떠받치는 것은
  "미검증" 상태로 둘 수 없다.** 사실이 그냥 기록될 뿐이면 미검증 표시로 충분하다. 그러나
  그것이 *왜 이렇게 설계했나* 의 근거라면, 확인하거나 다른 근거를 찾아야 한다. 확인 못 하면
  그 근거는 못 쓴다. `cold-reviewer` 가 그것을 찾도록 목록에 넣었다.
  **그 규칙을 세운 작업에서 그 규칙을 어겼다.** 같은 수정에서 `gh issue create` 를 `ask`
  에서 뺐고, 근거로 *"PreToolUse 의 deny 가 권한 평가보다 먼저 끝나는 것을 실측했다"* 를
  적었다. 실측은 있었고 일반화가 틀렸다 — 그때 그 설정에는 그 명령에 대한 `ask` 규칙이
  애초에 없었으므로 프롬프트가 안 뜬 것은 두 설명 중 어느 쪽으로도 읽힌다. 문서는 반대다:
  *"Hook decisions don't bypass permission rules"*, 그리고 "먼저 끝난다" 는 `exit 2` 로 죽는
  훅에만 해당한다. **인용이 원문인 것과 인용이 주장을 떠받치는 것은 다른 검사다.** 앞 절의
  규칙은 지켰는데 — 인용은 원문 그대로였다 — 그것이 결론을 실제로 떠받치는지를 안 봤다.

    진행하면서 5라운드 코멘트와 그 답 코멘트가 각각 두 벌 올라갔다(로컬 롤백은 이미 올라간
    코멘트를 안 지운다). 두 라운드 코멘트는 바이트 동일했다. 두 리뷰와 `merge-pr` 은

    앵커로 잡고 그 뒤를 싣는다. 그래서 한 벌이 더 붙자 그 사이의 답이 창 밖으로 밀렸다.

    ```

    모드에 이름을 붙여뒀는데, 원인이 앵커 이동이라 그 규칙이 안 걸렸다. 막는 것은 규칙이

    ```

## 2026-09-11 — 플래그 하나를 빼고 옮겨 적은 명령이 법칙 셋의 근거가 됐다 (PR #59)

- **작업**: `merge-pr` 이 머지 뒤 로컬 브랜치를 지우게 하고, 이슈를 열기 전에 목록을 보게
  했다. 새 라운드 코멘트 형식을 그것을 만든 PR 밖에서 처음 썼다.
- **사람이 잡은 것**: `merge-pr` 에 *「`git branch -d` 를 따로 실행하지 않는다 —
  `--delete-branch` 가 처리한다」* 가 있었다. PR #52 머지 뒤 로컬 브랜치가 남은 것을 보고 이
  줄을 거짓으로 여겼고(이슈 #42 넷째), 이 PR 이 그 한 줄을 고쳤다. **그런데 그 관측은 `-R`
  을 붙인 머지였고, 옛 줄은 `-R` 없는 스킬 명령에 대한 문장이었다.** 옛 줄이 틀렸다는 근거는
  처음부터 없었다. 사람이 세션 기록으로 확인한 두 줄:

  ```
  실제 실행     gh pr merge 52 -R 4estse4/ai-native-kit --squash --delete-branch
  #42 넷째      gh pr merge 52 --squash --delete-branch          (-R 이 빠졌다)
  ```

  이 세션이 그것을 이슈 #42 에 옮기면서 `-R` 을 뺐고, 스킬의 명령(`-R` 없음)이 로컬
  브랜치를 남긴다는 추론이 `-R` 을 붙인 실행에서 나왔다. 사람도 그 위에 섰다 — #42 넷째를
  시킬 때 「원인은 순서로 보인다」고 했고 `-R` 은 안 봤다. 3라운드의 「§2 의 산문 대조를
  걷어라」도 그 위에서 정했다. 이슈 #58(손으로 옮긴 증거가 잘린다)과 같은 모양이다. 잘린 것이 출력 줄이 아니라 명령의 플래그였다. `-R` 습관의
  출처로는 킷 `CLAUDE.md` 의 `gh issue list -R 4estse4/ai-native-kit` 예시가 지목됐다(사람이
  찾았다).
- **리뷰가 잡은 것**: 그 위에 선 법칙 셋이 다 틀렸다.

  | 넣은 때 | 문장 | 무엇이 틀렸나 | 잡은 때 |
  | --- | --- | --- | --- |
  | PR 을 열 때(`5fed693`) | 「`--delete-branch` 는 원격만 지운다. 실측이다」 | 「실측」이 `-R` 을 붙인 실행이었다. gh 도움말은 `Delete the local and remote branch after merge` 다 | 콜드 1라운드 |
  | PR 을 열 때(`5fed693`) | 「`-d` 는 스쿼시라 `main` 의 조상이 아니어서 거부한다. 그래서 `-D`」 | #42 가 「실측」으로 붙인 것은 `git branch --merged main` 이었다. **`-d` 와 다른 명령이다.** `-d` 는 업스트림이 있으면 업스트림을 본다 | 콜드 3라운드 |
  | 1라운드 수정(`ffaa267`) | 「`--not --remotes` 는 스쿼시라 다 민 브랜치에서도 전부 나온다」 | 갈림은 스쿼시가 아니라 **원격 추적 ref 가 지워졌는지**다 | 콜드 2라운드 |

  둘은 PR 을 열 때 이미 있었고 하나만 수정이 들여왔다. 둘째와 셋째는 같은 오귀인이다.

  그 둘을 잇는 머지 명령은 플래그가 빠진 채 옮겨져 있었다.

  **가드를 넣을 때마다 그 가드가 다음 라운드에서 걸렸다.**

  | 넣은 때 | 가드 | 걸린 것 |
  | --- | --- | --- |
  | PR 을 열 때 | `MERGED` 확인 뒤 `-D` | 지울 브랜치 이름의 출처가 없었다. 확인이 시점만 세우고 대상은 안 세웠다 |
  | 1라운드 수정 | 로컬 팁을 `git rev-parse` 로 대조 | **정상 경로에서 죽었다.** 없는 브랜치에서 `rc=128` 로 인자를 stdout 에 되뱉었다. 그리고 **파괴 뒤에** 놓였다 |
  | 2라운드 수정 | 2절에서 `--is-ancestor` | **밖에서 객체를 요구했다.** `headRefOid` 가 로컬에 없으면 `128` 로 멀쩡한 머지를 막았다 |
  | 3라운드 수정 | 2절 대조를 걷고 `-d` 를 가드로 | **스킬 경로에서 닿지 않았다.** 아래 |
  | 4라운드 수정 | 2절에서 글자로 대조, 4절은 「남아 있으면 지운다」 | |

  라운드마다 새로 물은 것이 하나씩 늘었다 — 정상 경로에서 죽나 · 파괴 뒤에 놓였나 · 방향을
  보나 · 밖에서 무엇을 요구하나.

  **`-d` 는 가드였지만 스킬이 도는 경로에서는 닿지 않았다.** `git branch -d` 를 직접 불러
  네 방향으로 깼을 때는 가드였다. 사람도 따로 재현해 같은 표를 얻었다:

  ```
  다 밀었고 refs/remotes/origin/<이름> 이 남아 있다   rc=0   지워진다
  커밋만 하고 안 밀었다                              rc=1   거부
  다 밀었지만 원격 추적 ref 가 pruned 됐다            rc=1   거부
  -D                                                 언제나 지운다
  ```
