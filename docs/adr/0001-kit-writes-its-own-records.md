# ADR-0001: 킷이 자기가 배포하는 기록 템플릿을 쓴다

- **상태**: 채택
- **날짜**: 2026-09-12

## 맥락

킷은 `common/templates/` 의 `adr.md` · `dev-log.md` · `plan.md` 를 프로젝트에 놓으면서
(`install.sh` 의 `DO_TEMPLATES` 블록), 자기 기록은 `docs/evidence.md` 한 파일에 적었다.
그 파일에 세 가지가 섞여 있었다 — 겪은 일, 결정의 근거, 그리고 실측. **셋은 수명이
다르다.** 겪은 일은 영원히 참이고, 결정 근거는 결정이 바뀌면 낡고, 실측은 코드가 바뀌면
낡는다. 한 파일에 섞이면 어느 줄이 어느 수명인지 표시할 수 없다.

이 ADR 을 쓰며 `main` = `8affdaf` 에서 확인한 값이다. 이슈 #63 이 열릴 때 적은 값과 같다:

```
$ wc -l docs/evidence.md
646 docs/evidence.md
$ grep -c '^## ' docs/evidence.md
14
$ grep '^## ' docs/evidence.md | grep -c '(20[0-9][0-9]-[0-9][0-9]'        # 제목에 날짜 있는 절
12
$ grep '^## ' docs/evidence.md | grep -cE '\(20[0-9]{2}-[0-9]{2}-[0-9]{2}'   # 그중 일 단위
0
$ grep '^## ' docs/evidence.md | grep -v '(20[0-9][0-9]-'                    # 제목에 날짜 없는 절
## 실전에서 드러난 것 (읽어서는 안 나오는 것들)
## 실증된 것
```

「실증된 것」은 현재형 제목인데 항목이 네 상태로 섞여 있었다 — 여전히 참인 것,
걷어냈다고 괄호로 덧댄 것(체크섬 · `install.sh --update`), 맥락이 바뀌었다고 덧댄 것,
그리고 대상 파일이 없어졌는데 표시가 없는 것(`install-operator.sh`).

쓰는 시점도 프로젝트와 반대였다. 킷 `CLAUDE.md` 는 「새로 겪은 것은 그 자리에서 거기
적는다」였고, 프로젝트의 dev-log 는 머지 직전에 한 번 쓴다. 그래서 PR #59 에서 잠정
결론(「`--delete-branch` 는 원격만 지운다」)이 라운드 도중에 영구 기록에 들어갔고, 틀린
것으로 판명돼 정정 절이 붙었고, 머지 뒤에 두 자리가 또 낡아 이슈 #62 가 생겼다.

마지막으로, 킷이 배포하는 기록 템플릿을 킷 자신이 한 번도 안 썼다. 이슈 #4(킷이 자기
계층을 자기 자신에게 적용하지 않는다)와 같은 모양이다.

## 결정

킷은 `docs/evidence.md` 를 없애고, 자기가 배포하는 템플릿대로 쓴다.

```
킷이 쓴다     docs/adr/0001-<결정>.md · docs/dev-log.md
              docs/plan/README.md · docs/plan/0001-<단계>.md
킷이 안 쓴다   docs/SPEC.md · docs/traceability.md
이름          스킬 devlog → dev-log
```

- **파일 번호는 `0001-` 로 통일한다.** 설치기가 템플릿을 `docs/adr/0000-template.md` ·
  `docs/plan/0000-template.md` 로 놓으므로 실제 문서는 `0001` 부터다.
- **`docs/plan/README.md` 가 지금 단계를 가리킨다.** 킷 `CLAUDE.md` 는 늘 README 만
  가리키고, 몇 번 단계인지는 README 가 든다. 바뀌는 값을 규칙 문서 밖에 두는 입구다.
  세션이 시작할 때 읽는 기록이 이것 하나다.
- **단계 문서의 작업 목록은 이슈 번호다.** 내용은 이슈가 들고, 계획은 순서와 그 이유만
  든다. 그 이슈를 닫는 PR 이 dev-log 단계에서 그 줄을 지우고, 지운 것을 dev-log 에 남긴다.
- **dev-log 는 머지 직전에 쓴다.** 프로젝트와 같은 시점이다. 라운드 도중의 잠정 결론이
  영구 기록에 들어가지 않는다.
- **「리뷰가 잡은 것」 칸은 킷의 dev-log 에만 둔다.** 템플릿과 `devlog` 스킬에는 넣지 않는다.
  사람이 정했다 — 그 칸을 배포하면 프로젝트가 칸을 채우려고 쓰게 되고, 기록이 아니라 연출이
  된다.
- **규칙이 자기 ADR 을 링크한다.** 에이전트가 ADR 을 읽는 경로가 그것 하나다. 다만
  **설치되는 파일은 킷의 ADR 과 dev-log 를 가리키지 않는다** — 설치된 레포에 없는
  경로다(이슈 #61). 링크는 킷 자신의 `CLAUDE.md` 와 `README.md` 에서만 한다.
- **`SPEC.md` · `traceability.md` 는 안 쓴다.** 결정이 아니라 미룬 것이다. 킷의 요구를
  문서로 쓰는 것은 그 자체로 큰 설계 작업이고, 쓰면 `trace` 스킬까지 킷에 넣어야 한다.
  그 사실은 이슈 #4 에 적었다.
- 킷 템플릿 `CLAUDE.md` 에는 plan 을 넣지 않는다. 설치기가 `docs/plan/README.md` 를
  놓지 않으므로, 템플릿이 그것을 가리키면 설치된 레포에 없는 파일을 가리키게 된다.
  작업 루프에 dev-log 단계를 넣는 것은 템플릿에도 한다 — `docs/dev-log.md` 는 설치된다.

이 결정은 나눠 들어간다. 기록을 가르는 것(A) · 계획 문서와 루프(B) · 스킬 개명과
설치되는 파일의 참조 청소(C). 킷 전용 파일과 설치되는 파일을 한 PR 에서 같이 바꾸지
않으려는 것이고, 그 판단을 여기서 하라고 적어 둔 것이 이슈 #51 이다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| `docs/evidence.md` 를 두고 절마다 수명을 표시한다 | 한 파일에 세 수명이 섞이는 구조가 문제다. 표시는 다음 편집에 안 따라온다 — 「실증된 것」의 네 상태가 그 결과다 |
| `SPEC.md` · `traceability.md` · `trace` 까지 킷에 넣는다 | 킷의 요구를 문서로 쓰는 별도의 큰 설계 작업이다. 미룬다 |
| 작업 순서를 GitHub 마일스톤으로 든다 | 마일스톤은 이슈 사이의 순서를 못 든다. 킷이 안 쓰던 기능이 하나 는다 |
| 계획 파일을 `p0-…` · `p1-…` 식으로 번호 붙인다 | 설치기가 놓는 템플릿이 `0000-template.md` 라 한 디렉터리에 두 규칙이 섞인다. `p` 는 영어 약자이고 템플릿이 쓰는 낱말 「단계」와도 안 맞는다 |
| 지나간 역사를 소급해 단계로 쪼갠다 | 지어내는 것이다. 지금 단계 하나에서 시작한다 |

## 결과

강제하는 것:

- 미결의 **내용**은 이슈에만 있다. `docs/plan/` 의 지금 단계 문서는 순서와 그 이유를 이슈
  번호로 든다. 킷 `CLAUDE.md` 의 「미결 목록을 적지 마라」는 그만큼 좁아진다.
- 킷 `CLAUDE.md` 의 규칙이 그 근거를 `docs/adr/` 로 가리킨다. 사건은 `docs/dev-log.md` 다.
- 설치되는 파일(`common/` · `claude-code/`)이 `docs/adr/` · `docs/dev-log.md` 의 킷 항목을
  가리키면 이슈 #61 의 검사가 막아야 한다.

포기한 것:

- 「그 자리에서 적는다」의 즉시성. 라운드 도중에 안 것은 라운드 코멘트에 남고, 영구
  기록에는 머지 직전에 정리된 것만 간다.

써보고 정할 것은 `docs/plan/` 의 지금 단계 문서 위험 표에 있다 — plan 템플릿에 README
인덱스를 넣을지, 「다루는 요구」 절을 선택 절로 바꿀지, 파일 번호 규칙을 템플릿에 적을지.

되돌리려면 킷 `CLAUDE.md` 의 근거 절과 세션 시작 규칙과 작업 루프, `docs/plan/README.md`,
그리고 `dev-log` 스킬의 plan 줄 처리를 건드려야 한다.
