# ADR-0004: `install.sh --update` 의 3-way 병합을 걷어낸다

- **상태**: 채택
- **날짜**: 2026-09-05 (PR #43)

## 맥락

원래 하려던 것은 설치된 프로젝트가 킷의 개선을 가져갈 수 있게 하는 것이었다. 킷은
계속 바뀌고, 프로젝트마다 손으로 옮기게 하면 아무도 안 옮긴다. 그래서 설치 시점의
원본(base)을 두고 킷 변경과 프로젝트 수정을 3-way 로 병합했다.

**병합이 풀려는 상황이 실제로는 안 일어났다.** 킷을 실제 프로젝트 하나(`sera`)에 설치해
24개 PR 을 굴린 뒤, 포크 시점 킷(`a93ee25`)을 같은 언어 선택으로 빈 레포에 재설치해
순수 델타를 냈다. 이 단계를 건너뛰면 언어 필터가 만든 차이를 프로젝트 수정으로 오인한다
— `gates.yml` 은 그냥 비교하면 181줄이 다르지만 프로젝트가 고친 것은 19줄이다.

결과: 프로젝트가 킷 파일에 손댄 자리는 24군데다 — 내용을 고친 19개, 지운 3개
(`baseline/` 트리는 통째로 하나로 셌다), 새로 만든 2개. 그중 **그 프로젝트만의 사정은
둘뿐이다** — 프로젝트 전용 CI 워크플로 하나와, `settings.json` 안에서 그 프로젝트의 원문
PDF 를 막는 `permissions.ask` 한 블록. 나머지는 전부 킷 자신의 버그였다. 그중 셋은 킷
쪽에서도 같은 기간에 따로 고쳤고, 마지막 것(시크릿 범위 스캔)은 양쪽이 낸 코드가
바이트 단위로 같았다:

```bash
FILES=$(git log --name-only --diff-filter=ACM --diff-merges=cc --pretty=format: "$RANGE" | sort -u | sed '/^$/d')
DIFF=$(git log -p -U0 --diff-merges=cc --pretty=format: "$RANGE")
```

그 셋은 당시 킷 `main` 에 없었다. 킷 쪽 수정은 미머지 브랜치 `fix/kit-gaps` 에만 있었고
그 PR(#35)은 닫혔다.

```
$ git grep -c 'diff-merges=cc' main
(출력 없음, exit 1)

$ git grep -c 'diff-merges=cc' fix/kit-gaps
fix/kit-gaps:common/gate/secrets.sh:3
fix/kit-gaps:docs/evidence.md:1
```

3-way 병합은 "커스터마이즈와 업스트림 변경의 충돌" 을 푸는 장치인데, 실제로 치른
비용은 **같은 버그를 두 곳에서 두 번 고치고, 그중 어느 쪽도 업스트림에 못 올린 것**
이었다. 병합으로는 풀리지 않는다.

구현 쪽도 수렴하지 않았다. base 를 어디 둘지의 시도 다섯이 전부 실패했고(`.ai-kit/baseline/`
커밋 · `kit_rev` 로 킷 히스토리에서 복원 · base 없이 현재끼리 비교 · 킷 안에서만 대조 ·
충돌이 남으면 `kit_rev` 고정), 콜드 리뷰 여섯 회차가 같은 갱신 경로 100여 줄 안에서
매번 새 결함을 찾았다. 그 표와 각 시도가 왜 실패했는지는 이슈 #38 에 있다.

## 결정

`--update` 와 3-way 병합을 통째로 걷어낸다. 지금 동작:

```
.ai-kit/gate · git-hooks · .github/workflows/gates.yml   →  항상 교체 (킷 소유)
없는 파일                                                 →  놓는다
이미 있고 내용이 다른 파일                                  →  건드리지 않고 diff 명령을 알려준다
```

설치는 한 번 땡겨오는 것이고 갱신은 프로젝트의 선택이다. 킷 `CLAUDE.md` 의 「킷은 아직
미완성이다 — 이전 버전을 고려하지 마라」가 이 결정의 규칙 쪽이다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| 3-way 병합을 두고 고친다 | base 를 둘 자리가 전부 실패했고, 여섯 회차의 콜드 리뷰가 수렴하지 않았다. 기능이 든 상태들이 서로를 건드렸다 |
| base 없이 킷 현재와 프로젝트 현재를 비교한다 | "프로젝트가 채웠다" 와 "킷이 바꿨다" 가 구분되지 않아 채운 파일이 매번 전부 충돌한다 |
| 킷 변경을 프로젝트가 손으로 옮긴다 | 실제로 확인한 비용은 반대 방향이다 — 프로젝트의 수정이 킷에 못 올라왔다. 병합이 푸는 문제가 아니라 업스트림에 올리는 흐름의 문제다 |

## 결과

설치된 프로젝트는 킷의 개선을 자동으로 받지 못한다. 다시 설치하면 킷 소유 파일은
교체되고, 프로젝트 소유 파일은 diff 명령만 안내받는다.

「`install.sh --update` 의 baseline + 3-way 병합」을 실증했다는 기록은 이 결정으로 대상이
없어졌다. 옛 구현은 PR #35 의 head 에 있다 — `git fetch origin refs/pull/35/head`. 브랜치는
지웠고, 되찾는 법과 단서는 이슈 #38 에 있다.

다시 만든다면 base 를 들지 말 것, 필요한 것이 "킷이 이 파일을 바꿨나" 뿐이라면 그것은
킷 안에서만 답할 수 있는 질문이라는 것, 파생 파일(`gates.yml`)과 저작 파일(`CLAUDE.md` ·
`SPEC.md`)을 가를 것, 한 번에 하나씩 만들고 매번 콜드 리뷰를 실행할 것 — 이슈 #38 의
「다시 만든다면」.
