# ADR-0003: vendor 체크섬 대조를 걷어낸다

- **상태**: 채택
- **날짜**: 2026-09-05 (PR #43)

## 맥락

`.ai-kit/VERSION` 에 vendor 내용의 체크섬을 적고 CI 가 재계산해 대조했다. 그 검사가
**킷의 다른 설계와 정면으로 부딪힌다.** `.ai-kit/README.md` 는 게이트에 문제가 있으면
그 레포에서 고치라고 말하는데, 체크섬은 그것을 CI 실패로 만든다.

설치된 데모 레포에서 실제 결함(`secrets.sh` 가 AWS secret access key 를 찾아내지 못하는 것)을
고치는 시나리오로 한 번 실행해 봤다:

```
1) .ai-kit/gate/secrets.sh 에 패턴 추가   → 차단됨 (결함이 고쳐졌다)
2) CI 의 vendored 잡                      → ::error:: 기록 3995903652f8ff97 ≠ 실제 f595946954f16a85
3) 안내대로 install.sh 재실행             → 수정 잔존 0건. 출력에 경고 한 줄 없음
```

2번은 실제 러너가 아니라 로컬에서 그 잡의 스크립트를 그대로 실행한 것이다(`recorded` 를
읽고 `gate_checksum` 을 재계산해 대조하는 세 줄). 3번이 결정적이다. **빨간 것을 푸는
유일한 안내가 그 수정을 말없이 지운다.**

조사해 보니 "체크섬 불일치 = CI 실패" 는 개발 도구의 관행도 아니었다. 같은 목적에
쓰는 것은 **재생성 후 diff** 다(k8s 의 `hack/verify-codegen.sh` 는 실패 메시지에
`Please run hack/update-codegen.sh` 를 담는다). 체크섬은 "달라졌다" 만 말하고 **어떻게
되돌리는지를 말하지 못한다.** 체크섬 기반 3-way 병합은 재생성이 불가능한 환경, 즉 OS
패키지 매니저(dpkg conffiles 의 md5sum, ucf 의 `diff3`)에 있다.

킷의 vendor 내용은 프로젝트 안에서 생성되는 것이 아니라 **다른 레포에서 복사돼 온 것**
이라, "재생성" 에 해당하는 동작이 곧 덮어쓰기다. 그래서 둘 중 어느 쪽도 아닌 자리에
있었다.

## 결정

체크섬 기록과 CI 의 대조를 걷어낸다. 설치본이 킷과 무엇이 다른지는 `install.sh --dry-run`
이 보여준다 — 판정하지 않고 보이기만 한다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| 체크섬을 두고 불일치를 CI 실패로 | 게이트를 그 레포에서 고치라는 설계와 부딪힌다. 복구 안내가 그 수정을 지운다 |
| 재생성 후 diff (k8s 식) | vendor 는 다른 레포에서 복사된 것이라 재생성이 곧 덮어쓰기다. 지킬 것을 지우는 재생성이다 |
| 체크섬 기반 3-way 병합 (dpkg · ucf 식) | 재생성이 불가능한 환경용이다. 그리고 킷은 3-way 병합 자체를 걷어냈다(ADR-0004) |

## 결과

설치본이 킷에서 얼마나 멀어졌는지를 CI 가 판정하지 않는다. 보는 것은 `--dry-run` 이고,
보는 시점은 사람이 다시 설치하려 할 때다.

「vendor 체크섬 드리프트 검출」을 실증했다는 기록은 이 결정으로 대상이 없어졌다.

다시 넣으려면 위 세 단계 시나리오를 먼저 통과시켜야 한다 — 특히 3번, 빨간 것을 푸는
안내가 수정을 지우지 않는지.
