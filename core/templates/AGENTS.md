## 이 문서를 쓰는 규칙

1. **규칙마다 집행자를 표시한다** — `[hook]` `[lint]` `[CI]` `[test]` `[review]` `[사람]`
2. **집행자가 `[review]`·`[사람]` 뿐인 규칙은 지켜지지 않는다고 가정한다.**
   불편하면 집행자를 기계로 바꿔라(린트 규칙·테스트·CI 검사).
3. **적용 대상이 없는 규칙은 지운다.** 존재하지 않는 코드를 규율하는 규칙은
   규칙 목록 전체의 신뢰도를 깎는다.
4. 길이 상한을 정하고 지킨다(권장 150줄). 넘으면 무언가를 지울 때다.

## 작업 루프

feature 브랜치 → 구현 → 테스트 → `commit` → `open-pr` → `review-diff` → 수정 → 머지.

- 파일 3개 이상 또는 구조에 영향 주는 변경은 **먼저 계획을 제시하고 승인받는다.**
- 외부 API·SDK 는 **기억으로 짜지 않는다.** 공식 문서나 실호출로 확인한다. `[review]`
  → 확인한 근거(문서 URL·실행 결과)를 코드 주석이나 ADR 에 남긴다.
- 읽지 않은 파일의 내용을 단정하지 않는다. 먼저 읽는다.
- 머지 전 검토에서 나온 수정은 **diff 제시 → 확인 → 커밋** 순서. 푸시 먼저 하지 않는다.

## 산출물 언어

규약이 없으면 산출물마다 언어가 흔들린다. 아래를 따른다.

| 산출물 | 언어 | 왜 |
| --- | --- | --- |
| 코드 주석 · 식별자 | **영어** | 코드가 가장 오래 살고 가장 널리 읽힌다 |
| 커밋 메시지 · PR 제목 | **영어** | 도구·grep·업계 관행 |
| 브랜치명 · 태그 | **영어(ASCII)** | URL·CLI 에서 비ASCII 는 깨진다 |
| **CI 워크플로(잡·스텝 이름)** | **영어(ASCII)** | 잡 이름은 브랜치 보호 required check 이름으로 쓰인다. 스텝 이름은 로그에서 영어 도구 출력과 섞이므로 함께 맞춘다 |
| PR 본문 · 리뷰 코멘트 | 팀 언어 | 정밀한 판단이 오가는 곳 — 가장 정확히 쓸 수 있는 언어로 |
| 설계 문서(SPEC·ADR·plan·dev-log) | 팀 언어 | 위와 같음 |
| README · RUNBOOK | 팀 언어 | 읽는 사람 기준 |
| 이 파일 · 스킬 · 에이전트 정의 | 팀 언어 + 영어 기술용어 | 아래 |
| 훅·스크립트의 사람용 메시지 | 팀 언어 | 읽는 사람이 운영자 |

**기술용어는 번역하지 않는다.** `%w` · `errors.Is` · `FOR UPDATE SKIP LOCKED` ·
`idempotency` 는 원어로 둔다 — 번역하면 오히려 모호해진다.

> 에이전트에게 주는 지시(이 파일·스킬)의 언어는 성능보다 **정밀도**가 기준이다.
> 어설픈 영어 규칙보다 정확한 팀 언어 규칙이 낫다. 진짜 리스크는 언어가 아니라
> **길이와 모호함**이다 — 이 파일의 150줄 상한이 언어 선택보다 중요하다.

## 산출물

설계 근거는 `docs/process/artifact-rules.md`(킷이 함께 설치한다). 요약:

- 검증 산출물은 **발견만** 쓴다. "문제없음"의 근거를 서술하지 않는다.
- "테스트 통과함" 같은 **주장 대신 명령 출력(증거)** 을 붙인다.
- AI 가 쓴 산출물은 다음 단계에서 **대조 대상**이지 배경이 아니다.
