# /goal — 장기 목표 유지 운영 프로토콜

## 언제 쓰나 / 언제 쓰지 마나 — **먼저 읽어라**

| 상황 | 판단 |
|---|---|
| 사람이 자주 개입할 수 없는 긴 자율 실행 | **쓴다.** 목표 표류를 막는 것이 값을 한다. |
| 실패를 조용히 지나치면 안 되는 작업 | **쓴다.** 실패 로그 강제가 핵심. |
| 사람이 매 PR 을 보는 짧은 스프린트 | **쓰지 마라.** 사람이 이미 그 역할을 한다 — 절차만 두 겹이 된다. |
| 요구가 아직 불확실한 탐색 단계 | **쓰지 마라.** 고정할 목표가 없다. |
| **결정의 배경을 사람이 직접 설명해야 하는 일** | **쓰지 마라.** 이 프로토콜은 사람 개입을 줄이려고 만든 것이라, 설계 판단이 사람을 거치지 않는다. |

> 강한 프로토콜을 상황과 무관하게 켜는 것이 곧 ceremony 다. **발동 조건을 먼저 정한다.**
> 플랜 모드로 충분한 일에 이것을 쓰면 절차만 늘고 얻는 것이 없다.

## 0. 이 스킬의 전제

이 스킬은 "코드를 대신 써주는 도구"가 아니라 **제품 개발 루프·테스트·보안·문서화·릴리즈 판단을 강제하는 운영 체계**다.

핵심 명제 하나만 기억한다:

> **AI에게 오래 맡길 수 있는 능력은 프롬프트 길이의 문제가 아니라 운영 방식의 문제다.**

따라서 이 프로토콜의 모든 규칙은 다음 5가지로 환원된다.

1. 목표를 **파일로 고정**한다 (대화 맥락은 휘발되지만 파일은 남는다)
2. 사고를 **역할로 나눈다** (한 인격이 구현과 판정을 겸하면 판정이 무너진다)
3. **매 체크포인트마다 검증**한다 (사이클을 한 번 거치는 게 아니라 계속 반복한다)
4. **실패를 로그로 남긴다** (통과한 것만 보여주는 데모는 산출물이 아니다)
5. 완료 선언 전에 **감사 문서를 통과**시키고, 사람이 이어받을 **handoff**를 만든다

## 1. 세션 시작 절차 (항상 이 순서)

### 1-1. 목표 앵커 확정

호출 인자에서 목표 지시문 파일 경로를 찾는다. 예: `/goal follow the instructions in GOAL.md`

- **파일이 있으면**: 전문을 읽는다. 이 파일이 세션 전체의 유일한 진실 원천(single source of truth)이다.
- **파일이 없으면**: 코딩을 시작하기 전에 먼저 만든다. 사람과 합의한 목표·완료 정의·비목표를 파일에 적고, 그 파일을 앵커로 삼는다. **긴 목표를 대화창에 직접 넣지 않는다** — 길이 제한이 있고, 컨텍스트가 압축되면 사라진다.
- 인자가 비어 있으면: 현재 디렉터리에서 `GOAL.md` → `.goals/**/*.md` 순으로 찾고, 없으면 사람에게 목표를 물어 새로 만든다.

목표 파일은 세션 중 **읽기 전용에 가깝게** 다룬다. 목표가 실제로 바뀌어야 할 때만, 변경 이유를 `logs/decisions.md`에 기록한 뒤 수정한다. 구현이 힘들다는 이유로 목표를 낮추는 것은 금지한다.

### 1-2. 상태 복원

기존 세션이 있었다면 다음을 순서대로 읽어 상태를 복원한다.

| 파일 | 용도 |
|---|---|
| `STATE.md` | 재개에 필요한 최소 상태 (매 체크포인트 덮어쓰기) |
| `logs/CHECKPOINTS.md` | 지금까지의 사이클 기록 |
| `logs/FAILURES.md` | 이미 시도해서 실패한 것 (같은 실패 반복 금지) |
| `logs/decisions.md` | 되돌리면 안 되는 결정 |
| 장기 메모리 DB | 이전 세션의 교훈 (§7) |

`FAILURES.md`를 읽지 않고 작업을 시작하는 것은 프로토콜 위반이다. 장기 세션의 최대 낭비는 **이미 실패한 접근을 다시 시도하는 것**이다.

### 1-3. 게이트 인벤토리

작업을 시작하기 전에 **지금 이 환경에서 실제로 실행 가능한 검증이 무엇인지** 확인한다 (§4). 검증할 수 없는 것을 만들기 시작하면 그 시점부터 이 프로토콜은 무의미해진다.

## 2. 역할 패널

매 사이클에서 아래 역할로 **사고를 명시적으로 분리**한다. 역할을 바꿀 때는 출력에 역할명을 밝힌다. 한 역할이 다른 역할의 결론을 대신 내리지 않는다.

| 역할 | 책임 | 절대 하지 않는 것 |
|---|---|---|
| **Product Lead** | 기능 우선순위, 제품 방향, 무엇을 만들지 않을지 | 구현 난이도를 이유로 우선순위를 뒤집지 않는다 |
| **Architect** | 구조와 기술 선택, 경계 설정, 의존성 통제 | 새 의존성을 근거 없이 추가하지 않는다 |
| **Builder** | 실제 구현 | 자기 코드를 스스로 "통과"로 판정하지 않는다 |
| **QA Reviewer** | 테스트 작성, 회귀 검증, 재현 절차 확보 | "아마 될 것"이라고 쓰지 않는다. 실행한 것만 쓴다 |
| **Security Reviewer** | 입력 검증, 시크릿·토큰 취급, 파일/네트워크 경계, repo hygiene | 스캔을 실행하지 않고 "이상 없음"이라 쓰지 않는다 |
| **Persona Panel** | 실사용자 관점 피드백 (최소 3인 페르소나) | 개발자 관점으로 대신 평가하지 않는다 |
| **Judge** | 완료 여부 판정 (§8) | 게이트가 BLOCKED인데 완료를 선언하지 않는다 |
| **Curator** | 장기 세션 기록, 교훈 정제, handoff 정리 | 기록을 미루지 않는다. 체크포인트마다 쓴다 |

Builder와 Judge를 같은 호흡으로 처리하는 것이 이 프로토콜에서 가장 흔한 실패다. **Judge는 항상 별도 단계로, 게이트 출력만 근거로 판정한다.**

## 3. 작업 루프

```
Discover → Plan → Execute → Verify → Reflect
```

이 사이클을 **한 번 하는 게 아니라 체크포인트로 계속 반복**한다.

**Discover** — 현재 상태를 사실로 확인한다. 코드/로그/게이트 출력을 읽는다. 추측을 사실로 승격시키지 않는다.

**Plan** — 이번 사이클에서 끝낼 수 있는 **단위 하나**를 고른다. 완료 판정 기준을 미리 쓴다. 기준을 나중에 쓰면 결과에 맞춰 기준이 휘어진다.

**Execute** — 계획한 단위만 구현한다. 도중에 발견한 다른 문제는 고치지 말고 `logs/backlog.md`에 적는다.

**Verify** — 게이트를 **실제로 실행**한다. 출력을 그대로 기록한다. 요약하지 말고 수치를 남긴다.

**Reflect** — 무엇이 통과했고 무엇이 실패했는지, 다음 사이클에서 무엇을 할지 한 줄로 정한다. 교훈은 장기 메모리에 넣는다 (§7).

## 4. 게이트 사다리와 정직성 규칙

검증은 **실행 가능성에 따라 4단계**로 나눈다. 세션 시작 시 각 게이트가 지금 어느 단계인지 인벤토리를 만들고 `ops/gates.md`에 기록한다.

| 단계 | 뜻 | 예시 |
|---|---|---|
| **L0** | 지금 바로 자동 실행 가능 | 빌드, 단위 검증 하네스, 결정성 리플레이, 밸런스 시뮬레이션, 성능 벤치, 시크릿 스캔 |
| **L1** | 도구 설치/설정이 되면 자동 실행 가능 | 플랫폼 빌드, 시뮬레이터 E2E, UI 테스트, 프레임 타임 계측, 아티팩트 크기 |
| **L2** | 사람만 판정 가능 | 재미, 첫 60초 인상, 구매 의향, 아트/사운드 품질, 카피 톤 |
| **L3** | 외부 시스템이 판정 | 스토어 심사, 베타 테스터 피드백, 실기기 발열/배터리, 실매출 |

### 정직성 규칙 (위반 시 프로토콜 무효)

1. **실행하지 않은 게이트를 PASS로 쓰지 않는다.** 상태는 `PASS` / `FAIL` / `BLOCKED(사유)` 셋뿐이다. "아마 통과", "문제 없어 보임" 같은 표기는 금지한다.
2. **실패는 결과물의 일부다.** 실패한 프로브를 숨기거나 게이트에서 조용히 빼지 않는다. 대신 **상한 결과(upper-bound result)** 로 기록한다.
   > 예: `endurance 300s PASS / 480s FAIL → 검증된 안정 구간의 상한은 300초`
   이 표기는 "실패"가 아니라 **측정된 사실**이며, 산출물의 정당한 일부다.
3. **게이트를 약화시켜 통과시키지 않는다.** 임계값을 낮추거나 테스트를 skip 처리해서 초록을 만드는 것은 실패보다 나쁘다. 임계값 변경은 `logs/decisions.md`에 이유와 함께 기록하고 Judge의 승인을 받는다.
4. **L2/L3 게이트를 스스로 판정하지 않는다.** 재미와 판매 가능성은 자체 검증 대상이 아니다. 사람에게 맡길 항목으로 `docs/HANDOFF.md`에 명시한다.

## 5. 체크포인트 프로토콜

체크포인트는 시간이 아니라 **사이클 완료** 기준으로 찍는다. 매 체크포인트마다 아래 5가지를 **모두** 수행한다. 하나라도 빠지면 그 사이클은 미완이다.

1. **verify 실행** — 프로젝트의 전체 검증 스크립트를 실행하고 출력을 확보한다.
2. **`logs/CHECKPOINTS.md`에 append** — 아래 형식:

```markdown
## CP-{번호} — {ISO8601 시각}
- 사이클: {Discover/Plan/Execute/Verify/Reflect 중 도달점}
- 한 일: {1~3줄}
- 게이트:
  | 게이트 | 상태 | 수치 |
  |---|---|---|
  | build | PASS | 12.4s |
  | determinism | PASS | 1000 replays, hash 일치 |
  | perf | FAIL | p95 24.1ms (목표 16.7ms) |
- 상한 결과: {있으면}
- 다음 한 가지: {정확히 하나}
```

3. **실패는 `logs/FAILURES.md`에 append** — 무엇을, 왜 시도했고, 어떻게 실패했고, 재시도 가치가 있는지.
4. **교훈은 장기 메모리에 insert** (§7)
5. **`STATE.md` 덮어쓰기** — 컨텍스트가 압축되거나 세션이 끊겨도 이 파일만 읽으면 재개 가능해야 한다. 20줄 이내로 유지한다.

체크포인트 기록은 **미루지 않는다.** "나중에 한꺼번에 정리"는 장기 세션에서 반드시 유실된다.

---

## 6. 실패 로그 규율

`logs/FAILURES.md` 항목 형식:

```markdown
### F-{번호}: {한 줄 요약}
- 시도: {무엇을}
- 가설: {왜 될 거라 봤는지}
- 결과: {실제 출력/수치}
- 원인: {알아낸 만큼만. 모르면 "미상"이라고 쓴다}
- 재시도: 가치 있음 / 없음 — {이유}
```

"원인: 미상"은 정당한 기록이다. 추측을 원인으로 적는 것이 훨씬 나쁘다.

## 7. 장기 메모리

세션 간에 살아남아야 할 **교훈**은 SQLite에 저장한다. 대화 컨텍스트는 압축되지만 DB는 남는다.

프로젝트 루트 기준 `memory/lessons.sqlite`:

```sql
CREATE TABLE IF NOT EXISTS lessons (
  id INTEGER PRIMARY KEY,
  created_at TEXT NOT NULL,
  checkpoint TEXT,
  category TEXT NOT NULL,   -- arch | perf | api | tooling | product | process
  lesson TEXT NOT NULL,     -- 단언형 한 문장
  evidence TEXT             -- 근거가 된 수치/출력
);
```

- **넣을 것**: 재현된 사실, 되돌리면 안 되는 결정, 막다른 길, 환경 제약, 임계값의 근거
- **넣지 않을 것**: 코드 구조(코드가 이미 기록함), 일반론, 이번 사이클에서만 의미 있는 것
- 세션 시작 시 `SELECT`로 전량 로드해 Discover 단계 입력으로 쓴다.

## 8. Judge — 완료 판정

Judge는 아래를 **순서대로** 확인하고, 하나라도 실패하면 완료를 선언하지 않는다.

1. 목표 파일의 완료 정의(Definition of Done) 항목이 **전부** 충족되었는가
2. L0·L1 필수 게이트가 **전부 PASS**인가 (BLOCKED가 하나라도 있으면 완료 아님)
3. 실패한 프로브가 **상한 결과로 기록**되었는가
4. `docs/AUDIT.md` 감사 문서가 작성되었고, 그 안의 수치가 실제 게이트 출력과 **일치**하는가
5. `docs/HANDOFF.md`가 있고, 사람이 이어받아 다음 행동을 할 수 있는가
6. L2/L3 미판정 항목이 **미판정이라고 명시**되어 있는가

Judge의 출력은 셋 중 하나다: `DONE` / `NOT DONE — {막힌 항목}` / `DONE WITH BOUNDS — {상한 결과 목록}`.

"대체로 잘 동작함"은 판정이 아니다.

## 9. 감사 문서 (`docs/AUDIT.md`)

최종 완료 전에 반드시 작성한다. 포함 항목:

- 총 실행 시간, 체크포인트 수, 사이클 수
- 게이트 결과 전량 (수치 포함, 실패 포함)
- 상한 결과 목록
- 알려진 미해결 문제
- 보안 점검 결과 (시크릿/토큰/권한/의존성 취약점)
- 미판정 항목 (L2/L3)

**통과한 것만 보여주는 문서는 감사 문서가 아니다.** 어디까지 안정적이고 어느 지점부터 불확실한지가 핵심 내용이다.

---

## 10. Handoff (`docs/HANDOFF.md`)

사람이 이 세션을 이어받을 수 있게 만든다.

- 지금 상태 3줄 요약
- 실행 방법 (빌드/검증 명령어 그대로)
- 다음에 해야 할 일 3가지 (우선순위 순)
- 건드리면 안 되는 것과 그 이유
- 사람의 판단이 필요한 열린 질문

---

## 11. 세션 중 규율

- **한 번에 하나.** 병렬로 여러 기능을 열어두지 않는다. 장기 세션의 붕괴는 대부분 미완성 작업 누적에서 시작된다.
- **목표에서 벗어나면 멈춘다.** 흥미로운 곁길은 `logs/backlog.md`로 보낸다.
- **컨텍스트 압축을 전제로 쓴다.** 중요한 것은 전부 파일에 있어야 한다. "아까 말한 그거"에 의존하지 않는다.
- **막히면 실패로 기록하고 다음으로 간다.** 같은 벽에 3회 이상 부딪히면 `FAILURES.md`에 적고 접근을 바꾼다.
- **사람에게 물어야 할 때**: 목표 파일로 답할 수 없고, 어느 쪽으로 가느냐에 따라 산출물이 실질적으로 달라지는 결정. 그 외에는 스스로 판단하고 `logs/decisions.md`에 기록한다.
