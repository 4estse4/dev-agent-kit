description: 맥락을 가진 쪽의 리뷰. 이 변경을 만든 세션이 그 결정을 알고 있는 상태에서 diff 와 PR 본문을 대조한다 — 무엇이 언제 정해지고 바뀌었는지 아는 쪽만 잡는 것이 있다. 콜드 리뷰(cold-reviewer)와 짝이고, 둘은 같은 diff 를 다른 처지에서 본다. 기계가 잡는 것은 리뷰하지 않는다.
argument-hint: "[PR 번호 | '번호 -R owner/repo' (다른 레포) | 비우면 현재 브랜치]"

> **아래 주입된 자리 중 하나라도 `!!` 로 시작하면 리뷰하지 마라.** 그 자리는 비어 있는
> 것이 아니라 **못 가져온 것**이다. 무엇이 실패했는지만 보고하고 멈춘다. `gh` 는 이 세션이
> 열린 레포에 대해 돌므로, 다른 레포의 PR 이면 `48 -R owner/repo` 로 불러야 한다.
>
> 자리마다 실패 문구가 다르다. **넷 다 뜻은 같다 — 그 자리를 못 가져왔으니 멈춘다:**
> `!! gh pr diff <번호> 실패 — diff 를 못 가져왔다` · `!! 변경 파일 목록을 못 가져왔다` ·
> `!! PR 본문을 못 가져왔다` · `!! 메타데이터를 못 가져왔다`.
>
> **PR 본문 자리가 `(PR 번호 없이 부름 — 로컬 브랜치 리뷰)` 면** 실패가 아니라 번호 없이
> 불린 것이다. 그러면 **대조할 본문이 없으므로 `### 본문 ↔ diff` 에 `일치.` 를 쓰지 마라** —
> "번호 없이 불려 본문을 못 봤다" 를 적는다. PR 리뷰라면 번호를 주고 다시 불러야 한다.

Diff:
!`if [ -z "$ARGUMENTS" ]; then git diff main...HEAD; else gh pr diff $ARGUMENTS || echo "!! gh pr diff $ARGUMENTS 실패 — diff 를 못 가져왔다"; fi`

변경 파일:
!`if [ -z "$ARGUMENTS" ]; then git diff main...HEAD --name-only; else gh pr diff $ARGUMENTS --name-only || echo "!! 변경 파일 목록을 못 가져왔다"; fi`

**PR 본문 (검증 대상 — 배경이 아니다):**
!`if [ -z "$ARGUMENTS" ]; then echo "(PR 번호 없이 부름 — 로컬 브랜치 리뷰)"; else gh pr view $ARGUMENTS --json title,body --jq '"TITLE: \(.title)\n\n\(.body)"' || echo "!! PR 본문을 못 가져왔다"; fi`

메타데이터:
!`if [ -n "$ARGUMENTS" ]; then gh pr view $ARGUMENTS --json headRefOid,headRepository --jq '"PERMALINK_BASE=https://github.com/\(.headRepository.nameWithOwner)/blob/\(.headRefOid)/"' || echo "!! 메타데이터를 못 가져왔다"; fi`

**직전 라운드 코멘트 + 그 뒤의 코멘트 전부 (검증 대상 — 아래 「재리뷰」). 사람의 답이 그 뒤 코멘트에 있다:**
!`_q='[.comments[].body] as $b | ([$b|to_entries[]|select(.value|contains("리뷰한 head:"))|.key]|last) as $i | if $i == null then "1라운드" else $b[$i:]|join("\n\n———\n\n") end'; if gh pr view $ARGUMENTS --json comments --jq "$_q" 2>/dev/null; then :; elif gh pr view $ARGUMENTS --json number >/dev/null 2>&1; then echo "!! 직전 코멘트를 못 가져왔다"; elif [ -z "$ARGUMENTS" ] && gh auth status >/dev/null 2>&1; then echo "1라운드"; else echo "!! 직전 코멘트를 못 가져왔다 (gh 실패 또는 PR 없음)"; fi`

> `$ARGUMENTS` 에 따옴표를 붙이지 마라. 붙이면 `48 -R owner/repo` 가 한 덩어리로 가고
> 빈 인자가 `""` 로 남아 현재 브랜치 모드가 사라진다. 남는 위험은 값에 `*` 가 들어갈 때의
> 글로빙 하나이고, `;` 는 실행되지 않는다 — 펼친 뒤에 하는 것은 쪼개기와 파일이름 확장이지
> 명령 재해석이 아니다.

## 리뷰하지 않는 것 (기계가 이미 잡는다)

아래는 린터·타입체커·테스트가 결정론적으로 잡는다. **리뷰에서 언급하지 마라.**
언급하고 싶어지면 그건 린터 설정이 빠졌다는 뜻이니, 리뷰가 아니라 설정을 고쳐라.

포맷 · 임포트 정렬 · 미사용 변수 · `%w` 래핑 누락 · body/rows/파일 close 누락 ·
context 전파 · 루프변수 캡처 · `any` 사용 · 훅 규칙 · 접근성 속성 · 알려진 취약 패턴

## 리뷰하는 것

1. **본문 ↔ diff 대조** — 본문이 말한 변경이 실제로 diff에 있나. "Tests run"에 적힌
   테스트가 실제로 존재하나. "Risks: None"이 맞나. **불일치는 그 자체로 발견이다.**
   **단 본문은 연 시점의 기록이다** — 붙은 출력을 지금 다시 돌려 다르게 나오는 것은
   정상이고 발견이 아니다. 발견은 **쓸 당시에도 거짓이었던 것**과 **본문이 세운 목적을
   이후 diff 가 벗어난 것** 둘이다. 낡은 것은 아래 `### 본문 정정` 에 적는다.
   근거는 `docs/process/verification-stages.md` 「PR 본문은 열 때 쓰고 끝이다」.
2. **응집도** — 이 diff가 한 가지 일을 하나. 무관한 변경이 섞였나.
3. **테스트 케이스 선택** — 커버리지 숫자가 아니라, *의미 있는* 경로를 덮나.
   에러 경로·경계값·동시 실행이 빠졌나. 삭제된 테스트가 있나.
4. **에러 분류** — 재시도 가능/불가 구분이 맞나. 삼켜진 실패가 있나.
5. **동시성·자원 수명** — goroutine·구독·타이머가 취소되고 종료되나.
6. **의도를 드러내는 이름** — 범위·타입·동작을 오해하게 하는 이름.
7. **투기적 추상화** — 지금 필요 없는 seam·필드·설정.
8. **프로젝트 규칙** — `CLAUDE.md` 의 하드룰 위반.
9. **직전 라운드가 즉석으로 만든 형식** — 위에 붙은 직전 라운드 코멘트와 **그 뒤 코멘트**에
   `open-pr` 템플릿(3.4 의 형식 · 3.5 의 형식)에 없는 절·칸·표기가 있으면 그것을 발견으로
   올린다. 즉석으로 만든 것은 **그 라운드에만 살고
   다음 세션은 안 한다.** **이 리뷰가 보는 이유**: 그 코멘트를 쓴 것이 같은 세션이라 무엇이
   즉석이었는지 아는 쪽이다. 콜드는 템플릿과 코멘트를 나란히 볼 처지가 아니다.
   **이번 라운드 코멘트는 아직 없다** — 그것은 3.4 에서 메인이 본다.

## 재리뷰(2라운드 이상)

**왜 이렇게 하는지는 `docs/process/verification-stages.md` 의 「라운드 사이에 무엇이
넘어가나」에 있다. 여기 옮겨 적지 마라.**

직전 라운드 코멘트와 **그 뒤에 달린 코멘트가 위에 통째로 붙어 있다**(`———` 로 나뉜다).
**사람이 3.5 에서 준 답은 그 뒤 코멘트에 있다.** 세 가지로 읽는다:

| 위에 붙은 것 | 뜻 |
| --- | --- |
| `1라운드` | 직전 코멘트가 없다. `### 이전 라운드` 절을 생략한다. **`gh` 가 살아 있는 것을 확인한 뒤에만 이 값이 나온다** |
| `!! 직전 코멘트를 못 가져왔다` | **PR 번호를 줬는데 못 가져왔다.** 1라운드가 아니다 — 그 사실을 `### 이전 라운드` 에 적고 진행한다 |
| `!! 직전 코멘트를 못 가져왔다 (gh 실패 또는 PR 없음)` | **번호 없이 불렀고 `gh` 가 죽었다.** 1라운드인지 아닌지를 알 수 없다 — 그 사실을 적고 진행한다. `gh` 가 살아 있고 PR 이 없을 때만 `1라운드` 가 나온다 |
| 코멘트 전문 | 재리뷰다. 아래대로 판정한다 |

**받은 것은 배경이 아니라 검증 대상이다.** 콜드 블록까지 읽는다 — 콜드가 지적하고
그것을 고친 것이 **너**이므로, 그 수정이 지적을 실제로 해소했는지 아는 쪽이 너다.
다만 그 목록은 네 탐색의 범위가 아니라 확인할 주장이고, **거기 없는 것을 찾는 것이
여전히 네 일이다.**

**이번 라운드의 콜드 결과는 보지 마라.** 콜드가 돌아오기 전에 이 리뷰를 끝낸다.

**보는 diff 는 PR 전체다.** 어디를 **먼저** 볼지만
`git log <직전 코멘트의 리뷰한 head>..HEAD --oneline` 으로 정한다.

**판정은 `### 이전 라운드` 절에 항목을 이름으로 적는다** — 수만 적으면 다음 라운드가
무엇을 다시 올릴지 못 읽는다. 직전 기록이 수만 남겼으면 그 라운드의 발견 목록으로
돌아가 재검증한다.

## 출력 형식 (엄수)

**못 찾은 것은 쓰지 않는다.** 항목별로 "✓ 문제없음"과 그 근거를 쓰지 마라 —
검증 불가능한 서술이고, 읽는 사람의 시간을 쓰면서 신뢰를 사칭한다.

```
## Self review

리뷰한 head: <PR 번호를 받았으면 `gh pr view <N> --json headRefOid -q .headRefOid` 의 값 40자 그대로. 로컬 브랜치 리뷰면 `git rev-parse HEAD`.>

checked: 본문대조 · 본문정정 · 응집도 · 테스트 · 에러분류 · 동시성 · 명명 · 추상화 · 규칙 · 즉석형식

### 이전 라운드
<재리뷰일 때만. 직전 코멘트의 항목마다 한 줄, 이름과 판정:
 해결 / 일부 해결 / 미해결 / 기각 / 결정 필요. 일부 해결·미해결은 그 앞 라운드에서
 이월된 것도 포함한다. 직전 코멘트를 못 가져왔으면 그 사실을 적는다.
 1라운드면 이 절을 생략.>

### 본문 ↔ diff
<본문이 세운 목적에서 diff 가 벗어났나 · 쓸 당시에도 거짓이던 문장이 있나.
 없으면: "벗어난 것 없음.">

### 본문 정정
<얼린 본문에서 지금 거짓인 것. 명령을 **다시 돌려** 그 출력을 붙인다 — 손으로 쓰지 마라.
 이 절에 적으면 그 항목은 닫힌다. 다음 라운드로 이월하지 않는다. 없으면 절을 생략.>

### 발견
1. [높음|중간|낮음] `path/file.go:120` — <한 줄 요약>
   <왜 문제인가 1~2문장. 반드시 구체적 실패 시나리오를 포함한다:
    어떤 입력·상태에서 무엇이 잘못되나.>

### 남기는 위험
- <머지해도 되지만 알고 있어야 할 것. 없으면 이 절 자체를 생략.>

**Verdict**: Approve | Request changes | Comment — <한 문장>
```

규칙:

- **`checked:` 에는 실제로 본 것만 남긴다.** 1라운드거나 단독 호출이면 볼 대상이 없는
  항목을 지운다 — `즉석형식`(직전 라운드 코멘트가 없다) · `본문대조`(PR 본문이 없다).
  안 지우면 **안 본 것을 봤다고 적는 줄**이 된다. 바로 위가 금지한 그것이다.
- 발견이 0건이면 `### 발견` 아래에 `없음.` 한 줄. 그것으로 끝이다.
- **구체적 실패 시나리오를 못 쓰겠으면 그것은 발견이 아니라 취향이다** — 적지 마라.
- 코드 위치는 `PERMALINK_BASE<path>#L<line>` 로 링크한다(PERMALINK_BASE 가 있을 때만).
- 리뷰 전체가 화면 한 장을 넘으면 대부분 R1 위반이다. 줄여라.
  이것이 접힌 블록에 들어간다고 해서(`open-pr` 3단계) 느슨해지지 않는다 — 접힘은
  **읽는 사람의 비용**을 없앨 뿐, 노이즈를 정당화하지 않는다. 화면 한 장을 넘지 않는
  것은 `open-pr` 이 쓰는 **요약**이고, 그건 이 리뷰가 짧아야 쓸 수 있다.

## 게시하지 않는다

**리뷰를 GitHub 에 직접 올리지 않는다.** 위 형식 그대로 부른 쪽에 돌려준다.
`open-pr` 이 콜드 리뷰 결과와 **합쳐서 한 번에** 올린다.

- 게시 자리가 하나여야 사람이 한 번에 본다. 두 리뷰가 따로 올리면 코멘트 둘을 각각
  읽어야 하고, 그 사이에 다음 라운드가 시작될 수 있다.
- `gh pr review --request-changes` 도 쓰지 마라. **PR 을 연 계정과 리뷰 계정이 같으면
  GitHub 이 거부한다** — 혼자 쓰는 레포에서는 항상 그렇다.
- 사람이 이 스킬을 단독으로 불렀으면 결과를 보여주고 **올릴지 묻는다.**
