## 0. 파급을 직접 확인한다. 리뷰에 맡기지 마라

**네가 쓴 것이다.** 아래는 리뷰가 매 라운드 대신 해주던 것이고, 그래서 라운드가 끝나지
않았다. 한 프로젝트에서 리뷰가 네 라운드 연속으로 같은 주석을 발견으로 냈고, 고칠 때마다 새로 틀린
말을 썼다. 한 PR 에서는 사람이 라운드마다 「같은 부류가 다른 자리에 있는지 찾아라」를
따로 지시해야 했고, 지시한 라운드에만 나왔다. 사람이 짚었다: "지적 받은데 하나만 하면
되는지 아님 다른데 동일한 문제, 혹은 동일한 유형의 문제가 없는지 조사하고 같이
고치라는건 이렇게 매번 별도 지시를 해야해?"

- **주장을 썼으면 출처와 대조한다.** 주석·문서·PR 본문에 "이렇게 동작한다" 를 적었으면 그
  근거 파일을 열어 맞는지 본다
- **이름을 바꾸거나 옮겼으면 `grep` 으로 옛 이름을 찾는다**
- **규칙·문장을 더했으면 그 파일 전체를 다시 읽는다.** diff 만 보지 마라
- **새 절차를 적었으면 끝까지 따라가 본다**
- **결함을 고쳤으면 같은 문장 · 같은 규칙 · 같은 모양이 다른 자리에 있는지 찾는다.**
  하나를 고치고 부류를 안 닫으면 다음 라운드가 옆 자리를 올린다. 같은 모양을 찾았어도 그 실패가
  실제로 일어날 수 있는 자리만 고친다는 짝은 `docs/process/artifact-rules.md` R7 이다

**찾을 때 줄을 이어 붙인다.** 문서는 낱말 사이에서 줄이 바뀌므로 줄 단위 `grep` 은 두 줄로
나뉜 낱말을 못 본다. 실제로 「기계 대조」가 「기계」와 「대조」로 나뉘어 검색되지 않았다. 코드는 줄
단위로 찾아도 되고, 문서는 이어 붙인 뒤 찾는 말의 낱말 사이에 ` *` 를 둔다(`기계 *대조`). 출력은
그 말의 앞뒤를 마침표까지다. 경로와 버전 번호의 `.` 에서도 끊긴다. `-c core.quotePath=false` 는
git 기본값이 한글 같은 비ASCII 파일명을 8진수로 내서 그 파일이 알림 없이 빠지는 것을 막는다:

    git -c core.quotePath=false ls-files '*.md' | while read -r f; do
      tr '\n' ' ' < "$f" | grep -o '[^.]*<찾는 말>[^.]*' | sed "s|^|$f: |"
    done

찾은 것이 없으면 1절을 진행한다. **PR 을 열기 전에 찾아서 고쳤으면, 커밋한 뒤 이 스킬을 다시
부른다.** 위에 주입된 커밋 목록 · 변경 규모 · 게이트 출력은 부른 시점의 트리라, 그대로
두면 2절이 옛 목록으로 「변경」을 쓰고 옛 게이트 결과로 열지를 정한다. 다음 라운드가 그것을
본문 ↔ diff 불일치로 올린다. 3.6 의 2 에서
이 단계를 실행했으면 다시 부르지 말고 3.6 의 3 을 진행한다. 처음부터 다시 진행하면 「1. 푸시」가 3.6 의 5 를
안 거친다. **이 단계를 건너뛰면 리뷰가 그것을 찾아내고, 그 수정이 또 다음 라운드를
만든다.**

## 1. 푸시

    git push -u origin HEAD

## 2. PR 을 연다

**열기 전에 제목과 본문 전문을 사람에게 보이고 승인받는다.** 보인다는 것은 승인을 묻기 바로 전에 세션의
응답에 그 글의 최종본 전문을 출력하는 것이다 — 파일 경로나 요약으로 대신하지 않는다. 이 스킬에서 승인을
받는 글은 모두 그렇다. 본문은 연 뒤로 고치지 않으므로
(아래 「본문 작성 규칙」) 틀린 채로 열면 고칠 자리가 없다. 승인받으면 `gh pr create` 로 열고,
**1라운드(3절)는 그 뒤 곧바로 진행한다.** 여는 것과 1라운드 사이에 다시 묻지 않는다 — 열었는데
리뷰가 진행되지 않는 상태는 쓸모가 없다. 어떤 행동에 사람의 승인이 필요한지와 그 기준은
`docs/process/verification-stages.md` 6.3 에 있다.

**권한 프롬프트는 이 승인을 대신하지 못한다.** `gh pr create` 는 `settings.json` 의 `ask` 에
있어 프롬프트가 표시되지만, 본문은 파일로 전달하므로(아래) 프롬프트에 보이는 것은 **파일 경로뿐이다.**
무엇이 나가는지 안 보인다. 제목은 브랜치 전체의 목적을 Conventional Commits 스타일로.
**제목에 이슈 번호를 쓰지 않는다.** 스쿼시 제목 끝에 `merge-pr` 이 PR 번호를 `(#N)` 으로 붙이므로,
이슈 번호까지 있으면 같은 표기 둘이 구분되지 않는다. 이슈 번호는 본문의 `Closes #N` 과 결정
코멘트에 적는다.

본문은 **아래 네 절만** 쓴다. 브랜치 전체를 요약하되, 각 절의 성격을 지킨다.

```markdown
## 무엇을 · 왜
<목록 항목 1~3개. 무엇이 바뀌었고 왜 필요했나.>

## 변경
<바뀐 파일을 하는 일끼리 묶어 적는다. 위 --stat 을 참고하되 파일 목록을 그대로 옮기지 않는다.>

## 검증
<`evidence.sh` 가 덧붙인 게이트 출력. 손으로 옮기지 않는다.>

새 테스트: <위 목록에서 추린 이름들. 없으면 "없음">

자동 검증이 확인하지 않은 것: <직접 확인한 것 / 확인 못 한 것. 없으면 "없음". 붙일 출력은 `evidence.sh` 로>

## 위험
<동작 변경 · 테스트가 다루지 않는 경계 경우 · 마이그레이션 절차. 없으면 "없음">
```

### 본문은 파일로 만들고 출력은 명령이 덧붙인다

**손으로 옮긴 출력이 잘렸다.** 한 PR 본문에서 18줄 출력의 앞 넷이 세 번 빠졌다. 「그대로
붙인다」는 규칙이 이미 있었는데도 출력이 잘렸다. 주입으로 온 게이트 출력은 정확했고 잘린 것은 전부
손으로 옮긴 쪽이었다. 그래서 옮기는 단계를 없앤다.

1. 조각을 둘 새 디렉터리를 만든다. 레포의 git 디렉터리 안이라 커밋되지 않고 `git status` 에도
   나오지 않는다. 그 대신 보호 경로다. 조각을 쓰고 고칠 때마다 `default` · `acceptEdits` 모드에서는
   권한 프롬프트가 표시되고, `auto` 에서는 분류기가 정하고, `dontAsk` 에서는 거부돼 본문을 못
   만든다. `allow` 로 미리 풀 수 없다(공식 문서의 protected paths). 셸 변수에
   담지 마라(3.1 과 같은 이유다). 출력된 경로를 그대로 쓴다:

       mktemp -d "$(git rev-parse --absolute-git-dir)/pr-body.XXXXXX"

2. 글은 `Write` 로 조각 파일에 쓴다. 출력은 `evidence.sh` 가 그다음 조각에 덧붙인다. 조각
   이름은 잇는 순서다(`10-head.part` · `20-gate.part` · `30-rest.part` …). 명령은 따옴표 heredoc
   으로 **한 번만** 전달한다. 보이는 명령과 실행되는 명령이 같다. `$ 명령` · 출력 · `rc=N` 이 코드
   블록째 들어간다:

       bash .claude/skills/open-pr/evidence.sh <디렉터리>/20-gate.part <<'CMD'
       bash .kit/gate/gate.sh
       CMD

   「자동 검증이 확인하지 않은 것」에 붙이는 출력도 같다. **명령을 두 번 적지 마라** — 보이는 쪽과
   실행되는 쪽이 어긋난다. 실패하는 명령은 `rc` 가 본문에 남고 스크립트도 그 코드로 끝난다.

   **`evidence.sh` 를 `allow` 에 넣지 마라.** 받은 글을 `bash -c` 로 실행하므로 권한 규칙이 그
   안을 못 본다. 허용해 두면 그 안의 `gh pr merge` · `git push --force` 가 프롬프트 없이 실행된다.
   그래서 스크립트가 레포 · 사람 settings 와 관리 settings 파일의 `ask` · `deny` 규칙 글자가 보이는 명령을
   거부한다. 서버 관리 settings · macOS 구성 프로필 · 실행할 때 준 `--settings` · `--disallowedTools` 의 규칙은
   이 스크립트가 대조하지 않는다. 그 규칙까지 지키려면 `evidence.sh` 를 allow 에 넣지 않는다. 증거는 읽기만
   하는 명령이다. 부를 때마다 권한 프롬프트가 표시될 수 있다. **거부된 명령의 출력은 증거로
   싣지 말고 무엇을 확인했는지 글로 적는다.** 직접 실행해 출력을 손으로 옮기면 이 절이 없앤 일이 다시 생긴다.
3. 조각을 이름 순서로 잇는다: `awk 1 <디렉터리>/*.part > <디렉터리>/body.md`
   `cat` 이 아니라 `awk 1` 인 이유: `Write` 로 쓴 조각이 줄바꿈 없이 끝나면 `cat` 은 다음 조각의
   여는 펜스(```)를 그 줄에 붙여 블록이 깨진다. `awk 1` 은 조각 끝에 줄바꿈을 채운다.
4. 사람에게 보이는 것은 이 `body.md` 전문이다. 고칠 곳이 나오면 그 조각을 고치고 3을 다시
   실행한다. 승인받으면 연다:

       gh pr create --title "<제목>" --body-file <디렉터리>/body.md

### 본문 작성 규칙

- **검증 절은 증거다.** "테스트 통과함" 같은 주장을 쓰지 말고 게이트를 `evidence.sh` 로 실행해
  그 출력을 덧붙인다. 게이트가 실패한 채로 PR 을 열지 않는다.
- **"자동 검증이 확인하지 않은 것"을 비워두지 마라.** 시각·레이아웃·여러 화면을 오가는 흐름은
  대개 자동 검증 밖이다. 직접 확인했으면 무엇을 어떻게 확인했는지,
  확인 못 했으면 못 했다고 쓴다. 적지 않으면 검증이 아무도 모르게 사라진다.
- **이 PR 이 끝내는 이슈가 있으면 「무엇을 · 왜」에 `Closes #N` 을 쓴다.** 머지가 그 이슈를
  닫는다. 이슈의 일부만 하는 PR 에는 쓰지 않는다. 연 뒤 라운드에서 끝내게 된 이슈는 본문을 고치지
  않고, 그 결정을 창(머리말 「끝낼 이슈」)으로 받아 사람 계정 코멘트로 올린다(3.5). 마지막 라운드 뒤에
  정했으면 그때 올린다. `dev-log` 와 `merge-pr` 이 모두 사람 계정 코멘트에서 이슈를 골라, 계획에서 지우고
  닫는다. `merge-pr` 은 그 이슈를 스쿼시 커밋 메시지의 `Closes` 로 넣어 머지가 닫는다.
- **이 본문은 다음 단계에서 diff 와 대조된다.** 지키지 못할 주장을 쓰지 마라.
- 본문이 화면 한 장을 넘으면 대부분 과하다.
- **본문은 지금 한 번 쓰고 끝이다. 라운드마다 고치지 마라.** 그래서 **라운드가 바꿀 값을
  본문에 적지 마라** — 설정 파일의 내용을 복사해 붙이는 것 같은 파생 출력이 그것이다.
  고쳐야 할 때 아무도 안 고쳐주고, 그러면 `$` 가 붙은 채 거짓이 된다. 붙일 것은 **이 시점에
  실행한 게이트 출력**이고, 그건 낡는 것이 아니라 그때의 기록이다.
  이유는 `docs/process/verification-stages.md` 4.

## 3. 리뷰 한 라운드

아래 순서를 지킨다.

### 3.1 head 를 읽는다

셸 변수에 담지 마라 — 읽어서 출력한다:

    gh pr view <N> --json headRefOid -q .headRefOid

**그 값을 보고서에 적어둔다.** 명령을 여러 번 부르는 사이에 셸 상태는 유지되지 않는다 —
`H0=$(…)` 로 담으면 다음 호출에서 그 변수가 비어 있고, 그 명령은 출력도 없어서 값을 눈으로
받지도 못한다. 그러면 3.3 게시 전 대조 가 **언제나 "다르다"** 가 되어 게시에 영영 도달하지
못한다(실제로 확인함).

라운드 중에는 커밋도 푸시도 본문 수정도 하지 않는다 — 두 리뷰가 서로 다른 것을 본다.

**사람이 라운드 도중에 지시하면 그 라운드는 거기서 끝난다.** 지시대로 고치고
커밋한 것은 **이미 다음 라운드의 head 다.** 이 라운드 코멘트는 3.1 에서 읽은 head 로
게시하고, 그 지시로 한 것은 코멘트의 「리뷰 뒤에 한 것」에 적는다. 지시는 창으로 받아 라운드
코멘트 뒤에 사람 계정 코멘트로 올린다(3.5). 「리뷰 뒤에 한 것」에는 `(사람)` 으로 옮기지 않는다 —
그 코멘트가 아직 없어 훅이 대조할 원본이 없다(「라운드 코멘트 형식」). 3.3 의
대조는 이 경우를 무효로 삼지 않는다 — 그 대조가 확인하는 것은 **두 리뷰가 같은 것을
봤나**이지 라운드 내내 head 가 그대로였나가 아니다.

**두 리뷰에 diff 를 건네지 마라.** 각자 `gh pr diff <N>` 로 직접 가져오게 한다. 건네주면 그것이
옛것인지 아무도 모르고, `gh pr diff` 는 커밋을 지정하는 옵션이 없어서 "이 SHA 를 봐라" 를
시킬 방법도 없다. 그래서 고정은 **지시**가 아니라 3.3 게시 전 대조 의 **사후 대조**로 지킨다.

### 3.2 두 리뷰를 실행한다

**한 리뷰가 `!!` 로 멈추면 그 라운드는 무효다** — 게시하지 말고 원인을 고친 뒤 3.1 head
읽기 부터 다시 진행한다. **원인이 이미 게시된 코멘트면 고치지 마라**(3.5 의 「원 라운드 코멘트는
고치지 않는다」) — 그때는 무엇이 막혔는지 사람에게 올리고 멈춘다. 라운드가 무효가 되는
다른 조건은 3.3 게시 전 대조 에 있다. 한쪽만 실행된 결과를 올리면 그 라운드가 반쪽인 것이 코멘트에 드러나지 않는다.

**순서는 없다** — 서로 독립이므로 병렬로 실행해도 된다. `self-review` 스킬(맥락 있음)과
`cold-reviewer` 에이전트(맥락 없음).

**`self-review` 에 PR 번호를 전달해라** — `/self-review <N>`. 다른 레포의 PR 이면
`/self-review <N> -R owner/repo`. 전달하지 않으면 그 스킬이 로컬 브랜치 모드로 실행되어 **PR 본문
자리가 비고, 그러면 그 스킬의 「본문 ↔ diff 대조」 임무가 대조할 것 없이 실행된다.** 그때 비는
자리는 `!!` 가 아니라 평범한 안내문이라 눈에 안 띈다.
발동 조건은 `docs/process/verification-stages.md` 에 있다.

### 3.3 게시 전 대조

같은 명령을 다시 실행해 출력을 3.1 head 읽기 에서 적어둔 값과 **눈으로 비교한다**:

    gh pr view <N> --json headRefOid -q .headRefOid

다르면 라운드 도중에 누가 푸시한 것이고 **두 리뷰가 서로 다른 코드를 봤을 수 있다.**
그 라운드는 무효다 — 게시하지 말고 3.1 head 읽기 부터 다시 진행한다. 다른 조건 하나는
3.2 두 리뷰를 실행한다 에 있다(한 리뷰가 `!!` 로 멈춤).
**사람이 지시해서 움직인 경우는 아니다** — 3.1 의 「사람이 라운드 도중에 지시하면」대로
그대로 게시하고
「리뷰 뒤에 한 것」에 적는다.

두 리뷰가 적은 `리뷰한 head:` 가 3.1 head 읽기 의 값과 다른 경우도 같다. 그 줄은 이 대조의
교차 확인이지, 그 자체가 판정은 아니다.

### 3.4 코멘트 하나로 게시한다

두 리뷰 다 게시하지 않고 돌려주므로 올리는 것은 여기 한 자리다. 인라인 `--body` 를 쓰지 마라 —
백틱·따옴표가 든 리뷰를 셸이 깨뜨린다.

    gh pr comment <N> --body-file <절대 경로>

**이 한 줄로만 입력한다.** 다른 명령과 잇거나(`&&` · `;` · `if … then` · 줄바꿈) 주석 ·
리다이렉트 · 래퍼를 붙이면, PR 을 번호 말고 URL 로 적거나 상대 경로를 전달하면 아래 훅이
게시인지 가리지 않고 막는다. 게시를 가려 막으려 하면 우회가 늘어서 훅이 이 모양만 받는다.
`\` 줄넘김은 된다. 훅은 명령 글자 어디에든 이 명령이 보이면 그 명령 전체가 이 모양인지
검사한다. 그 글자가 든 검색이나 heredoc 도 막힌다. 찾을 때는 `pr comment` 로 찾고, 초안은
`Write` 로 쓴다.

**라운드 코멘트는 사람의 승인 없이 올린다.** 아래 게시 전 확인을 통과하면 올리고, 접히지
않은 부분 전문과 링크를 3.5 의 보고에 싣는다. 사람은 그것을 읽고 다음에 할 일을 창에서 고른다.
뗀 것은 게시 전 승인이지 사람에게 보여 주는 것이 아니다.

**승인 대신 에이전트 훅이 `(사람)` 인용을 대조한다.** `.claude/hooks/round_comment_quotes.sh` 가
이 명령을 가로채, 인용이 이 PR 의 사람 계정 코멘트에 글자 그대로 없으면 막는다. 원본의 단위는 불릿
하나나 줄 하나다 — 사람 계정 코멘트는 한 줄이 결정 하나라서(3.5), 서로 다른 결정 줄의 조각을 `…` 로
이으면 막힌다. 창에서 고른 보기로 만든 코멘트든 사람이 PR 웹에서 쓴 글이든 같다. 봇 계정으로 올린 글은
원본이 아니다. 따옴표 없이 `(사람)` 라벨만 단 항목도 막는다. 대조할 인용이 없어 훅의 대조가 우회되기
때문이다. 막히면 인용을 사람 계정 코멘트에 있는 글자로 고치거나, 기록이 없는 것이면 `(사람)` 을 떼고
`셀프+` 로 올린다(「출처 다섯」의 규칙 2). **다른 도구로 올려 훅의 대조를 우회하지 마라.**
라운드 코멘트는 다음 라운드의 두 리뷰가 「지난 코멘트 정정」으로 고치는 글이고, 그 두
리뷰가 다시 판정하지 않는 것이 `(사람)` 인용 하나라서 그것을 기계가 본다. 무엇이 남는지는
`docs/process/verification-stages.md` 6.3 에 있다.

**콜드 리뷰 전문은 옮겨 적지 않는다.** 기록 훅(`.claude/hooks/review_record.sh`)이 리뷰 에이전트가 돌려준
보고를 봇 디렉터리에 `리뷰한 head:` 별로 남긴다. 「콜드 리뷰 전문」 블록에는
`bash .claude/hooks/cold_review.sh <리뷰한 head>` 의 출력을 그대로 넣는다. 같은 자리의
`.claude/hooks/round_comment_cold.sh` 가 그 블록을 그 head 의 기록과 글자로 대조해, 다르거나 기록이 없으면
막는다. 봇 설정이 없으면 기록이 없어 라운드 코멘트를 막는다.

**설치된 레포에서는 권한 프롬프트가 한 번 표시된다.** `gh pr comment` 는 `ask` 에 있고, 훅이
통과시켜도 `ask` 는 남는다. 프롬프트에 보이는 것은 `--body-file` 의 경로뿐이라 그것은
초안의 승인이 아니다. 라운드 코멘트와 `merge-pr` 의 결정 코멘트가 같은 명령으로 올라가서 규칙으로 둘을
구분하지 못하므로 `ask` 를 그대로 둔다. 이유는 `docs/process/verification-stages.md` 6.3 에 있다.

**게시하기 전에 같은 head 의 라운드 코멘트가 이미 있는지 본다. `0` 이 나올 때만 게시한다.**
그 밖이면 게시하지 말고 사람에게 보고한다 — 3.6 의 5와 같은 이유로 **빈 출력은 통과가 아니다**:

    gh pr view <N> --json comments \
      --jq '[.comments[].body|select(test("^\\s*## 리뷰 "))
             |(split("\n")|map(select(startswith("리뷰한 head: ")))|.[0] // "")]
            |map(select(contains("<3.1 에서 읽은 head>")))|length'

**head 를 필터 안에 직접 넣는다.** `gh pr view --jq` 는 필터 하나만 받아서 jq 의 `--arg` 를
전달할 수 없다 — `accepts at most 1 arg(s)` 로 실패한다. `// ""` 는 `리뷰한 head: ` 줄이 없는
코멘트에서 `.[0]` 이 `null` 을 내 검사가 오류로 멈추는 것을 막는다(3.6 의 5와 같다).

**head 는 `리뷰한 head: ` 로 시작하는 첫 줄에서 읽는다.** 한때 코멘트의 셋째 줄로 읽어, 제목과
head 줄 사이에 줄이 끼거나 제목 바로 뒤에 head 줄이 오면 head 를 못 찾았다. 접힌 리뷰 전문에도 같은
줄이 있지만 맨 위의 것이 먼저 나온다.

**같은 자리에서 `—` 도 본다.** 아래 「기호 — 역할 하나씩」이 불릿 줄과 그 이어짐에 금지한
것이고, **사람이 매 라운드 손으로 확인하던 것**이다. 출력이 나오면 게시하지 말고 고친다:

    sed '/^<details>/,$d' <코멘트 파일> | awk '
      { isb = ($0 ~ /^[[:space:]]*([-*][[:space:]]|→)/) }
      /^[[:space:]]*$/ { inb = 0; next }
      isb { inb = 1; hum = ($0 ~ /\(사람[^)]*\) "/) }
      !isb && $0 !~ /^[[:space:]]/ { inb = 0 }
      inb && !hum && /—/ { print NR ": " $0 }'

무엇을 보고 무엇을 빼나:

- **접히지 않는 부분만 본다**(`sed` 가 첫 `<details>` 부터 지운다). 두 리뷰 전문은 그대로
  싣는 것이라 고칠 수 없다. 전문까지 보면 3라운드 코멘트에서 고칠 줄이 0 인데 25줄이 검사 결과에 나왔다.
- **불릿의 이어짐 줄까지 본다.** 불릿 다음의 들여쓴 줄은 빈 줄이나 들여쓰지 않은 줄이
  나올 때까지 그 불릿이다. 첫 줄만 보는 `grep` 은 100자 안팎에서 줄이 바뀐 둘째 줄을 못 봤고,
  **그것이 가장 흔한 모양이었다.** 킷 레포의 한 PR 의 1·2라운드 코멘트에서 첫 줄 검사는
  13줄, 이것은 37줄을 찾아냈다.
- **사람 인용은 뺀다. 여러 줄로 이어져도 뺀다.** `(사람) "`·`(사람, N라운드부터) "` 로
  시작한 불릿은 다음 불릿이나 `→` 줄이 나올 때까지 인용이다. 낱말을 안 바꾸는 규칙이
  우선한다(「출처 다섯」 규칙 1). **그 뒤의 `→` 줄은 이쪽 판단이라 다시 본다.**
- **`*` 뒤에 공백을 요구한다.** `**볼드**` 로 시작하는 산문 줄을 불릿으로 오인하지 않게.

**실제로 올라간 코멘트의 줄 모양을 넣어 이 검사가 제대로 찾는지 확인했다.** 처음 판은 작성자가
떠올린 경우 열셋만 시험했고, 줄이 바뀐 이어짐 줄이 그 목록에 없었다(사람이 실행해서 찾았다). 지금 판은 킷 레포의
PR 둘에 올라간 코멘트 서른하나에 실행했고, 거기서 나온 모양으로 입력 열일곱 개를 만들어
다시 확인했다. 찾는 것: 불릿 · `→` · 줄이 바뀐 `→` 의 둘째 줄 · 줄이 바뀐 불릿의 둘째 줄 ·
사람 인용 뒤 `→` · 「사람」이라는 낱말만 든 불릿 · 판정 인용 뒤 `→`. 찾지 않는 것: 제목 줄 ·
볼드 산문 · 줄이 바뀐 사람 인용의 둘째 줄 · 이월 표기 사람 인용 · 판정 및 근거의 사람 인용 ·
볼드도 불릿도 아닌 산문 · 표 · `---` · 빈 줄 뒤 들여쓴 코드 · `<details>` 안 불릿.

**규칙으로는 안 막힌다.** 「같은 것을 두 번 올리지 마라」를 읽을 세션이 **자기가 이미
올렸다는 것을 모르는** 경우가 이 중복을 만든다(되감긴 세션 · 승인 프롬프트가 실패로 보인
경우). 그래서 규칙이 아니라 **게시 전 확인**이다.

**두 벌이 되면 그 사이에 사람이 정한 것이 사라진다.** 앵커는 `## 리뷰 ` 로 시작하는 **마지막**
코멘트이고 두 리뷰가 받는 범위는 그 뒤이므로, 한 벌 더 붙으면 앞의 사람 계정 코멘트가 그 범위에서 빠진다. 두
리뷰는 그것을 **「사람이 아직 정하지 않았다」와 구분하지 못한다.** 실제로 그렇게 됐다. 세션이 되감겼다 다시
진행하면서 라운드 코멘트가 두 벌 올라갔고, 그때 PR 에 있던 사람의 결정 셋 중 두 리뷰에 실린 것은 하나도 없었다.

**아래 「라운드 코멘트 형식」대로 쓴다.**

**발견을 다 반영하지 마라. 1라운드부터다.** 콜드는 깨는 방법을 만들어내므로 지어낸 형태와
실제로 생길 형태가 같은 무게로 온다. *평범한 편집에서 생기나 · 막는 비용이 코드와 오탐을 늘리지
않나 · 적대자가 있나* 를 **콜드가 낸 항목마다** 묻고, **안 하는 쪽을 제안하는 것은 비추천
바구니에 이유와 함께 올린다.** 다 반영하다 검사가 그것이 막은 사고보다 길어지고 오탐 셋이
새로 생긴 적이 있다. 근거는 `docs/process/verification-stages.md` 3.6.

### 3.5 멈추고 사람에게 보고한다

> **주의 — 킷은 봇과 함께 쓴다.** 레포에 봇 설정(`.claude/bot.json`)이 없으면 세션과 사람이 한 계정이라
> 글쓴이로 사람의 글을 가려낼 수 없다. 그래서 창 기록 훅과 `human_comment.sh` 가 동작하지 않아 사람의 결정이
> 사람 계정 코멘트로 남지 않고, `(사람)` 인용을 확인하는 훅은 그 인용이 든 라운드 코멘트(3.4)를 막는다. **리뷰 라운드와
> 머지도 끝까지 가지 못한다** — 3.6 의 5 가 늘 `0` 을 내 푸시하지 못하고, 머지 전에 보는 같은 셈도 `0` 이며,
> `merge-pr` 2절은 사람의 Approve 를 판정하지 못해 멈춘다. 봇을 켜는 법은 `docs/process/kit-guide.md` 의
> 「봇 계정과 사람의 승인」 절에 있다.

다음 라운드를 진행하는 것도, 머지하는 것도 **사람이 정한다.** 보고는 **올린 라운드 코멘트의
접히지 않은 부분 전문과 링크**다(3.4). `<details>` 앞을 전부 그대로 싣는다. 요약하지 않는다.
사람은 브라우저를 열어 코멘트를 읽지 않는다. 링크만 주면 사람은 무엇이 올라갔는지 모른 채
다음 할 일을 고른다.

몇 라운드째인지 · 두 리뷰의 `Verdict` · 바구니별 발견 · 다음에 무엇을 할지 한 줄은 그 안에
이미 있으므로 **보고에 따로 다시 쓰지 않는다.** 두 자리에 따로 쓰면 어긋나고, 사람은 어느 쪽을 보고
정해야 할지 모른다.

그리고 **창으로 묻는다.** 머리말은 「N라운드 코멘트」다 — 킷이 그 코멘트를 부르는 이름이고, 보기의
「제안대로」가 가리키는 제안이 그 코멘트에 있다. 보기의 예는 「제안대로 고치고 N+1라운드」 · 「제안대로
고치고 머지」 · 「고치지 않고 멈춘다」이고, **「PR 웹에 쓴다」를 늘 둔다**(아래). 결정 필요 항목이 있으면 항목마다
질문을 하나 더 두고, 머리말은 그 질문이 정하는 것을 가리키는 명사로 짓는다. 「답」 · 「질문」은 머리말로 쓰지
않는다. **질문에는 「이 결정은 사람 계정으로 PR #N 에 그대로 올라간다」를 적는다.** 그 글자가 있는 창만
기록된다(아래).

**고른 것은 사람 계정으로 올린다.** 이번 head 의 라운드 코멘트가 올라가 있으면 곧바로 올리고, 라운드 도중에
받은 결정이면 라운드 코멘트를 올린 뒤에 올린다(3.1) — 먼저 올리면 앵커 앞에 놓여 다음 라운드의 두 리뷰가 못
본다. 창이 끝나면 Claude Code 가 PostToolUse 훅
(`.claude/hooks/window_record.sh`)을 실행하고, 그 훅이 고른 보기로 `- <머리말>: <보기>` 줄을 만들어 봇
디렉터리에 적는다. 세션은 그 디렉터리를 읽지도 쓰지도 못하고, 봇 설정이 있는 레포 안에서 창 기록 훅을 직접
실행하는 명령도 막기 훅이 막는다. 올리는 명령은 이것 하나이고, 레포 루트에서 한 줄로만 입력한다(다른 명령과 잇거나 하위 디렉터리에서
입력하면 막기 훅이 막는다. 창 기록 훅의 안내와 막기 훅의 거절 사유가 레포 루트로 옮기라고 적는다):

    bash .claude/hooks/human_comment.sh <N>

그 PR 의 아직 올리지 않은 기록을 창이 끝난 차례대로 한 코멘트에 모아 사람 계정으로 올린다. 세션은 글을
쓰지 않는다 — 초안도 sha256 도 없고, 설치되는 `settings.json` 이 레포 루트에서 입력한 이 명령을 허용해 권한
프롬프트도 없다. 창에서
고른 것이 곧 게시 동의이고, 질문에 적은
글자가 그것을 사람에게 알린다. 기록은 봇 디렉터리에 남으므로 창과 게시 사이에 컴팩션이 일어나도 사라지지
않는다. 이 코멘트를 아래에서 **사람 계정 코멘트**라 부른다. **GitHub 의 PR 이슈 코멘트에는 스레드가
없다** — 뒤에 붙는 또 하나의 코멘트일 뿐이다.

- **보기 대신 직접 쓴 말**(보기 대신 창에 쓴 것 · 보기에 단 메모 · 대화로 한 말)은 그대로 올리지 않는다. 답을
  비운 질문도 올리지 않는다 — 같은 머리말의 창으로 다시 묻는다. 창 기록
  훅은 그 질문을 줄로 적지 않고, 스크립트는 그런 기록이 있으면 올리지 않고 까닭을 낸다. 아래 「출처 다섯」의
  규칙 1 대로 결정이 담긴 이어진 한 구간을 글자 그대로 보기로 만든 창을 다시 띄우고, 고른 구간을 올린다. 그런
  구간이 없으면 세션이 요지를 결정 하나씩 짧게 적은 보기로 만든 창을 띄운다 — 보기 이름이 곧 사람 계정
  코멘트의 줄이라, 두 리뷰와 `merge-pr` 이 글쓴이로 거른 뒤에도 요지가 남는다. 맞는 보기가 없으면 사람은 다시
  직접 쓰고, 세션은 보기를 고쳐 다시 묻는다. **다시 띄우는 창은 처음 창과 머리말이 같다** — 스크립트는 같은
  머리말의 줄이 뒤에 기록되어야 그 직접 쓴 말을 정해진 것으로 보고, 그때 쌓인 기록을 모두 올린다. 머리말이
  다르면 그 PR 의 사람 계정 코멘트가 계속 올라가지 않는다. 사람이 자리를 비워 저절로 닫힌 창과 질문을 더
  요청하며 닫은 창은 기록되지 않으므로, 같은 창을 다시 띄운다.
- **사람이 PR 웹에서 직접 쓴 코멘트도 사람 계정 코멘트다.** 두 리뷰와 `merge-pr` 은 봇이 올린 라운드
  코멘트 뒤의 사람 계정 코멘트를 사람의 결정으로 읽는다(아래). 사람이 「PR 웹에 쓴다」를 고르면 그 줄도
  올린 뒤, 머리말 「PR 웹 코멘트」 창을 띄운다 — 질문은 「PR #N 에 결정을 쓰셨나요?」, 보기는 「PR 웹에 썼다」 ·
  「창으로 정한다」이고 게시 표지는 적지 않는다. 「PR 웹에 썼다」를 고르면 라운드 코멘트 뒤의 사람 계정 코멘트를
  읽고, 「창으로 정한다」를 고르면 「N라운드 코멘트」 창을 다시 띄운다. 사람은 다 쓴 것을 글자로 입력해 알리지
  않고 이 창에서 고른다.
- **창을 닫은 뒤 창 기록 훅의 안내(「…줄을 기록했다」 · 「보기로 정하지 않은 질문」 · 「…기록하지 않았다」 가운데
  하나)가 오지 않았으면** 먼저
  질문의 게시 표지가 글자 그대로인지 본다. 틀렸으면(띄어쓰기 · 존댓말로 바꾼 것) 표지를 고쳐 같은 창을 다시
  띄운다. 표지가 맞는데도 안내가 없으면 창 기록 훅이 실행되지 않은 것이다(세션이 시작된 뒤 훅 등록이 바뀌었거나
  `python3` 이 없다). 그때는 같은 창을 다시 띄우지 않는다 — 그 창도 기록되지 않는다. 대신 PR 링크와 쓸 글(그
  창의 머리말과 고른 보기)을 적어 PR 웹에 써 달라고 요청하고, 「PR 웹 코멘트」 창을 보기 「PR 웹에 썼다」 ·
  「멈춘다」로 띄운다. `human_comment.sh` 가 「모두 올렸다」로 끝나면 그 PR 의 기록은 모두 올라갔다는 뜻이지, 이번
  창의 결정이 올라갔다는 뜻은 아니다. 3.6 의 5 명령으로 본다 — `1` 이상이면 이번 결정은 이미 올라간 것이라 다시
  받지 않고, `0` 이면 이번 창이 기록되지 않은 것이라 위처럼 게시 표지부터 본다.

세션은 사람 계정 코멘트를 읽고 정해진 대로 한 라운드 더 진행하거나 머지 단계를 시작한다. 무엇을 어떻게 고칠지 ·
커밋 SHA 같은 해석은 사람 계정 코멘트에 적지 않고, 다음 라운드 코멘트의 「N라운드 정리」의 「판정 및 근거」에
`(사람)` 인용과 함께 적는다. 사람 계정 코멘트가 무엇인지는 `.claude/hooks/human_review.sh` 머리에 있다.

**원 라운드 코멘트는 고치지 않는다.** 뒤에 코멘트를 달아서가 아니라 **그것이 그 라운드의
기록이기 때문**이다 — 고치면 무엇이 언제 정해졌는지가 사라진다.

**사람 계정 코멘트는 세션이 고치지 않는다.** 글쓴이가 아닌 계정이 마지막으로 고친 코멘트는 원본에서
빠진다. 틀린 결정이 올라갔으면 사람이 PR 웹에서 고치거나, 창으로 다시 정해 새 코멘트로 올린다 — 새
코멘트는 앞의 것 뒤에 붙으므로 두 리뷰는 둘을 차례대로 읽는다.

**형식** — 사람 계정 코멘트에는 `- <주제>: <고른 보기>` 줄만 있다. 주제는 창 머리말이고, 질문이 여럿이면
줄도 여럿이다. 여러 보기를 고를 수 있는 질문은 고른 보기를 ` · ` 로 잇는다. 제목 · 안내 문장 · `(사람)` 라벨 ·
`→` 줄 · `---` 는 없다. 보기에 세션이 붙인 추천 표시(「(추천)」 · `(Recommended)`)는 훅이 뗀다 — 사람이 한
말이 아니다.

```markdown
- 1라운드 코멘트: 제안대로 고치고 2라운드
- 끝낼 이슈: #77 도 이 PR 로 끝낸다
```

**`사람` 라벨은 다음 라운드 코멘트에서 처음 붙는다.** 그 코멘트의 「판정 및 근거」 같은 자리가 사람 계정
코멘트의 줄을 `(사람) "…"` 로 인용한다 — 보기 글자만 옮겨도, 줄 전체를 옮겨도 된다. 「라운드 코멘트 형식」의
「`사람` 은 분류 라벨이 아니라 검증 우회 통로다」 셋이 여기서부터 적용되고, 훅이 사람 계정 코멘트와
대조한다(3.4).

**사람 계정 코멘트가 다음 라운드의 두 리뷰와 `merge-pr` 에 전달되는 것은 둘에 달려 있다.**

- **첫 줄이 `## 리뷰 ` 로 시작하지 않는다.** 그 문자열이 **라운드 코멘트를 고르는 유일한
  표시**다 — `merge-pr` 이 그것으로 마지막 라운드 코멘트를 골라 `리뷰한 head:` 를 서버
  head 와 대조하고, **두 리뷰의 주입도 그것을 앵커로 삼는다.** `- ` 로 시작하는 줄만 있으므로 그럴 일이
  없다. 사람이 PR 웹에서 쓸 때만 이 글자로 시작하지 않게 한다. 한때 앵커가 `리뷰한 head:` 라는 **본문
  어디에나 나올 수 있는 부분 문자열**이었고, 사람의 글이 그 글자를 인용하면 앵커가 그 코멘트로 옮겨가
  **직전 라운드 코멘트가 통째로 안 실렸다**(재현함).
- **고르는 곳은 글쓴이로 고른다.** 두 리뷰와 `merge-pr` 은 봇이 올린 라운드 코멘트 뒤의 사람 계정
  (`authorAssociation` 이 OWNER · MEMBER · COLLABORATOR) 코멘트를 사람의 결정으로 고른다. 위치로 고르면
  제3자 코멘트와 `merge-pr` 자신의 결정 코멘트가 같이 선택된다. 봇 설정이 없어 라운드 코멘트가 사람
  계정이면 아무것도 고르지 않는다(이 절 머리의 주의).

**1이 여기 있는 이유.** 그 지시는 3.5 의 산문에만 있었고 이 목록에는 없었다. 순서대로
따라가는 세션은 그것을 **반드시** 빠뜨린다. 한 PR 에서 두 라운드 연속으로 빠졌고, 두 번 다
그다음 라운드의 두 리뷰가 사람이 정한 것을 못 본 채 진행됐다.

**5가 있는 이유. 1을 목록에 넣는 것으로는 지켜지지 않았다.** 1을 넣은 바로 그 커밋이 1을 건너뛰고
푸시됐다. 목록 항목은 읽고 지나칠 수 있지만 **명령은 출력을 읽어야 다음 단계를 진행할 수 있다.** 이 킷에서
목록에 적은 것이 지켜지지 않은 적이 넷(게시 전 승인 · `—` 금지 · 로컬 브랜치 삭제 · 이 순서)이고,
지켜진 것은 전부 명령이었다(3.4 의 같은 head 확인 · `—` 검사).

**`1` 이상일 때만 푸시하는 이유.** gh 가 실패하면(네트워크 · 만료된 인증) 이 명령은 `0` 을
안 낸다. **아무것도 안 낸다**(`rc=1`). 「`0` 이면 멈춘다」로 적으면 빈 출력이 그 조건을
빠져나가 푸시된다. 판정 못 한 것을 통과로 처리하지 않는다.

5의 명령은 **이번 head 의 라운드 코멘트**를 앵커로 삼는다. `리뷰한 head:` 줄이 3.1 에서 읽은
값인 코멘트를 고르고, 그 코멘트를 봇이 올렸으면 그 뒤의 사람 계정 코멘트가 몇 개인가를 센다. 정상
경로에서 그 코멘트는 마지막 `## 리뷰 ` 코멘트이기도 해서 **다음 라운드의 두 리뷰가 받는 범위와 같다.**
그래서 `0` 은 곧 「이번 라운드의 코멘트가 안 올라갔거나, 올라갔어도 그 뒤에 사람 계정 코멘트가
없다」이다.

**앵커를 head 로 좁힌 이유.** 한때 마지막 `## 리뷰 ` 코멘트를 앵커로 썼다. 게시를 사람의 승인
뒤에 하게 되면서 **이번 라운드의 코멘트가 안 올라간 채 이 단계를 진행할 수 있게 됐고**, 그러면 앵커가
직전 라운드 코멘트에 머물러 **직전 라운드 뒤의 결정을 세어 통과했다.** 라운드 코멘트가 아예 없을
때도 통과했다 — 앵커가 없으면 `$i` 가 `null` 이고 jq 에서 `null + 1` 은 `1` 이라 첫 코멘트
뒤부터 셌다. `// ""` 는 `리뷰한 head: ` 줄이 없는 코멘트에서 `.[0]` 이 `null` 을 내 검사가 오류로
멈추는 것을 막는다. 셋 다 재현하고 고친 뒤 다시 확인했다. head 는 3.4 의 게시 전 확인과 같은
방법으로 읽는다.

5 의 명령에 코멘트 모양들을 넣어 확인했다. 봇의 라운드 코멘트 뒤에 사람 계정
코멘트가 있다 `1` · 사람이 PR 웹에서 쓴 코멘트가 있다 `1` 은 통과하고, 이번 라운드 코멘트뿐 · 사람 계정
코멘트가 라운드 코멘트보다 앞 · `리뷰한 head: ` 줄이 없는 라운드 코멘트 · 접힌 전문의 head 로 고른 앵커 ·
봇의 라운드 코멘트 뒤에 봇의 다른 코멘트(옛 제목의 글 포함)나 OWNER · MEMBER · COLLABORATOR 가 아닌 사람의
코멘트뿐 · 사람 계정의 라운드 코멘트(봇 설정 없음) 뒤의 코멘트뿐은 `0` 이다.

**고친 자리만 보면 반쯤 고친 것이 그대로 나간다.** 수정 하나마다 아래를 찾아 열어 보고,
안 고쳐도 되겠으면 **왜 그런지 말할 수 있어야 한다.**

| 무엇을 고쳤나 | 무엇이 어긋나게 됐을 수 있나 |
| --- | --- |
| 이름·문자열 | 옛 이름을 아직 쓰는 자리. 코드만이 아니라 그것을 적어둔 글까지 |
| 코드 | 그 코드를 부르는 쪽과 감싸는 쪽. 그 코드가 무엇을 한다고 적어둔 글 |
| 규칙 | 그 규칙을 실제로 쓰는 자리. **정의만 고치면 쓰는 자리가 정의와 어긋난다** |
| 파일 이름·경로 | 그것을 가리키는 모든 곳. 설치되는 파일 안까지 |

**찾는 일을 리뷰에 맡기면 그 발견이 다음 라운드가 된다.** 한 라운드의 필수 여덟 중 넷이 그렇게 나왔다.

푸시를 빠뜨리면 다음 라운드가 옛 head 를 다시 읽는다. **머지 단계까지 진행하면 `merge-pr` 2절이
찾아낸다** — 로컬 브랜치의 팁이 서버 head 와 글자로 다르면 머지 전에 멈춘다.
다만 그것은 마지막 확인이고, 그 사이 라운드들은 옛 코드를 본 채로 다 진행된 뒤다.

그리고 다음 라운드 코멘트를 쓸 때 **사람 계정 코멘트를 아래 「사람이 정한 것을 적는 자리」대로 옮긴다.**

**머지하거나 PR 을 닫기로 했으면 라운드는 없다.** 그래도 창에서 정한 것은 1 처럼 사람 계정 코멘트로
올린다. 그것이 기록이고, `merge-pr` 이 2절에서 **마지막 라운드 코멘트 뒤의 코멘트까지 읽어** 3절의
결정 코멘트로 옮긴다. **`merge-pr` 을 실행하기 전에 5 의 명령이 `1` 이상인지 본다.** 안 올린 채
`merge-pr` 을 실행하면 그 스킬의 2절이 마지막 라운드 코멘트 뒤의 코멘트를 읽을 때 오류 없이 빈 문자열을
받고, 결정 코멘트에서 사람이 정한 것이 알림 없이 빠진다.

**머지하기로 한 쪽은 `merge-pr` 전에 `dev-log <N>` 을 실행한다.** 번호를 전달해야 그 스킬이 PR 본문의
`Closes #N` 을 본다. 그 스킬이 이 PR 의 dev-log 항목을 만들고, `merge-pr` 2절이 서버 head 에
그 항목이 있는지 본다. PR 을 닫는 쪽은 아니다.

**마지막 라운드 뒤에 사람이 이 PR 로 이슈를 끝내기로 정했으면 `dev-log` 전에 사람 계정 코멘트를
하나 더 올린다.** 그 결정을 창(머리말 「끝낼 이슈」)으로 받아 1 처럼 올린다. `dev-log` 는 그 코멘트를 보고
계획 줄을 지우고, `merge-pr` 은 그 코멘트에서 닫을 이슈를 고른다(2절 「본문 작성 규칙」).

**본문은 손대지 마라.** 라운드가 만든 것은 코멘트에 쌓이고, 최종 정리는 `merge-pr` 이 머지
직전에 코멘트 하나로 올린다. 근거는 `docs/process/verification-stages.md` 4.

> **왜 멈추나.** 한 프로젝트에서 이 자리가 비어 있어 라운드가 **사람 승인 없이 20회** 진행됐다.
> 설정 파일 한 개를 옮기는 작업이었고, 실제 변경은 여섯 번째 커밋에서 끝났으며 나머지
> 18커밋은 그 변경을 *설명하는 문장*을 고치는 것이었다. 코멘트 40건. 그때 스킬에 적혀 있던
> 것은 "3단계로 돌아와 다시 돌린다" 한 줄이었고 멈추라는 말이 없었다.
>
> **라운드 수에 상한을 두지 않는다.** 진짜로 고칠 것이 계속 나오면 여러 번 진행해야 한다.
> 사람이 정하기만 하면 된다.

## 라운드 코멘트 형식

**접히지 않은 부분이 화면 한 장을 넘으면 안 된다** — 한 장을 넘는 부분은 아무도 안 읽는다.
실제로 안 읽혔다.

### 템플릿

```markdown

리뷰한 head: <3.1 head 읽기 에서 적어둔 40자 그대로>

**리뷰 뒤에 한 것**
<두 리뷰가 실행된 뒤 사람이 지시해서 한 것. 없으면 절을 생략한다.>
- 사람이 라운드 도중에 지시한 것을 한 줄로. `(사람)` 라벨도 따옴표도 안 쓴다
  → 무엇을 했나. `<SHA>`

**밀린 결정**
<같은 항목이 세 번째 라운드에도 `미해결` · `일부 해결` 로 오른 것. 발견이 아니라 사람이 정할 일이라 바구니에서는 「결정 필요」로 옮긴다. 없으면 절을 생략한다.>

<앞선 라운드 코멘트에 거짓이 있었으면 여기 적는다. 없으면 절을 생략한다.>
- 1라운드 "게이트를 실행해 통과를 봤다"

### 2라운드 발견
```

**1라운드에는 정리할 앞 라운드가 없다.** `### 1라운드 정리` 와 그 아래 절(집계 · 지난 코멘트
정정 · 판정 및 근거 · 리뷰 간 이견 조정)을 쓰지 않고, 소제목은 `### 1라운드 발견` 하나다. 위
템플릿은 2라운드의 예다.

### 규칙

**불릿 뼈대.**

    - [판정] (출처[, N라운드부터]) 내용
      → 판단

- **첫 값은 왼쪽 끝에 온다.** 어느 절에 무엇이 오는지는 **아래 표가 정한다.** 뒤에 두면
  문장 길이가 제각각이라 왼쪽 끝을 훑어 읽을 수 없다.
- **`→` 는 둘째 줄 맨 앞.** 들여쓰기를 늘리지 마라 — 한 번 더 들여쓴 불릿은 「하위 항목」으로 읽히는데
  이건 같은 항목의 이어짐이다.
- **`→` 가 있는 항목은 그 앞을 따옴표로 감싼다.** 따옴표 안이 「그쪽이 한 말」,
  화살표 뒤가 「이쪽 판단」이다. `→` 가 없으면 따옴표도 없다 — **`(사람)` 항목만 예외다.**
  거꾸로 「리뷰 뒤에 한 것」은 `→` 가 있어도 따옴표가 없고 `(사람)` 라벨도 없다. 거기 적는
  지시는 라운드 코멘트 뒤에야 사람 계정 코멘트로 올라가므로 훅이 대조할 원본이 아직 없고, 훅은 따옴표
  없는 `(사람)` 라벨을 막는다(3.4). 그 지시는 창으로 받아 사람 계정 코멘트로 올린다(3.5).
- **`→` 를 쓰는 절도 아래 표가 정한다.** 표에서 `→` 가 없는 절에는 부연을 달지 마라. 항목
  문장이 이미 말한다.
  **`(사람)` 항목은 다르다** — 따옴표에 사람이 쓴 문장을 그대로 넣는다. 부연이 아니라
  **사람이 초안에서 대조할 재료**이고, `사람` 은 재판정을 안 거치는 유일한 출처라
  그 재료가 없으면 대조해 확인할 것이 없다. 측정값이나
  명령 출력은 **리뷰 전문이나 `docs/dev-log.md`** 에 적는다 — 바구니 항목에 들어갈 것이
  아니다.
- **필수 항목은 무엇이 틀렸는지 한 문장으로 쓴다.** 재현과 근거는 리뷰 전문에 두고, 고칠 방향은
  「맨 아래 한 줄」의 볼드 뒤에 필수마다 짧게 적는다(아래). 필수에는 `→` 가 없어서, 고칠 방법과
  근거까지 항목 문장에 넣으면 항목이 길어진다.

| 절 | 첫 값 | 따옴표 | `→` |
| --- | --- | --- | --- |
| 리뷰 뒤에 한 것 | 지시한 것(출처 라벨 없음) | 없음 | 있음 |
| 밀린 결정 | 출처(`N라운드부터`) | `(사람)` 만 있음 | 없음 |
| 집계 | `- [셀프]` | 없음 | 없음 |
| 지난 코멘트 정정 | 라운드 번호 | 있음 | 있음 |
| 판정 및 근거 | 판정 → 출처 | 있음 | 있음 |
| 리뷰 간 이견 조정 | 결론(출처 없음) | 있음 | 있음 |
| 필수 | 출처 | `(사람)` 만 있음 | 없음 |
| 비추천 | 출처 | 있음 | 있음 |
| 결정 필요 | `*nit*` 있으면 그것, 없으면 출처 | `(사람)` 만 있음 | 없음 |

**「리뷰 뒤에 한 것」은 `리뷰한 head:` 바로 아래에 둔다.** 두 리뷰가 실행된 뒤 사람이
지시해서 한 것을 적는 자리다 — 읽는 사람이 **그 head 가 왜 서버 head 와 다른지**를 거기서
안다. 근거는 3.1 의 「사람이 라운드 도중에 지시하면」. 없으면 절을 생략한다.

**「밀린 결정」은 「리뷰 뒤에 한 것」 아래, 첫 소제목(`###`) 위에 둔다.** 같은 항목이 세 번째
라운드에도 `미해결` · `일부 해결` 로 오르면 그것은 발견이 아니라 결정이 미뤄진 것이다
(`docs/process/verification-stages.md` 3.7). 사람이 코멘트에서 가장 먼저 읽는 자리에 둔다.
그 항목은 바구니에서 「필수」에 두지 않고 「결정 필요」로 옮겨 이월 표기와 함께 올린다. 없으면
절을 생략한다.

**「지난 코멘트 정정」은 두 리뷰가 낸 같은 이름의 절에서 옮겨 온다.** 「집계」 바로 아래에 둔다. 라운드 코멘트는 안 고치는 것이 규칙이라
(그것이 그 라운드의 기록이다), **거짓이 발견돼도 그 자리에서 지울 수 없다.** 안 적으면 다음
라운드의 두 리뷰가 그 거짓을 그대로 읽는다. 두 리뷰 출력의 `### 본문이 틀린 곳` 과 **하는 일이
나뉜다**(자리가 붙어 있지는 않다) — 저쪽은 PR 본문에서 지금 틀린 곳을 적고, 이쪽은 앞선 라운드
코멘트의 거짓을 적는다. **무엇이 거짓이었고 실제로 확인한 것이 무엇인지**를 적는다. 없으면 절을
생략한다. **본문이 틀린 곳은 바구니에 올리지 않는다.** 본문은 고치지 않으므로 고칠 항목이 아니고,
`merge-pr` 이 두 리뷰 전문에서 모아 결정 코멘트로 옮긴다.

**「집계」에서 그 리뷰가 판정하지 않은 항목은 `미판정:N` 으로 적는다.** 안 적으면 두 줄의
합이 다른 이유를 읽는 사람이 못 짚는다.

**「리뷰 간 이견 조정」만 출처 자리에 결론이 온다** — 두 리뷰의 판정이 다른 것이므로 출처가 둘이라
앞에 못 붙는다. 두 판정은 둘째 줄에 리뷰 이름 옆 괄호로 적는다.

**섹션과 급.** `##` 코멘트 제목 · `###` 라운드 · `**볼드**` 절과 바구니.
**바구니를 `###` 로 올리지 마라** — `**비추천** 없음.` 처럼 한 줄로 끝나는 바구니를 헤딩으로
쓸 수 없고(내용이 헤딩과 앵커에 들어간다), `###` 이 다섯이면 여백 때문에 「화면 한 장」에
불리하다. 라운드 헤딩에는 **번호를 붙인다**(`### 1라운드 정리` · `### 2라운드 발견`) — 번호
없이 쓰면 이전 코멘트와 나란히 놓였을 때 어느 라운드 것인지 안 보인다.
**구분선은 맨 아래 한 줄 앞뒤에만** 쓴다. 라운드를 나누는 것은 `###` 이다.

**바구니 셋** — 필수 · 비추천 · 결정 필요. 「이래도 그만 저래도 그만」인 것은 `*nit*` 을
문장 맨 앞에 붙이고 결정 필요에 넣는다. **`*nit*` 은 결정 필요에만 쓴다** — 사소한데 꼭
고쳐야 한다는 것은 성립하지 않는다.
**바구니 머리에 수를 적지 마라** — 아래 목록이 그 수의 출처인데 항목을 지울 때 머리가 안
따라온다. 빈 바구니는 `**비추천** 없음.` 이고 `—` 를 쓰지 않는다.

**위 예시의 여덟 건을 어느 절에 적나** — 집계의 수와 아래 절들이 서로를 설명해야 한다.
리뷰가 낸 해결 셋은 집계에만(사람 지시였으면 「판정 및 근거」에 적는다) · `기각` 하나는 「판정 및 근거」에서 닫히고 · `일부 해결` 「빈 범위 경고」와
`미해결` 「빈 범위 통과」와 `결정 필요` 「언어 선택을 물을지」는 바구니에 이월 표기로 ·
판정이 다른 「훅 대조」는 「이견 조정」에만 적고 바구니에는 오른다. 셀프가 「언어 선택을 물을지」를
안 올려 `미판정:1` 이고, 그래서 두 줄의 판정어 구성은 다르지만 **합은 각각 8이다.**

**판정어 다섯을 적는 자리.** 「집계」의 수와 「판정 및 근거」의 줄 수가 다른 것이 정상이다:

| 판정어 | 어디에 |
| --- | --- |
| 해결 | 집계에 수만. **단 사람이 지시해서 한 것은** 「판정 및 근거」에 근거와 함께 |
| 기각 | 판정 및 근거에 근거와 함께. 닫힌 것이다 |
| 일부 해결 | 판정 및 근거에 근거와 함께, **그리고** 아래 바구니에 이월 표기로 |
| 미해결 · 결정 필요 | 아래 바구니에 이월 표기로 |
| 미판정 | 집계에 수만 |

세 번째 라운드에도 `미해결` · `일부 해결` 인 항목은 「밀린 결정」에 적고, 바구니에서는 「필수」가
아니라 「결정 필요」에 둔다(위 「밀린 결정」 문단).

**두 리뷰의 판정이 다른 항목은 「리뷰 간 이견 조정」에만 적는다.** 그 절이 두 판정을 다 싣기
때문에 「판정 및 근거」에 또 적으면 같은 항목이 두 벌이 된다. **바구니에는 그대로 오른다** —
판정이 다르다는 것이 닫혔다는 뜻은 아니다.

`일부 해결` 을 두 자리에 적는 것은 **안 닫혔기 때문**이다. 근거만 적고 바구니에서 빼면
다음 라운드가 그 항목의 존재를 모르고, `docs/process/verification-stages.md` 3.7 의 두 라운드
시한도 세어지지 않는다.

**출처 다섯** — 셀프 · 콜드 · 셀프·콜드 · 셀프+ · 사람. `셀프+` 는 셀프 리뷰에 더해 그
세션이 코멘트를 쓰며 더 찾은 것이다. **두 리뷰 어느 쪽도 안 낸 것을 출처 없이 두면 읽는
사람은 출처를 빠뜨린 형식 오류로 여긴다.**

**`사람` 은 분류 라벨이 아니라 검증 우회 통로다.** 다른 넷은 바구니에 들어가 다음 라운드의
두 리뷰가 다시 본다. `사람` 만 재판정을 안 거치고 「판정 및 근거」나 「필수」에 바로 적힌다.
실제로 그 통로로 거짓 귀속이 들어와 커밋 하나를 만들고 되돌린 적이 있다 — 악의가 아니라
**압축** 때문에 생겼다. 발견과 사람 지시를 한 덩어리로 정리하면서 리뷰의 발견에 `(사람)` 라벨이 붙었고, **기계는
의도를 안 보므로 결과는 같다.** 셋을 지킨다:

1. **따옴표 안은 사람 계정 코멘트의 글자 그대로다.** 요약하지도 다듬지도 마라. 길면 잘라 쓰되 낱말을
   바꾸지 않는다. 그래야 3 처럼 기계가 맞춰 볼 수 있다. **눈으로 맞춰 보는 것만으로는 모자란다** —
   사람이 한 적 없는 말이 따옴표 안에 든 채 사람이 보고도 알아채지 못한 적이 있다. 경위는
   `docs/process/verification-stages.md` 6.3 에 있다. 그래서 사람 계정 코멘트는 세션이 쓰지 않고, 창에서
   고른 보기로만 만든다(3.5).
   **자를 때는 그 결정 하나로 좁혀지는 데까지는 남긴다.** 「고친다」처럼 사람이 정한 것에 여러 번
   나오는 말만 남기면 사람이 어느 결정인지 못 알아본다. 사람의 문장에 백틱 밖의 큰따옴표나
   `(사람)` 라벨과 같은 글자가 있으면 그 자리를 `…` 로 바꾼다(「기호」 표 아래).
   **결정과 상관없는 말은 옮기지 않는다.** 결정이 담긴 이어진 한 구간만 글자 그대로 인용하고, 앞뒤를
   잘라도 `…` 를 붙이지 않는다. 옮길 구간이 없으면 따옴표 없이 서술한다(사람이 ~하라고 했다). 기록에
   남는 모든 자리(코멘트 · PR 본문 · dev-log · 커밋 메시지)에서 그렇다.
2. **`(사람)` 은 기록이 있는 것에만 쓴다.** 기록은 **이 PR 의 사람 계정 코멘트에 남아 있는 것**뿐이고,
   훅이 그것을 대조한다(3.4). 직접 들었지만 아직 사람 계정 코멘트에 없는 말(라운드 도중의 지시)은 라운드
   코멘트에 `(사람)` 으로 옮기지 않는다. 한 일만 적고, 그 지시는 창으로 받아 사람 계정 코멘트로 올린다.
   따옴표 없이 `(사람)` 라벨만 단 항목은 훅이 막는다. 그 밖은 `셀프+` 이고, 바구니에 올라가 사람이 정해야
   닫힌다.
   **컴팩션 뒤에 사람 계정 코멘트를 다시 읽는 것은 정상 경로다** — 그 코멘트는 세션 기억보다 오래가는
   기록이다.
   **기록이 없는 항목에 `(사람)` 을 붙이면 그 항목은 리뷰도 승인도 거치지 않는다.**
3. **기계 검증은 봇 신원만으로 안 닫힌다.** 봇이 있어도 봇이 쓴 코멘트 안의 `사람` 라벨은
   여전히 자기 주장이다. 닫는 것은 **작성자와 대조의 조합**이고, 1의 「그대로 인용」이 그
   대조의 전제다. 요약해 적으면 봇이 있어도 검사를 실행할 수 없다.
   **라운드 코멘트의 인용은 훅이 사람 계정 코멘트와 대조한다(3.4).** 그 글쓴이는 GitHub 이 기록하고, 그
   글자는 사람이 창에서 고른 보기다(3.5). 그래서 그 결정이 사람 계정의 글로 GitHub 에 남아 누구나 확인할 수
   있다.

**이월** — 바구니 항목의 괄호에 `(출처, N라운드부터)`. `N` 은 **그 발견이 처음 나온 라운드**이지
이월 횟수가 아니다. 이번에 나온 것은 라운드를 안 적는다. `docs/process/verification-stages.md`
3.7 의 두 라운드 시한이 이 표기로 세어진다.

**맨 아래 한 줄** — 앞뒤로 `---`(위에 빈 줄을 둬야 앞 줄이 제목으로 안 바뀐다), **라벨 없음**,
**제안하는 다음 작업만 볼드**, 뒤따르는 필수마다의 고칠 방향과 제안의 근거는 볼드 없이, **이
줄만 존댓말**. 나머지는 규범 문서라 평서체지만 여기는 **사람에게 묻는 유일한 자리**다. `추천:` 같은
라벨을 붙이면 바구니 비추천과 짝으로 읽혀 **네 번째 바구니처럼 보인다.** 층위가 다르다 —
바구니는 항목이고 이 줄은 라운드 전체다.

**기호 — 역할 하나씩.**

| | |
| --- | --- |
| `**볼드**` | 절·바구니 이름 · 판정 · 따르는 쪽 · 맨 아래 제안하는 작업 |
| `" "` | 그쪽이 한 말. `→` 있는 항목과 **모든 `(사람)` 항목**에 쓴다. `(사람)` 은 낱말을 바꾸지 않는다 |
| `→` | 그래서 이렇게 판단했다. 둘째 줄 맨 앞 |
| `( )` | 출처와 이월 · 이견 절의 리뷰별 판정 |
| `[ ]` | 집계 줄의 리뷰 이름 |
| `:` | `라벨:수` 에만 |
| `·` | 나열 |
| `*기울임*` | `*nit*` |
| `—` | **불릿 줄과 그 이어짐에 쓰지 마라.** `-` 로 시작하는 줄에 `—` 가 있으면 두 기호가 구분되지 않는다. 산문 문단·제목·표는 겹칠 것이 없으므로 그대로 쓴다 |
| 백틱 | 코드에만 — 파일 경로·명령·설정 키·플래그. **판정어·바구니·출처는 백틱 없이 쓴다.** 예외는 제목 줄의 Verdict |

**중첩 괄호를 만들지 마라.** 세션이 쓰는 글에만 적용된다. `(사람)` 인용 안의 괄호는 사람의 글자라
그대로 둔다.

**사람의 문장에 백틱 밖의 큰따옴표나 `(사람)` 라벨과 같은 글자가 있으면
그 글자 자리를 `…` 로 바꿔 한 따옴표 안에 쓴다.** 사람 계정 코멘트에 `그건 "머지로" 해도 된다` 가
있으면 `"그건 … 머지로 … 해도 된다"` 다. 훅은 인용을 큰따옴표 짝으로 나눠 대조하고, 짝과 짝 사이는
세션의 글로 여겨 대조하지 않는다. 그 글자를 그대로 두면 사람이 따옴표로 감싼 낱말이 짝 사이에 남아
대조에서 빠지고, 짝이 안 맞는 큰따옴표나 따옴표가 뒤따르지 않는 라벨 글자가 든 항목은 막힌다.
그 글자 자리에서 `"그건" … "머지로"` 처럼 따옴표를 여럿으로 나누지도 않는다 — 훅은 따옴표마다 따로
대조해 따옴표끼리의 순서와 어느 줄에서 왔는지를 보지 않는다. 한 따옴표 안에서 `…` 로 줄인 조각은
사람 계정 코멘트의 불릿 하나(또는 줄 하나) 안에 순서대로 있어야 통과한다. 백틱 안은 훅이 가린 채
대조하므로 그대로 둔다.

**물음 셋의 답을 코멘트에 적지 마라.** 3.4 의 물음 셋(평범한 편집에서 생기나 · 비용 ·
적대자)은 **판단하는 과정**이다. 그것을 물어서 바구니를 고르는 것이고, **바구니 이름이 곧
그 답이다.**

**두 리뷰의 전문을 그대로 싣는다.** 요약하지도, 합치지도, **중복을 지우지도 않는다.**
어느 발견이 어디서 왔는지가 사라지면 두 리뷰를 나눈 이유가 사라진다.
`<details>` 는 GitHub 코멘트에서 렌더링된다 — **태그 앞뒤로 빈 줄**을 둬야 안의 마크다운이
처리된다.

**두 리뷰가 같은 것을 짚었으면 출처를 `셀프·콜드` 로 적는다.** 독립된 둘이 같은 곳을 가리킨
것은 더 강한 신호다. 겹친다고 한쪽을 지우지 마라.

**이 코멘트에 템플릿에 없는 절·칸·표기를 새로 만들었으면 그것을 발견으로 올려라.** 즉석으로
만든 것은 **그 라운드에만 있고 다음 세션은 안 한다.** 형식에 안 들어간 좋은 것은 없어진 것과
같다 — 한 라운드가 넷을 즉석으로 만들었고, 사람이 물어보지 않았으면 넷 다 사라졌다.
판정은 그다음이다. 올리지 않으면 판정할 기회조차 없다.

**바구니 셋의 뜻과 판정어 다섯과의 차이는 `docs/process/verification-stages.md` 3.5 에
있다. 뜻은 거기 있고 여기엔 쓰는 법만 적는다:**
바구니에 기각을 두지 않는다. 비추천에는 이유를 한 줄 적는다.

### 사람이 정한 것을 적는 자리

사람이 정한 것을 담는 절을 따로 만들지 마라. 적을 자리가 이미 다섯 있고 **기준은 언제 정했나**다 —
이 라운드가 진행되는 중에 정했으면 「리뷰 뒤에 한 것」이고, 그 앞 라운드 뒤에 정했으면 정한 내용과,
이 코멘트를 쓰는 시점에 그대로 고쳤는지로 정해진다. 인용은 사람 계정 코멘트의 줄을 `(사람) "…"` 로
옮긴다(3.5).

| 사람이 정한 것 | 어디에 |
| --- | --- |
| **이 라운드가 진행되는 중에 온 지시** | 「리뷰 뒤에 한 것」. 아래 넷보다 먼저 본다 |
| 「안 한다」 | 「N라운드 정리」의 「판정 및 근거」에 기각으로 |
| 「해라」 + 했다 | 같은 절에 해결로 |
| 「해라」 + 안 했다 | 「N+1라운드 발견」의 「필수」에 `(사람, N라운드부터)` |
| 정하지 않음 | 그 항목이 있던 바구니에 이월 표기로 |

**N라운드에 지시받아 이미 고친 것을 N+1라운드 「필수」에 넣지 마라.** 그건 N라운드 발견의
처리 결과이므로 「N라운드 정리」에 해결로 들어간다. **안 한 것만** 다음 라운드 필수에 적는다.

다른 절을 가리킬 때는 「N라운드 정리」의 「판정 및 근거」 처럼 **섹션과 절을 같이** 적어라 —
한 코멘트에 라운드가 둘이라 절 이름만으로는 어느 쪽인지 안 정해진다.
