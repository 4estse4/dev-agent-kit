이 브랜치의 커밋:
!`git log --oneline main..HEAD`

변경 규모:
!`git diff main...HEAD --stat`

**게이트 실행 결과 (본문에 그대로 붙일 증거):**
!`bash .ai-kit/gate/gate.sh 2>&1 || true`

새로 추가된 테스트:
!`git diff main...HEAD -U0 -- '*_test.go' '*.test.ts' '*.test.tsx' '*_test.py' | grep -E '^\+\s*(func Test|it\(|test\(|describe\()' | sed 's/^+[[:space:]]*/  /' | head -40`

$ARGUMENTS

---

`git log main..HEAD` 가 비면 중단: `Error: 이 브랜치에 커밋이 없습니다.`

1. 푸시: `git push -u origin HEAD`

2. `gh pr create` 로 PR 을 연다. 제목은 브랜치 전체의 목적을 Conventional Commits 스타일로.
   본문은 **아래 네 절만** 쓴다. 브랜치 전체를 요약하되, 각 절의 성격을 지킨다.

```
## 무엇을 · 왜
<1~3 bullet. 무엇이 바뀌었고 왜 필요했나.>

## 변경
<파일 수준 목록. 위 --stat 을 참고하되 나열이 아니라 의미 단위로 묶는다.>

## 검증
<위 "게이트 실행 결과" 출력을 그대로 붙인다 — 요약하지 않는다.>
새 테스트: <위 목록에서 추린 이름들. 없으면 "없음">
자동화가 닿지 않은 것: <직접 확인한 것 / 확인 못 한 것. 없으면 "없음">

## 위험
<동작 변경 · 미커버 엣지 · 마이그레이션 절차. 없으면 "없음">
```

## 본문 작성 규칙

- **검증 절은 증거다.** "테스트 통과함" 같은 주장을 쓰지 말고 게이트 출력을 붙인다.
  게이트가 실패한 채로 PR 을 열지 않는다.
- **"자동화가 닿지 않은 것"을 비워두지 마라.** 시각·레이아웃·여러 화면을 오가는 흐름은
  대개 자동 검증 밖이다. 직접 확인했으면 무엇을 어떻게 확인했는지,
  확인 못 했으면 못 했다고 쓴다. 적지 않으면 검증이 조용히 사라진다.
- **이 본문은 다음 단계에서 diff 와 대조된다.** 지키지 못할 주장을 쓰지 마라.
- 본문이 화면 한 장을 넘으면 대부분 과하다.

3. **리뷰 한 라운드.** 아래 순서를 지킨다.

   1. **head 를 고정한다**: `gh pr view <N> --json headRefOid -q .headRefOid`.
      두 층에 그 SHA 를 준다. 라운드 중에는 커밋도 푸시도 본문 수정도 하지 않는다 —
      두 층이 서로 다른 것을 보게 된다.
   2. **두 층을 돌린다. 순서는 없다** — 서로 독립이므로 병렬로 띄워도 된다.
      `review-diff` 스킬(셀프)과 `cold-reviewer` 에이전트(콜드).
      발동 조건은 `docs/process/verification-layers.md` 에 있다.
   3. **두 결과를 하나의 코멘트로 게시한다.** 두 층 다 게시하지 않고 돌려주므로
      올리는 것은 여기 한 자리다. 인라인 `--body` 를 쓰지 마라 — 백틱·따옴표가 든
      리뷰를 셸이 깨뜨린다.

          gh pr comment <N> --body-file <파일>

   4. **멈춘다. 그리고 사람에게 보고한다.** 다음 라운드를 도는 것도, 머지하는 것도
      **사람이 정한다.** 보고에 이 넷이 들어간다:

      - 몇 라운드째이고 두 층의 `Verdict` 가 각각 무엇인가
      - 발견을 **꼭 고쳐야 할 것 / 판단이 필요한 것 / 안 고쳐도 되는 것**으로 나눈 수
      - 코멘트 링크
      - **네 추천 한 줄** — 예: "위 3건 고치고 한 라운드 더" · "2건만 고치고 머지"

      그리고 **답을 기다린다.** 사람이 줄 수 있는 답의 예:
      *"고치고 한 라운드 더"* · *"고치고 추가 라운드 없이 머지"* · *"그건 무시하고 이대로 머지"*.

   5. 사람이 다음 라운드를 지시했을 때만 3단계로 돌아온다. 돌아오기 전에:
      고친다 → 커밋한다 → **푸시한다** → `headRefOid` 가 방금 커밋인지 확인한다 →
      **본문을 이 커밋까지 갱신한다**. 푸시를 빼먹으면 다음 라운드가 옛 head 를 다시 읽고,
      `merge-pr` 은 그것을 정상으로 본다.

   > **왜 멈추나.** 한 프로젝트에서 이 자리가 비어 있어 라운드가 **사람 승인 없이 20회**
   > 돌았다. 설정 파일 한 개를 옮기는 작업이었고, 실제 변경은 여섯 번째 커밋에서 끝났으며
   > 나머지 18커밋은 그 변경을 *설명하는 문장*을 고치는 것이었다. 코멘트 40건, 서브에이전트
   > 토큰 200만. 그때 스킬에 적혀 있던 것은 "3단계로 돌아와 다시 돌린다" 한 줄이었고
   > 멈추라는 말이 없었다.
   >
   > **라운드 수에 상한을 두지 않는다.** 진짜로 고칠 것이 계속 나오면 여러 번 돌아야 한다.
   > 정하는 것이 사람이면 된다.
