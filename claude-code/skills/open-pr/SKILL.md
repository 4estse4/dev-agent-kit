이 브랜치의 커밋:
!`git log --oneline main..HEAD`

변경 규모:
!`git diff main...HEAD --stat`

> `!! 새 테스트가 …개라` 가 뜨면 위 목록은 앞부분뿐이다 — 본문의 `새 테스트` 칸에
> 그 사실을 적는다. 목록에 없는 것을 "없다" 로 쓰지 마라.

**게이트 실행 결과 (본문에 그대로 붙일 증거):**
!`bash .ai-kit/gate/gate.sh 2>&1 || true`

새로 추가된 테스트:
!`git diff main...HEAD -U0 -- '*_test.go' '*.test.ts' '*.test.tsx' '*_test.py' | grep -E '^\+\s*(func Test|it\(|test\(|describe\()' | sed 's/^+[[:space:]]*/  /' | head -40; _t=$(git diff main...HEAD -U0 -- '*_test.go' '*.test.ts' '*.test.tsx' '*_test.py' | grep -cE '^\+\s*(func Test|it\(|test\(|describe\()'); [ "$_t" -gt 40 ] && echo "  !! 새 테스트가 ${_t}개라 위는 앞 40개뿐이다"`

$ARGUMENTS

---

`git log main..HEAD` 가 비면 중단: `Error: 이 브랜치에 커밋이 없습니다.`

1. 푸시: `git push -u origin HEAD`

2. `gh pr create` 로 PR 을 연다. **권한 프롬프트가 뜬다** — `settings.json` 의 `ask` 에 있고, 이 스킬 안이라고 해서 비켜가지 않는다. 그것이 의도다: 세우는 것이 "스킬을 거쳤나" 가 아니라 "사람이 봤나" 이기 때문이다. 승인될 때까지 기다린다. 제목은 브랜치 전체의 목적을 Conventional Commits 스타일로.
   본문은 **아래 네 절만** 쓴다. 브랜치 전체를 요약하되, 각 절의 성격을 지킨다.

```
## 무엇을 · 왜
<1~3 bullet. 무엇이 바뀌었고 왜 필요했나.>

## 변경
<파일 수준 목록. 위 --stat 을 참고하되 나열이 아니라 의미 단위로 묶는다.>

## 검증
<위 "게이트 실행 결과" 출력을 그대로 붙인다 — 요약하지 않는다.>
새 테스트: <위 목록에서 추린 이름들. 없으면 "없음">
자동화가 닿지 않은 것: <직접 확인한 것 / 확인 못 한 것. 없으면 "없음">

## 위험
<동작 변경 · 미커버 엣지 · 마이그레이션 절차. 없으면 "없음">
```

## 본문 작성 규칙

- **검증 절은 증거다.** "테스트 통과함" 같은 주장을 쓰지 말고 게이트 출력을 붙인다.
  게이트가 실패한 채로 PR 을 열지 않는다.
- **"자동화가 닿지 않은 것"을 비워두지 마라.** 시각·레이아웃·여러 화면을 오가는 흐름은
  대개 자동 검증 밖이다. 직접 확인했으면 무엇을 어떻게 확인했는지,
  확인 못 했으면 못 했다고 쓴다. 적지 않으면 검증이 조용히 사라진다.
- **이 본문은 다음 단계에서 diff 와 대조된다.** 지키지 못할 주장을 쓰지 마라.
- 본문이 화면 한 장을 넘으면 대부분 과하다.
- **본문은 지금 한 번 쓰고 끝이다. 라운드마다 고치지 마라.** 그래서 **라운드가 바꿀 값을
  본문에 적지 마라** — 설정 파일의 내용을 떠서 붙이는 것 같은 파생 출력이 그것이다.
  고쳐야 할 때 아무도 안 고쳐주고, 그러면 `$` 가 붙은 채 거짓이 된다. 붙일 것은 **이 시점에
  실행한 게이트 출력**이고, 그건 낡는 것이 아니라 그때의 기록이다.
  이유는 `docs/process/verification-layers.md` 의 「PR 본문은 열 때 쓰고 끝이다」.

3. **리뷰 한 라운드.** 아래 순서를 지킨다.

   1. **head 를 읽어 출력한다** — 셸 변수에 담지 마라:

          gh pr view <N> --json headRefOid -q .headRefOid

      **그 값을 보고서에 적어둔다.** 명령을 여러 번 부르는 사이에 셸 상태는 유지되지
      않는다 — `H0=$(…)` 로 담으면 다음 호출에서 그 변수가 비어 있고, 그 명령은
      출력도 없어서 값을 눈으로 받지도 못한다. 그러면 3번의 대조가 **언제나 "다르다"**
      가 되어 게시에 영영 도달하지 못한다(실측).

      라운드 중에는 커밋도 푸시도 본문 수정도 하지 않는다 — 두 층이 서로 다른 것을 본다.

      **두 층에 diff 를 건네지 마라.** 각자 `gh pr diff <N>` 로 직접 가져오게 한다.
      건네주면 그것이 옛것인지 아무도 모르고, `gh pr diff` 는 커밋을 지정하는 옵션이
      없어서 "이 SHA 를 봐라" 를 시킬 방법도 없다. 그래서 고정은 **지시**가 아니라
      아래 3번의 **사후 대조**로 지킨다.
   2. **두 층을 돌린다. 순서는 없다** — 서로 독립이므로 병렬로 띄워도 된다.
      `self-review` 스킬(맥락 있음)과 `cold-reviewer` 에이전트(맥락 없음).

      **`self-review` 에 PR 번호를 넘겨라** — `/self-review <N>`. 다른 레포의 PR 이면
      `/self-review <N> -R owner/repo`. 안 넘기면 그 스킬이 로컬 브랜치 모드로 돌아
      **PR 본문 자리가 비고, 그러면 이 스킬의 1번 임무(본문 ↔ diff 대조)가 대조할 것
      없이 돈다.** 그때 비는 자리는 `!!` 가 아니라 평범한 안내문이라 눈에 안 띈다.
      발동 조건은 `docs/process/verification-layers.md` 에 있다.
   3. **게시하기 전에 head 가 움직였는지 확인한다.** 같은 명령을 다시 돌려 출력을
      1번에서 적어둔 값과 **눈으로 비교한다**:

          gh pr view <N> --json headRefOid -q .headRefOid

      다르면 라운드 도중에 누가 푸시한 것이고 **두 층이 서로 다른 코드를 봤을 수 있다.**
      그 라운드는 무효다 — 게시하지 말고 1번부터 다시 돈다.

      두 층이 적은 `리뷰한 head:` 가 1번의 값과 다른 경우도 같다. 그 줄은 이 대조의
      교차 확인이지, 그 자체가 판정은 아니다.

   4. **두 결과를 코멘트 하나로 게시한다.** 두 층 다 게시하지 않고 돌려주므로 올리는
      것은 여기 한 자리다. 인라인 `--body` 를 쓰지 마라 — 백틱·따옴표가 든 리뷰를
      셸이 깨뜨린다.

          gh pr comment <N> --body-file <파일>

      형식은 이렇다. **접히지 않은 부분이 화면 한 장을 넘으면 안 된다** — 그 위는
      아무도 안 읽는다. 실제로 안 읽혔다.

      **2라운드 이상이면 지난 라운드 정리가 먼저다.** 직전 코멘트에 오른 항목을
      **두 층 것 전부** 세어 한 줄로 적는다. 한 층의 건수만 적으면 다른 층의 지적이
      아무도 모르게 사라진다 — 실제로 그렇게 사라졌다. **그리고 일부 해결·미해결은 아래
      목록에 다시 올린다.** 닫힐 때까지 매 라운드 오른다.
      **판정어는 다섯이고 요약에도 그대로 쓴다** — `기각` 을 `해결` 에 접으면
      "고친 것" 과 "안 하기로 정한 것" 의 구분이 사람이 읽는 유일한 자리에서 사라진다.
      **같은 항목이 세 번째 라운드에도 미해결이면** 그것은 발견이 아니라 결정이 밀린
      것이다. 요약 맨 앞에 그렇게 적고 사람에게 올린다.
      근거는 `docs/process/verification-layers.md` 의 「라운드 사이에 무엇이 넘어가나」.

      ```markdown
      ## 리뷰 2라운드 — 셀프 `Request changes` · 콜드 `Comment`

      리뷰한 head: <3.1 에서 읽어 적어둔 40자 그대로>

      1라운드 8건(셀프 3 · 콜드 5) — 5건 해결 · 1건 기각 · 1건 미해결(아래에 다시
      올림) · 1건 결정 필요.

      **꼭 고쳐야 함 2**
      - `install.sh:143` 재설치가 언어 선택을 유실한다 — **셀프·콜드 둘 다**
      - `secrets.sh:40` 빈 범위를 통과시킨다 — 콜드

      **결정 필요 3**
      - `gates.yml:74` 체크섬 대조를 남길지 — 셀프
      - …

      **안 고쳐도 됨 1** — `README:12` 표현 — 콜드

      추천: 위 2건 고치고 한 라운드 더.

      <details>

      <summary>셀프 리뷰 전문</summary>

      …self-review 가 돌려준 것 그대로…

      </details>

      <details>

      <summary>콜드 리뷰 전문</summary>

      …cold-reviewer 가 돌려준 것 그대로…

      </details>
      ```

      규칙 넷:

      - **요약은 통계가 아니라 결정 모양으로 쓴다.** "높음 1 · 중간 2" 는 읽어도 무엇을
        할지 모른다. 한 줄에 **위치 · 무슨 문제 · 누가 짚었나**. 그래야 전문을 열지 않고도
        "1번만 고치고 머지" 라고 답할 수 있다.
      - **두 층의 전문을 그대로 싣는다.** 요약하지도, 합치지도, **중복을 지우지도 않는다.**
        어느 지적이 어디서 왔는지가 사라지면 두 층을 나눈 이유가 사라진다.
      - **두 층이 같은 것을 짚었으면 요약 줄에 그렇게 적는다.** 독립된 두 층이 같은 곳을
        가리킨 것은 더 강한 신호다. 겹친다고 한쪽을 지우지 마라.
      - `<details>` 는 GitHub 코멘트에서 렌더링된다. **태그 앞뒤로 빈 줄**을 둬야 안의
        마크다운이 처리된다.

   5. **멈춘다. 그리고 사람에게 보고한다.** 다음 라운드를 도는 것도, 머지하는 것도
      **사람이 정한다.** 보고에 이 넷이 들어간다:

      - 몇 라운드째이고 두 층의 `Verdict` 가 각각 무엇인가
      - 발견을 **꼭 고쳐야 할 것 / 판단이 필요한 것 / 안 고쳐도 되는 것**으로 나눈 수
      - 코멘트 링크
      - **네 추천 한 줄** — 예: "위 3건 고치고 한 라운드 더" · "2건만 고치고 머지"

      그리고 **답을 기다린다.** 사람이 줄 수 있는 답의 예:
      *"고치고 한 라운드 더"* · *"고치고 추가 라운드 없이 머지"* · *"그건 무시하고 이대로 머지"*.

   6. 사람이 다음 라운드를 지시했을 때만 **이 3단계의 1번**으로 돌아온다. 돌아오기 전에:
      고친다 → 커밋한다 → **푸시한다** → `headRefOid` 가 방금 커밋인지 확인한다.
      푸시를 빼먹으면 다음 라운드가 옛 head 를 다시 읽고, `merge-pr` 은 그것을 정상으로 본다.

      **본문은 손대지 마라.** 라운드가 만든 것은 코멘트에 쌓이고, 최종 정리는 `merge-pr`
      이 머지 직전에 코멘트 하나로 올린다. 근거는 `docs/process/verification-layers.md`
      의 「PR 본문은 열 때 쓰고 끝이다」.

   > **왜 멈추나.** 한 프로젝트에서 이 자리가 비어 있어 라운드가 **사람 승인 없이 20회**
   > 돌았다. 설정 파일 한 개를 옮기는 작업이었고, 실제 변경은 여섯 번째 커밋에서 끝났으며
   > 나머지 18커밋은 그 변경을 *설명하는 문장*을 고치는 것이었다. 코멘트 40건. 그때 스킬에 적혀 있던 것은 "3단계로 돌아와 다시 돌린다" 한 줄이었고
   > 멈추라는 말이 없었다.
   >
   > **라운드 수에 상한을 두지 않는다.** 진짜로 고칠 것이 계속 나오면 여러 번 돌아야 한다.
   > 정하는 것이 사람이면 된다.
