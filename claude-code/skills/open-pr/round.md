## 3. 리뷰 한 라운드

아래 순서를 지킨다.

### 3.1 head 를 읽는다

셸 변수에 담지 마라 — 읽어서 출력한다:

    gh pr view <N> --json headRefOid -q .headRefOid

**그 값을 세션의 응답에 적어 둔다.** 명령을 여러 번 부르는 사이에 셸 상태는 유지되지 않는다 —
`H0=$(…)` 로 담으면 다음 호출에서 그 변수가 비어 있고, 그 명령은 출력도 없어서 값을 눈으로
받지도 못한다. 그러면 3.3 의 게시 전 대조가 **언제나 "다르다"** 가 되어 게시에 영영 도달하지
못한다(실제로 확인함).

**사람이 라운드 도중에 지시하면 그 라운드는 거기서 끝난다.** 지시대로 고치고
커밋한 것은 **이미 다음 라운드의 head 다.** 이 라운드 코멘트는 3.1 에서 읽은 head 로
게시하고, 그 지시로 한 것은 코멘트의 「리뷰 뒤에 한 것」에 적는다. 지시는 창으로 받아 라운드
코멘트 뒤에 사람 계정 코멘트로 올린다(3.5). 「리뷰 뒤에 한 것」에는 `(사람)` 으로 옮기지 않는다 —
그 코멘트가 아직 없어 훅이 대조할 원본이 없다(「라운드 코멘트 형식」).

**두 리뷰에 diff 를 건네지 마라.** 각자 `gh pr diff <N>` 로 직접 가져오게 한다. 건네주면 그것이
옛것인지 아무도 모르고, `gh pr diff` 는 커밋을 지정하는 옵션이 없어서 "이 SHA 를 봐라" 를
시킬 방법도 없다. 그래서 두 리뷰가 같은 head 를 봤는지는 **지시**로 정하지 않고 3.3 의 게시 전 대조로
**사후에 확인한다**.

### 3.2 두 리뷰를 실행한다

**한 리뷰가 `!!` 로 멈추면 그 라운드는 무효다** — 게시하지 말고 원인을 고친 뒤 3.1 부터
다시 진행한다. **원인이 이미 게시된 코멘트면 고치지 마라**(3.5 의 「원 라운드 코멘트는
고치지 않는다」) — 그때는 무엇이 막혔는지 사람에게 알리고 멈춘다. 라운드가 무효가 되는
다른 조건은 3.3 에 있다. 한쪽만 실행된 결과를 올리면 그 라운드가 반쪽인 것이 코멘트에 드러나지 않는다.

두 리뷰는 `self-review` 스킬(맥락 있음)과 `cold-reviewer` 에이전트(맥락 없음)다. **순서는 없다** — 서로
독립이므로 병렬로 실행해도 된다.

**`self-review` 에 PR 번호를 전달해라** — `/self-review <N>`. 다른 레포의 PR 이면
`/self-review <N> -R owner/repo`. 전달하지 않으면 그 스킬이 로컬 브랜치 모드로 실행되어 **PR 본문
자리가 비고, 그러면 그 스킬의 「본문 ↔ diff 대조」가 대조할 것 없이 실행된다.** 그때 비는
자리는 `!!` 가 아니라 평범한 안내문이라 눈에 안 띈다.
`cold-reviewer` 를 언제 실행하는지는 `docs/process/verification-stages.md` 3 에 있다.

### 3.3 게시 전 대조

같은 명령을 다시 실행해 출력을 3.1 에서 적어 둔 값과 **눈으로 비교한다**:

    gh pr view <N> --json headRefOid -q .headRefOid

다르면 라운드 도중에 누가 푸시한 것이고 **두 리뷰가 서로 다른 코드를 봤을 수 있다.**
그 라운드는 무효다 — 게시하지 말고 3.1 부터 다시 진행한다. 다른 조건 하나는
3.2 에 있다(한 리뷰가 `!!` 로 멈춤).
**head 가 사람의 지시로 움직였으면 무효가 아니다** — 이 대조가 확인하는 것은 **두 리뷰가 같은 것을
봤나**이지 라운드 내내 head 가 그대로였나가 아니다. 3.1 의 「사람이 라운드 도중에 지시하면」대로
그대로 게시하고 「리뷰 뒤에 한 것」에 적는다.

두 리뷰가 적은 `리뷰한 head:` 가 3.1 에서 읽은 값과 다르면 그 라운드도 무효다. 그 줄은 위 명령 대조의
교차 확인이라, 그 줄이 같다고 위 대조를 건너뛰지 않는다.

### 3.4 코멘트 하나로 게시한다

두 리뷰 다 게시하지 않고 돌려주므로 올리는 것은 여기 한 자리다. 인라인 `--body` 를 쓰지 마라 —
리뷰에 든 백틱·따옴표를 셸이 해석해 글자가 바뀐다.

    gh pr comment <N> --body-file <절대 경로>

**이 한 줄로만 입력한다.** 다른 명령과 잇거나(`&&` · `;` · `if … then` · 줄바꿈), 주석 ·
리다이렉트 · 래퍼를 붙이거나, PR 을 번호 말고 URL 로 적거나, 상대 경로를 전달하면 아래 훅이
게시인지 가리지 않고 막는다. 훅이 게시인지를 가려 막으면 우회할 길이 늘어나므로, 훅은 이 모양만 받는다.
`\` 줄넘김은 된다. 훅은 명령 문자열 어디에든 이 명령이 보이면 그 명령 전체가 이 모양인지
검사한다. 그 글자가 든 검색이나 heredoc 도 막힌다. 찾을 때는 `pr comment` 로 찾고, 초안은
`Write` 로 쓴다.

**라운드 코멘트는 사람의 승인 없이 올린다.** 아래 게시 전 확인을 통과하면 올리고, 두 리뷰 전문을
뺀 전문과 링크를 3.5 의 보고에 싣는다. 사람은 그것을 읽고 다음에 할 일을 창에서 고른다.
승인 없이 올린다는 것은 게시 전 승인을 받지 않는다는 뜻이지, 사람에게 보이지 않는다는 뜻이 아니다.

**승인 대신 에이전트 훅이 `(사람)` 인용을 대조한다.** `.claude/hooks/round_comment_quotes.sh` 가
이 명령을 가로채, 인용이 이 PR 의 사람 계정 코멘트에 글자 그대로 없으면 막는다. 원본의 단위는 불릿
하나나 줄 하나다 — 사람 계정 코멘트는 한 줄이 결정 하나라서(3.5), 서로 다른 결정 줄의 조각을 `…` 로
이으면 막힌다. 창에서 고른 보기로 만든 코멘트든 사람이 PR 웹에서 쓴 글이든 같다. 봇 계정으로 올린 글은
원본이 아니다. 따옴표 없이 `(사람)` 라벨만 단 항목도 막는다. 대조할 인용이 없어 훅의 대조가 우회되기
때문이다. 막히면 인용을 사람 계정 코멘트에 있는 글자로 고치거나, 기록이 없는 것이면 `(사람)` 을 떼고
`셀프+` 로 올린다(`comment-format.md` 의 「출처 다섯」의 규칙 2). **다른 도구로 올려 훅의 대조를 우회하지 마라.**
라운드 코멘트는 다음 라운드의 두 리뷰가 「지난 코멘트 정정」으로 고치는 글이고, 그 두
리뷰가 다시 판정하지 않는 것이 `(사람)` 인용 하나라서 그것을 기계가 본다. 승인 없이 올리면서 게시 전에
아무도 보지 않게 된 것은 `docs/process/verification-stages.md` 6.3 에 있다.

**콜드 리뷰 전문은 옮겨 적지 않는다.** 기록 훅(`.claude/hooks/review_record.sh`)이 에이전트 종류가
`cold-reviewer` 인 에이전트가 돌려준 보고를 봇 디렉터리에 `리뷰한 head:` 별로 남긴다. 그래서 콜드 리뷰는
`cold-reviewer` 에이전트로 실행한다 — 다른 종류(general-purpose 등)로 실행하면 기록이 없다. 「콜드 리뷰 전문」
블록에는 그 출력을 조각 파일로 받아 넣는다:

    bash .claude/hooks/cold_review.sh <리뷰한 head> > <조각 파일>

출력을 읽고 다시 적지 않는다 — 한 글자만 달라도 막힌다. 머리 · 셀프 전문 · 콜드 전문 조각을 `awk 1` 로
이어 `--body-file` 의 파일을 만든다(2절의 본문 조각과 같다). 같은 게시 명령을 가로채는 `.claude/hooks/round_comment_cold.sh` 가
그 블록을 그 head 의 기록과 글자로 대조해, 다르거나 기록이 없으면 막는다. 봇 설정이 없으면 기록이 없어 라운드
코멘트를 막는다.

**길이 훅(`.claude/hooks/post_length.sh`)도 같은 게시 명령을 가로챈다.** 접히지 않은 부분의 총량이나 한 줄이
상한을 넘으면 막는다. 두 리뷰 전문은 접혀 있어 `<summary>` 만 센다. 막히면 항목을 줄이고, 총량이면
`comment-format.md` 의 「총량에 막히면」대로 낮음 항목을 접는다. 다른 도구로 올려 이 훅을 우회하지 마라.

**설치된 레포에서는 권한 프롬프트가 한 번 표시된다.** `gh pr comment` 는 `ask` 에 있고, 훅이
통과시켜도 `ask` 는 남는다. 프롬프트에 보이는 것은 `--body-file` 의 경로뿐이라 그것은
초안의 승인이 아니다. 라운드 코멘트와 `merge-pr` 의 결정 코멘트가 같은 명령으로 올라가서 규칙으로 둘을
구분하지 못하므로 `ask` 를 그대로 둔다. 이유는 `docs/process/verification-stages.md` 6.3 에 있다.

**게시하기 전에 같은 head 의 라운드 코멘트가 이미 있는지 본다. `0` 이 나올 때만 게시한다.**
그 밖이면 게시하지 말고 사람에게 보고한다 — 3.6 의 5와 같은 이유로 **빈 출력은 통과가 아니다**:

    gh pr view <N> --json comments \
      --jq '[.comments[].body|select(test("^\\s*## 리뷰 "))
             |(split("\n")|map(select(startswith("리뷰한 head: ")))|.[0] // "")]
            |map(select(contains("<3.1 에서 읽은 head>")))|length'

**head 를 필터 안에 직접 넣는다.** `gh pr view --jq` 는 필터 하나만 받아서 jq 의 `--arg` 를
전달할 수 없다 — `accepts at most 1 arg(s)` 로 실패한다. `// ""` 는 `리뷰한 head: ` 줄이 없는
코멘트에서 `.[0]` 이 `null` 을 내 검사가 오류로 멈추는 것을 막는다(3.6 의 5와 같다).

**head 는 `리뷰한 head: ` 로 시작하는 첫 줄에서 읽는다.** 한때 코멘트의 셋째 줄로 읽어, 제목과
head 줄 사이에 줄이 끼거나 제목 바로 뒤에 head 줄이 오면 head 를 못 찾았다. 접힌 리뷰 전문에도 같은
줄이 있지만 맨 위의 것이 먼저 나온다.

**규칙으로는 안 막힌다.** 「같은 것을 두 번 올리지 마라」는 규칙은 세션이 자기가 이미 올렸다는 것을
모르면(되감긴 세션 · 승인 프롬프트가 실패로 보인 경우) 소용이 없다. 그래서 규칙이 아니라 **게시 전 확인**이다.

**두 벌이 되면 그 사이에 사람이 정한 것이 사라진다.** 앵커는 `## 리뷰 ` 로 시작하는 **마지막**
코멘트이고 두 리뷰가 받는 범위는 그 뒤이므로, 한 벌 더 붙으면 앞의 사람 계정 코멘트가 그 범위에서 빠진다. 두
리뷰는 그것을 **「사람이 아직 정하지 않았다」와 구분하지 못한다.** 실제로 그렇게 됐다. 세션이 되감겼다 다시
진행하면서 라운드 코멘트가 두 벌 올라갔고, 그때 PR 에 있던 사람의 결정 셋 중 두 리뷰에 실린 것은 하나도 없었다.

**게시하기 전에 `—` 도 본다.** `comment-format.md` 의 「기호 — 역할 하나씩」이 불릿 줄과 그 이어짐에 금지한
것이고, **사람이 매 라운드 손으로 확인하던 것**이다. 출력이 나오면 게시하지 말고 고친다:

    awk '
      /^[[:space:]]*<summary>(셀프|콜드) 리뷰 전문<\/summary>/ { r = 1; d = 0; next }
      r && /^[[:space:]]*<details/ { d++; next }
      r && /^[[:space:]]*<\/details>/ { if (d) d--; else r = 0; next }
      r { next }
      { isb = ($0 ~ /^[[:space:]]*([-*][[:space:]]|→)/) }
      /^[[:space:]]*$/ { inb = 0; next }
      isb { inb = 1; hum = ($0 ~ /\(사람[^)]*\) "/) }
      !isb && $0 !~ /^[[:space:]]/ { inb = 0 }
      inb && !hum && /—/ { print NR ": " $0 }' <코멘트 파일>

무엇을 보고 무엇을 빼나:

- **두 리뷰 전문만 빼고 본다**(`<summary>셀프 리뷰 전문</summary>` · `<summary>콜드 리뷰 전문</summary>` 부터 그 블록을
  닫는 `</details>` 까지 건너뛴다. 전문 안에 접힌 블록이 또 있으면 짝을 세어 바깥 블록의 끝을 찾는다 — 리뷰어가
  재현 스크립트를 접어 둔 라운드 코멘트가 있었다). 두 리뷰 전문은 그대로 싣는 것이라 고칠 수 없다. 전문까지 보면 3라운드 코멘트에서 고칠
  줄이 0 인데 25줄이 검사 결과에 나왔다. `comment-format.md` 의 「총량에 막히면」대로 접은 낮음 블록은 본다 — 세션이
  쓴 바구니이고, 3.5 보고로 사람에게 간다. 그 블록은 코멘트 가운데에 오므로, 첫 `<details>` 부터 지우던 동안은 그
  뒤의 바구니와 맨 아래 제안을 보지 않았다. 줄 번호는 코멘트 파일의 줄 번호다.
- **불릿의 이어짐 줄까지 본다.** 불릿 다음의 들여쓴 줄은 빈 줄이나 들여쓰지 않은 줄이
  나올 때까지 그 불릿이다. 첫 줄만 보는 `grep` 은 100자 안팎에서 줄이 바뀐 둘째 줄을 못 봤고,
  **그것이 가장 흔한 모양이었다.** 킷 레포의 한 PR 의 1·2라운드 코멘트에서 첫 줄 검사는
  13줄, 이것은 37줄을 찾아냈다.
- **사람 인용은 뺀다. 여러 줄로 이어져도 뺀다.** `(사람) "`·`(사람, N라운드 발견) "` 로
  시작한 불릿은 다음 불릿이나 `→` 줄이 나올 때까지 인용이다. 낱말을 안 바꾸는 규칙이
  우선한다(`comment-format.md` 의 「출처 다섯」 규칙 1). **그 뒤의 `→` 줄은 이쪽 판단이라 다시 본다.**
- **`*` 뒤에 공백을 요구한다.** `**볼드**` 로 시작하는 산문 줄을 불릿으로 오인하지 않게.

**실제로 올라간 코멘트의 줄 모양을 넣어 이 검사가 제대로 찾는지 확인했다.** 처음 판은 작성자가
떠올린 경우 열셋만 시험했고, 줄이 바뀐 이어짐 줄이 그 목록에 없었다(사람이 실행해서 찾았다). 지금 판은 킷 레포의
PR 둘에 올라간 코멘트 서른하나에 실행했고, 거기서 나온 모양으로 입력 열일곱 개를 만들어
다시 확인했다. 찾는 것: 불릿 · `→` · 줄이 바뀐 `→` 의 둘째 줄 · 줄이 바뀐 불릿의 둘째 줄 ·

볼드도 불릿도 아닌 산문 · 표 · `---` · 빈 줄 뒤 들여쓴 코드 · 두 리뷰 전문 안 불릿.

**`comment-format.md` 의 「라운드 코멘트 형식」대로 쓴다.**

**발견을 다 반영하지 마라. 1라운드부터다.** 콜드는 불변식을 어기는 방법을 만들어내므로 지어낸 형태와
실제로 생길 형태가 같은 무게로 온다. *평범한 편집에서 생기나 · 막는 비용이 코드와 오탐을 늘리지
않나 · 적대자가 있나* 를 **콜드가 낸 항목마다** 묻고, **안 하는 쪽은 반영하지 않기 제안
바구니에 이유와 함께 올린다.** 다 반영하다 검사가 그것이 막은 사고보다 길어지고 오탐 셋이
새로 생긴 적이 있다. 근거는 `docs/process/verification-stages.md` 3.6.
