## 0. 파급을 직접 확인한다. 리뷰에 맡기지 마라

**네가 쓴 것이다.** 아래는 리뷰가 매 라운드 대신 해주던 것이고, 그래서 라운드가 끝나지
않았다. 한 프로젝트에서 리뷰가 네 라운드 연속으로 같은 주석을 발견으로 냈고, 고칠 때마다 새로 틀린
말을 썼다. 한 PR 에서는 사람이 라운드마다 「같은 부류가 다른 자리에 있는지 찾아라」를
따로 지시해야 했고, 지시하지 않은 라운드에서는 세션이 같은 부류를 찾지 않았다. 사람이 짚었다: "지적 받은데 하나만 하면
되는지 아님 다른데 동일한 문제, 혹은 동일한 유형의 문제가 없는지 조사하고 같이
고치라는건 이렇게 매번 별도 지시를 해야해?"

- **주장을 썼으면 출처와 대조한다.** 주석·문서·PR 본문에 "이렇게 동작한다" 를 적었으면 그
  근거 파일을 열어 맞는지 본다
- **이름을 바꾸거나 옮겼으면 `grep` 으로 옛 이름을 찾는다**
- **규칙·문장을 더했으면 그 파일 전체를 다시 읽는다.** diff 만 보지 마라
- **새 절차를 적었으면 끝까지 따라가 본다**
- **결함을 고쳤으면 같은 문장 · 같은 규칙 · 같은 모양이 다른 자리에 있는지 찾는다.**
  하나를 고치고 부류를 안 닫으면 다음 라운드가 옆 자리를 올린다. 같은 모양을 찾았어도 그 실패가
  실제로 일어날 수 있는 자리만 고친다(`docs/process/artifact-rules.md` R7)

**문서를 검색할 때는 줄을 이어 붙인다.** 문서는 낱말 사이에서 줄이 바뀌므로 줄 단위 `grep` 은 두 줄에 걸친
검색어를 못 찾는다. 실제로 「기계 대조」가 두 줄로 나뉘어 검색되지 않았다. 코드는 줄 단위로 찾아도 되고, 문서는
줄을 이어 붙인 뒤 검색어의 낱말 사이에 ` *` 를 둔다(`기계 *대조`). 검색 결과에는 검색어 앞뒤로 가장 가까운
마침표까지가 나오고, 경로와 버전 번호의 `.` 에서도 끊긴다. `-c core.quotePath=false` 는 git 기본값이 한글 같은
비ASCII 파일명을 8진수로 내서 그 파일이 결과에서 빠지는 것을 막는다:

    git -c core.quotePath=false ls-files '*.md' | while read -r f; do
      tr '\n' ' ' < "$f" | grep -o '[^.]*<검색어>[^.]*' | sed "s|^|$f: |"
    done

찾은 것이 없으면 1절을 진행한다. **PR 을 열기 전에 찾아서 고쳤으면, 커밋한 뒤 이 스킬을 다시
부른다.** `SKILL.md` 에 주입된 커밋 목록 · 변경 규모 · 게이트 출력은 부른 시점의 트리라, 그대로
두면 2절이 옛 목록으로 「리뷰 포인트」를 쓰고 옛 게이트 결과로 열지를 정한다. 첫 리뷰 라운드가 그 「리뷰 포인트」를
본문 ↔ diff 불일치로 올린다. 3.6 의 2 에서
이 단계를 실행했으면 다시 부르지 말고 3.6 의 3 을 진행한다. 처음부터 다시 진행하면 「1. 푸시」가 3.6 의 5 를
안 거친다. **이 단계를 건너뛰면 리뷰가 그것을 찾아내고, 그 수정이 또 다음 라운드를
만든다.**
