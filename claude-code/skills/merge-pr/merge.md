## 3. 머지

머지 **전에**, 사람이 무엇을 보고 정했는지를 PR 에 남긴다 — 머지 후에는 그 맥락을
복원할 곳이 없다. 리뷰가 남아 있는데 그것을 고치지 않고 머지하기로 했다면 특히 그렇다.

**올리기 전에 초안 전문을 사람에게 보이고 승인받는다.** 보인다는 것은 승인을 묻기 바로 전에 세션의 응답에
그 글과 명령의 최종본 전문을 출력하는 것이다 — 파일 경로나 요약으로 대신하지 않는다. 이 스킬에서 승인을
받는 것은 모두 그렇다. 결정 코멘트는 머지와 한 몸이고 머지 전에 남기는 마지막 기록이라, 올리기 전에 사람의 승인을 받는다. 기준은
`docs/process/verification-stages.md` 6.3 에 있다. 아래 권한
프롬프트는 이 승인을 대신하지 못한다 — 파일 경로만 보인다. **봇 설정이 있으면 사람의 Approve 가 결정
코멘트 · 머지 명령 · 4절의 브랜치 삭제의 승인이다.** 이 셋은 창으로 묻지 않는다. 순서는 아래 「봇 설정이 있을
때」다. 아래 「이 PR 이 끝낸 이슈」는 봇 설정이 있어도 창으로 승인받는다(닫을 이슈가 있을 때만) — Approve 는
코드에 대한 승인이라 본문 밖에서 정한 이슈를 보여 주지 않는다. 4절의 후속 코멘트도 창으로 승인받는다.

**초안과 함께 아래 머지 명령 전문도 보인다.** 스쿼시 커밋의 제목과 본문이 그 명령 안에 있고,
틀리면 히스토리 재작성 없이는 못 고친다. 권한 프롬프트는 승인이 아니고, 프롬프트가 표시되지
않는 레포도 있다. 여러 줄 본문이 프롬프트에 다 보이는지는 확인하지 않았다. 프롬프트에서
거절하면 아래 거절 경로가 실행되어 결정 코멘트가 두 벌이 된다. 그래서 사람이 제목과 본문을 보는
자리는 여기다.

**이 PR 이 끝낸 이슈를 닫는 명령도 같이 보인다.** 아래 목록의 「머지가 닫지 않지만 이 PR 이 끝낸
이슈」가 있을 때만이다. 이슈를 닫는 것도 사람의 승인을 받는 행동이고, 닫힌 이슈는 열린 이슈
목록에서 사라져 잘못 닫혀도 알아챌 계기가 없다. 이슈마다 한 줄이고, 머지가 끝난 뒤 이 절 끝에서
실행한다:

    gh issue close <번호> --comment "<이 PR 의 URL> 로 끝냈다."

**봇 설정이 있으면 닫는 명령 대신 머지 명령의 `--body` 에 `Closes #<번호>` 줄을 더한다.** auto-merge 로 머지되면
머지 뒤에 세션이 닫는 명령을 실행할 자리가 없기 때문이다. 창으로 승인받은 뒤에 더하고, 자리는 머지 명령 틀이 보인
곳이다 — 트레일러 줄 뒤에 붙이면 트레일러가 사라진다(아래 머지 명령의 설명). 스쿼시 커밋 메시지의 닫는
키워드는 그 커밋이 기본 브랜치에 들어갈 때 이슈를 닫는다(GitHub 문서 「Linking a pull request to an issue」:
"You can also use closing keywords in a commit message. The issue will be closed when you merge the commit into
the default branch"). PR 본문은 고치지 않는다(아래 「본문을 고쳐서 맞추려 하지 마라」). 같은 문서가 "the pull
request that contains the commit will not be listed as a linked pull request" 라고 하므로 그 번호는
`closingIssuesReferences` 에 나오지 않는다 — 결정 코멘트의 「머지가 닫을 수 있는 이슈」 줄에 따로 적는다.

**4절의 삭제 명령 둘도 같이 보인다.** 원격 브랜치를 지우는 `git push origin --delete
<headRefName>` 과 로컬 브랜치를 지우는 `git branch -D <headRefName>` 이다. 머지 명령이
브랜치를 지우지 않으므로(아래 머지 명령 뒤의 설명) 이 둘은 머지 뒤에 따로 실행되지만, 승인은
머지와 함께 여기서 받는다. 원격 삭제는 레포 밖으로 나가는 행동이고, 둘 다 되돌리기 어렵다. fork 에서 온 PR 이면 원격 삭제는
하지 않으므로(4절) 로컬 삭제 하나만 보인다. auto-merge 로 머지하면 원격 브랜치는 레포 설정 「Automatically
delete head branches」가 지우고, 4절은 머지 뒤 다음 작업을 시작할 때 실행한다(아래 「봇 설정이 있을 때」).

결정 코멘트는 이 명령으로 올린다:

    gh pr comment <N> --body-file <절대 경로>

이 한 줄로만 입력한다. 다른 명령과 이은 것과 상대 경로는 `open-pr` 3.4 의 훅이 막는다.

**이 코멘트도 `open-pr` 2절의 본문처럼 조각 파일로 만든다.** 글은 `Write` 로 쓰고, 명령
출력(2절의 커밋 나열 · 아래 닫히는 이슈 줄 · 본문 검증을 다시 실행한 값)은 `evidence.sh` 가
덧붙인다. 조각을 `awk 1` 로 이은 파일이 위 `--body-file` 의 경로다. 거부된 명령은 `open-pr`
2절대로 출력 대신 확인한 것을 글로 적는다. `<스킬 디렉터리>` 자리에는 이 파일을 읽어 온 디렉터리의 경로를 넣는다(`SKILL.md` 의 「꼭 지킬 것」):

    bash <스킬 디렉터리>/../open-pr/evidence.sh <디렉터리>/<NN-이름>.part <<'CMD'
    <명령>
    CMD

손으로 옮기면 실행한 것과 다른 명령이 적힌다. 한 결정 코멘트에 실제로 실행한 `git fetch -q` 가
`-q` 없이 옮겨졌고, 긴 명령은 `…` 로 줄었다.

**이 코멘트가 이 PR 의 최종 정리다.** PR 본문은 열 때 쓰고 그 뒤로 고치지 않았으므로(`open-pr` 의
`body.md` 「본문 작성 규칙」), 그 뒤에 달라진 것을 말하는 자리가 여기밖에 없다. 아래를 적는다:

- 라운드 수와 마지막 라운드의 두 `Verdict`
- 리뷰를 거치지 않은 커밋. 마지막 라운드 코멘트의 head 뒤에 온 커밋을 `docs/dev-log.md` 하나만
  바뀐 것과 그 밖의 것으로 나눠 적고, 커밋마다 건드린 파일을 같이 적고, 사람이 그것을 알고
  머지를 지시했다고 적는다(2절). auto-merge 를 켜는 경우에는 그 목록을 Approve 를 요청하는 응답에 출력했다고
  적는다 — Approve 는 아직 없다. 나열을 판정 못 했으면 그 사실을 적는다. 없으면 이 줄을 아예
  쓰지 않는다
- PR 본문이 지금은 틀린 곳. 라운드가 본문의 결론을 바꿨으면 무엇이 어떻게 바뀌었는지,
  그리고 본문에 붙인 증거 중 지금 다시 실행하면 다르게 나오는 것(다시 실행한 값은 `evidence.sh` 로).
  없으면 `본문 그대로`
- 마지막 라운드 뒤 사람이 정한 것(2절이 읽은 사람 계정 코멘트). 그 라운드에 안 고친 것과 안 하기로
  한 것. 사람 계정 코멘트의 줄을 그대로 옮긴다
- 고쳐야 한다고 올라왔는데 고치지 않고 머지하는 것이 있으면 그것과 이유
- 머지가 닫을 수 있는 이슈. 아래 「닫히는 이슈 줄」의 명령을 `evidence.sh` 로 실행해 덧붙인다. 번호가
  안 나오면 `닫는 키워드 없음`. 봇 설정이 있어 머지 명령의 `--body` 에 `Closes #<번호>` 를 더했으면 그 번호를
  따로 적는다 — 그 명령들의 출력에 나오지 않는다
- 머지가 닫지 않지만 이 PR 이 끝낸 이슈. 연 뒤 라운드에서 끝내게 되어 본문에 `Closes #N` 이 없는
  이슈다. 이 PR 의 모든 사람 계정 코멘트에서 사람이 끝내기로 정한 이슈만 적고, 그 인용을 근거로 든다.
  2절은 마지막 라운드 코멘트 뒤의 것만 읽으므로, 이 줄을 쓸 때는 아래 명령으로 앞 라운드 뒤의 것까지
  읽는다. 사람 계정 코멘트는 2절처럼 봇이 올린 라운드 코멘트가 있는 PR 의 사람 계정 코멘트다.
  `dev-log` 가 계획 줄을 지울 때 본 것도 PR 코멘트 전체다. 없으면 이 줄을 아예 쓰지 않는다

      gh pr view <N> --json comments \
        --jq '.comments as $c
              | ([$c[]|select(.body|test("^\\s*## 리뷰 "))
                  |.authorAssociation|IN("OWNER","MEMBER","COLLABORATOR")|not]|any) as $bot
              | [$c[]|select($bot and (.authorAssociation|IN("OWNER","MEMBER","COLLABORATOR")))
                     |.body]|join("\n\n———\n\n")'

- 남은 것을 이슈로 옮겼으면 그 번호
- 2절에서 이 PR 의 dev-log 항목이 없었거나 판정 못 했으면 그 사실. 있었으면 이 줄을 아예 쓰지 않는다
- `사람이 머지를 결정했다`. auto-merge 를 켜는 경우에는 `사람이 지금 head <짧은 SHA> 를 Approve 하면 GitHub 이
  머지한다(auto-merge)` 로 적는다 — 이 코멘트는 Approve 전에 올라가므로 「Approve 했다」 같은 아직 없는 일을
  적지 않는다

**「PR 본문이 지금은 틀린 곳」 줄** — 라운드 코멘트의 `### 본문이 틀린 곳` 들을 모아 옮긴다.
결론만 적으면 거짓이 된 출력을 적을 자리가 없어져 닫히지 않는 이월이 된다.

**「마지막 라운드 뒤 사람이 정한 것」 줄** — 라운드 코멘트에 없는
유일한 기록이라 여기서 안 옮기면 사라진다. 요약하지 마라(`open-pr` 의 `comment-format.md` 「출처 다섯」의 규칙 1) —
이 코멘트는 머지 **전에** 쓰는 마지막 기록이라 요약하면 되돌릴 자리가 없고,
사람이 대조할 원문도 사라진다. 머지 뒤에야 나온 것은 4절이 이 코멘트 뒤에 코멘트로 붙인다.
없으면 그 줄을 뺀다.

**닫히는 이슈 줄** — 머지로 이슈를 닫는 것은 PR 본문의 닫는 키워드만이 아니다. 스쿼시
제목에 든 키워드도 닫는다. 제목은 아래 머지 명령이 `--subject` 로 전달하는 「PR 제목 (#N)」이다.
본문은 아래에서 `--body` 로 직접 전달하므로 브랜치 커밋의 메시지는
스쿼시 커밋에 안 들어가고, 거기에만 든 키워드는 안 닫는다. 그래도 아래 셋을 다 실행한다.
닫히지 않을 번호가 섞이는 것이 빠뜨리는 것보다 낫다. 출력은 `evidence.sh` 가 덧붙인 그대로다. 차례로
`closingIssuesReferences` 의 번호, 제목 줄, 키워드 목록이다. 제목 줄은 스쿼시 제목이 될
줄이고(셸이 해석하는 글자 앞의 `\` 는 머지 명령의 큰따옴표 안에서 빠진다), 키워드 목록은 PR 제목과 커밋 메시지 전체에서 찾은 닫는 키워드다. 무엇이 실제로
닫히는지는 사람이 그 출력을 보고 판단한다 — 세션이 판정하지 않는다. 번호가 안 나오면
`닫는 키워드 없음` 이다:

    gh pr view <N> --json closingIssuesReferences --jq '[.closingIssuesReferences[].number]'
    gh pr view <N> --json title,number --jq '"\(.title) (#\(.number))" | gsub("(?<c>[\"$`\\\\])"; "\\\(.c)")'
    gh pr view <N> --json title,commits --jq '.title, (.commits[]
        | if (.messageHeadline|endswith("…")) and (.messageBody|startswith("…"))
          then (.messageHeadline|rtrimstr("…")) + (.messageBody|ltrimstr("…"))
          else .messageHeadline + "\n" + .messageBody end)' \
      | grep -Eiow '(close[sd]?|fix(e[sd])?|resolve[sd]?):?[[:space:]]+([[:alnum:]_.-]+/[[:alnum:]_.-]+)?#[0-9]+'

**`closingIssuesReferences` 만 보지 마라.** 그 필드는 PR 본문의 키워드는 세지만 스쿼시 제목의
키워드도 커밋 메시지의 키워드도 안 센다. 버릴 레포에서 아래 머지 명령에 `--subject` 를 더하기 전의
명령으로 둘을 봤다.
닫는 키워드를 PR 제목에만 둔 PR 은 그 필드가 비어 있었는데 머지가 이슈를 닫았다. 닫은
것은 그 제목을 단 스쿼시 커밋이다. 닫는 키워드를 커밋 메시지의 본문에만 둔 PR 은 그
필드가 비어 있었고 이슈도 안 닫혔다. 둘 다 커밋이 둘인 PR 이었다. 지금은 머지 명령이 제목을
전달하므로 커밋 수와 상관없이 제목은 PR 제목이다. 제목을 `--subject` 로 전달한 커밋이 하나인
PR 에서도 제목의 키워드가 이슈를 닫았다. 그래서 출력은 이렇게 읽는다. 그 필드의 번호는
닫힌다. 제목 줄에 닫는 키워드와 같이 든 번호도 닫힌다. 키워드 목록에만 있는 번호는 **닫히지
않는 번호**다. 커밋 제목은 커밋 수와 상관없이 스쿼시 커밋에 안 실린다.

**`messageHeadline` 은 긴 제목을 자른다.** 끝에 `…` 를 붙이고, 나머지를 `…` 로 시작하는
`messageBody` 앞에 둔다. 그대로 읽으면 제목 끝의 키워드가 두 줄로 나뉘어 검색되지 않고, 번호
한가운데서 잘리면 앞자리만 검색돼 다른 번호가 나온다. 그래서 잘린 둘을 다시 잇는다. `-w` 는
`prefix #N` 처럼 낱말 안에 든 `fix` 를 빼려는 것이다.

**세션이 가려내지 않는다.** 한때 번호마다 상태를 조회해 이미 닫힌 것을 가려내게 했다가 뺐다.
판정 규칙을 두면 경계 사례가 생긴다 — 이미 닫힌 번호 · 이슈가 아니라 PR 인 번호 · 조회가 실패한
번호다. 그 경계마다 앞에서 이미 말한 문장과 어긋났다. 그 조회는 `allow` 에 없어서 설치된
레포에서는 번호마다 권한 프롬프트가 하나씩 표시된다.
출력을 그대로 보이면 그 경계가 없다. 커밋 메시지가 검증 결과로 닫는 키워드를
인용했거나 이미 닫힌 번호가 섞여 있으면, 그것도 출력에 있는 대로 보이고 사람이 판단한다.

이슈 닫기는 사람의 승인을 받는 행동인데, 머지로 닫히는 것은 닫는 명령이 따로 없어서 사람이
볼 자리가 이 초안뿐이다. PR 본문의 닫는 키워드는 여는 순간에 봤지만 본문은 그 뒤로 고치지 않고,
그 뒤 라운드에서 범위가 줄 수 있다. 커밋 메시지는 사람이 승인하는 대상이 아니다.
**없을 때도 적는다.** 사람이 승인하는 대상이라 줄이 빠지면 닫히는 것이 없는지 안 본 것인지
모른다.

**본문을 고쳐서 맞추려 하지 마라.** 본문은 연 시점의 기록이고, 그것이 낡는 것은 결함이
아니라 설계다 — 이유는 `docs/process/verification-stages.md` 4. 열한 라운드 동안 본문을
갱신하다 **여섯 번 거짓이 된** 기록이 그 절에 있다.

    gh pr merge <N> --squash --subject "<제목 조회의 출력>" --body "- PR: <이 PR 의 URL>
    - Issue: <닫히는 이슈의 URL>
    Closes #<본문 밖에서 끝낸 이슈의 번호>

    <브랜치 커밋의 트레일러 줄>"

**이어지는 줄은 첫 칸에서 시작한다.** 위 블록의 들여쓰기는 마크다운의 것이다. 들여쓴 채
전달하면 트레일러 줄이 공백으로 시작해 git 이 그것을 트레일러로 읽지 못한다.

**`--delete-branch` 를 붙이지 마라. 브랜치는 4절이 지운다.** gh 는 머지 뒤 로컬 브랜치를 먼저
지우는데, git worktree 에서는 거기서 실패한다. detached 면 현재 브랜치를 못 읽고, PR 브랜치에
있으면 base 로 옮기려는데 base 를 다른 worktree 가 쓰고 있다. 원래 체크아웃에서 번호로 머지해도
PR 브랜치를 다른 worktree 가 쓰면 그 브랜치를 지우지 못한다. 로컬 삭제가 실패하면 gh 는 원격
삭제도 건너뛰고 `rc=1` 로 끝난다(gh v2.92.0 `pkg/cmd/pr/merge/merge.go`). 서버의 머지는 이미
끝났는데 명령은 실패한 것처럼 보인다. `--squash` 를 주고 `--delete-branch` 를 빼면
gh 는 브랜치를 묻지도 지우지도 않는다.

**`-R` 을 붙이지 마라.** 이 스킬은 클론 안에서 실행되므로 필요 없다.

**사람이 이 프롬프트에서 거절하면 머지하지 않고 멈춘다.** 위 결정 코멘트는 이미
나갔으므로 **같은 코멘트를 다시 올리지 마라** — 대신 그 뒤에 코멘트로 한 줄을 남긴다:
`머지하지 않았다(권한 프롬프트에서 거절됨).` 다시 머지하라는 지시를 받으면 그때
새 결정 코멘트를 올린다. 안 그러면 `사람이 머지를 결정했다` 가 여러 벌 남아 어느 것이
실제 결정인지 알 수 없게 된다.

**제목은 `--subject` 로 전달한다.** 전달하지 않으면 GitHub 이 레포 설정 `squash_merge_commit_title`
대로 정하고, 기본값 `COMMIT_OR_PR_TITLE` 은 커밋이 하나인 PR 에서 그 커밋의 제목을 쓴다. PR 제목에
둔 규약이 알림 없이 빠진다. 전달하면 GitHub 은 그 글자를 그대로 쓰고 `(#N)` 을 붙이지 않는다(버릴
레포에서 커밋이 하나인 PR 둘로 봤다). 그래서 제목 조회가 「PR 제목 (#N)」을 만든다.

**본문은 인라인 `--body` 로 전달한다.** 전달하지 않으면 GitHub 이 브랜치 커밋 메시지를 전부 이어 붙여
스쿼시 본문으로 쓴다. 라운드를 여러 번 진행한 PR 에서는 그것이 백 줄을 넘고, 커밋마다의 트레일러가
그대로 쌓여 같은 줄이 커밋 수만큼 되풀이된다. 전달하면 GitHub 은 그 기본 본문도, 끝에
덧붙이던 자기 `Co-authored-by:` 줄도 붙이지 않는다. 무엇을 왜 바꿨는지는 PR 본문과 결정
코멘트와 dev-log 항목에 이미 있다. 그래서 본문에는 이 PR 과 닫히는 이슈의 주소와, 브랜치 커밋이 단
트레일러를 중복 없이 적는다. 스쿼시 제목의 `(#N)` 은 GitHub 웹에서만 링크이고 `git log` 에서는
글자라, 주소를 본문에 적는다.

제목은 이 조회가 낸다. 위 「닫히는 이슈 줄」의 제목 줄과 같은 식이다:

    gh pr view <N> --json title,number --jq '"\(.title) (#\(.number))" | gsub("(?<c>[\"$`\\\\])"; "\\\(.c)")'

두 주소는 이 조회가 낸다. 첫 줄이 이 PR 의 URL 이고 나머지가 `closingIssuesReferences` 의 이슈
URL 이다:

    gh pr view <N> --json url,closingIssuesReferences --jq '.url, (.closingIssuesReferences[]|.url)'

트레일러는 이 조회가 낸다. 브랜치의 커밋들이 단 트레일러에서 중복을 없앤 목록이다. 그
코드를 실제로 쓴 모델이 남고, 머지하는 세션이 값을 고르지 않는다. 서버에서 읽으므로
로컬 브랜치가 없어도 된다. 번호로 머지하는 경로에서는 로컬 `HEAD` 가 `main` 이다:

    gh pr view <N> --json commits --jq '.commits[].messageBody' \
      > "${TMPDIR:-/tmp}/pr<N>-commit-bodies.txt"; echo "rc=$?"
    grep -i '^Co-Authored-By:' "${TMPDIR:-/tmp}/pr<N>-commit-bodies.txt" | sort -u

**파이프에 바로 넣지 마라.** 조회가 실패해도 파이프라인은 빈 출력에 `rc=0` 이라
「트레일러가 없다」와 구분되지 않고, 그대로 진행하면 트레일러 없는 스쿼시 커밋이 `main` 에
들어간다. 2절의 dev-log 확인과 같은 이유다. `rc` 가 `0` 이 아니면 판정 못 한 것이라 중단한다.

- `--subject` 의 값은 제목 조회의 출력 그대로다. 조회가 셸이 해석하는 글자(`"` · `$` · 백틱 · `\`)
  앞에 `\` 를 붙여 내므로 큰따옴표 안에 그대로 넣는다. 세션이 고르거나 고치지 않는다. 백틱과
  작은따옴표가 든 제목을 버릴 레포에서 이 명령 그대로 머지해, 스쿼시 제목이 PR 제목 그대로인 것을 봤다
- `- PR:` 과 `- Issue:` 의 값은 주소 조회의 출력 그대로다. 세션이 고르거나 조립하지 않는다. 이슈
  줄이 안 나오면 `- Issue:` 줄을 빼고, 둘 이상이면 이슈마다 한 줄이다
- `Closes #<번호>` 줄은 봇 설정이 있고 본문 밖에서 끝낸 이슈가 있을 때만 쓴다(위 「봇 설정이 있으면 닫는 명령
  대신」). 이슈마다 한 줄이고, 틀의 자리(`- Issue:` 줄 바로 아래, 트레일러 줄 앞의 빈 줄 위)에 둔다. 트레일러
  줄 뒤에 붙이면 git 이 그 문단을 트레일러로 읽지 못해 스쿼시 커밋에서 트레일러가 사라진다. 없으면 그 줄을 뺀다
- 라벨은 영어다. 커밋 메시지는 영어라는 규칙이 이 본문에도 적용된다
- 트레일러 줄은 트레일러 조회의 출력 그대로다. 한 줄이면 한 줄, 여럿이면 줄마다 하나다. `rc=0`
  인데 아무것도 안 나오면 트레일러 줄을 쓰지 않는다. 세션이 지어내지 않는다

**`--body-file` 을 쓰지 마라.** 파일로 전달하면 명령에 경로만 남아, 사람에게 보이는 머지 명령
전문에도 권한 프롬프트에도 커밋에 들어갈 글이 없다. 인라인이면 명령이 곧 내용이다. 이
본문에는 셸이 깨뜨릴 백틱도 따옴표도 없다.

**빈 문자열을 전달하지 마라.** 본문이 통째로 비고 **트레일러까지 사라진다**(실제로 한
프로젝트의 `main` 커밋 둘에서 그렇게 됐고, 히스토리 재작성 없이는 못 고친다). 사람이
고치지 않기로 한 발견은 위 결정 코멘트에 이미 적으므로 여기 다시 적을 것이 없다.

**권한 프롬프트가 표시된다.** 이 명령과 위의 `gh pr comment` 는 둘 다 `settings.json` 의
`ask` 에 있고, 이 스킬 안에서 실행해도 마찬가지다. 사람이 승인할 때까지 기다린다 —
`SKILL.md` 의 「꼭 지킬 것」이 요구하는 "사람이 머지를 지시했다" 를 기계로 한 번 더 확인하는 자리다.
**프롬프트로 사람이 확인할 수 있는 것은 명령까지다.** `gh pr merge` 는 명령이 곧 내용이지만
여러 줄 본문까지 프롬프트에 보이는지는 확인하지 않았고, 결정 코멘트는 `--body-file` 이라
**프롬프트에 파일 경로만 보인다.**

**머지가 끝나면 이 PR 이 끝낸 이슈를 닫는다.** 위에서 보이고 승인받은 `gh issue close` 명령을
그대로 실행한다. 이 명령은 `settings.json` 의 `ask` 에 있어 권한 프롬프트를 거친다. 사람이
거절하면 이슈를 연 채 두고 5절의 보고에 한 줄 덧붙인다. `dev-log` 가 계획 문서에서 그 이슈의
줄을 지웠으면 그 사실도 같이 적는다 — 이슈는 열려 있는데 계획에서는 빠진다. 명령을 보이지
않았으면(끝낸 이슈가 없으면) 아무것도 닫지 않는다.

### 봇 설정이 있을 때 — auto-merge 를 켜고 끝낸다

2절에서 auto-merge 를 켤 수 있다고 본 PR 이다. 차례는 이렇다.

1. 결정 코멘트 초안 · 아래 머지 명령 전문을 응답에 출력한다. 머지가 닫지 않지만 이 PR 이 끝낸 이슈가 있으면
   그 이슈를 머지 명령의 `--body` 에 `Closes #<번호>` 줄로 넣고 창으로 승인받는다. 없으면 창은 없다.
2. 결정 코멘트를 올린다(위 `gh pr comment` 한 줄).
3. auto-merge 를 켠다:

       gh pr merge <N> --auto --squash --match-head-commit <headRefOid> --subject "<제목 조회의 출력>" --body "- PR: <이 PR 의 URL>
       - Issue: <닫히는 이슈의 URL>
       Closes #<본문 밖에서 끝낸 이슈의 번호>

       <브랜치 커밋의 트레일러 줄>"

   `--subject` · `--body` 는 위 머지 명령과 같은 규칙으로 쓴다. gh 는 `--match-head-commit` 의 값을 auto-merge 의
   `expectedHeadOid` 로 전달한다(gh v2.92.0 `pkg/cmd/pr/merge/http.go`). GitHub 이 그 값을 머지할 때도 대조하는지는
   확인하지 않았다. 켠 뒤에 오는 새 커밋을 막는 것은 막기 훅뿐이고, 그 훅은 세션의 푸시만 막는다(아래). 사람이
   PR 브랜치에 푸시하면 막는 것이 없다 — 마지막 푸시 승인은 푸시한 사람의 Approve 만 세지 않으므로, 쓰기 권한이
   있는 다른 사람이 Approve 하는 순간 새 커밋이 든 채로, 켤 때 담긴 옛 제목 · 본문과 옛 결정 코멘트대로 머지된다. 그래서
   사람은 PR 브랜치에 푸시하기 전에 세션에 알려 auto-merge 를 끄게 한다(`docs/process/kit-guide.md` 3절).

   **켜는 명령이 실패하면** 결정 코멘트가 말하는 「Approve 하면 GitHub 이 머지한다」가 거짓이 된다. 결정 코멘트
   뒤에 코멘트로 한 줄 `auto-merge 를 켜지 못했다: <gh 가 낸 오류의 첫 줄>. 사람이 Approve 하면 세션이 확인하고
   머지한다.` 를 남기고, 2절의 「그 밖이면 세션이 Approve 를 확인한다」를 따른다. 요청 블록도 그 절의 것(결과 줄
   둘을 바꾼 것)이다. 봇이 auto-merge 를 켤 권한이 없거나, 2절과 이 명령 사이에 PR 이 바로 머지할 수 있는 상태가
   되어 막기 훅이 막은 경우다.
4. 응답을 2절의 Approve 요청 블록과 창으로 끝낸다. 블록 ① 의 결과 줄 「GitHub: 곧바로 머지 (레포 설정
   auto-merge, 따로 확인 없음)」이 Approve 하면 확인 없이 바로 머지된다는 것을 알린다 — auto-merge 없이 머지할
   때는 Approve 뒤에 세션이 한 번 더 확인했으므로, 사람은 누르기 전에 그 차이를 알아야 한다. 머지되면 GitHub 이
   head 브랜치를 지운다. 5절의 `Auto-merge on …` 줄도 이 응답에 적는다.

**머지되기 전에 다시 해야 하면 먼저 끈다.** 브랜치에 푸시해야 할 때와, 사람이 결정 코멘트나 스쿼시 제목 · 본문을
고치라고 할 때다. 차례는 이렇다.

1. `gh pr merge <N> --disable-auto` 로 끈다.
2. 옛 결정 코멘트 뒤에 코멘트로 한 줄 `auto-merge 를 껐다. 이 결정 코멘트로는 머지하지 않는다.` 를 남긴다. 올리는
   시점의 사실만 적는다 — 다시 켤지는 그 뒤의 일이다.
3. 푸시해야 하면 푸시한다.
4. 2절부터 다시 한다(결정 코멘트 · auto-merge · 요청). 푸시했으면 2절의 「리뷰 반영 확인」이 새 커밋을 나열하며
   멈추고, 한 라운드 더 할지는 사람이 정한다.

끄지 않으면 사람이나 다른 리뷰어가 Approve 하는 순간 켤 때 담긴 옛 제목 · 본문과 옛 결정 코멘트대로 머지된다.
옛 결정 코멘트를 편집하지 않는 이유는 3절의 거절 경로와 같다 — 한 번 올린 기록이 바뀐다. 막기 훅(`bot_guard.sh`)이
auto-merge 가 켜진 PR 의 브랜치로 가는 푸시를 막는다.

**다음 작업을 시작할 때 auto-merge 가 켜진 열린 PR 과 머지된 PR 을 본다.** 머지는 사람이 Approve 한 순간 GitHub 이
하므로 세션이 그 자리에 없고, Approve 를 받고도 머지되지 못할 수도 있다. 다음 작업의 브랜치를 만들기 전에 둘을 본다:

    gh pr list --state open --json number,headRefName,reviewDecision,mergeStateStatus,autoMergeRequest --jq '.[] | select(.autoMergeRequest != null) | "#\(.number) \(.headRefName) \(.reviewDecision) \(.mergeStateStatus)"'
    gh pr list --state merged --limit 30 --json number,headRefName --jq '.[] | "#\(.number) \(.headRefName)"'

- auto-merge 가 켜진 열린 PR 가운데 `reviewDecision` 이 `APPROVED` 인 것은 Approve 를 받고도 머지되지 못한 것이다.
  브랜치가 base 보다 뒤처졌거나(`BEHIND` — `install.sh --protect` 가 켜는 브랜치 보호는 최신 브랜치를 요구한다),
  충돌했거나(`DIRTY`), 필요한 검사가 실패했거나 풀리지 않은 리뷰 대화가 있다(`BLOCKED` — `--protect` 가 켜는 브랜치
  보호는 대화 해결도 요구한다). 사람에게 그 PR 과 상태를 알린다. 브랜치를 갱신하는 절차는 킷에 아직 없으므로 세션이
  스스로 갱신하지 않는다 — base 를 합치면 2절의 「리뷰 반영 확인」이 다른 PR 의 커밋을 이 PR 의 커밋으로 나열하고,
  충돌을 푼 내용은 파일 없이 나열한다. 어떻게 할지는 사람이 정한다
- `REVIEW_REQUIRED` 인 것은 Approve 를 기다리는 중이라 그대로 둔다
- 머지된 PR 가운데 로컬 브랜치가 남은 것(`git rev-parse --verify --quiet <headRefName>` 이 출력을 낸다)은
  머지 뒤 정리를 하지 않은 것이다 — 사람이 GitHub 에서만 Approve 하고 「PR #N 최종 검토」 창을 고르지 않았거나,
  세션이 그 전에 끝났을 때 그렇다. `merge-pr <N>` 으로 정리한다(2절이 `MERGED` 를 보고 4절과 5절만 한다). 사람이
  이미 다음 일을 시켜서 이 확인을 하는 중이면 정리한 뒤 그 일로 돌아가고(5절), 시킨 일 없이 정리만 했으면 다른
  일을 시작하기 전에 「다음 일」 창(2절)으로 묻는다

그리고 다음 작업의 브랜치는 `origin/<baseRefName>` 에서 만든다. 앞 PR 브랜치 위에 만들면 앞 PR 이 스쿼시로 머지된
뒤 다음 PR 의 diff 에 그 변경이 다시 나온다. 세션 시작 안내(`bot_session.sh`)와 템플릿 `CLAUDE.md` 의 작업 루프도
이것을 알린다 — 새 세션이나 컴팩션 뒤의 세션은 이 스킬을 읽지 않은 채 다음 작업을 시작한다. 원격 브랜치를 레포
설정 「Automatically delete head branches」가 지웠으면 4절의 원격 삭제는 `remote ref does not exist` 로 끝난다. 그
설정이 꺼진 레포에서는 4절이 지운다(승인은 Approve 다). 머지 뒤에야 나온 것이 있으면 4절의 후속 코멘트로 붙인다.
