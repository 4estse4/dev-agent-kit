## 1. PR 번호 확정
`$ARGUMENTS` 가 있으면 그것, 없으면 위 출력. 둘 다 없으면 중단:
`Error: PR 번호를 확정할 수 없습니다.`

## 2. 머지 전 안전 확인

### 전제 — 사람이 머지를 지시했을 때만 진행한다

**지시가 있어야 이 스킬이 돈다.** 두 리뷰가 `Approve` 를 냈다는 것은 그 리뷰들의
의견이지 허락이 아니고, CI 가 초록인 것도 허락이 아니다. 허락은 사람이 한다.

지시 없이 여기까지 왔으면 머지하지 말고 **`open-pr` 3.5 멈추고 보고 대로 보고하고 멈춘다.**

### 그다음 — 하나라도 실패하면 즉시 중단

- `gh pr view <N> --json state,headRefName,headRefOid` → `state` 가 `OPEN` 이 아니면 중단.
  나머지 둘은 아래와 4절이 쓴다.
- `gh pr checks <N>` → `fail` 또는 `pending` 이 하나라도 있으면 중단하고 해당 체크를 나열한다.
- 위 `git status --porcelain` 이 비어 있지 않으면 중단.
- **푸시 안 한 커밋 확인. 머지 전인 여기서 한다.** 3절의 `--delete-branch` 는 로컬 브랜치를
  지울 수 있고 **그때 gh 는 푸시 여부를 보지 않는다.** 4절로 미루면 이미 없어진 뒤다:

      git rev-parse --verify --quiet <headRefName>          # 아무것도 안 나오면(rc=1) 볼 것이 없다
      git merge-base --is-ancestor <그 값> <headRefOid>      # rc 가 0 이 아니면 중단한다

  **같은지로 보지 마라 — 조상인지로 본다.** 로컬이 서버 head 보다 **뒤처진** 것은 지워도
  잃을 것이 없고(예전에 받아둔 브랜치를 번호로 머지하는 경우), **앞선** 것만 위험하다.
  같은지로 보면 안전한 쪽까지 막아서 머지된 브랜치가 그대로 쌓인다.
  네 방향으로 깨봤다 — 같음 `0` · 뒤처짐 `0` · 앞섬 `1` · 없는 객체 `128`.
  **`0` 이 아닌 것은 다 중단이다.** 판정 못 한 것을 통과로 치지 않는다.
- **리뷰 반영 확인.** `open-pr` 이 올린 **마지막 라운드 코멘트**를 읽는다:

      gh pr view <N> --json comments \
        --jq '[.comments[] | select(.body|test("^\\s*## 리뷰 "))] | last | .body'

  그 코멘트 **맨 위의** `리뷰한 head:` 를 **위 첫 줄에서 받아둔 `headRefOid`** 와 비교한다.
  접힌 전문 안에도 같은 줄이 있으므로 맨 위 것을 쓴다.

  **다르면** 마지막 라운드 뒤에 커밋이 더 쌓인 것이고 그 커밋들은 아무도 안 봤다.
  중단하고 **어느 커밋인지 나열해** 사람에게 말한다(`git log <그 head>..HEAD --oneline`).
  사람이 그것을 알고도 머지하라고 하면 진행하되, **3절의 결정 코멘트에 그 커밋 목록과
  "리뷰를 거치지 않았다" 를 적는다.** 이것은 정상 경로다 — `open-pr` 이 사람에게
  제시하는 답에 "고치고 추가 라운드 없이 머지" 가 들어 있고, 그렇게 하면 head 는
  반드시 달라진다. 막는 것이 목적이 아니다. **리뷰를 거치지 않은 커밋이 있다는 사실을
  기록 없이 지나가지 않게 하는 것**이 목적이다.

  **`리뷰한 head:` 줄이 아예 없으면** 옛 형식의 코멘트다. 대조할 수 없으므로 통과로
  치지 말고, 그 사실을 말하고 사람의 판단을 받는다.

  두 리뷰의 `Verdict` 는 그 코멘트 첫 줄에 있다. `Request changes` 가 해소되지 않았으면
  중단 — 사람이 그것을 넘기기로 했다면 그 사실을 3절에 적는다.

  라운드 코멘트를 못 찾으면 **리뷰가 돌지 않은 것이다.** 중단한다.

  **그 코멘트 뒤의 코멘트도 읽는다** — `open-pr` 3.5 의 코멘트이고, **마지막 라운드 뒤에
  사람이 정한 것이 거기 있다.** 그 라운드가 끝난 뒤에 온 답이라 라운드 코멘트에는 없다:

      gh pr view <N> --json comments \
        --jq '[.comments[].body] as $b
              | ([$b|to_entries[]|select(.value|test("^\\s*## 리뷰 "))|.key]|last) as $i
              | if $i == null then [] else $b[$i+1:] end
              | map(select(test("^\\s*### .*라운드에 사람이 준 답")))
              | join("\n\n———\n\n")'

  **위치만으로 고르지 않는다.** 그 창에는 **이 스킬이 올린 코멘트도 들어간다** — 아래
  「사람이 거절하면」 경로가 결정 코멘트와 `머지하지 않았다…` 한 줄을 그 뒤에 남기고,
  다시 지시받으면 새 결정 코멘트를 올린다. 위치만 보면 옛 결정 코멘트가 **사람의 답으로**
  새 결정 코멘트에 인용되고, `사람이 머지를 결정했다` 가 여러 벌 남는 그 상태가 형태만
  바꿔 돌아온다. 그래서 3.5 의 코멘트가 쓰는 제목으로 좁힌다.

> 이 확인은 편의이지 강제가 아니다. 진짜 강제는 GitHub 브랜치 보호다
> (킷의 `install.sh --protect` 가 설정한다). 브랜치 보호가 없는 레포라면 그 사실을 먼저 알린다.

## 3. 머지
`git log main..HEAD --format='%s'` 로 커밋 제목을 보고 사소한 것(리뷰수정·fixup·포맷)을 뺀
목록을 만든 뒤:

머지 **전에**, 사람이 무엇을 보고 정했는지를 PR 에 남긴다 — 머지 후에는 그 맥락을
복원할 곳이 없다. 리뷰가 남아 있는데 그것을 넘기고 머지하기로 했다면 특히 그렇다.

    gh pr comment <N> --body-file <파일>

**이 코멘트가 이 PR 의 최종 정리다.** PR 본문은 열 때 쓰고 얼렸으므로(`open-pr` 「본문
작성 규칙」), 그 뒤에 달라진 것을 말하는 자리가 여기밖에 없다. 아래를 적는다:

- 라운드 수와 마지막 라운드의 두 `Verdict`
- PR 본문이 지금은 틀린 곳. 라운드가 본문의 결론을 바꿨으면 무엇이 어떻게 바뀌었는지,
  그리고 본문에 붙인 증거 중 지금 다시 돌리면 다르게 나오는 것. 없으면 `본문 그대로`
- 마지막 라운드 뒤 3.5 의 코멘트에 사람이 남긴 답. 그 라운드에 안 고친 것과 안 하기로
  한 것. 사람이 쓴 문장을 그대로 옮긴다
- 이 PR 이 킷이 배포하는 파일의 이름이나 경로를 바꿨으면, 설치된 레포에 옛 이름으로
  무엇이 남는지. 안 바꿨으면 이 줄을 아예 쓰지 않는다
- 고쳐야 한다고 올라왔는데 고치지 않고 머지하는 것이 있으면 그것과 이유
- 남은 것을 이슈로 옮겼으면 그 번호
- `사람이 머지를 결정했다`

**둘째 줄** — 라운드 코멘트의 `### 본문 정정` 들을 모아 옮긴다. 결론만 적으면 거짓이 된
출력이 갈 곳이 없어져 닫히지 않는 이월이 된다.

**셋째 줄** — 라운드 코멘트에 없는 유일한 기록이라 여기서 안 옮기면 사라진다. 요약하지
마라(`open-pr` 「출처 다섯」의 규칙 1) — 이 코멘트는 머지 뒤 **유일한 최종 기록**이라 요약하면
되돌릴 자리가 없고, 승인 프롬프트에서 사람이 대조할 원문도 사라진다. 없으면 그 줄을 뺀다.

**넷째 줄** — `install.sh` 는 킷이 **지금 배포하는** 파일만 순회하므로 옛 이름은 안 지워진다.
`개명 없음` 도 쓰지 마라 — 프로젝트는 킷이 배포하는 파일을 소유하지 않으므로, 늘 뜨면
**한 레포에서만 참인 줄을 모든 레포가 진다.**

**본문을 고쳐서 맞추려 하지 마라.** 본문은 연 시점의 기록이고, 그것이 낡는 것은 결함이
아니라 설계다 — 이유는 `docs/process/verification-stages.md` 의 「PR 본문은 열 때 쓰고
끝이다」. 열한 라운드 동안 본문을 갱신하다 **여섯 번 거짓이 된** 기록이 그 절에 있다.

    gh pr merge <N> --squash --delete-branch

**`-R` 을 붙이지 마라.** 이 스킬은 클론 안에서 도므로 필요 없고, **그 플래그가 gh 의 로컬
브랜치 삭제를 끄는 조건이라는 지적이 리뷰에서 나왔다.** 붙이지 않는 것으로 조건을 하나
줄여둔다.

> **이 명령이 로컬 브랜치까지 지우는지는 아직 모른다.** 아는 것은 셋뿐이다 —
> `gh pr merge --help` (2.92.0)가 `Delete the local and remote branch after merge` 라고
> 적고, **안 지우는 조건은 그 문서에 없다.** 그런데 PR #52 머지 뒤 로컬
> `docs/weigh-findings-before-fixing` 은 **남았고**, 그 뒤로 머지된 브랜치 열셋이 로컬에
> 쌓여 있었다. **어느 조건이 갈랐는지는 확인 못 했다** — 그때의 실제 호출을 되짚을 수 없다.
> **이 스킬이 다음에 도는 머지 한 번이 그것을 정한다.** 그때 gh 가
> `Deleted local branch <이름>` 을 찍는지 보고 이 절과 4절을 다시 쓴다.

**사람이 이 프롬프트에서 거절하면 머지하지 않고 멈춘다.** 위 결정 코멘트는 이미
나갔으므로 **같은 코멘트를 다시 올리지 마라** — 대신 그 뒤에 코멘트로 한 줄을 남긴다:
`머지하지 않았다(권한 프롬프트에서 거절됨).` 다시 머지하라는 지시를 받으면 그때
새 결정 코멘트를 올린다. 안 그러면 `사람이 머지를 결정했다` 가 여러 벌 남아 어느 것이
실제 결정인지 알 수 없게 된다.

**`--body` 를 넘기지 마라.** 빈 문자열을 주면 GitHub 이 넣는 기본 스쿼시 본문이 통째로
지워지고 **그 안의 `Co-Authored-By` 트레일러까지 사라진다**(이슈 #41 의 기록. 실제로
한 프로젝트의 `main` 커밋 둘에서 그렇게 됐다). 사람이 넘기기로 한 지적은 위 결정
코멘트에 이미 적으므로 여기 다시 적을 값이 없다.

**권한 프롬프트가 뜬다.** 이 명령과 위의 `gh pr comment` 는 둘 다 `settings.json` 의
`ask` 에 있고, 이 스킬 안이라고 해서 비켜가지 않는다. 사람이 승인할 때까지 기다린다 —
이 스킬 §전제 가 요구하는 "사람이 머지를 지시했다" 를 기계로 한 번 더 세우는 자리다.

## 4. main 복귀와 로컬 브랜치 삭제
`git checkout main` → `git pull --ff-only`.
fast-forward 실패 시 중단: `Error: main 을 fast-forward 할 수 없습니다.`

**`--delete-branch` 가 로컬까지 지웠는지는 그때그때 다르다.** 그래서 **있으면 지우고 없으면
넘어간다** — 없는 것은 실패가 아니다:

    git rev-parse --verify --quiet <headRefName>   # 아무것도 안 나오면(rc=1) 끝이다. 5절로 간다
    gh pr view <N> --json state -q .state          # MERGED 가 아니면 중단한다
    git branch -D <headRefName>                    # 위 둘을 통과했을 때만 여기 온다

`<headRefName>` 은 2절이 이미 받아둔 값이다. **이름을 여기서 새로 구하지 마라** — 이 절은
`git checkout main` **뒤**라 현재 브랜치는 `main` 이고, `$ARGUMENTS` 로 **다른 PR 을 번호로
머지하는 것이 정상 경로**다(`argument-hint`). 이름을 따로 얻으면 `MERGED` 확인과 삭제
대상이 갈라진다. **그 확인은 시점만 세우지 대상은 안 세운다.**

**`--verify --quiet` 를 빼지 마라.** 맨 `git rev-parse <없는 브랜치>` 는 `rc=128` 로 죽으면서
**인자를 stdout 으로 되뱉는다**(`fatal:` 은 stderr 로 가서 안 보일 수 있다). 그러면 읽는 쪽이
그것을 SHA 자리에서 받고, gh 가 이미 지운 **정상 경로에서 이 절이 멈춘다.** 실측:

    $ git rev-parse nosuchbranch          → stdout `nosuchbranch`, rc=128
    $ git rev-parse --verify --quiet nosuchbranch  → 출력 없음, rc=1

**`-d` 로는 안 지워진다** — 스쿼시 머지라 브랜치가 `main` 의 조상이 아니어서
`not fully merged` 로 거부한다. 그래서 `-D` 다.

**`-D` 는 확인 없이 지우지만 되돌릴 수 있다** — 지운 팁 SHA 를 출력한다
(`Deleted branch <이름> (was <SHA>)`). 진짜로 잃는 것은 **커밋만 하고 안 민 것**인데,
그것을 지키는 자리는 여기가 아니라 **2절**이다. 3절의 `--delete-branch` 가 먼저 지울 수
있으므로 이 절의 검사로는 늦는다.

**`git log <브랜치> --not --remotes` 로 푸시 여부를 세지 마라.** 갈림은 스쿼시가 아니라
**원격 추적 ref 가 남아 있는지**여서, `--delete-branch` 뒤에는 **다 민 브랜치의 커밋도 전부
나온다.** 세 단계로 재현했다:

    $ git log feat --not --remotes --oneline   # push 직후, origin/feat 있음
    $ git log feat --not --remotes --oneline   # squash 머지 + push 뒤, origin/feat 아직 있음
    $ git push origin --delete feat && git fetch -p
    $ git log feat --not --remotes --oneline
    0e5bde8 f1                                 ← 앞의 둘은 비었고 여기서만 나온다

## 5. 한 줄 보고
`Merged PR #<N>. main at <short SHA>.`

이후 새 작업을 시작하지 않는다.
