## 1. PR 번호 확정
`$ARGUMENTS` 가 있으면 그것, 없으면 위 출력. 둘 다 없으면 중단:
`Error: PR 번호를 확정할 수 없습니다.`

## 2. 머지 전 안전 확인

### 전제 — 사람이 머지를 지시했을 때만 진행한다

**지시가 있어야 이 스킬이 돈다.** 두 리뷰가 `Approve` 를 냈다는 것은 그 리뷰들의
의견이지 허락이 아니고, CI 가 초록인 것도 허락이 아니다. 허락은 사람이 한다.

지시 없이 여기까지 왔으면 머지하지 말고 **`open-pr` 3.5 멈추고 보고 대로 보고하고 멈춘다.**

### 그다음 — 하나라도 실패하면 즉시 중단

- `gh pr view <N> --json state,headRefName,headRefOid,baseRefName,isCrossRepository` → `state` 가 `OPEN` 이 아니면 중단.
  나머지 넷은 바로 아래와 4절이 쓴다. **셸 변수에 담지 마라. 읽어서 출력한다** — 명령을 여러
  번 부르는 사이에 셸 상태는 유지되지 않는다(`open-pr` 3.1 이 그 사고로 적어둔 규칙이다).
- `gh pr checks <N>` → `fail` 또는 `pending` 이 하나라도 있으면 중단하고 해당 체크를 나열한다.
- 위 `git status --porcelain` 이 비어 있지 않으면 중단.
- **로컬 브랜치가 서버와 같은지 본다. 머지 전인 여기서 한다:**

      git rev-parse --verify --quiet <headRefName>   # 출력이 없으면 로컬에 그 브랜치가 없다. 넘어간다

  출력이 있으면 그 SHA 를 위에서 받은 `headRefOid` 와 **글자로** 견준다. **다르면 중단하고
  사람에게 말한다.** 대개 커밋만 하고 안 민 것이 있는 것이다. 로컬이 뒤처진 경우도 여기서
  멈추는데, 그쪽은 멈춰도 잃는 것이 없다.

  **왜 머지 전인가.** 4절의 `git branch -D` 는 로컬에만 있는 커밋이 있어도 그 브랜치째 지운다.
  그리고 푸시하지 않은 커밋은 머지에도 들어가지 않는다. 그래서 **머지하기 전이자 지우기 전인 여기서
  본다.**

  **왜 글자로 견주나.** 두 커밋의 관계(`git merge-base --is-ancestor`)를 보면 서버 쪽 커밋이
  로컬에 있어야 판정되고, 없으면 `rc=128` 로 떨어져 멀쩡한 머지를 막는다. 글자 비교는 로컬
  객체를 요구하지 않는다.
- **이 PR 의 dev-log 항목이 있나.** 서버 head 에서 본다 — 로컬은 안 민 커밋을 들고 있을 수 있고,
  번호로 머지하는 정상 경로에서는 그 head 의 객체가 로컬에 없을 수 있다. 그래서 로컬 객체를
  요구하지 않는 조회로 본다. **파일로 먼저 받고 종료 코드를 본 뒤에 센다. 파이프에 넣지 마라:**

      gh api "repos/{owner}/{repo}/contents/docs/dev-log.md?ref=<headRefOid>" \
          -H "Accept: application/vnd.github.raw" > "${TMPDIR:-/tmp}/pr<N>-dev-log.md"; echo "rc=$?"
      grep -cE '^## .*\(PR [^)]*#<N>([^0-9]|\)|$)' "${TMPDIR:-/tmp}/pr<N>-dev-log.md"

  판정은 셋이다. `rc=0` 에 `1` 이상이면 있다. `rc=0` 에 `0` 이면 파일은 있는데 항목이 없다 — 중단하고
  사람에게 말한다. dev-log 는 머지 직전에 쓰는 것이라(`dev-log` 스킬) 여기서 없으면 안 쓴 것이다.
  사람이 그것을 알고도 머지하라고 하면 진행하되, **3절의 결정 코멘트에 「dev-log 항목 없음」을
  적는다.** `rc` 가 `0` 이 아니면(404 든 네트워크든) 판정 못 한 것이라 중단한다. 그것을 알고도
  머지하라고 하면 결정 코멘트에 「dev-log 항목 판정 못 함」을 적는다 — 판정 못 한 것을 「없음」으로
  적는 것이 이 확인이 없애려는 거짓 기록이다.
  `gh api` 는 설치되는 `settings.json` 의 `ask` 에 있어 설치된 레포에서는 이 조회에 권한 프롬프트가
  하나 뜬다. 읽기뿐이라 승인하면 그대로 간다.
  **파이프에 넣지 않는 이유**: `gh api` 는 실패해도 오류 JSON 을 stdout 으로 내고 `grep -c` 가
  그것을 `0` 으로 센다 — 「항목 없음」과 같은 숫자다. 파일로 받으면 종료 코드가 둘을 가른다.
  **파일을 `${TMPDIR:-/tmp}` 에 두는 이유**: 레포 안에 쓰면 위 `git status --porcelain` 확인이
  깨지고, `$(mktemp)` 를 변수에 담으면 명령을 따로 부르는 사이에 셸 상태가 안 남는다(위 첫 불릿과
  같은 이유다).
  정규식이 `(PR #<N>)` 보다 느슨한 이유: 한 항목이 PR 둘을 들 수 있다(`(PR #13 · #14)`). 번호 뒤를
  `[^0-9]` 로 막아 `#6` 이 `#69` 에 맞지는 않는다. `git show <headRefOid>:docs/dev-log.md` 를 쓰지
  않는 이유: 객체가 로컬에 없을 때와 파일이 없을 때가 같은 `fatal` 과 `0` 을 내 둘을 못 가른다.
- **리뷰 반영 확인.** `open-pr` 이 올린 **마지막 라운드 코멘트**를 읽는다:

      gh pr view <N> --json comments \
        --jq '[.comments[] | select(.body|test("^\\s*## 리뷰 "))] | last | .body'

  그 코멘트 **맨 위의** `리뷰한 head:` 를 **위 첫 줄에서 받아둔 `headRefOid`** 와 비교한다.
  접힌 전문 안에도 같은 줄이 있으므로 맨 위 것을 쓴다.

  **다르면** 마지막 라운드 뒤에 커밋이 더 쌓인 것이고 그 커밋들은 아무도 안 봤다.
  중단하고 **어느 커밋인지 파일까지 나열해** 사람에게 말한다. 끝점은 위에서 받은 `headRefOid`
  다. 로컬 `HEAD` 가 아니다. 번호로 머지하는 정상 경로에서는 `HEAD` 가 `main` 이라 목록이
  비거나 남의 커밋이 나온다. 그 객체가 로컬에 없을 수 있으므로 먼저 받는다:

      git fetch origin <headRefName>; echo "rc=$?"
      git log <그 head>..<headRefOid> --format='%h %s' --name-only; echo "rc=$?"

  `git fetch` 는 설치되는 `settings.json` 의 `allow` 에 없어 설치된 레포에서는 이 fetch 에 권한
  프롬프트가 하나 뜬다. 읽기뿐이라 승인하면 그대로 간다.
  판정은 둘이다. `fetch` 나 `log` 의 `rc` 가 `0` 이 아니면 판정 못 한 것이라 중단한다. dev-log
  확인과 같은 규칙이다. 그것을 알고도 머지하라고 하면 결정 코멘트에 「나열 판정 못 함」을
  적는다. **head 가 다른데 목록이 비면 둘 중 하나다.** 서버 head 가 마지막 라운드 head 의
  조상이면 되감기다. 브랜치가 리뷰한 것보다 뒤로 돌아갔다. 그 사실을 사람에게 말하고
  중단한다. 그 밖에 목록이 비면 명령이 잘못 돈 것이라 중단한다. 둘을 가르는 명령:

      git merge-base --is-ancestor <headRefOid> <그 head>; echo "rc=$?"   # 0 이면 되감기

  끝점이 `origin/<headRefName>` 이 아닌 이유: 2절의 다른 확인이 전부 `headRefOid` 에 묶여
  있고, 그 값을 읽은 뒤 누가 밀면 브랜치 이름이 가리키는 것이 달라진다.
  사람이 그것을 알고도 머지하라고 하면 진행하되, **3절의 결정 코멘트에 그 커밋 목록과
  "리뷰를 거치지 않았다" 를 적는다.** 이것은 정상 경로다 — `open-pr` 이 사람에게
  제시하는 답에 "고치고 추가 라운드 없이 머지" 가 들어 있고, 그렇게 하면 head 는
  반드시 달라진다. 막는 것이 목적이 아니다. **리뷰를 거치지 않은 커밋이 있다는 사실을
  기록 없이 지나가지 않게 하는 것**이 목적이다.

  **dev-log 커밋은 늘 여기 걸린다.** `dev-log` 스킬이 머지 직전에 돌므로 그 커밋은 마지막
  라운드 뒤에 온다. dev-log 를 쓴 PR 마다 이 확인이 멈추고, 그것은 결함이 아니라 이 확인이
  하는 일이다. 사람에게 말할 때 커밋을 둘로 갈라 적는다. `docs/dev-log.md` **하나만** 바뀐
  커밋과 그 밖의 커밋이다. 기준은 파일이지 커밋 제목이 아니다. 위 나열 명령이 커밋마다
  건드린 파일을 내므로 갈래는 그 출력대로다. 세션이 판정하지 않는다. dev-log 항목과 계획
  줄 삭제가 한 커밋이면 파일이 둘이라 「그 밖」이다. 그 커밋이 계획 문서의 다른 줄을 같이
  건드렸는지는 파일 이름만으로 모르므로 사람이 한 번 본다. **사람이 보는 것은 그 밖의
  커밋이다.** 3절의 「리뷰를 거치지 않은 커밋」 줄에도 같은 구분으로 적는다. 「dev-log 만
  바뀐 커밋은 빼고 센다」는 예외는 넣지 않는다. 가르는 쪽이 틀리면 리뷰를 안 거친 변경이
  조용히 지나가고, 가르지 못할 때는 사람에게 보인다.

  **`리뷰한 head:` 줄이 아예 없으면** 옛 형식의 코멘트다. 대조할 수 없으므로 통과로
  치지 말고, 그 사실을 말하고 사람의 판단을 받는다.

  두 리뷰의 `Verdict` 는 그 코멘트 첫 줄에 있다. `Request changes` 가 해소되지 않았으면
  중단 — 사람이 그것을 넘기기로 했다면 그 사실을 3절에 적는다.

  라운드 코멘트를 못 찾으면 **리뷰가 돌지 않은 것이다.** 중단한다.

  **그 코멘트 뒤의 코멘트도 읽는다** — `open-pr` 3.5 의 코멘트이고, **마지막 라운드 뒤에
  사람이 정한 것이 거기 있다.** 그 라운드가 끝난 뒤에 온 답이라 라운드 코멘트에는 없다:

      gh pr view <N> --json comments \
        --jq '[.comments[].body] as $b
              | ([$b|to_entries[]|select(.value|test("^\\s*## 리뷰 "))|.key]|last) as $i
              | if $i == null then [] else $b[$i+1:] end
              | map(select(test("^\\s*### .*라운드 코멘트를 읽고 사람이 정한 것")))
              | join("\n\n———\n\n")'

  **위치만으로 고르지 않는다.** 그 창에는 **이 스킬이 올린 코멘트도 들어간다** — 아래
  「사람이 거절하면」 경로가 결정 코멘트와 `머지하지 않았다…` 한 줄을 그 뒤에 남기고,
  다시 지시받으면 새 결정 코멘트를 올린다. 위치만 보면 옛 결정 코멘트가 **사람의 답으로**
  새 결정 코멘트에 인용되고, `사람이 머지를 결정했다` 가 여러 벌 남는 그 상태가 형태만
  바꿔 돌아온다. 그래서 3.5 의 코멘트가 쓰는 제목으로 좁힌다.

> 이 확인은 편의이지 강제가 아니다. 진짜 강제는 GitHub 브랜치 보호다
> (킷의 `install.sh --protect` 가 설정한다). 브랜치 보호가 없는 레포라면 그 사실을 먼저 알린다.

## 3. 머지

머지 **전에**, 사람이 무엇을 보고 정했는지를 PR 에 남긴다 — 머지 후에는 그 맥락을
복원할 곳이 없다. 리뷰가 남아 있는데 그것을 넘기고 머지하기로 했다면 특히 그렇다.

**올리기 전에 초안 전문을 사람에게 보이고 승인받는다.** 머지와 한 몸이고 머지 전에 쓰는
마지막 기록이라 사람의 승인을 받는 행동이다. 기준은
`docs/process/verification-stages.md` 6.3 에 있다. 아래 권한
프롬프트는 이 승인을 대신하지 못한다 — 파일 경로만 보인다.

**초안과 함께 아래 머지 명령 전문도 보인다.** 스쿼시 커밋의 본문이 그 명령 안에 있고,
틀리면 히스토리 재작성 없이는 못 고친다. 권한 프롬프트는 승인이 아니고, 프롬프트가 안
뜨는 레포도 있다. 여러 줄 본문이 프롬프트에 다 보이는지는 확인하지 않았다. 프롬프트에서
거절하면 아래 거절 경로가 돌아 결정 코멘트가 두 벌이 된다. 그래서 사람이 본문을 보는
자리는 여기다.

**4절의 삭제 명령 둘도 같이 보인다.** 원격 브랜치를 지우는 `git push origin --delete
<headRefName>` 과 로컬 브랜치를 지우는 `git branch -D <headRefName>` 이다. 머지 명령이
브랜치를 지우지 않으므로(아래 머지 명령 뒤의 설명) 이 둘은 머지 뒤에 따로 실행되지만, 승인은
머지와 함께 여기서 받는다. 원격 삭제는 레포 밖으로 나가는 행동이고, 둘 다 되돌리기 어렵다. fork 에서 온 PR 이면 원격 삭제는
하지 않으므로(4절) 로컬 삭제 하나만 보인다.

    gh pr comment <N> --body-file <절대 경로>

이 한 줄로만 친다. 다른 명령과 이은 것과 상대 경로는 `open-pr` 3.4 의 훅이 막는다.

**이 코멘트도 `open-pr` 2절의 본문처럼 조각 파일로 만든다.** 글은 `Write` 로 쓰고, 명령
출력(2절의 커밋 나열 · 아래 닫히는 이슈 줄 · 본문 검증을 다시 돌린 값)은 `evidence.sh` 가
덧붙인다. 조각을 `awk 1` 로 이은 파일이 위 `--body-file` 의 경로다. 거부된 명령은 `open-pr`
2절대로 출력 대신 확인한 것을 글로 적는다:

    bash .claude/skills/open-pr/evidence.sh <디렉터리>/<NN-이름>.part <<'CMD'
    <명령>
    CMD

손으로 옮기면 돌린 것과 다른 명령이 적힌다. 한 결정 코멘트에 실제로 돌린 `git fetch -q` 가
`-q` 없이 옮겨졌고, 긴 명령은 `…` 로 줄었다.

**이 코멘트가 이 PR 의 최종 정리다.** PR 본문은 열 때 쓰고 얼렸으므로(`open-pr` 「본문
작성 규칙」), 그 뒤에 달라진 것을 말하는 자리가 여기밖에 없다. 아래를 적는다:

- 라운드 수와 마지막 라운드의 두 `Verdict`
- 리뷰를 거치지 않은 커밋. 마지막 라운드 코멘트의 head 뒤에 온 커밋을 `docs/dev-log.md` 하나만
  바뀐 것과 그 밖의 것으로 갈라 적고, 커밋마다 건드린 파일을 같이 적고, 사람이 그것을 알고
  머지를 지시했다고 적는다(2절). 나열을 판정 못 했으면 그 사실을 적는다. 없으면 이 줄을 아예
  쓰지 않는다
- PR 본문이 지금은 틀린 곳. 라운드가 본문의 결론을 바꿨으면 무엇이 어떻게 바뀌었는지,
  그리고 본문에 붙인 증거 중 지금 다시 돌리면 다르게 나오는 것(다시 돌린 값은 `evidence.sh` 로).
  없으면 `본문 그대로`
- 마지막 라운드 뒤 3.5 의 코멘트에 사람이 남긴 답. 그 라운드에 안 고친 것과 안 하기로
  한 것. 사람이 쓴 문장을 그대로 옮긴다
- 옛 이름으로 무엇이 남는지. 이 PR 이 킷이 배포하는 파일의 이름이나 경로를 바꿨으면, 설치된
  레포에 옛 이름으로 무엇이 남는지. 안 바꿨으면 이 줄을 아예 쓰지 않는다
- 고쳐야 한다고 올라왔는데 고치지 않고 머지하는 것이 있으면 그것과 이유
- 머지가 닫을 수 있는 이슈. 아래 「닫히는 이슈 줄」의 명령을 `evidence.sh` 로 돌려 덧붙인다. 번호가
  안 나오면 `닫는 키워드 없음`
- 남은 것을 이슈로 옮겼으면 그 번호
- 2절에서 이 PR 의 dev-log 항목이 없었거나 판정 못 했으면 그 사실. 있었으면 이 줄을 아예 쓰지 않는다
- `사람이 머지를 결정했다`

**「PR 본문이 지금은 틀린 곳」 줄** — 라운드 코멘트의 `### 본문 정정` 들을 모아 옮긴다.
결론만 적으면 거짓이 된 출력이 갈 곳이 없어져 닫히지 않는 이월이 된다.

**「마지막 라운드 뒤 3.5 의 코멘트에 사람이 남긴 답」 줄** — 라운드 코멘트에 없는
유일한 기록이라 여기서 안 옮기면 사라진다. 요약하지 마라(`open-pr` 「출처 다섯」의 규칙 1) —
이 코멘트는 머지 **전에** 쓰는 마지막 기록이라 요약하면 되돌릴 자리가 없고,
사람이 대조할 원문도 사라진다. 머지 뒤에야 나온 것은 4절이 이 코멘트 뒤에 코멘트로 붙인다.
없으면 그 줄을 뺀다.

**「옛 이름으로 무엇이 남는지」 줄** — `install.sh` 는 킷이 **지금 배포하는** 파일만
순회하므로 옛 이름은 안 지워진다. `개명 없음` 도 쓰지 마라 — 프로젝트는 킷이 배포하는
파일을 소유하지 않으므로, 늘 뜨면 **한 레포에서만 참인 줄을 모든 레포가 진다.**

**닫히는 이슈 줄** — 머지로 이슈를 닫는 것은 PR 본문의 닫는 키워드만이 아니다. 스쿼시
제목에 든 키워드도 닫는다. 제목은 레포의 기본값을 따른다. PR 제목이거나, 커밋이 하나면
그 커밋의 제목이다. 본문은 아래에서 `--body` 로 직접 넘기므로 브랜치 커밋의 메시지는
스쿼시 커밋에 안 들어가고, 거기에만 든 키워드는 안 닫는다. 그래도 아래 셋을 다 돌린다.
닫히지 않을 번호가 섞이는 것이 빠뜨리는 것보다 낫다. 출력은 `evidence.sh` 가 덧붙인 그대로다. 차례로
`closingIssuesReferences` 의 번호, 제목 줄, 키워드 목록이다. 제목 줄은 스쿼시 제목이 될
줄이고, 키워드 목록은 PR 제목과 커밋 메시지 전체에서 걸린 닫는 키워드다. 무엇이 실제로
닫히는지는 사람이 그 출력을 보고 판단한다 — 세션이 판정하지 않는다. 번호가 안 나오면
`닫는 키워드 없음` 이다:

    gh pr view <N> --json closingIssuesReferences --jq '[.closingIssuesReferences[].number]'
    gh pr view <N> --json title,commits \
      --jq 'if (.commits|length)==1 then .commits[0].messageHeadline else .title end'
    gh pr view <N> --json title,commits --jq '.title, (.commits[]
        | if (.messageHeadline|endswith("…")) and (.messageBody|startswith("…"))
          then (.messageHeadline|rtrimstr("…")) + (.messageBody|ltrimstr("…"))
          else .messageHeadline + "\n" + .messageBody end)' \
      | grep -Eiow '(close[sd]?|fix(e[sd])?|resolve[sd]?):?[[:space:]]+([[:alnum:]_.-]+/[[:alnum:]_.-]+)?#[0-9]+'

**`closingIssuesReferences` 만 보지 마라.** 그 필드는 PR 본문의 키워드는 세지만 스쿼시 제목의
키워드도 커밋 메시지의 키워드도 안 센다. 버릴 레포에서 아래 머지 명령으로 둘을 봤다.
닫는 키워드를 PR 제목에만 둔 PR 은 그 필드가 비어 있었는데 머지가 이슈를 닫았다. 닫은
것은 그 제목을 단 스쿼시 커밋이다. 닫는 키워드를 커밋 메시지의 본문에만 둔 PR 은 그
필드가 비어 있었고 이슈도 안 닫혔다. 둘 다 커밋이 둘인 PR 이었고, 커밋이 하나인 PR 은 안
봤다. 그래서 출력은 이렇게 읽는다. 그 필드의 번호는 닫힌다. 제목 줄에 닫는 키워드와 같이
든 번호도 닫힌다. 키워드 목록에만 있는 번호는 **닫히지 않는 번호**다. 커밋이 여럿인 PR 의
커밋 제목은 본문처럼 스쿼시 커밋에 안 실린다.

**`messageHeadline` 은 긴 제목을 자른다.** 끝에 `…` 를 붙이고, 나머지를 `…` 로 시작하는
`messageBody` 앞에 둔다. 그대로 읽으면 제목 끝의 키워드가 두 줄로 갈려 안 걸리고, 번호
한가운데서 잘리면 앞자리만 걸려 다른 번호가 나온다. 그래서 잘린 둘을 다시 잇는다. `-w` 는
`prefix #N` 처럼 낱말 안에 든 `fix` 를 빼려는 것이다. 제목 줄의 조회는 잘린 제목을 다시
잇지 않는다. 그 줄이 `…` 로 끝나면 잘린 뒤쪽은 키워드 목록에서 본다.

**세션이 가려내지 않는다.** 한때 번호마다 상태를 조회해 이미 닫힌 것을 가려내게 했다가 뺐다.
판정 규칙은 경계 사례를 부른다 — 이미 닫힌 번호 · 이슈가 아니라 PR 인 번호 · 조회가 실패한
번호다. 그 경계마다 앞에서 이미 말한 문장과 어긋났다. 그 조회는 `allow` 에 없어서 설치된
레포에서는 번호마다 권한 프롬프트가 하나씩 뜬다.
출력을 그대로 보이면 그 경계가 없다. 커밋 메시지가 검증 결과로 닫는 키워드를
인용했거나 이미 닫힌 번호가 섞여 있으면, 그것도 출력에 있는 대로 보이고 사람이 판단한다.

이슈 닫기는 사람의 승인을 받는 행동인데, 머지로 닫히는 것은 닫는 명령이 따로 없어서 사람이
볼 자리가 이 초안뿐이다. PR 본문의 닫는 키워드는 여는 순간에 봤지만 본문은 얼어 있고,
그 뒤 라운드에서 범위가 줄 수 있다. 커밋 메시지는 사람이 승인하는 대상이 아니다.
**없을 때도 적는다.** 사람이 승인하는 대상이라 줄이 빠지면 닫히는 것이 없는지 안 본 것인지
모른다.

**본문을 고쳐서 맞추려 하지 마라.** 본문은 연 시점의 기록이고, 그것이 낡는 것은 결함이
아니라 설계다 — 이유는 `docs/process/verification-stages.md` 4. 열한 라운드 동안 본문을
갱신하다 **여섯 번 거짓이 된** 기록이 그 절에 있다.

    gh pr merge <N> --squash --body "- PR: <이 PR 의 URL>
    - Issue: <닫히는 이슈의 URL>

    <브랜치 커밋의 트레일러 줄>"

**이어지는 줄은 첫 칸에서 시작한다.** 위 블록의 들여쓰기는 마크다운의 것이다. 들여쓴 채
넘기면 트레일러 줄이 공백으로 시작해 git 이 그것을 트레일러로 읽지 못한다.

**`--delete-branch` 를 붙이지 마라. 브랜치는 4절이 지운다.** gh 는 머지 뒤 로컬 브랜치를 먼저
지우는데, git worktree 에서는 거기서 실패한다. detached 면 현재 브랜치를 못 읽고, PR 브랜치에
있으면 base 로 옮기려는데 base 를 다른 worktree 가 쓰고 있다. 원래 체크아웃에서 번호로 머지해도
PR 브랜치를 다른 worktree 가 쓰면 그 브랜치를 지우지 못한다. 로컬 삭제가 실패하면 gh 는 원격
삭제도 건너뛰고 `rc=1` 로 끝난다(gh v2.92.0 `pkg/cmd/pr/merge/merge.go`). 서버의 머지는 이미
끝났는데 명령은 실패한 것처럼 보인다(이슈 #91). `--squash` 를 주고 `--delete-branch` 를 빼면
gh 는 브랜치를 묻지도 지우지도 않는다.

**`-R` 을 붙이지 마라.** 이 스킬은 클론 안에서 도므로 필요 없다.

**사람이 이 프롬프트에서 거절하면 머지하지 않고 멈춘다.** 위 결정 코멘트는 이미
나갔으므로 **같은 코멘트를 다시 올리지 마라** — 대신 그 뒤에 코멘트로 한 줄을 남긴다:
`머지하지 않았다(권한 프롬프트에서 거절됨).` 다시 머지하라는 지시를 받으면 그때
새 결정 코멘트를 올린다. 안 그러면 `사람이 머지를 결정했다` 가 여러 벌 남아 어느 것이
실제 결정인지 알 수 없게 된다.

**본문은 인라인 `--body` 로 넘긴다.** 안 넘기면 GitHub 이 브랜치 커밋 메시지를 전부 이어 붙여
스쿼시 본문으로 쓴다. 라운드가 돈 PR 에서는 그것이 백 줄을 넘고, 커밋마다의 트레일러가
그대로 쌓여 같은 줄이 커밋 수만큼 되풀이된다. 넘기면 GitHub 은 그 기본 본문도, 끝에
덧붙이던 자기 `Co-authored-by:` 줄도 붙이지 않는다. 무엇을 왜 바꿨는지는 PR 본문과 결정
코멘트와 dev-log 항목이 이미 든다. 그래서 본문은 거기로 가는 주소와, 브랜치 커밋이 단
트레일러를 중복 없이 든다. 스쿼시 제목의 `(#N)` 은 GitHub 웹에서만 링크이고 `git log` 에서는
글자라, 주소를 본문에 적는다.

두 주소는 이 조회가 낸다. 첫 줄이 이 PR 의 URL 이고 나머지가 `closingIssuesReferences` 의 이슈
URL 이다:

    gh pr view <N> --json url,closingIssuesReferences --jq '.url, (.closingIssuesReferences[]|.url)'

트레일러는 이 조회가 낸다. 브랜치의 커밋들이 단 트레일러에서 중복을 없앤 목록이다. 그
코드를 실제로 쓴 모델이 남고, 머지하는 세션이 값을 고르지 않는다. 서버에서 읽으므로
로컬 브랜치가 없어도 된다. 번호로 머지하는 경로에서는 로컬 `HEAD` 가 `main` 이다:

    gh pr view <N> --json commits --jq '.commits[].messageBody' \
      > "${TMPDIR:-/tmp}/pr<N>-commit-bodies.txt"; echo "rc=$?"
    grep -i '^Co-Authored-By:' "${TMPDIR:-/tmp}/pr<N>-commit-bodies.txt" | sort -u

**파이프에 바로 넣지 마라.** 조회가 실패해도 파이프라인은 빈 출력에 `rc=0` 이라
「트레일러가 없다」와 구분되지 않고, 그대로 가면 트레일러 없는 스쿼시 커밋이 `main` 에
들어간다. 2절의 dev-log 확인과 같은 이유다. `rc` 가 `0` 이 아니면 판정 못 한 것이라 중단한다.

- `- PR:` 과 `- Issue:` 의 값은 첫 조회의 출력 그대로다. 세션이 고르거나 조립하지 않는다. 이슈
  줄이 안 나오면 `- Issue:` 줄을 빼고, 둘 이상이면 이슈마다 한 줄이다
- 라벨은 영어다. 커밋 메시지는 영어라는 규칙이 이 본문에도 적용된다
- 트레일러 줄은 둘째 조회의 출력 그대로다. 한 줄이면 한 줄, 여럿이면 줄마다 하나다. `rc=0`
  인데 아무것도 안 나오면 트레일러 줄을 쓰지 않는다. 세션이 지어내지 않는다

**`--body-file` 을 쓰지 마라.** 파일로 넘기면 명령에 경로만 남아, 사람에게 보이는 머지 명령
전문에도 권한 프롬프트에도 커밋에 들어갈 글이 없다. 인라인이면 명령이 곧 내용이다. 이
본문에는 셸이 깨뜨릴 백틱도 따옴표도 없다.

**빈 문자열을 넘기지 마라.** 본문이 통째로 비고 **트레일러까지 사라진다**(실제로 한
프로젝트의 `main` 커밋 둘에서 그렇게 됐고, 히스토리 재작성 없이는 못 고친다). 사람이
고치지 않기로 한 발견은 위 결정 코멘트에 이미 적으므로 여기 다시 적을 값이 없다.

**권한 프롬프트가 뜬다.** 이 명령과 위의 `gh pr comment` 는 둘 다 `settings.json` 의
`ask` 에 있고, 이 스킬 안이라고 해서 비켜가지 않는다. 사람이 승인할 때까지 기다린다 —
이 스킬 §전제 가 요구하는 "사람이 머지를 지시했다" 를 기계로 한 번 더 확인하는 자리다.
**프롬프트로 사람이 확인할 수 있는 것은 명령까지다.** `gh pr merge` 는 명령이 곧 내용이지만
여러 줄 본문까지 프롬프트에 보이는지는 확인하지 않았고, 결정 코멘트는 `--body-file` 이라
**프롬프트에 파일 경로만 보인다.**

## 4. base 복귀와 브랜치 삭제

`<baseRefName>` · `<headRefName>` · `isCrossRepository` 는 2절이 받아둔 값이다. **이름을 여기서 새로 구하지 마라.**
이 절은 base 로 옮긴 **뒤**에 브랜치를 지우고, `$ARGUMENTS` 로 **다른 PR 을 번호로 머지하는
것이 정상 경로**다(`argument-hint`).

**base 로 돌아온다:**

    if [ "$(git rev-parse --absolute-git-dir)" = "$(git rev-parse --path-format=absolute --git-common-dir)" ] && git switch <baseRefName>; then git pull --ff-only; else git fetch origin && git switch --detach origin/<baseRefName> && { git fetch -q origin <baseRefName>:<baseRefName> 2>/dev/null || true; }; fi

원래 체크아웃에서(`--absolute-git-dir` 와 `--git-common-dir` 가 같다) `git switch` 가 되면 base 브랜치에서
fast-forward 한다. fast-forward 실패 시 중단: `Error: <baseRefName> 을 fast-forward 할 수 없습니다.`
**절대 경로 형태로 견준다.** 원래 체크아웃의 하위 디렉터리에서 `--git-dir` 는 절대 경로를, `--git-common-dir` 는
`../../.git` 같은 상대 경로를 출력해서, 그대로 견주면 원래 체크아웃을 worktree 로 판정한다. 세션의 작업
디렉터리는 호출 사이에 유지되므로 하위 디렉터리에서 실행되는 일이 흔하다.

**git worktree 에서는 base 로 옮기지 않는다. fetch 한 뒤 `origin/<baseRefName>` 에 detach 한다.** worktree 가
base 브랜치에 있으면 원래 체크아웃이 base 로 옮기지 못한다. 원래 체크아웃이 다른 브랜치에 있으면 worktree 의
`git switch` 는 성공하므로, 되는지를 보지 않고 worktree 인지로 가른다(이슈 #121). 원래 체크아웃에서도 다른
worktree 가 base 를 쓰면 `git switch` 가 `fatal: '<baseRefName>' is already used by worktree at …` 로 실패하고,
그때도 detach 한다. PR 브랜치에서 내려와야 아래에서 그 브랜치를 지울 수 있다.

**detach 한 뒤 로컬 base 브랜치도 fast-forward 한다(`git fetch origin <baseRefName>:<baseRefName>`).** 로컬 base 가
머지 전에 남으면, 그 뒤 만든 브랜치에서 `open-pr` · `dev-log` · `trace` 가 주입하는 `git log main..HEAD` 가 방금
머지한 커밋을 그 브랜치의 변경으로 보여 준다. base 를 쓰는 체크아웃이 있으면 git 이
`refusing to fetch into branch … checked out at …` 로 거부하고, 그 체크아웃은 그곳의 사람이 직접 pull 한다.
그래서 이 갱신의 실패는 줄의 종료 코드에 섞지 않는다(`|| true`). **이 거부는 git 2.35 부터다.** 그 전 git 은
현재 worktree 의 브랜치만 보호해서, 원래 체크아웃이 쓰는 base 의 ref 만 옮기고 그 작업 트리는 머지 전으로
둔다. 킷이 상정하는 macOS · ubuntu CI 의 git 은 그보다 새것이다.

**이 줄의 종료 코드가 0 이 아니면 중단한다.** fetch 가 네트워크 때문에 실패하면 그 줄이 실패한다.
fetch 를 따로 두면 fetch 가 실패해도 받아 둔 옛 `origin/<baseRefName>` 에 조용히 detach 해서, 머지 전
커밋에 있는 채 브랜치를 지우고 5절이 그 SHA 를 보고한다. base 로 옮기는 경로는 `git pull --ff-only` 가
fetch 한다.

**이 줄은 설치된 레포에서 어느 갈래로 가든 권한 프롬프트를 거친다.** Claude Code 는 `;` · `&&` 로 나뉜
조각마다 따로 규칙에 맞는지 보고(권한 문서의 Compound commands: "A rule must match each subcommand
independently."), `git fetch` 는 설치되는 `settings.json` 의 `allow` 에 없다. 어느 갈래가 실행될지는
실행 전에 모른다. 사람이 거절하면 줄 전체가 실행되지 않는다. 그때도 중단하고, 5절의 보고에 머지는
끝났고 base 복귀와 브랜치 삭제는 하지 않았다고 적는다. 스킬을 다시 불러도 2절에서 멈추므로(`state` 가
`OPEN` 이 아니다) 남은 일은 사람이 정한다.

**원격 브랜치를 지운다. `isCrossRepository` 가 `true` 면 지우지 않는다:**

    git push origin --delete <headRefName>

fork 에서 온 PR 의 head 브랜치는 fork 에 있다. origin 에 같은 이름의 브랜치가 있으면 그것은 base
레포의 다른 브랜치다. gh 도 이 경우 원격 삭제를 건너뛰었다(v2.92.0 `deleteRemoteBranch` 의
`crossRepoPR`). 그때는 명령을 실행하지 않고 5절에 「fork PR 이라 원격 브랜치를 지우지 않았다」고 적는다.

`remote ref does not exist` 로 실패하면 이미 지워진 것이다. 레포가 머지 뒤 원격 브랜치를
자동으로 지우는 설정이면 그렇다. 그 밖의 실패는 5절의 보고에 한 줄 덧붙인다. 이 명령은
`settings.json` 의 `ask` 에 있어 권한 프롬프트를 거친다. 승인은 3절에서 명령을 보이고 받았다.
사람이 이 프롬프트에서 거절하면 원격 브랜치를 남긴 채 아래 로컬 삭제로 가고, 5절에 남겼다고 한
줄 덧붙인다.

**로컬 브랜치가 남아 있으면 지운다.** 2절이 로컬과 서버가 같다는 것을 머지 전에 확인했으므로
지워도 잃을 것이 없다:

    git rev-parse --verify --quiet <headRefName>   # 출력이 없으면 로컬에 없다. 5절로 간다
    git branch -D <headRefName>                    # 출력이 있으면 지운다

`cannot delete branch '<headRefName>' used by worktree at <경로>` 로 실패하면 다른 worktree 가
그 브랜치를 쓰고 있다. 원래 체크아웃에서 번호로 머지했고 PR 브랜치는 worktree 의 세션이 쓰는
경우다. 지우지 말고 남긴 채 5절로 가서, 그 경로와 함께 남겼다고 한 줄 덧붙인다.

**`-d` 가 아니라 `-D` 인 이유.** 원격 추적 ref 가 pruned 된 레포에서는 `-d` 가 다 민
브랜치도 거부한다. 2절이 이미 확인한 것을 다시 확인하느라 멀쩡한 삭제를 막을 까닭이 없다.

**`-D` 에서 권한 프롬프트가 뜬다**(`settings.json` 의 `ask`). 사람이 거절하면 브랜치를 남긴
채 5절로 가고, 남겼다고 한 줄 덧붙인다.

**`--verify --quiet` 를 빼지 마라.** 맨 `git rev-parse <없는 브랜치>` 는 `rc=128` 로 죽으면서
**인자를 stdout 으로 되뱉는다**(`fatal:` 은 stderr 로 간다). 읽는 쪽이 그것을 SHA 자리에서
받으면, 이미 지워진 **정상 경로에서 이 절이 멈춘다.** 실제로 확인한 결과:

    $ git rev-parse nosuchbranch                    → stdout `nosuchbranch`, rc=128
    $ git rev-parse --verify --quiet nosuchbranch   → 출력 없음, rc=1

**머지 뒤에야 나오는 것.** 머지해야 비로소 확인되는 것이 있다(4절의 삭제가 실제로 됐는지
처럼). **결정 코멘트는 머지 전에 닫혔으므로 그 결과를 결정 코멘트에 넣지 마라.** 3절의
「같은 코멘트를 다시 올리지 마라 — 그 뒤에 코멘트로」와 같은 방식으로 **결정 코멘트 뒤에
코멘트를 하나 더 붙인다.** 결정 코멘트를 편집으로 채우면 한 번 올린 기록이 바뀌고, 편집한
뒤에 생긴 것은 또 빠진다. 실제로 둘 다 났다 — 결정 코멘트의 빈 칸을 머지 뒤 편집으로
채웠고, 그 편집 뒤에 연 이슈가 최종 기록에서 빠졌다. **이 후속 코멘트도 초안을 보이고
승인받은 뒤 올린다.** 3.5 의 코멘트처럼 지금은 받는 승인이다(같은 절).

## 5. 한 줄 보고
`Merged PR #<N>. main at <short SHA>. dev-log: 있음|없음|판정 못 함.`

`없음` 과 `판정 못 함` 은 2절에서 사람이 알고도 머지를 지시한 경우뿐이고, 그 사실은 결정 코멘트에
적혀 있다. 판정 못 한 것을 `없음` 으로 적지 않는다 — 그것이 2절의 그 확인이 없애려는 거짓 기록이다.

이후 새 작업을 시작하지 않는다.
