!`gh pr view --json number -q .number 2>/dev/null`

$ARGUMENTS

## 1. PR 번호 확정
`$ARGUMENTS` 가 있으면 그것, 없으면 위 출력. 둘 다 없으면 중단:
`Error: PR 번호를 확정할 수 없습니다.`

## 2. 머지 전 안전 확인

### 전제 — 사람이 머지를 지시했을 때만 진행한다

**지시가 있어야 이 스킬을 실행한다.** 두 리뷰가 `Approve` 를 냈다는 것은 그 리뷰들의
의견이지 허락이 아니고, CI 가 초록인 것도 허락이 아니다. 허락은 사람이 한다.

지시 없이 이 스킬을 실행했으면 머지하지 말고 **`open-pr` 3.5 대로 사람에게 보고하고 멈춘다.** 예외는 하나다 —
다음 작업을 시작할 때 머지된 PR 을 정리하려고 부르는 것(3절 「다음 작업을 시작할 때 auto-merge 가 켜진 열린 PR 과
머지된 PR 을 본다」)은 지시 없이 부른다. 그때 2절은 `MERGED` 를 보고 4절과 5절만 한다.

레포에 봇 설정(`.claude/bot.json`)이 있으면 머지 승인은 사람 계정의 Approve 다. 세션은 결정 코멘트를 올리고
GitHub auto-merge 를 켠 뒤 Approve 를 부탁하고, Approve 가 달리면 GitHub 이 머지한다(3절 「봇 설정이 있을
때」). 사람의 지시는 그 절차를 시작하라는 것이고, 머지를 허락하는 것은 Approve 다.

### 그다음 — 하나라도 실패하면 즉시 중단

- `gh pr view <N> --json state,headRefName,headRefOid,baseRefName,isCrossRepository` → `state` 가 `OPEN` 이 아니면 중단.
  봇 설정이 있고 `MERGED` 이면 auto-merge 로 머지된 뒤다 — 아래 확인 가운데 「로컬 브랜치가 서버와 같은지」만
  보고 4절과 5절을 한다(3절 「봇 설정이 있을 때」의 머지 뒤 정리). 그 확인을 빼면 4절의 `git branch -D` 가 켠 뒤에
  만들고 푸시하지 못한 커밋까지 지운다. 나머지 넷은 바로 아래와 4절이 쓴다. **셸 변수에 담지 마라. 읽어서 출력한다** — 명령을 여러
  번 부르는 사이에 셸 상태는 유지되지 않는다(`open-pr` 3.1 이 그 사고로 적어둔 규칙이다).
- `gh pr checks <N>` → `fail` 또는 `pending` 이 하나라도 있으면 중단하고 해당 체크를 나열한다.
- 위 `git status --porcelain` 이 비어 있지 않으면 중단.
- **로컬 브랜치가 서버와 같은지 본다. 머지 전인 여기서 한다:**

      git rev-parse --verify --quiet <headRefName>   # 출력이 없으면 로컬에 그 브랜치가 없다. 건너뛴다

  출력이 있으면 그 SHA 를 위에서 받은 `headRefOid` 와 **글자로** 견준다. **다르면 중단하고
  사람에게 말한다.** 대개 커밋만 하고 푸시하지 않은 것이 있는 것이다. 로컬이 뒤처진 경우도 여기서
  멈추는데, 그쪽은 멈춰도 잃는 것이 없다.

  **왜 머지 전인가.** 4절의 `git branch -D` 는 로컬에만 있는 커밋이 있어도 그 브랜치째 지운다.
  그리고 푸시하지 않은 커밋은 머지에도 들어가지 않는다. 그래서 **머지하기 전이자 지우기 전인 여기서
  본다.**

  **왜 글자로 견주나.** 두 커밋의 관계(`git merge-base --is-ancestor`)를 보면 서버 쪽 커밋이
  로컬에 있어야 판정되고, 없으면 `rc=128` 로 실패해 멀쩡한 머지를 막는다. 글자 비교는 로컬
  객체를 요구하지 않는다.
- **이 PR 의 dev-log 항목이 있나.** 서버 head 에서 본다 — 로컬에는 푸시하지 않은 커밋이 있을 수 있고,
  번호로 머지하는 정상 경로에서는 그 head 의 객체가 로컬에 없을 수 있다. 그래서 로컬 객체를
  요구하지 않는 조회로 본다. **파일로 먼저 받고 종료 코드를 본 뒤에 센다. 파이프에 넣지 마라:**

      gh api "repos/{owner}/{repo}/contents/docs/dev-log.md?ref=<headRefOid>" \
          -H "Accept: application/vnd.github.raw" > "${TMPDIR:-/tmp}/pr<N>-dev-log.md"; echo "rc=$?"
      grep -cE '^## .*\(PR [^)]*#<N>([^0-9]|\)|$)' "${TMPDIR:-/tmp}/pr<N>-dev-log.md"

  판정은 셋이다. `rc=0` 에 `1` 이상이면 있다. `rc=0` 에 `0` 이면 파일은 있는데 항목이 없다 — 중단하고
  사람에게 말한다. dev-log 는 머지 직전에 쓰는 것이라(`dev-log` 스킬) 여기서 없으면 안 쓴 것이다.
  사람이 그것을 알고도 머지하라고 하면 진행하되, **3절의 결정 코멘트에 「dev-log 항목 없음」을
  적는다.** `rc` 가 `0` 이 아니면(404 든 네트워크든) 판정 못 한 것이라 중단한다. 그것을 알고도
  머지하라고 하면 결정 코멘트에 「dev-log 항목 판정 못 함」을 적는다 — 판정 못 한 것을 「없음」으로
  적는 것이 이 확인이 없애려는 거짓 기록이다.
  `gh api` 는 설치되는 `settings.json` 의 `ask` 에 있어 설치된 레포에서는 이 조회에 권한 프롬프트가
  하나 표시된다. 읽기뿐이라 승인하면 그대로 진행한다.
  **파이프에 넣지 않는 이유**: `gh api` 는 실패해도 오류 JSON 을 stdout 으로 내고 `grep -c` 가
  그것을 `0` 으로 센다 — 「항목 없음」과 같은 숫자다. 파일로 받으면 종료 코드가 둘을 구분한다.
  **파일을 `${TMPDIR:-/tmp}` 에 두는 이유**: 레포 안에 쓰면 위 `git status --porcelain` 확인이
  깨지고, `$(mktemp)` 를 변수에 담으면 명령을 따로 부르는 사이에 셸 상태가 안 남는다(위 첫 불릿과
  같은 이유다).
  정규식이 `(PR #<N>)` 보다 느슨한 이유: 한 항목이 PR 둘을 들 수 있다(`(PR #13 · #14)`). 번호 뒤를
  `[^0-9]` 로 막아 `#6` 이 `#69` 에 맞지는 않는다. `git show <headRefOid>:docs/dev-log.md` 를 쓰지
  않는 이유: 객체가 로컬에 없을 때와 파일이 없을 때가 같은 `fatal` 과 `0` 을 내 둘을 구분하지 못한다.
- **리뷰 반영 확인.** `open-pr` 이 올린 **마지막 라운드 코멘트**를 읽는다:

      gh pr view <N> --json comments \
        --jq '[.comments[] | select(.body|test("^\\s*## 리뷰 "))] | last | .body'

  그 코멘트 **맨 위의** `리뷰한 head:` 를 **위 첫 줄에서 받아둔 `headRefOid`** 와 비교한다.
  접힌 전문 안에도 같은 줄이 있으므로 맨 위 것을 쓴다.

  **다르면** 마지막 라운드 뒤에 커밋이 더 쌓인 것이고 그 커밋들은 아무도 안 봤다.
  중단하고 **어느 커밋인지 파일까지 나열해** 사람에게 말한다. 끝점은 위에서 받은 `headRefOid`
  다. 로컬 `HEAD` 가 아니다. 번호로 머지하는 정상 경로에서는 `HEAD` 가 `main` 이라 목록이
  비거나 남의 커밋이 나온다. 그 객체가 로컬에 없을 수 있으므로 먼저 받는다:

      git fetch origin <headRefName>; echo "rc=$?"
      git log <그 head>..<headRefOid> --format='%h %s' --name-only; echo "rc=$?"

  `git fetch` 는 설치되는 `settings.json` 의 `allow` 에 없어 설치된 레포에서는 이 fetch 에 권한
  프롬프트가 하나 표시된다. 읽기뿐이라 승인하면 그대로 진행한다.
  판정은 둘이다. `fetch` 나 `log` 의 `rc` 가 `0` 이 아니면 판정 못 한 것이라 중단한다. dev-log
  확인과 같은 규칙이다. 그것을 알고도 머지하라고 하면 결정 코멘트에 「나열 판정 못 함」을
  적는다. **head 가 다른데 목록이 비면 둘 중 하나다.** 서버 head 가 마지막 라운드 head 의
  조상이면 되감기다. 브랜치가 리뷰한 것보다 뒤로 돌아갔다. 그 사실을 사람에게 말하고
  중단한다. 그 밖에 목록이 비면 명령이 잘못 실행된 것이라 중단한다. 둘을 구분하는 명령:

      git merge-base --is-ancestor <headRefOid> <그 head>; echo "rc=$?"   # 0 이면 되감기

  끝점이 `origin/<headRefName>` 이 아닌 이유: 2절의 다른 확인이 전부 `headRefOid` 에 묶여
  있고, 그 값을 읽은 뒤 누가 푸시하면 브랜치 이름이 가리키는 것이 달라진다.
  사람이 그것을 알고도 머지하라고 하면 진행하되, **3절의 결정 코멘트에 그 커밋 목록과
  "리뷰를 거치지 않았다" 를 적는다.** 이것은 정상 경로다 — `open-pr` 이 사람에게
  제시하는 답에 "고치고 추가 라운드 없이 머지" 가 들어 있고, 그렇게 하면 head 는
  반드시 달라진다. 막는 것이 목적이 아니다. **리뷰를 거치지 않은 커밋이 있다는 사실을
  기록 없이 머지되지 않게 하는 것**이 목적이다.

  **dev-log 커밋은 늘 이 목록에 나온다.** `dev-log` 스킬이 머지 직전에 실행되므로 그 커밋은 마지막
  라운드 뒤에 온다. dev-log 를 쓴 PR 마다 이 확인이 멈추고, 그것은 결함이 아니라 이 확인이
  하는 일이다. 사람에게 말할 때 커밋을 둘로 나눠 적는다. `docs/dev-log.md` **하나만** 바뀐
  커밋과 그 밖의 커밋이다. 기준은 파일이지 커밋 제목이 아니다. 위 나열 명령이 커밋마다
  건드린 파일을 내므로 분류는 그 출력대로다. 세션이 판정하지 않는다. dev-log 항목과 계획
  줄 삭제가 한 커밋이면 파일이 둘이라 「그 밖」이다. 그 커밋이 계획 문서의 다른 줄을 같이
  건드렸는지는 파일 이름만으로 모르므로 사람이 한 번 본다. **사람이 보는 것은 그 밖의
  커밋이다.** 3절의 「리뷰를 거치지 않은 커밋」 줄에도 같은 구분으로 적는다. 「dev-log 만
  바뀐 커밋은 빼고 센다」는 예외는 넣지 않는다. 구분하는 쪽이 틀리면 리뷰를 안 거친 변경이
  조용히 머지되고, 구분하지 못할 때는 사람에게 보인다.

  **`리뷰한 head:` 줄이 아예 없으면** 옛 형식의 코멘트다. 대조할 수 없으므로 통과로
  처리하지 말고, 그 사실을 말하고 사람의 판단을 받는다.

  두 리뷰의 `Verdict` 는 그 코멘트 첫 줄에 있다. `Request changes` 가 해소되지 않았으면
  중단 — 사람이 그것을 해소하지 않고 머지하기로 했다면 그 사실을 3절에 적는다.

  라운드 코멘트를 못 찾으면 **리뷰가 실행되지 않은 것이다.** 중단한다.

  **그 코멘트 뒤의 코멘트도 읽는다** — 사람의 결정이고, **마지막 라운드 뒤에 사람이 정한 것이
  거기 있다.** 그 라운드가 끝난 뒤에 온 답이라 라운드 코멘트에는 없다:

      gh pr view <N> --json comments \
        --jq '.comments as $c
              | ([$c|to_entries[]|select(.value.body|test("^\\s*## 리뷰 "))|.key]|last) as $i
              | if $i == null then []
                else $c[$i+1:]
                  | map(select((.body|test("^\\s*### .*라운드 코멘트를 읽고 사람이 정한 것"))
                               or (($c[$i].authorAssociation|IN("OWNER","MEMBER","COLLABORATOR")|not)
                                   and (.authorAssociation|IN("OWNER","MEMBER","COLLABORATOR")))))
                end
              | map(.body) | join("\n\n———\n\n")'

  **위치만으로 고르지 않는다.** 그 창에는 **이 스킬이 올린 코멘트도 들어간다** — 아래
  「사람이 거절하면」 경로가 결정 코멘트와 `머지하지 않았다…` 한 줄을 그 뒤에 남기고,
  다시 지시받으면 새 결정 코멘트를 올린다. 위치만 보면 옛 결정 코멘트가 **사람의 답으로**
  새 결정 코멘트에 인용되고, `사람이 머지를 결정했다` 가 여러 벌 남는 문제가 다른 모양으로
  다시 생긴다. 그래서 3.5 의 코멘트가 쓰는 제목으로 좁히고, 라운드 코멘트를 사람 계정이 아닌 계정(봇)이
  올렸으면 사람 계정(`authorAssociation` 이 OWNER · MEMBER · COLLABORATOR)의 코멘트도 고른다. 봇 설정이
  있으면 사람은 PR 웹에서 제목 없이 결정을 쓸 수 있고, 이 스킬의 코멘트는 봇 계정이라 빠진다. 봇 설정이
  없으면 라운드 코멘트도 사람 계정이라 제목만 본다 — 동료의 코멘트는 결정이 아니다.
- **auto-merge 를 켤 수 있나.** 레포에 봇 설정(`.claude/bot.json`)이 있을 때만 본다:

      gh pr view <N> --json reviewDecision,mergeStateStatus
      gh api "repos/{owner}/{repo}" --jq .allow_auto_merge

  `reviewDecision` 이 `REVIEW_REQUIRED` 이고 `mergeStateStatus` 가 `BLOCKED` 이고 `allow_auto_merge` 가 `true`
  면 3절의 「봇 설정이 있을 때」로 간다 — 결정 코멘트를 올리고 auto-merge 를 켠 뒤 Approve 를 부탁한다.
  **다른 상태에서 `--auto` 를 주지 마라.** gh 는 바로 머지할 수 있는 PR(`CLEAN` · `HAS_HOOKS` · `UNSTABLE`)에서
  `--auto` 를 무시하고 그 자리에서 머지한다(gh v2.92.0 `pkg/cmd/pr/merge/merge.go` 의 `isImmediatelyMergeable`).
  승인을 요구하지 않는 레포(`reviewDecision` 이 비었다)에서는 검사가 끝나는 순간 Approve 없이 머지된다. 막기
  훅(`bot_guard.sh`)도 그 상태의 `--auto` 를 막는다. `mergeStateStatus` 가 `UNKNOWN` 이면 GitHub 이 아직 계산하는 것이라
  잠시 뒤 다시 본다. `gh api` 는 설치되는 `settings.json` 의 `ask` 에 있어 권한 프롬프트가 하나 표시된다. 읽기뿐이라
  승인하면 그대로 진행한다.

  **그 밖이면 세션이 Approve 를 확인한다.** 이미 승인된 PR · 승인을 요구하지 않는 레포 · auto-merge 를 허용하지
  않은 레포다:

      bash .claude/hooks/human_review.sh approved <N>; echo "rc=$?"

  판정은 셋이다. `rc=0` 이면 `✓ <계정> 가 지금 head <SHA> 를 Approve 했다` 가 나온다. 그 Approve 가
  머지 승인이다 — 3절의 결정 코멘트 · 머지 명령(`--auto` 없이)과 4절의 브랜치 삭제를 창으로 묻지 않고 실행한 뒤,
  올린 결정 코멘트 전문과 실행한 명령을 5절의 보고에 싣는다. `rc=1` 이면 Approve 가 없거나, 이전 커밋에 대한
  것이거나, 쓰기 권한자의 Request changes 가 남아 있거나, 브랜치 보호가 요구하는 승인이 모자라다 — 중단하고
  `✗` 줄을 사람에게 보이고, 3절의 결정 코멘트와 명령 전문을 출력한 뒤 아래 부탁 블록으로 응답을 끝낸다. 그
  블록의 「그 뒤」는 「Approve 한 뒤 알려 주면 이 스킬을 다시 실행해 머지한다」다. 승인이 모자란 까닭은 둘이다.
  필요 승인 수가 모자라면 다른 리뷰어의 Approve 를 기다린다. 승인한 사람이 PR 브랜치에 마지막으로 푸시했으면
  그 Approve 는 세어지지 않으므로(마지막 푸시 승인), 세션이 다시 푸시한 뒤 Approve 를 다시 받는다. `rc=2` 는
  판정 못 한 것이라 중단한다. 설치된 레포에서는 이 명령에 권한 프롬프트가 하나 표시된다. 읽기뿐이라 승인하면
  그대로 진행한다. 어떤 Approve 를 인정하는지는 `.claude/hooks/human_review.sh` 머리에 있다.

  **Approve 를 기다리며 확인을 되풀이하지 않는다.** 정해진 시간 동안 몇 초마다 Approve 를 조회하는 식으로
  기다리지 않는다. 협업에서는 Approve 가 몇 시간 뒤에 달릴 수 있어 시간이 끝나면 결국 사람이 알려야 하고,
  그동안 세션은 다른 일을 못 한다. 부탁으로 응답을 끝내고, 머지는 auto-merge 가 하거나 사람이 알린 뒤에 한다
  (`docs/process/verification-stages.md` 6.3).

  **Approve 를 부탁하는 블록.** 응답은 이 블록으로 끝낸다(`docs/process/verification-stages.md` 6.3). 할 일 ·
  어디서 · 순서 · 그 뒤 세션이 할 일을 적는다. 할 일 줄 뒤에는 무엇이 GitHub 에 올라가고 무엇이 실행만 되는지를
  나눠 적는다 — 결정 코멘트는 PR 코멘트로, 머지 명령의 `--subject` · `--body` 는 `main` 의 커밋 메시지로
  올라가고, 브랜치 삭제는 실행만 된다(원격 브랜치가 지워진다). 길은 둘이고 사람이 고른다. PR 웹은
  `https://github.com/<owner>/<repo>/pull/<N>/files` 에서 오른쪽 위의 초록 버튼(새 화면 「Submit review ▾」, 예전
  화면 「Review changes」) → 「Approve」 → 「Submit review」다. 새 화면에서는 주소가 `/changes` 로 바뀐다.
  터미널은 이 세션 밖의 사람 터미널에서 `gh pr review <N> -R <owner>/<repo> --approve` 다 — 세션이 실행하는
  gh 는 봇 계정이라 PR 작성자의 승인이 되어 GitHub 이 받지 않는다. 알림에도 링크를 넣는다. **세션이
  Approve 하지 않는다** — PR 작성자인 봇은 자기 PR 을 승인할 수 없고, 승인은 사람의 것이어야 한다.

  봇 설정이 없으면 이 항목을 건너뛰고 3절의 초안 승인으로 머지를 승인받는다 — 세션과 사람이 한 계정이라
  PR 작성자인 사람이 자기 PR 을 Approve 할 수 없다.

> 이 확인은 편의이지 강제가 아니다. 진짜 강제는 GitHub 브랜치 보호다
> (킷의 `install.sh --protect` 가 설정한다). 브랜치 보호가 없는 레포라면 그 사실을 먼저 알린다.

## 3. 머지

머지 **전에**, 사람이 무엇을 보고 정했는지를 PR 에 남긴다 — 머지 후에는 그 맥락을
복원할 곳이 없다. 리뷰가 남아 있는데 그것을 고치지 않고 머지하기로 했다면 특히 그렇다.

**올리기 전에 초안 전문을 사람에게 보이고 승인받는다.** 보인다는 것은 승인을 묻기 바로 전에 세션의 응답에
그 글과 명령의 최종본 전문을 출력하는 것이다 — 파일 경로나 요약으로 대신하지 않는다. 이 스킬에서 승인을
받는 것은 모두 그렇다. 머지와 한 몸이고 머지 전에 쓰는 마지막 기록이라 사람의 승인을 받는 행동이다. 기준은
`docs/process/verification-stages.md` 6.3 에 있다. 아래 권한
프롬프트는 이 승인을 대신하지 못한다 — 파일 경로만 보인다. **봇 설정이 있으면 사람의 Approve 가 결정
코멘트 · 머지 명령 · 4절의 브랜치 삭제의 승인이다.** 이 셋은 창으로 묻지 않는다. 순서는 아래 「봇 설정이 있을
때」다. 아래 「이 PR 이 끝낸 이슈」는 봇 설정이 있어도 창으로 승인받는다(닫을 이슈가 있을 때만) — Approve 는
코드에 대한 승인이라 본문 밖에서 정한 이슈를 보여 주지 않는다. 4절의 후속 코멘트도 창으로 승인받는다.

**초안과 함께 아래 머지 명령 전문도 보인다.** 스쿼시 커밋의 제목과 본문이 그 명령 안에 있고,
틀리면 히스토리 재작성 없이는 못 고친다. 권한 프롬프트는 승인이 아니고, 프롬프트가 표시되지
않는 레포도 있다. 여러 줄 본문이 프롬프트에 다 보이는지는 확인하지 않았다. 프롬프트에서
거절하면 아래 거절 경로가 실행되어 결정 코멘트가 두 벌이 된다. 그래서 사람이 제목과 본문을 보는
자리는 여기다.

**이 PR 이 끝낸 이슈를 닫는 명령도 같이 보인다.** 아래 목록의 「머지가 닫지 않지만 이 PR 이 끝낸
이슈」가 있을 때만이다. 이슈를 닫는 것도 사람의 승인을 받는 행동이고, 닫힌 이슈는 열린 이슈
목록에서 사라져 잘못 닫혀도 알아챌 계기가 없다. 이슈마다 한 줄이고, 머지가 끝난 뒤 이 절 끝에서
실행한다:

    gh issue close <번호> --comment "<이 PR 의 URL> 로 끝냈다."

**봇 설정이 있으면 닫는 명령 대신 머지 명령의 `--body` 에 `Closes #<번호>` 줄을 더한다.** 창으로 승인받은
뒤다. 자리는 머지 명령 틀이 보인 곳이다 — 트레일러 줄 뒤에 붙이면 트레일러가 사라진다(아래 머지 명령의 설명). auto-merge 로 머지되면 머지 뒤에 세션이 닫는 명령을 실행할 자리가 없다. 스쿼시 커밋 메시지의 닫는
키워드는 그 커밋이 기본 브랜치에 들어갈 때 이슈를 닫는다(GitHub 문서 「Linking a pull request to an issue」:
"You can also use closing keywords in a commit message. The issue will be closed when you merge the commit into
the default branch"). PR 본문은 고치지 않는다(아래 「본문을 고쳐서 맞추려 하지 마라」). 같은 문서가 "the pull
request that contains the commit will not be listed as a linked pull request" 라고 하므로 그 번호는
`closingIssuesReferences` 에 나오지 않는다 — 결정 코멘트의 「머지가 닫을 수 있는 이슈」 줄에 따로 적는다.

**4절의 삭제 명령 둘도 같이 보인다.** 원격 브랜치를 지우는 `git push origin --delete
<headRefName>` 과 로컬 브랜치를 지우는 `git branch -D <headRefName>` 이다. 머지 명령이
브랜치를 지우지 않으므로(아래 머지 명령 뒤의 설명) 이 둘은 머지 뒤에 따로 실행되지만, 승인은
머지와 함께 여기서 받는다. 원격 삭제는 레포 밖으로 나가는 행동이고, 둘 다 되돌리기 어렵다. fork 에서 온 PR 이면 원격 삭제는
하지 않으므로(4절) 로컬 삭제 하나만 보인다. auto-merge 로 머지하면 원격 브랜치는 레포 설정 「Automatically
delete head branches」가 지우고, 4절은 머지 뒤 다음 작업을 시작할 때 실행한다(아래 「봇 설정이 있을 때」).

    gh pr comment <N> --body-file <절대 경로>

이 한 줄로만 입력한다. 다른 명령과 이은 것과 상대 경로는 `open-pr` 3.4 의 훅이 막는다.

**이 코멘트도 `open-pr` 2절의 본문처럼 조각 파일로 만든다.** 글은 `Write` 로 쓰고, 명령
출력(2절의 커밋 나열 · 아래 닫히는 이슈 줄 · 본문 검증을 다시 실행한 값)은 `evidence.sh` 가
덧붙인다. 조각을 `awk 1` 로 이은 파일이 위 `--body-file` 의 경로다. 거부된 명령은 `open-pr`
2절대로 출력 대신 확인한 것을 글로 적는다:

    bash .claude/skills/open-pr/evidence.sh <디렉터리>/<NN-이름>.part <<'CMD'
    <명령>
    CMD

손으로 옮기면 실행한 것과 다른 명령이 적힌다. 한 결정 코멘트에 실제로 실행한 `git fetch -q` 가
`-q` 없이 옮겨졌고, 긴 명령은 `…` 로 줄었다.

**이 코멘트가 이 PR 의 최종 정리다.** PR 본문은 열 때 쓰고 그 뒤로 고치지 않았으므로(`open-pr` 「본문
작성 규칙」), 그 뒤에 달라진 것을 말하는 자리가 여기밖에 없다. 아래를 적는다:

- 라운드 수와 마지막 라운드의 두 `Verdict`
- 리뷰를 거치지 않은 커밋. 마지막 라운드 코멘트의 head 뒤에 온 커밋을 `docs/dev-log.md` 하나만
  바뀐 것과 그 밖의 것으로 나눠 적고, 커밋마다 건드린 파일을 같이 적고, 사람이 그것을 알고
  머지를 지시했다고 적는다(2절). auto-merge 를 켜는 경우에는 그 목록을 Approve 를 부탁하는 응답에 출력했다고
  적는다 — Approve 는 아직 없다. 나열을 판정 못 했으면 그 사실을 적는다. 없으면 이 줄을 아예
  쓰지 않는다
- PR 본문이 지금은 틀린 곳. 라운드가 본문의 결론을 바꿨으면 무엇이 어떻게 바뀌었는지,
  그리고 본문에 붙인 증거 중 지금 다시 실행하면 다르게 나오는 것(다시 실행한 값은 `evidence.sh` 로).
  없으면 `본문 그대로`
- 마지막 라운드 뒤 사람이 남긴 답(2절이 읽은 코멘트). 그 라운드에 안 고친 것과 안 하기로
  한 것. 사람이 쓴 문장을 그대로 옮긴다
- 옛 이름으로 무엇이 남는지. 이 PR 이 킷이 배포하는 파일의 이름이나 경로를 바꿨으면, 설치된
  레포에 옛 이름으로 무엇이 남는지. 안 바꿨으면 이 줄을 아예 쓰지 않는다
- 고쳐야 한다고 올라왔는데 고치지 않고 머지하는 것이 있으면 그것과 이유
- 머지가 닫을 수 있는 이슈. 아래 「닫히는 이슈 줄」의 명령을 `evidence.sh` 로 실행해 덧붙인다. 번호가
  안 나오면 `닫는 키워드 없음`. 봇 설정이 있어 머지 명령의 `--body` 에 `Closes #<번호>` 를 더했으면 그 번호를
  따로 적는다 — 그 명령들의 출력에 나오지 않는다
- 머지가 닫지 않지만 이 PR 이 끝낸 이슈. 연 뒤 라운드에서 끝내게 되어 본문에 `Closes #N` 이 없는
  이슈다. 이 PR 의 모든 사람의 답에서 사람이 끝내기로 정한 이슈만 적고, 그 인용을 근거로 든다.
  2절은 마지막 라운드 코멘트 뒤의 것만 읽으므로, 이 줄을 쓸 때는 아래 명령으로 앞 라운드의 답까지
  읽는다. 사람의 답은 2절처럼 3.5 의 코멘트이거나, 라운드 코멘트를 봇이 올렸을 때 사람 계정의 코멘트다.
  `dev-log` 가 계획 줄을 지울 때 본 것도 PR 코멘트 전체다. 없으면 이 줄을 아예 쓰지 않는다

      gh pr view <N> --json comments \
        --jq '.comments as $c
              | ([$c[]|select(.body|test("^\\s*## 리뷰 "))
                  |.authorAssociation|IN("OWNER","MEMBER","COLLABORATOR")|not]|any) as $bot
              | [$c[]|select((.body|test("^\\s*### .*라운드 코멘트를 읽고 사람이 정한 것"))
                             or ($bot and (.authorAssociation|IN("OWNER","MEMBER","COLLABORATOR"))))
                     |.body]|join("\n\n———\n\n")'

- 남은 것을 이슈로 옮겼으면 그 번호
- 2절에서 이 PR 의 dev-log 항목이 없었거나 판정 못 했으면 그 사실. 있었으면 이 줄을 아예 쓰지 않는다
- `사람이 머지를 결정했다`. auto-merge 를 켜는 경우에는 `사람이 지금 head <짧은 SHA> 를 Approve 하면 GitHub 이
  머지한다(auto-merge)` 로 적는다 — 이 코멘트는 Approve 전에 올라가므로 「Approve 했다」 같은 아직 없는 일을
  적지 않는다

**「PR 본문이 지금은 틀린 곳」 줄** — 라운드 코멘트의 `### 본문이 틀린 곳` 들을 모아 옮긴다.
결론만 적으면 거짓이 된 출력을 적을 자리가 없어져 닫히지 않는 이월이 된다.

**「마지막 라운드 뒤 사람이 남긴 답」 줄** — 라운드 코멘트에 없는
유일한 기록이라 여기서 안 옮기면 사라진다. 요약하지 마라(`open-pr` 「출처 다섯」의 규칙 1) —
이 코멘트는 머지 **전에** 쓰는 마지막 기록이라 요약하면 되돌릴 자리가 없고,
사람이 대조할 원문도 사라진다. 머지 뒤에야 나온 것은 4절이 이 코멘트 뒤에 코멘트로 붙인다.
없으면 그 줄을 뺀다.

**「옛 이름으로 무엇이 남는지」 줄** — `install.sh` 는 킷이 **지금 배포하는** 파일만
순회하므로 옛 이름은 안 지워진다. `개명 없음` 도 쓰지 마라 — 프로젝트는 킷이 배포하는
파일을 소유하지 않으므로, 늘 적으면 **한 레포에서만 참인 줄이 모든 레포의 결정 코멘트에 남는다.**

**닫히는 이슈 줄** — 머지로 이슈를 닫는 것은 PR 본문의 닫는 키워드만이 아니다. 스쿼시
제목에 든 키워드도 닫는다. 제목은 아래 머지 명령이 `--subject` 로 전달하는 「PR 제목 (#N)」이다.
본문은 아래에서 `--body` 로 직접 전달하므로 브랜치 커밋의 메시지는
스쿼시 커밋에 안 들어가고, 거기에만 든 키워드는 안 닫는다. 그래도 아래 셋을 다 실행한다.
닫히지 않을 번호가 섞이는 것이 빠뜨리는 것보다 낫다. 출력은 `evidence.sh` 가 덧붙인 그대로다. 차례로
`closingIssuesReferences` 의 번호, 제목 줄, 키워드 목록이다. 제목 줄은 스쿼시 제목이 될
줄이고(셸이 해석하는 글자 앞의 `\` 는 머지 명령의 큰따옴표 안에서 빠진다), 키워드 목록은 PR 제목과 커밋 메시지 전체에서 찾은 닫는 키워드다. 무엇이 실제로
닫히는지는 사람이 그 출력을 보고 판단한다 — 세션이 판정하지 않는다. 번호가 안 나오면
`닫는 키워드 없음` 이다:

    gh pr view <N> --json closingIssuesReferences --jq '[.closingIssuesReferences[].number]'
    gh pr view <N> --json title,number --jq '"\(.title) (#\(.number))" | gsub("(?<c>[\"$`\\\\])"; "\\\(.c)")'
    gh pr view <N> --json title,commits --jq '.title, (.commits[]
        | if (.messageHeadline|endswith("…")) and (.messageBody|startswith("…"))
          then (.messageHeadline|rtrimstr("…")) + (.messageBody|ltrimstr("…"))
          else .messageHeadline + "\n" + .messageBody end)' \
      | grep -Eiow '(close[sd]?|fix(e[sd])?|resolve[sd]?):?[[:space:]]+([[:alnum:]_.-]+/[[:alnum:]_.-]+)?#[0-9]+'

**`closingIssuesReferences` 만 보지 마라.** 그 필드는 PR 본문의 키워드는 세지만 스쿼시 제목의
키워드도 커밋 메시지의 키워드도 안 센다. 버릴 레포에서 아래 머지 명령에 `--subject` 를 더하기 전의
명령으로 둘을 봤다.
닫는 키워드를 PR 제목에만 둔 PR 은 그 필드가 비어 있었는데 머지가 이슈를 닫았다. 닫은
것은 그 제목을 단 스쿼시 커밋이다. 닫는 키워드를 커밋 메시지의 본문에만 둔 PR 은 그
필드가 비어 있었고 이슈도 안 닫혔다. 둘 다 커밋이 둘인 PR 이었다. 지금은 머지 명령이 제목을
전달하므로 커밋 수와 상관없이 제목은 PR 제목이다. 제목을 `--subject` 로 전달한 커밋이 하나인
PR 에서도 제목의 키워드가 이슈를 닫았다. 그래서 출력은 이렇게 읽는다. 그 필드의 번호는
닫힌다. 제목 줄에 닫는 키워드와 같이 든 번호도 닫힌다. 키워드 목록에만 있는 번호는 **닫히지
않는 번호**다. 커밋 제목은 커밋 수와 상관없이 스쿼시 커밋에 안 실린다.

**`messageHeadline` 은 긴 제목을 자른다.** 끝에 `…` 를 붙이고, 나머지를 `…` 로 시작하는
`messageBody` 앞에 둔다. 그대로 읽으면 제목 끝의 키워드가 두 줄로 나뉘어 검색되지 않고, 번호
한가운데서 잘리면 앞자리만 검색돼 다른 번호가 나온다. 그래서 잘린 둘을 다시 잇는다. `-w` 는
`prefix #N` 처럼 낱말 안에 든 `fix` 를 빼려는 것이다.

**세션이 가려내지 않는다.** 한때 번호마다 상태를 조회해 이미 닫힌 것을 가려내게 했다가 뺐다.
판정 규칙을 두면 경계 사례가 생긴다 — 이미 닫힌 번호 · 이슈가 아니라 PR 인 번호 · 조회가 실패한
번호다. 그 경계마다 앞에서 이미 말한 문장과 어긋났다. 그 조회는 `allow` 에 없어서 설치된
레포에서는 번호마다 권한 프롬프트가 하나씩 표시된다.
출력을 그대로 보이면 그 경계가 없다. 커밋 메시지가 검증 결과로 닫는 키워드를
인용했거나 이미 닫힌 번호가 섞여 있으면, 그것도 출력에 있는 대로 보이고 사람이 판단한다.

이슈 닫기는 사람의 승인을 받는 행동인데, 머지로 닫히는 것은 닫는 명령이 따로 없어서 사람이
볼 자리가 이 초안뿐이다. PR 본문의 닫는 키워드는 여는 순간에 봤지만 본문은 그 뒤로 고치지 않고,
그 뒤 라운드에서 범위가 줄 수 있다. 커밋 메시지는 사람이 승인하는 대상이 아니다.
**없을 때도 적는다.** 사람이 승인하는 대상이라 줄이 빠지면 닫히는 것이 없는지 안 본 것인지
모른다.

**본문을 고쳐서 맞추려 하지 마라.** 본문은 연 시점의 기록이고, 그것이 낡는 것은 결함이
아니라 설계다 — 이유는 `docs/process/verification-stages.md` 4. 열한 라운드 동안 본문을
갱신하다 **여섯 번 거짓이 된** 기록이 그 절에 있다.

    gh pr merge <N> --squash --subject "<제목 조회의 출력>" --body "- PR: <이 PR 의 URL>
    - Issue: <닫히는 이슈의 URL>
    Closes #<본문 밖에서 끝낸 이슈의 번호>

    <브랜치 커밋의 트레일러 줄>"

**이어지는 줄은 첫 칸에서 시작한다.** 위 블록의 들여쓰기는 마크다운의 것이다. 들여쓴 채
전달하면 트레일러 줄이 공백으로 시작해 git 이 그것을 트레일러로 읽지 못한다.

**`--delete-branch` 를 붙이지 마라. 브랜치는 4절이 지운다.** gh 는 머지 뒤 로컬 브랜치를 먼저
지우는데, git worktree 에서는 거기서 실패한다. detached 면 현재 브랜치를 못 읽고, PR 브랜치에
있으면 base 로 옮기려는데 base 를 다른 worktree 가 쓰고 있다. 원래 체크아웃에서 번호로 머지해도
PR 브랜치를 다른 worktree 가 쓰면 그 브랜치를 지우지 못한다. 로컬 삭제가 실패하면 gh 는 원격
삭제도 건너뛰고 `rc=1` 로 끝난다(gh v2.92.0 `pkg/cmd/pr/merge/merge.go`). 서버의 머지는 이미
끝났는데 명령은 실패한 것처럼 보인다. `--squash` 를 주고 `--delete-branch` 를 빼면
gh 는 브랜치를 묻지도 지우지도 않는다.

**`-R` 을 붙이지 마라.** 이 스킬은 클론 안에서 실행되므로 필요 없다.

**사람이 이 프롬프트에서 거절하면 머지하지 않고 멈춘다.** 위 결정 코멘트는 이미
나갔으므로 **같은 코멘트를 다시 올리지 마라** — 대신 그 뒤에 코멘트로 한 줄을 남긴다:
`머지하지 않았다(권한 프롬프트에서 거절됨).` 다시 머지하라는 지시를 받으면 그때
새 결정 코멘트를 올린다. 안 그러면 `사람이 머지를 결정했다` 가 여러 벌 남아 어느 것이
실제 결정인지 알 수 없게 된다.

**제목은 `--subject` 로 전달한다.** 전달하지 않으면 GitHub 이 레포 설정 `squash_merge_commit_title`
대로 정하고, 기본값 `COMMIT_OR_PR_TITLE` 은 커밋이 하나인 PR 에서 그 커밋의 제목을 쓴다. PR 제목에
둔 규약이 조용히 빠진다. 전달하면 GitHub 은 그 글자를 그대로 쓰고 `(#N)` 을 붙이지 않는다(버릴
레포에서 커밋이 하나인 PR 둘로 봤다). 그래서 제목 조회가 「PR 제목 (#N)」을 만든다.

**본문은 인라인 `--body` 로 전달한다.** 전달하지 않으면 GitHub 이 브랜치 커밋 메시지를 전부 이어 붙여
스쿼시 본문으로 쓴다. 라운드를 여러 번 진행한 PR 에서는 그것이 백 줄을 넘고, 커밋마다의 트레일러가
그대로 쌓여 같은 줄이 커밋 수만큼 되풀이된다. 전달하면 GitHub 은 그 기본 본문도, 끝에
덧붙이던 자기 `Co-authored-by:` 줄도 붙이지 않는다. 무엇을 왜 바꿨는지는 PR 본문과 결정
코멘트와 dev-log 항목에 이미 있다. 그래서 본문에는 이 PR 과 닫히는 이슈의 주소와, 브랜치 커밋이 단
트레일러를 중복 없이 적는다. 스쿼시 제목의 `(#N)` 은 GitHub 웹에서만 링크이고 `git log` 에서는
글자라, 주소를 본문에 적는다.

제목은 이 조회가 낸다. 위 「닫히는 이슈 줄」의 제목 줄과 같은 식이다:

    gh pr view <N> --json title,number --jq '"\(.title) (#\(.number))" | gsub("(?<c>[\"$`\\\\])"; "\\\(.c)")'

두 주소는 이 조회가 낸다. 첫 줄이 이 PR 의 URL 이고 나머지가 `closingIssuesReferences` 의 이슈
URL 이다:

    gh pr view <N> --json url,closingIssuesReferences --jq '.url, (.closingIssuesReferences[]|.url)'

트레일러는 이 조회가 낸다. 브랜치의 커밋들이 단 트레일러에서 중복을 없앤 목록이다. 그
코드를 실제로 쓴 모델이 남고, 머지하는 세션이 값을 고르지 않는다. 서버에서 읽으므로
로컬 브랜치가 없어도 된다. 번호로 머지하는 경로에서는 로컬 `HEAD` 가 `main` 이다:

    gh pr view <N> --json commits --jq '.commits[].messageBody' \
      > "${TMPDIR:-/tmp}/pr<N>-commit-bodies.txt"; echo "rc=$?"
    grep -i '^Co-Authored-By:' "${TMPDIR:-/tmp}/pr<N>-commit-bodies.txt" | sort -u

**파이프에 바로 넣지 마라.** 조회가 실패해도 파이프라인은 빈 출력에 `rc=0` 이라
「트레일러가 없다」와 구분되지 않고, 그대로 진행하면 트레일러 없는 스쿼시 커밋이 `main` 에
들어간다. 2절의 dev-log 확인과 같은 이유다. `rc` 가 `0` 이 아니면 판정 못 한 것이라 중단한다.

- `--subject` 의 값은 제목 조회의 출력 그대로다. 조회가 셸이 해석하는 글자(`"` · `$` · 백틱 · `\`)
  앞에 `\` 를 붙여 내므로 큰따옴표 안에 그대로 넣는다. 세션이 고르거나 고치지 않는다. 백틱과
  작은따옴표가 든 제목을 버릴 레포에서 이 명령 그대로 머지해, 스쿼시 제목이 PR 제목 그대로인 것을 봤다
- `- PR:` 과 `- Issue:` 의 값은 주소 조회의 출력 그대로다. 세션이 고르거나 조립하지 않는다. 이슈
  줄이 안 나오면 `- Issue:` 줄을 빼고, 둘 이상이면 이슈마다 한 줄이다
- `Closes #<번호>` 줄은 봇 설정이 있고 본문 밖에서 끝낸 이슈가 있을 때만 쓴다(위 「봇 설정이 있으면 닫는 명령
  대신」). 이슈마다 한 줄이고, 틀의 자리(`- Issue:` 줄 바로 아래, 트레일러 줄 앞의 빈 줄 위)에 둔다. 트레일러
  줄 뒤에 붙이면 git 이 그 문단을 트레일러로 읽지 못해 스쿼시 커밋에서 트레일러가 사라진다. 없으면 그 줄을 뺀다
- 라벨은 영어다. 커밋 메시지는 영어라는 규칙이 이 본문에도 적용된다
- 트레일러 줄은 트레일러 조회의 출력 그대로다. 한 줄이면 한 줄, 여럿이면 줄마다 하나다. `rc=0`
  인데 아무것도 안 나오면 트레일러 줄을 쓰지 않는다. 세션이 지어내지 않는다

**`--body-file` 을 쓰지 마라.** 파일로 전달하면 명령에 경로만 남아, 사람에게 보이는 머지 명령
전문에도 권한 프롬프트에도 커밋에 들어갈 글이 없다. 인라인이면 명령이 곧 내용이다. 이
본문에는 셸이 깨뜨릴 백틱도 따옴표도 없다.

**빈 문자열을 전달하지 마라.** 본문이 통째로 비고 **트레일러까지 사라진다**(실제로 한
프로젝트의 `main` 커밋 둘에서 그렇게 됐고, 히스토리 재작성 없이는 못 고친다). 사람이
고치지 않기로 한 발견은 위 결정 코멘트에 이미 적으므로 여기 다시 적을 것이 없다.

**권한 프롬프트가 표시된다.** 이 명령과 위의 `gh pr comment` 는 둘 다 `settings.json` 의
`ask` 에 있고, 이 스킬 안에서 실행해도 마찬가지다. 사람이 승인할 때까지 기다린다 —
이 스킬 §전제 가 요구하는 "사람이 머지를 지시했다" 를 기계로 한 번 더 확인하는 자리다.
**프롬프트로 사람이 확인할 수 있는 것은 명령까지다.** `gh pr merge` 는 명령이 곧 내용이지만
여러 줄 본문까지 프롬프트에 보이는지는 확인하지 않았고, 결정 코멘트는 `--body-file` 이라
**프롬프트에 파일 경로만 보인다.**

**머지가 끝나면 이 PR 이 끝낸 이슈를 닫는다.** 위에서 보이고 승인받은 `gh issue close` 명령을
그대로 실행한다. 이 명령은 `settings.json` 의 `ask` 에 있어 권한 프롬프트를 거친다. 사람이
거절하면 이슈를 연 채 두고 5절의 보고에 한 줄 덧붙인다. `dev-log` 가 계획 문서에서 그 이슈의
줄을 지웠으면 그 사실도 같이 적는다 — 이슈는 열려 있는데 계획에서는 빠진다. 명령을 보이지
않았으면(끝낸 이슈가 없으면) 아무것도 닫지 않는다.

### 봇 설정이 있을 때 — auto-merge 를 켜고 끝낸다

2절에서 auto-merge 를 켤 수 있다고 본 PR 이다. 차례는 이렇다.

1. 결정 코멘트 초안 · 아래 머지 명령 전문을 응답에 출력한다. 머지가 닫지 않지만 이 PR 이 끝낸 이슈가 있으면
   그 이슈를 머지 명령의 `--body` 에 `Closes #<번호>` 줄로 넣고 창으로 승인받는다. 없으면 창은 없다.
2. 결정 코멘트를 올린다(위 `gh pr comment` 한 줄).
3. auto-merge 를 켠다:

       gh pr merge <N> --auto --squash --match-head-commit <headRefOid> --subject "<제목 조회의 출력>" --body "- PR: <이 PR 의 URL>
       - Issue: <닫히는 이슈의 URL>
       Closes #<본문 밖에서 끝낸 이슈의 번호>

       <브랜치 커밋의 트레일러 줄>"

   `--subject` · `--body` 는 위 머지 명령과 같은 규칙으로 쓴다. gh 는 `--match-head-commit` 의 값을 auto-merge 의
   `expectedHeadOid` 로 전달한다(gh v2.92.0 `pkg/cmd/pr/merge/http.go`). GitHub 이 그 값을 머지할 때도 대조하는지는
   확인하지 않았다. 켠 뒤에 오는 새 커밋을 막는 것은 막기 훅뿐이고, 그 훅은 세션의 푸시만 막는다(아래). 사람이
   PR 브랜치에 푸시하면 막는 것이 없다 — 마지막 푸시 승인은 푸시한 사람의 Approve 만 세지 않으므로, 쓰기 권한이
   있는 다른 사람이 Approve 하는 순간 새 커밋이 켤 때 담긴 옛 제목 · 본문과 옛 결정 코멘트대로 머지된다. 그래서
   사람은 PR 브랜치에 푸시하기 전에 세션에 알려 auto-merge 를 끄게 한다(`docs/process/kit-guide.md` 3절).

   **켜는 명령이 실패하면** 결정 코멘트가 말하는 「Approve 하면 GitHub 이 머지한다」가 거짓이 된다. 결정 코멘트
   뒤에 코멘트로 한 줄 `auto-merge 를 켜지 못했다: <gh 가 낸 오류의 첫 줄>. 사람이 Approve 한 뒤 알리면 세션이
   확인하고 머지한다.` 를 남기고, 2절의 「그 밖이면 세션이 Approve 를 확인한다」로 간다. 부탁 블록의 「그 뒤」도
   그 절의 것이다. 봇이 auto-merge 를 켤 권한이 없거나, 2절과 이 명령 사이에 PR 이 바로 머지할 수 있는 상태가 되어
   막기 훅이 막은 경우다.
4. 응답을 2절의 부탁 블록으로 끝낸다. 할 일 줄에 「Approve 하면 확인 없이 바로 머지된다」를 적는다 — auto-merge
   없이 머지할 때는 Approve 뒤에 세션이 한 번 더 확인했으므로, 사람은 누르기 전에 그 차이를 알아야 한다. 「그
   뒤」는 「GitHub 이 머지하고 head 브랜치를 지운다. 알려 주지 않아도 된다」다. 5절의 `Auto-merge on …` 줄도
   이 응답에 적는다.

**머지되기 전에 다시 해야 하면 먼저 끈다.** 브랜치에 푸시해야 할 때와, 사람이 결정 코멘트나 스쿼시 제목 · 본문을
고치라고 할 때다. 차례는 이렇다.

1. `gh pr merge <N> --disable-auto` 로 끈다.
2. 옛 결정 코멘트 뒤에 코멘트로 한 줄 `auto-merge 를 껐다. 이 결정 코멘트로는 머지하지 않는다.` 를 남긴다. 올리는
   시점의 사실만 적는다 — 다시 켤지는 그 뒤의 일이다.
3. 푸시해야 하면 푸시한다.
4. 2절부터 다시 한다(결정 코멘트 · auto-merge · 부탁). 푸시했으면 2절의 「리뷰 반영 확인」이 새 커밋을 나열하며
   멈추고, 한 라운드 더 할지는 사람이 정한다.

끄지 않으면 사람이나 다른 리뷰어가 Approve 하는 순간 켤 때 담긴 옛 제목 · 본문과 옛 결정 코멘트대로 머지된다.
옛 결정 코멘트를 편집하지 않는 이유는 3절의 거절 경로와 같다 — 한 번 올린 기록이 바뀐다. 막기 훅(`bot_guard.sh`)이
auto-merge 가 켜진 PR 의 브랜치로 가는 푸시를 막는다.

**다음 작업을 시작할 때 auto-merge 가 켜진 열린 PR 과 머지된 PR 을 본다.** 머지는 사람이 Approve 한 순간 GitHub 이
하므로 세션이 그 자리에 없고, Approve 를 받고도 머지되지 못할 수도 있다. 다음 작업의 브랜치를 만들기 전에 둘을 본다:

    gh pr list --state open --json number,headRefName,reviewDecision,mergeStateStatus,autoMergeRequest --jq '.[] | select(.autoMergeRequest != null) | "#\(.number) \(.headRefName) \(.reviewDecision) \(.mergeStateStatus)"'
    gh pr list --state merged --limit 30 --json number,headRefName --jq '.[] | "#\(.number) \(.headRefName)"'

- auto-merge 가 켜진 열린 PR 가운데 `reviewDecision` 이 `APPROVED` 인 것은 Approve 를 받고도 머지되지 못한 것이다.
  브랜치가 base 보다 뒤처졌거나(`BEHIND` — `install.sh --protect` 가 켜는 브랜치 보호는 최신 브랜치를 요구한다),
  충돌했거나(`DIRTY`), 필요한 검사가 실패했거나 풀리지 않은 리뷰 대화가 있다(`BLOCKED` — `--protect` 가 켜는 브랜치
  보호는 대화 해결도 요구한다). 사람에게 그 PR 과 상태를 알린다. 브랜치를 갱신하는 절차는 킷에 아직 없으므로 세션이
  스스로 갱신하지 않는다 — base 를 합치면 2절의 「리뷰 반영 확인」이 다른 PR 의 커밋을 이 PR 의 커밋으로 나열하고,
  충돌을 푼 내용은 파일 없이 나열한다. 어떻게 할지는 사람이 정한다
- `REVIEW_REQUIRED` 인 것은 Approve 를 기다리는 중이라 그대로 둔다
- 머지된 PR 가운데 로컬 브랜치가 남은 것(`git rev-parse --verify --quiet <headRefName>` 이 출력을 낸다)은
  `merge-pr <N>` 으로 정리한다 — 2절이 `MERGED` 를 보고 4절과 5절만 한다

그리고 다음 작업의 브랜치는 `origin/<baseRefName>` 에서 만든다. 앞 PR 브랜치 위에 만들면 앞 PR 이 스쿼시로 머지된
뒤 다음 PR 의 diff 에 그 변경이 다시 나온다. 세션 시작 안내(`bot_session.sh`)와 템플릿 `CLAUDE.md` 의 작업 루프도
이것을 알린다 — 새 세션이나 컴팩션 뒤의 세션은 이 스킬을 읽지 않은 채 다음 작업을 시작한다. 원격 브랜치를 레포
설정 「Automatically delete head branches」가 지웠으면 4절의 원격 삭제는 `remote ref does not exist` 로 끝난다. 그
설정이 꺼진 레포에서는 4절이 지운다(승인은 Approve 다). 머지 뒤에야 나온 것이 있으면 4절의 후속 코멘트로 붙인다.

## 4. base 복귀와 브랜치 삭제

`<baseRefName>` · `<headRefName>` · `isCrossRepository` 는 2절이 받아둔 값이다. **이름을 여기서 새로 구하지 마라.**
이 절은 base 로 옮긴 **뒤**에 브랜치를 지우고, `$ARGUMENTS` 로 **다른 PR 을 번호로 머지하는
것이 정상 경로**다(`argument-hint`).

**base 로 돌아온다:**

    if [ "$(git rev-parse --absolute-git-dir)" = "$(git rev-parse --path-format=absolute --git-common-dir)" ] && git switch <baseRefName>; then git pull --ff-only; else git fetch origin && git switch --detach origin/<baseRefName> && { git fetch -q origin <baseRefName>:<baseRefName> 2>/dev/null || true; }; fi

원래 체크아웃에서(`--absolute-git-dir` 와 `--git-common-dir` 가 같다) `git switch` 가 되면 base 브랜치에서
fast-forward 한다. fast-forward 실패 시 중단: `Error: <baseRefName> 을 fast-forward 할 수 없습니다.`
**절대 경로 형태로 견준다.** 원래 체크아웃의 하위 디렉터리에서 `--git-dir` 는 절대 경로를, `--git-common-dir` 는
`../../.git` 같은 상대 경로를 출력해서, 그대로 견주면 원래 체크아웃을 worktree 로 판정한다. 세션의 작업
디렉터리는 호출 사이에 유지되므로 하위 디렉터리에서 실행되는 일이 흔하다.

**git worktree 에서는 base 로 옮기지 않는다. fetch 한 뒤 `origin/<baseRefName>` 에 detach 한다.** worktree 가
base 브랜치에 있으면 원래 체크아웃이 base 로 옮기지 못한다. 원래 체크아웃이 다른 브랜치에 있으면 worktree 의
`git switch` 는 성공하므로, 되는지를 보지 않고 worktree 인지로 구분한다. 원래 체크아웃에서도 다른
worktree 가 base 를 쓰면 `git switch` 가 `fatal: '<baseRefName>' is already used by worktree at …` 로 실패하고,
그때도 detach 한다. PR 브랜치에서 내려와야 아래에서 그 브랜치를 지울 수 있다.

**detach 한 뒤 로컬 base 브랜치도 fast-forward 한다(`git fetch origin <baseRefName>:<baseRefName>`).** 로컬 base 가
머지 전 커밋에 머물면, 그 뒤 만든 브랜치에서 `open-pr` · `dev-log` · `trace` 가 주입하는 `git log main..HEAD` 가 방금
머지한 커밋을 그 브랜치의 변경으로 보여 준다. base 를 쓰는 체크아웃이 있으면 git 이
`refusing to fetch into branch … checked out at …` 로 거부하고, 그 체크아웃은 그곳의 사람이 직접 pull 한다.
그래서 이 갱신의 실패는 줄의 종료 코드에 섞지 않는다(`|| true`). **이 거부는 git 2.35 부터다.** 그 전 git 은
현재 worktree 의 브랜치만 보호해서, 원래 체크아웃이 쓰는 base 의 ref 만 옮기고 그 작업 트리는 머지 전으로
둔다. 킷이 전제하는 macOS · ubuntu CI 의 git 은 그보다 새것이다.

**이 줄의 종료 코드가 0 이 아니면 중단한다.** fetch 가 네트워크 때문에 실패하면 그 줄이 실패한다.
fetch 를 따로 두면 fetch 가 실패해도 받아 둔 옛 `origin/<baseRefName>` 에 조용히 detach 해서, 머지 전
커밋에 있는 채 브랜치를 지우고 5절이 그 SHA 를 보고한다. base 로 옮기는 경로는 `git pull --ff-only` 가
fetch 한다.

**이 줄은 설치된 레포에서 어느 분기가 실행되든 권한 프롬프트를 거친다.** Claude Code 는 `;` · `&&` 로 나뉜
조각마다 따로 규칙에 맞는지 보고(권한 문서의 Compound commands: "A rule must match each subcommand
independently."), `git fetch` 는 설치되는 `settings.json` 의 `allow` 에 없다. 어느 분기가 실행될지는
실행 전에 모른다. 사람이 거절하면 줄 전체가 실행되지 않는다. 그때도 중단하고, 5절의 보고에 머지는
끝났고 base 복귀와 브랜치 삭제는 하지 않았다고 적는다. 봇 설정이 없으면 스킬을 다시 불러도 2절에서
멈추므로(`state` 가 `OPEN` 이 아니다) 남은 일은 사람이 정한다. 봇 설정이 있으면 다시 부른 스킬의 2절이
`MERGED` 를 보고 이 절을 다시 실행하므로, 사람이 거절한 명령이 다시 권한 프롬프트로 나온다.

**원격 브랜치를 지운다. `isCrossRepository` 가 `true` 면 지우지 않는다:**

    git push origin --delete <headRefName>

fork 에서 온 PR 의 head 브랜치는 fork 에 있다. origin 에 같은 이름의 브랜치가 있으면 그것은 base
레포의 다른 브랜치다. gh 도 이 경우 원격 삭제를 건너뛰었다(v2.92.0 `deleteRemoteBranch` 의
`crossRepoPR`). 그때는 명령을 실행하지 않고 5절에 「fork PR 이라 원격 브랜치를 지우지 않았다」고 적는다.

`remote ref does not exist` 로 실패하면 이미 지워진 것이다. 레포가 머지 뒤 원격 브랜치를
자동으로 지우는 설정이면 그렇다. 그 밖의 실패는 5절의 보고에 한 줄 덧붙인다. 이 명령은
`settings.json` 의 `ask` 에 있어 권한 프롬프트를 거친다. 승인은 3절에서 명령을 보이고 받았다.
사람이 이 프롬프트에서 거절하면 원격 브랜치를 남긴 채 아래 로컬 삭제를 진행하고, 5절에 남겼다고 한
줄 덧붙인다.

**로컬 브랜치가 남아 있으면 지운다.** 2절이 로컬과 서버가 같다는 것을 머지 전에 확인했으므로
지워도 잃을 것이 없다:

    git rev-parse --verify --quiet <headRefName>   # 출력이 없으면 로컬에 없다. 5절을 진행한다
    git branch -D <headRefName>                    # 출력이 있으면 지운다

`cannot delete branch '<headRefName>' used by worktree at <경로>` 로 실패하면 다른 worktree 가
그 브랜치를 쓰고 있다. 원래 체크아웃에서 번호로 머지했고 PR 브랜치는 worktree 의 세션이 쓰는
경우다. 지우지 말고 남긴 채, 5절의 보고에 그 경로와 함께 남겼다고 한 줄 덧붙인다.

**`-d` 가 아니라 `-D` 인 이유.** 원격 추적 ref 가 지워진(prune) 레포에서는 `-d` 가 다 푸시한
브랜치도 거부한다. 2절이 이미 확인한 것을 다시 확인하느라 멀쩡한 삭제를 막을 까닭이 없다.

**`-D` 에서 권한 프롬프트가 표시된다**(`settings.json` 의 `ask`). 사람이 거절하면 브랜치를 남기고,
5절의 보고에 남겼다고 한 줄 덧붙인다.

**`--verify --quiet` 를 빼지 마라.** 옵션 없이 실행한 `git rev-parse <없는 브랜치>` 는 `rc=128` 로 실패하면서
**인자를 stdout 으로 그대로 출력한다**(`fatal:` 은 stderr 로 출력된다). 읽는 쪽이 그것을 SHA 자리에서
받으면, 이미 지워진 **정상 경로에서 이 절이 멈춘다.** 실제로 확인한 결과:

    $ git rev-parse nosuchbranch                    → stdout `nosuchbranch`, rc=128
    $ git rev-parse --verify --quiet nosuchbranch   → 출력 없음, rc=1

**머지 뒤에야 나오는 것.** 머지해야 비로소 확인되는 것이 있다(4절의 삭제가 실제로 됐는지
처럼). **결정 코멘트는 머지 전에 올린 기록이므로 그 결과를 결정 코멘트에 넣지 마라.** 3절의
「같은 코멘트를 다시 올리지 마라 — 그 뒤에 코멘트로」와 같은 방식으로 **결정 코멘트 뒤에
코멘트를 하나 더 붙인다.** 결정 코멘트를 편집으로 채우면 한 번 올린 기록이 바뀌고, 편집한
뒤에 생긴 것은 또 빠진다. 실제로 둘 다 있었다 — 결정 코멘트의 빈 칸을 머지 뒤 편집으로
채웠고, 그 편집 뒤에 연 이슈가 최종 기록에서 빠졌다. **이 후속 코멘트도 응답에 초안 전문을 출력하고
승인받은 뒤 올린다.** 지금은 받는 승인이다(`docs/process/verification-stages.md` 6.3).

## 5. 한 줄 보고
`Merged PR #<N>. main at <short SHA>. dev-log: 있음|없음|판정 못 함.`

auto-merge 를 켜고 끝낸 응답(3절 「봇 설정이 있을 때」)에서는 머지 전이라 이렇게 적는다:
`Auto-merge on PR #<N> at <short head SHA>. dev-log: 있음|없음|판정 못 함.` 머지 뒤 정리에서 위 줄을 적는다.

`없음` 과 `판정 못 함` 은 2절에서 사람이 알고도 머지를 지시한 경우뿐이고, 그 사실은 결정 코멘트에
적혀 있다. 판정 못 한 것을 `없음` 으로 적지 않는다 — 그것이 2절의 그 확인이 없애려는 거짓 기록이다.

이후 새 작업을 시작하지 않는다. 다음 작업을 시작할 때의 정리로 불렀으면(2절 전제의 예외) 사람이 시킨 그 작업으로
돌아간다. 머지된 PR 이 더 있으면 그 PR 도 정리한 뒤다.
