## 2. 머지 전 안전 확인

### 전제 — 사람이 머지를 지시했을 때만 진행한다

이 전제는 `SKILL.md` 의 「꼭 지킬 것」에 있다.

### 그다음 — 하나라도 실패하면 즉시 중단

- `gh pr view <N> --json state,headRefName,headRefOid,baseRefName,isCrossRepository` → `state` 가 `OPEN` 이 아니면 중단.
  봇 설정이 있고 `MERGED` 이면 auto-merge 로 머지된 뒤다 — 아래 확인 가운데 「로컬 브랜치가 서버와 같은지」만
  보고 4절과 5절을 한다(3절 「봇 설정이 있을 때」의 머지 뒤 정리). 그 확인을 빼면 4절의 `git branch -D` 가 auto-merge 를
  켠 뒤에 만들고 푸시하지 못한 커밋까지 지운다. `state` 밖의 네 값은 바로 아래 확인과 4절이 쓴다. **셸 변수에 담지 마라. 읽어서
  출력한다** — 명령을 여러 번 부르는 사이에 셸 상태는 유지되지 않는다(`open-pr` 3.1 이 그 사고로 적어 둔 규칙이다).
- `gh pr checks <N>` → `fail` 또는 `pending` 이 하나라도 있으면 중단하고 해당 체크를 나열한다.
- `SKILL.md` 에 주입된 `git status --porcelain` 이 비어 있지 않으면 중단.
- **로컬 브랜치가 서버와 같은지 본다. 머지 전인 여기서 한다:**

      git rev-parse --verify --quiet <headRefName>   # 출력이 없으면 로컬에 그 브랜치가 없다. 건너뛴다

  출력이 있으면 그 SHA 를 위에서 받은 `headRefOid` 와 **글자로** 견준다. **다르면 중단하고
  사람에게 말한다.** 대개 푸시하지 않은 커밋이 로컬에 남아 있다. 로컬이 뒤처진 경우도 여기서
  멈추는데, 그쪽은 멈춰도 잃는 것이 없다.

  **왜 머지 전인가.** 4절의 `git branch -D` 는 로컬에만 있는 커밋이 있어도 그 브랜치째 지운다.
  그리고 푸시하지 않은 커밋은 머지에도 들어가지 않는다. 그래서 **머지하기 전이자 지우기 전인 여기서
  본다.**

  **왜 글자로 견주나.** 두 커밋의 관계(`git merge-base --is-ancestor`)를 보면 서버 쪽 커밋이
  로컬에 있어야 판정되고, 없으면 `rc=128` 로 실패해 멀쩡한 머지를 막는다. 글자 비교는 로컬
  객체를 요구하지 않는다.
- **이 PR 의 dev-log 항목이 있나.** 서버 head 에서 본다 — 로컬에는 푸시하지 않은 커밋이 있을 수 있고,
  번호로 머지하는 정상 경로에서는 그 head 의 객체가 로컬에 없을 수 있다. 그래서 로컬 객체를
  요구하지 않는 조회로 본다. **파일로 먼저 받고 종료 코드를 본 뒤에 센다. 파이프에 넣지 마라:**

      gh api "repos/{owner}/{repo}/contents/docs/dev-log.md?ref=<headRefOid>" \
          -H "Accept: application/vnd.github.raw" > "${TMPDIR:-/tmp}/pr<N>-dev-log.md"; echo "rc=$?"
      grep -cE '^## .*\(PR [^)]*#<N>([^0-9]|\)|$)' "${TMPDIR:-/tmp}/pr<N>-dev-log.md"

  판정은 셋이다. `rc=0` 에 `1` 이상이면 있다. `rc=0` 에 `0` 이면 파일은 있는데 항목이 없다 — 중단하고
  사람에게 말한다. dev-log 는 머지 직전에 쓰는 것이라(`dev-log` 스킬) 여기서 없으면 안 쓴 것이다.
  dev-log 항목이 없는 것을 알고도 사람이 머지하라고 하면 진행하되, **3절의 결정 코멘트에 「dev-log 항목 없음」을
  적는다.** `rc` 가 `0` 이 아니면(404 든 네트워크든) 판정 못 한 것이라 중단한다. 판정하지 못한 것을 알고도
  사람이 머지하라고 하면 결정 코멘트에 「dev-log 항목 판정 못 함」을 적는다 — 판정 못 한 것을 「없음」으로
  적는 것이 이 확인이 없애려는 거짓 기록이다.
  `gh api` 는 설치되는 `settings.json` 의 `ask` 에 있어 설치된 레포에서는 이 조회에 권한 프롬프트가
  하나 표시된다. 읽기뿐이라 승인하면 그대로 진행한다.
  **파이프에 넣지 않는 이유**: `gh api` 는 실패해도 오류 JSON 을 stdout 으로 내고 `grep -c` 가
  그것을 `0` 으로 센다 — 「항목 없음」과 같은 숫자다. 파일로 받으면 종료 코드가 둘을 구분한다.
  **파일을 `${TMPDIR:-/tmp}` 에 두는 이유**: 레포 안에 쓰면 그 파일이 작업 트리에 남아 이 스킬을 다시 부를 때
  위 `git status --porcelain` 확인에서 중단되고, `$(mktemp)` 를 변수에 담으면 명령을 따로 부르는 사이에 셸 상태가 안 남는다(위 첫 불릿과
  같은 이유다).
  정규식이 `(PR #<N>)` 보다 느슨한 이유: 한 항목이 PR 둘을 들 수 있다(`(PR #13 · #14)`). 번호 뒤를
  `[^0-9]` 로 막아 `#6` 이 `#69` 에 맞지는 않는다. `git show <headRefOid>:docs/dev-log.md` 를 쓰지
  않는 이유: 객체가 로컬에 없을 때와 파일이 없을 때가 같은 `fatal` 과 `0` 을 내 둘을 구분하지 못한다.
- **리뷰 반영 확인.** `open-pr` 이 올린 **마지막 라운드 코멘트**를 읽는다:

      gh pr view <N> --json comments \
        --jq '[.comments[] | select(.body|test("^\\s*## 리뷰 "))] | last | .body'

  그 코멘트 **맨 위의** `리뷰한 head:` 를 **위 첫 줄에서 받아 둔 `headRefOid`** 와 비교한다.
  접힌 전문 안에도 같은 줄이 있으므로 맨 위 것을 쓴다.

  **다르면** 마지막 라운드 뒤에 커밋이 더 쌓인 것이고 그 커밋들은 아무도 안 봤다.
  중단하고 **어느 커밋인지 파일까지 나열해** 사람에게 말한다. 끝점은 위에서 받은 `headRefOid`
  다. 로컬 `HEAD` 가 아니다. 번호로 머지하는 정상 경로에서는 `HEAD` 가 `main` 이라 목록이
  비거나 남의 커밋이 나온다. 그 객체가 로컬에 없을 수 있으므로 먼저 받는다:

      git fetch origin <headRefName> <baseRefName>; echo "rc=$?"
      git -c core.quotePath=false log --remerge-diff <그 head>..<headRefOid> ^origin/<baseRefName> --format='%h [%p] %s' --name-only; echo "rc=$?"

  `git fetch` 는 설치되는 `settings.json` 의 `allow` 에 없어 설치된 레포에서는 이 fetch 에 권한
  프롬프트가 하나 표시된다. 읽기뿐이라 승인하면 그대로 진행한다. 나열과 아래 머지 커밋 보기는 `git -c` 로 시작해
  `allow` 의 `git log` · `git show` 규칙에 맞지 않으므로, 이 둘을 위한 규칙을 `allow` 에 따로 두었다.

  **base 를 합친 브랜치에서도 이 PR 의 커밋만 나오게 한다.** `^origin/<baseRefName>` 은 base 를 합친 머지로
  들어온 base 의 커밋을 뺀다 — 그 커밋은 각자의 PR 에서 리뷰를 거쳤다. 빼지 않으면 그 커밋이 이 PR 의 리뷰를
  거치지 않은 커밋으로 나온다. base 를 함께 받는 이유: 받아 둔 base 가 옛것이면, 그 뒤 base 에 들어와 이 브랜치에
  합친 커밋이 빠지지 않고 나열에 나온다. `--first-parent` 로 빼지 않는 이유: base 가 아닌 브랜치를 합친 머지에서
  그 브랜치의 커밋까지 숨긴다. `--remerge-diff` 는 머지 커밋 아래에 자동 머지와 다르게 된 파일만 적는다 — 충돌을
  푼 파일과 머지하면서 고친 파일이다. 한쪽만 남겨 푼 충돌의 파일도 나온다. 충돌 없이 합친 머지 커밋은 파일 없이
  나온다. `-c core.quotePath=false` 는 한글 같은 비ASCII 파일 이름이 8진수로 나오지 않게 한다. `[%p]` 에 부모가
  둘인 커밋이 머지 커밋이고, 머지 커밋마다 이것을 실행해 무엇을 어떻게 풀었는지 본다:

      git -c core.quotePath=false show --remerge-diff --format='%h %s' <머지 커밋>; echo "rc=$?"

  출력은 충돌 표시와 그것을 푼 줄, 머지하면서 고친 줄이다. 머리 한 줄만 나오면 충돌 없이 합친 것이다.

  판정은 둘이다. `fetch` · `log` · `show` 의 `rc` 가 `0` 이 아니면 판정 못 한 것이라 중단한다. dev-log
  확인과 같은 규칙이다. 판정하지 못한 것을 알고도 사람이 머지하라고 하면 결정 코멘트에 「나열 판정 못 함」을
  적는다. **head 가 다른데 목록이 비면 둘 중 하나다.** 서버 head 가 마지막 라운드 head 의
  조상이면 되감기다. 브랜치가 리뷰한 것보다 뒤로 돌아갔다. 그 사실을 사람에게 말하고
  중단한다. 그 밖에 목록이 비면 명령이 잘못 실행된 것이라 중단한다. 둘을 구분하는 명령:

      git merge-base --is-ancestor <headRefOid> <그 head>; echo "rc=$?"   # 0 이면 되감기

  끝점이 `origin/<headRefName>` 이 아닌 이유: 2절의 다른 확인이 전부 `headRefOid` 에 묶여
  있고, 그 값을 읽은 뒤 누가 푸시하면 브랜치 이름이 가리키는 것이 달라진다.
  사람이 리뷰를 거치지 않은 그 커밋들을 알고도 머지하라고 하면 진행하되, **3절의 결정 코멘트에 그 커밋 목록과
  "리뷰를 거치지 않았다" 를 적는다.** 이것은 정상 경로다 — `open-pr` 이 사람에게
  창으로 제시하는 보기에 "고치고 추가 라운드 없이 머지" 가 들어 있고, 그렇게 하면 head 는
  반드시 달라진다. 막는 것이 목적이 아니다. **리뷰를 거치지 않은 커밋이 있다는 사실을
  기록 없이 머지되지 않게 하는 것**이 목적이다.

  **dev-log 커밋은 늘 이 목록에 나온다.** `dev-log` 스킬이 머지 직전에 실행되므로 그 커밋은 마지막
  라운드 뒤에 온다. dev-log 를 쓴 PR 마다 이 확인이 멈추고, 그것은 결함이 아니라 이 확인이
  하는 일이다. 사람에게 말할 때 커밋을 셋으로 나눠 적는다. 머지 커밋, `docs/dev-log.md`
  **하나만** 바뀐 커밋, 그 밖의 커밋이다. 기준은 부모 수와 파일이지 커밋 제목이 아니다. 위 나열
  명령이 커밋마다 부모와 건드린 파일을 내므로 분류는 그 출력대로다. 세션이 판정하지 않는다.
  머지 커밋은 파일이 무엇이든 따로 적고, 위 `git show --remerge-diff` 의 출력을 붙인다 —
  dev-log 끝에서 부딪힌 것을 푼 머지도 다른 PR 의 항목을 지웠는지는 그 출력으로만 보인다. dev-log
  항목과 계획 줄 삭제가 한 커밋이면 파일이 둘이라 「그 밖」이다. 그 커밋이 계획 문서의 다른 줄을 같이
  건드렸는지는 파일 이름만으로 모르므로 사람이 한 번 본다. **사람이 보는 것은 머지 커밋과 그 밖의
  커밋이다.** 3절의 「리뷰를 거치지 않은 커밋」 줄에도 같은 구분으로 적는다. 「dev-log 만
  바뀐 커밋은 빼고 센다」는 예외는 넣지 않는다. 구분하는 쪽이 틀리면 리뷰를 안 거친 변경이
  알림 없이 머지되고, 구분하지 못할 때는 사람에게 보인다.

  **base 를 합친 머지 커밋은 「브랜치 갱신」 결정이 있을 때만 다시 묻지 않고 진행한다.** 그 결정은 사람이 3절
  「Approve 를 받고도 머지되지 않으면」의 「브랜치 갱신」 창에서 합치기를 고른 것이고, 아래 「그 코멘트 뒤의
  코멘트」에 사람 계정 코멘트로 있다. 그 결정이 있으면 그것이 그 머지 커밋으로 머지하라는 지시다. 다만 머지 커밋
  아래에 `docs/dev-log.md` 밖의 파일이 나오면 그 파일에서 충돌을 풀거나 고친 줄은 두 리뷰가 보지 않은 것이라,
  사람에게 그 사실을 말하고 한 라운드 더 한다(`open-pr` 3.6). `docs/dev-log.md` 하나만 나오거나 파일이 없으면
  라운드 없이, 결정 코멘트에 실은 `--remerge-diff` 출력을 사람이 보고 Approve 한다. 그 결정이 없는 base 머지
  커밋(PR 웹의 「Update branch」로 만든 것이나 대화로 정해 합친 것)은 다른 커밋과 같이, 사람이 리뷰를 거치지 않은
  것을 알고도 머지하라고 할 때만 진행한다.

  **`리뷰한 head:` 줄이 아예 없으면** 옛 형식의 코멘트다. 대조할 수 없으므로 통과로
  처리하지 말고, 그 사실을 말하고 사람의 판단을 받는다.

  두 리뷰의 `Verdict` 는 그 코멘트 첫 줄에 있다. `Request changes` 가 해소되지 않았으면
  중단 — 사람이 그것을 해소하지 않고 머지하기로 했다면 그 사실을 3절에 적는다.

  라운드 코멘트를 못 찾으면 **리뷰가 실행되지 않은 것이다.** 중단한다.

  **그 코멘트 뒤의 코멘트도 읽는다** — 사람의 결정이고, **마지막 라운드 뒤에 사람이 정한 것이
  거기 있다.** 그 라운드가 끝난 뒤에 정한 것이라 라운드 코멘트에는 없다:

      gh pr view <N> --json comments \
        --jq '.comments as $c
              | ([$c|to_entries[]|select(.value.body|test("^\\s*## 리뷰 "))|.key]|last) as $i
              | if $i == null then []
                else $c[$i+1:]
                  | map(select(($c[$i].authorAssociation|IN("OWNER","MEMBER","COLLABORATOR")|not)
                               and (.authorAssociation|IN("OWNER","MEMBER","COLLABORATOR"))))
                end
              | map(.body) | join("\n\n———\n\n")'

  **위치만으로 고르지 않는다.** 라운드 코멘트 뒤에는 **이 스킬이 올린 코멘트도 들어간다** — `merge.md` 의
  「사람이 이 프롬프트에서 거절하면」 경로가 결정 코멘트와 `머지하지 않았다…` 한 줄을 그 뒤에 남기고,
  다시 지시받으면 새 결정 코멘트를 올린다. 위치만 보면 옛 결정 코멘트가 **사람이 정한 것으로**
  새 결정 코멘트에 인용되고, `사람이 머지를 결정했다` 가 여러 벌 남는 문제가 다른 모양으로
  다시 생긴다. 그래서 글쓴이로 고른다 — 봇이 올린 라운드 코멘트 뒤의 사람 계정(`authorAssociation` 이
  OWNER · MEMBER · COLLABORATOR) 코멘트다. 창에서 고른 보기로 만든 사람 계정 코멘트(`open-pr` 3.5)와 사람이
  PR 웹에서 쓴 코멘트가 그것이고, 이 스킬의 코멘트는 봇 계정이라 빠진다. 봇 설정이 없어 라운드 코멘트가 사람
  계정이면 아무것도 고르지 않는다 — 킷은 봇과 함께 쓴다.
- **auto-merge 를 켤 수 있나.** 레포에 봇 설정(`.claude/bot.json`)이 있을 때만 본다:

      gh pr view <N> --json reviewDecision,mergeStateStatus
      gh api "repos/{owner}/{repo}" --jq .allow_auto_merge

  `reviewDecision` 이 `REVIEW_REQUIRED` 이고 `mergeStateStatus` 가 `BLOCKED` 이고 `allow_auto_merge` 가 `true`
  면 3절의 「봇 설정이 있을 때」를 따른다 — 결정 코멘트를 올리고 auto-merge 를 켠 뒤 Approve 를 요청한다.
  **다른 상태에서 `--auto` 를 주지 마라.** gh 는 바로 머지할 수 있는 PR(`CLEAN` · `HAS_HOOKS` · `UNSTABLE`)에서
  `--auto` 를 무시하고 그 자리에서 머지한다(gh v2.92.0 `pkg/cmd/pr/merge/merge.go` 의 `isImmediatelyMergeable`).
  승인을 요구하지 않는 레포(`reviewDecision` 이 비었다)에서는 검사가 끝나는 순간 Approve 없이 머지된다. 가드
  훅(`bot_guard.sh`)도 그 상태의 `--auto` 를 막는다. `mergeStateStatus` 가 `UNKNOWN` 이면 GitHub 이 아직 계산하는 것이라
  잠시 뒤 다시 본다. `gh api` 는 설치되는 `settings.json` 의 `ask` 에 있어 권한 프롬프트가 하나 표시된다. 읽기뿐이라
  승인하면 그대로 진행한다.

  **그 밖이면 세션이 Approve 를 확인한다.** 이미 승인된 PR · 승인을 요구하지 않는 레포 · auto-merge 를 허용하지
  않은 레포다:

      bash .claude/hooks/human_review.sh approved <N>; echo "rc=$?"

  판정은 셋이다. `rc=0` 이면 `✓ <계정> 가 지금 head <SHA> 를 Approve 했다` 가 나온다. 그 Approve 가
  머지 승인이다 — 3절의 결정 코멘트 · 머지 명령(`--auto` 없이)과 4절의 브랜치 삭제를 창으로 묻지 않고 실행한 뒤,
  올린 결정 코멘트 전문과 실행한 명령을 5절의 보고에 싣는다. `rc=1` 이면 Approve 가 없거나, 이전 커밋에 대한
  것이거나, 쓰기 권한자의 Request changes 가 남아 있거나, 브랜치 보호가 요구하는 승인이 모자라다 — 중단하고
  `✗` 줄을 사람에게 보이고, 3절의 결정 코멘트와 명령 전문을 출력한 뒤 아래 Approve 요청 블록과 창으로 응답을
  끝낸다. auto-merge 를 켜지 않았으므로 블록의 결과 줄 둘을 바꾼다(아래). 사람이 창에서 「Approve 했다」를 고르면
  이 스킬을 다시 실행해 머지한다. 승인이 모자란 까닭은 둘이다.
  필요 승인 수가 모자라면 다른 리뷰어의 Approve 를 기다린다. 승인한 사람이 PR 브랜치에 마지막으로 푸시했으면
  그 Approve 는 세어지지 않으므로(마지막 푸시 승인), 세션이 다시 푸시한 뒤 Approve 를 다시 받는다. `rc=2` 는
  판정 못 한 것이라 중단한다. 설치된 레포에서는 이 명령에 권한 프롬프트가 하나 표시된다. 읽기뿐이라 승인하면
  그대로 진행한다. 어떤 Approve 를 인정하는지는 `.claude/hooks/human_review.sh` 머리에 있다.

  **Approve 를 기다리며 확인을 되풀이하지 않는다.** 정해진 시간 동안 몇 초마다 Approve 를 조회하는 식으로
  기다리지 않는다. 협업에서는 Approve 가 몇 시간 뒤에 달릴 수 있어 시간이 끝나면 결국 사람이 알려야 하고,
  그동안 세션은 다른 일을 못 한다. 요청 블록과 창으로 응답을 끝내고, 사람이 창에서 고른 뒤에 한 번 본다
  (`docs/process/verification-stages.md` 6.3). Approve 를 확인한 뒤 GitHub 이 머지하기를 기다리는 것은 다르다 —
  3절의 「Approve 를 받고도 머지되지 않으면」이 정한다.

  **Approve 요청 블록.** 응답은 이 블록으로 끝내고 바로 뒤에 창을 띄운다(`docs/process/verification-stages.md`
  6.3). 블록은 이 모양 그대로 출력한다:

      ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
      **PR #N 최종 검토: Approve 요청** (head abc1234)
      https://github.com/<owner>/<repo>/pull/<N>/files

      ▶ 머지해도 되면
         ① PR 페이지에서 「Submit review ▾」 → Approve → Submit review
            └ GitHub: 곧바로 머지 (레포 설정 auto-merge, 따로 확인 없음)
         ② 아래 창에서 「Approve 했다」 선택
            └ 세션: 머지 확인
                ├ 머지됨 → 「다음 일」 창
                ├ Approve 됐는데 머지 안 됨 → 까닭 알림 · 할 일 질문 (늦어지는 것이면 10분까지 기다림)
                └ Approve 가 안 보임 → 그 사실 알림

      ▶ 고칠 것이 있으면
         ① GitHub 에서는 아무것도 하지 않음
         ② 아래 창에서 「고칠 것이 있다」 선택
            └ 세션: 무엇을 고칠지 대화로 물음 → 고침 → 이 요청을 다시 함

      ※ 참고 — 터미널로 Approve 하려면: 이 세션 밖에서 gh pr review <N> -R <owner>/<repo> --approve
      ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - 줄 규칙: 기호 없는 줄은 읽는 사람이 할 일, `└` 는 그 단계의 결과이고 누가 하는지 `GitHub:` · `세션:` 을
    반드시 붙인다. `├` · `└` 는 결과가 나뉘는 경우, ① ② 는 순서다. 끝맺음은 명사형이다. 「부탁」은 쓰지 않고
    「요청」이라 한다.
  - auto-merge 를 켜지 않고 요청할 때(위 「그 밖이면」의 `rc=1`)는 결과 줄 둘만 바꾼다 — ① 의 `└` 는
    「GitHub: 머지하지 않음 (auto-merge 꺼짐)」, ② 의 `└` 는 「세션: Approve 확인 → 머지」다.
  - 블록 위에는 무엇이 GitHub 에 올라가고 무엇이 실행만 되는지를 적는다 — 결정 코멘트는 PR 코멘트로, 머지
    명령의 `--subject` · `--body` 는 `main` 의 커밋 메시지로 올라가고, 브랜치 삭제는 실행만 된다(원격 브랜치가
    지워진다). PR 웹의 새 화면에서는 주소가 `/changes` 로 바뀌고, 예전 화면의 버튼 이름은 「Review changes」다.
  - 터미널 길은 이 세션 밖의 사람 터미널이다 — 세션이 실행하는 gh 는 봇 계정이라 PR 작성자의 승인이 되어
    GitHub 이 받지 않는다. 알림에도 링크를 넣는다. **세션이 Approve 하지 않는다** — PR 작성자인 봇은 자기 PR 을
    승인할 수 없고, 승인은 사람의 것이어야 한다.

  **블록 바로 뒤의 창.** 머리말은 「PR #N 최종 검토」, 질문은 「PR #N 을 Approve 하셨나요, 고칠 것이 있나요?」,
  보기는 「Approve 했다」 · 「고칠 것이 있다」 둘이다. 「Approve 했다」를 고르면 PR 이 머지됐는지 한 번 보고 블록의
  ② 에 적은 경우대로 한다. Approve 됐는데 열려 있으면 3절의 「Approve 를 받고도 머지되지 않으면」대로 한다.
  머지됐으면 이 스킬을 `merge-pr <N>` 으로 다시 불러 4절과 5절(로컬 정리와 보고)을 한 뒤 「다음 일」 창으로
  묻는다 — 2절이 `MERGED` 를 보고 그 둘만 한다. 「고칠 것이 있다」 · 직접 쓴 말 · 대화로 받은 것은 `open-pr` 3.5
  대로 창에서 고른 글자로 사람 계정 코멘트를 만든다. GitHub 리뷰 본문은 읽지 않는다 — 사람의 결정은 질문 창과
  대화, 그리고 사람 계정 코멘트로만 받는다.

  **「다음 일」 창.** 머지나 PR 닫기가 끝나면 세션은 다음 작업을 스스로 시작하지 않고 이 창으로 묻는다. 머지 밖에서
  일 하나가 끝났을 때(이슈 코멘트를 올린 뒤 등)와 새 세션이 할 일을 고를 때도 이 문단대로 고른다. 머리말은 「다음
  일」, 질문은 「PR #N 이 머지됐다. 다음에 무엇을 할까요?」(닫았으면 「닫았다」, 머지 밖이면 끝난 일을 적고, 새 세션이면
  「이 세션에서 할 일을 고른다. 무엇을 할까요?」)다. 보기는 다음에 할 일의 후보들이고, 근거를 들어 가장 낫다고 판단한
  하나에 「(추천)」을 붙이고 그 근거를 보기 설명에 적는다. 「멈춘다」를 늘 둔다. PR 에 올라갈 결정이 아니므로 게시
  표지는 적지 않는다. 머지 뒤면 창 앞에 머지 결과와 정리한 것(5절의 보고)을 응답에 출력한다.

  **후보는 그때마다 열린 이슈 전체에서 다시 고른다.** 앞서 정한 순서(이슈 본문에 적은 순서 · `docs/plan/` 의 지금 단계
  문서의 작업 목록)도 다시 따질 후보의 하나이고, 그대로 따르지 않는다. 하던 일의 다음 차례만 보기로 올리면 먼저 할
  것이 보기에 오르지 않는다. 목록은 이것으로 받는다:

      bash .claude/hooks/backlog.sh

  `rc` 가 `0` 이 아니면 목록을 못 받았거나 잘렸을 수 있다. 그 목록으로 고르지 않는다 — 출력을 응답에 싣고, 「다음 일」
  창을 보기 「다시 받는다」 · 「멈춘다」로 연다. 「다시 받는다」를 고르면 다시 실행해 이 문단대로 고른다. 순서는
  이렇게 정한다:

  1. 지금 깨져 있는 것 — 쓰면 바로 막히는 것, 하드룰을 지키는 장치의 구멍
  2. 다른 일을 막고 있는 것
  3. 하던 묶음의 다음 차례
  4. 나머지

  결정을 기다리는 이슈는 그 결정을 보기로 올린다. 출력의 「후보에서 뺄 열린 이슈」는 다른 세션이 맡은 일이라 보기에
  넣지 않는다 — 열린 PR 의 닫는 이슈와 본문의 `Refs #N`, PR 이 없는 다른 worktree 브랜치의 커밋이 줄 머리에 닫는
  키워드나 `Refs` 로 적은 번호다. 그런 줄이 하나도 없는 worktree 는 커밋이 말하는 번호를 모두 뺀다. PR 본문과 커밋이 근거로 든 다른 번호는
  빼지 않는다(worktree 줄의 「근거로 든 번호」). 출력이 「맡은 일을 모름」으로 낸 worktree(기본 브랜치에 없는 커밋이
  없거나 커밋에 번호가 없는 브랜치)는 어느 이슈인지 짐작해 빼지 않는다. 대신 창 앞 응답에 그 worktree 의 경로와 브랜치를
  적고, 「(추천)」을 붙인 보기의 설명에 그 worktree 가 맡은 일과 겹칠 수 있다고 적는다. 그런 worktree 의 이름을 응답에
  적고도 그 worktree 가 이미 맡은 이슈를 추천한 적이 있다.

  **창 앞 응답에 고른 근거를 적는다.** 상위 후보와 그 순서인 이유, 뺀 번호와 어디서 나왔는지를 적는다. 보기는
  「멈춘다」를 빼면 셋까지라, 셋에 못 든 후보도 응답에 남긴다. 사람은 그것을 보고 보기 밖의 일을 고를 수 있다.

  **정한 순서가 단계 문서의 작업 목록과 다르면** 그 순서로 시작한 PR 이 첫 커밋에서 목록을 그 순서와 이유로 고친다.
  순서는 창 앞 응답에만 있어서, 그 PR 의 머지 직전까지 미루면 그 사이 컴팩션으로 사라진다. 단계 문서가 없으면
  건너뛴다.

  **고르면 곧바로 맡았다는 표시를 둔다.** 사람이 고른 일이 브랜치에서 할 일이면(창의 보기든 대화로 고른 보기 밖의
  일이든), 계획을 보이기 전에 위 목록을 다시 받는다. 고른 번호가 창 앞 목록의 「후보에서 뺄 열린 이슈」에는 없다가
  다시 받은 목록의 그 절에 새로 오르면 창을 연 뒤 다른 세션이 그 이슈를 맡은 것이다. 브랜치를 만들지 않고 그 줄을
  응답에 싣고 「다음 일」 창으로 다시 묻는다. 창 앞 목록의 그 절에 이미 있던 번호를 사람이 알고 골랐으면 막지 않는다. 그 밖이면 `origin` 의
  기본 브랜치에서 브랜치를 만들고, 본문 끝에 `Refs #<번호>` 를 단 첫 커밋을 둔다. 위 문단대로 작업 목록을 고칠 것이
  있으면 그 커밋이고, 없으면 빈 커밋이다. 빈 커밋은 `commit` 스킬로 만들 수 없어(스테이지가 비면 멈춘다)
  `git commit --allow-empty` 로 직접 만들고, `Refs` 줄은 `commit` 스킬의 규칙대로(콜론 없이, 트레일러와 빈 줄로 나눠)
  적는다. 첫 커밋 뒤에 목록을 한 번 더 받아, 고른 번호가 새로 다른 세션의 일로 나오면 그 줄을 보이고 어느 세션이 할지
  사람에게 묻는다 — 목록을 다시 받은 뒤 첫 커밋 전에 다른 세션도 같은 이슈를 맡은 것이다. 이 목록에 자기 worktree 는
  나오지 않는다. 고른 것이 새 이슈를 여는 것이면 그 이슈를 연 직후에 첫 커밋을 둔다. 결정 보기와 「멈춘다」처럼
  브랜치에서 하지 않는 것을 고르면 두지 않는다. PR 이 열리기 전에 다른 세션의 「다음 일」 목록이 그 이슈를 맡은 일로
  아는 것은 이 커밋뿐이다. 계획을 보이고 승인받은 뒤로 첫 커밋을 미루면 그동안
  다른 세션의 목록에 그 브랜치가 「맡은 일을 모름」으로 나오고, 같은 이슈가 후보에 오른다. 빈 커밋은 스쿼시 머지에서
  기본 브랜치에 남지 않는다. PR 을 열기 전에 사람이 그 일을 그만두게 하거나 다른 일을 고르면 그 브랜치에서 내려와
  브랜치를 지운다. 지우지 않으면 아무도 하지 않는 이슈가 다른 세션의 후보에서 계속 빠진다.

> 이 확인은 편의이지 강제가 아니다. 진짜 강제는 GitHub 브랜치 보호다
> (킷의 `install.sh --protect` 가 설정한다). 브랜치 보호가 없는 레포라면 그 사실을 먼저 알린다.
